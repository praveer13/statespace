# W1-T12: recording the S1 runs

The recording script of the eleven S1 runs of spine section 9.5 and the harnesses it drives. The inputs are in `runs/inputs/S1/` (its README says what each run is); the records are `runs/RUN-z3-boot-variant.json` and ten more, with logs and SMT-LIB exports in `runs/<RUN-id>/`.

| File | What it is |
|---|---|
| `record.mjs` | `record` executes every run and writes the records; `check` re-derives each record's `values` and `checks` from its committed logs, builds each Z3 record's generated notes again from the record's own configurations, values and logs, checks that a browser configuration's session lies inside its docker run, and checks the shared helper block and the two verbatim copies from `research/` |
| `lib.mjs` | the pure part: log parsing, the merge of a run's configurations, the expectations (the curriculum's keys; for each query without an export, the plain query that stands in for it and, for an Optimize answer, its minimum worked out by hand), the checks. No process, no clock |
| `lib.test.mjs` | its tests, with planted faults (a flipped verdict, a witness that does not replay, a wrong core, an export that differs, a cvc5 that disagrees, a query without an export whose plain query is missing, is not `unsat` or was not run by cvc5, an Optimize minimum that differs, the committed refund-mint logs without `no_smaller_mint`, a psql log whose `ERROR` lines are out of order, a query printed twice or by one configuration only, an `exports-identical` detail that would speak of exports a query does not have, a failing int-twin check whose detail would still claim the drain), the facts the notes are built from (the browsers' timer granularity, the tour's text against the command line's), and one run of `record.mjs check` |
| `notes.test.mjs` | tests of the note builders in `record.mjs`, each fed data in which its statement holds and data in which it does not (no export for some queries, models that differ in the browsers or elsewhere, figures finer than a browser's, a recording of some runs only), and checks of the committed records against their own data: each `exports-identical` detail against the queries' exports, and each browser configuration's session inside its docker run |
| `check.test.mjs` | planted-fault tests of `record.mjs check`: a scratch copy of the eleven records, their logs and the inputs, with one fault planted at a time (a flipped verdict, an export removed or changed, a helper block that drifts, an edited record, a copy that is not the research source, a cvc5 that disagrees, a psql log out of order, a missing record, an Optimize answer whose plain query is gone from logs, exports and record alike, a timing note that calls the docker run the session, a note that says every query has an export, the old fixed `exports-identical` detail, a browser configuration without the session's span, and a session that does not lie inside its docker run); the check must pass on the untouched copy and fail on each fault |
| `pyodide-node.mjs` | one Python script in Pyodide 314.0.7 with the Z3 wheel under Node, in a fresh engine and a fresh namespace |
| `pyodide-browser.mjs`, `browser/` | every Z3 script in one Pyodide module worker per browser (Chromium, Firefox, WebKit), run inside the Playwright container |
| `cvc5-check.sh` | cvc5 on a folder of SMT-LIB files, inside the Bench image |

## Re-running

```
W1T12_SCRATCH=<a scratch directory outside the repository> node scripts/spikes/W1-T12/record.mjs record
node scripts/spikes/W1-T12/record.mjs check
node --test "scripts/spikes/W1-T12/*.test.mjs"
```

`record` needs Node 22, `uv` (it runs `uv run --no-project --with z3-solver==5.3.1`), Docker with `statespace-bench:w0t05`, `postgres:18` and `mcr.microsoft.com/playwright:v1.63.0-noble`, and network access for the pinned packages. It fetches Pyodide 314.0.7 and the Z3 wheel with W0-S02's `fetch-engines.mjs`, which checks both against their published digests, into the scratch directory, and never commits them. `--only RUN-id,RUN-id` records some runs; `--skip-browsers` leaves the browser configurations out (a record made that way is a development aid: its checks still pass, and it lists fewer configurations). A configuration that ran its own command (native, the Z3 command line, Node, cvc5, the Rust container, and for PostgreSQL the psql command) has the `started_at` and `duration_s` of that command. A browser configuration comes from one docker run per browser, in which one browser session ran every Z3 script in turn: its `started_at` is when that session began (after the browser launched), shared by every Z3 record of the same recording (all nine in the committed records), its `duration_s` is that script's own time in the worker, and its `environment` keeps the session's span (`session_wall_ms`) apart from the whole docker run's (`docker_run_started_at`, `docker_run_wall_ms`), which adds the container's and the browser's start-up and shutdown. `budget.harness_timeout_s` is when the recording script would have stopped a command (600 s; 900 s for a browser's docker run). The PostgreSQL and Rust runs need neither Pyodide nor the wheel, so `--only RUN-pg-numeric-bound,RUN-rust-i64` fetches no engines.

## Choices worth knowing

- **Verdicts and replays are compared, witnesses are not.** Every `sat` model is replayed in plain integers, from every configuration that gave one (in Python by the script itself; the tour's starter and the int twin's line in BigInt by the recording script), and the check is that each replays. Models differ between engines for a few queries, and the records say which.
- **The browser configurations share one worker.** The harness runs the nine Z3 scripts in turn in one Pyodide instance per browser, each in a fresh namespace, which is how INS-z3 will serve requests; every other configuration starts a fresh engine for each script.
- **Exports are renamed.** Z3's `to_smt2()` names let-bound terms after AST ids, and the ids differ between processes, so each export's let names are renamed in order of appearance; the raw text's hash is kept beside the renamed one, and a record says whether the raw text agreed across its configurations.
- **psql's two streams are merged inside the container.** `docker exec` without a terminal carries a container's stdout and stderr as two streams, and its CLI prints them in no fixed order, so the PostgreSQL run goes through `sh -c 'psql … 2>&1'`, where psql's writes reach one pipe in the order psql made them. The check `psql-order` fails a log in which an `ERROR` line comes after the `sqlstate` or `balance` echo that follows its statement.
- **cvc5 sees SMT-LIB text.** Every `sat` or `unsat` query that has an SMT-LIB export is run on the Bench's cvc5, whose verdict must equal Z3's. Two kinds of query have no export, and each is checked through a plain query that has one, named in `lib.mjs`'s `PLAIN_CHECKS` and required to be `unsat` (`checked_by` in the query's check): an Optimize answer, by a query that asks for anything below its minimum (RUN-z3-double-capture's `no_smaller_hold` and `no_smaller_pool_patched`, RUN-z3-refund-mint's `no_smaller_mint` and `no_smaller_mint_patch_exact`), and RUN-z3-vacuous-unsat's two unsat cores, whose premise sets are its `max0_range_premises` and `max0_guarded_premises` queries. Which members form a core, and that it is minimal, is checked by Z3 alone.
- **Notes say what the data show.** A note sentence about the recording (which queries have an export, which configurations' models differ, how fine each browser's timings were, whether the tour's API printed the command line's text) is worked out from the configurations, values and logs of the record it is written into, and so is the detail of the `exports-identical` check, and `record.mjs check` builds those sentences again from the committed record and compares. The sentences that stay fixed describe what a recording cannot change: the scripts and their encodings, what the curriculum asks of them, and how the recording script runs them.
- **Nothing private is recorded.** Host paths in argv and logs become `<sandbox>/…`; the record names what each placeholder stands for.
