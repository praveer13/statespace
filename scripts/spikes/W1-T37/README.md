# GATE-calls and the Z3 pair (W1-T37)

**Task:** W1-T37, GATE-calls (spine section 11.2; V2-12; ARCHITECTURE.md sections 13.2 and 13.3). **Date:** 2026-10-25 (machine clock). **Deliverables:** `scripts/verify-calls.mjs` (the gate, fast lane) and `scripts/conformance/z3-pyodide-native.mjs` (GATE-conformance's pair "Pyodide Z3 = native Z3", and the Z3 engine port GATE-generators borrows). This folder holds their shared code (`lib/`), the S1 fixture pages (`fixtures/s1/`), the cells the first verification round used to show two faults (`fixtures/probes/`), the tests and the mutation suite.

Every authored Call It answer must reproduce on its engine. For a Z3 cell the engine is two engines, native Z3 and Pyodide's Z3 under Node (the tab's), both z3 5.3.1 [X RUN-z3-starter, RUN-z3-starter-pyodide], and every `unsat` an authored cell shows is cross-checked with the Bench's cvc5 1.4.2, the binary RUN-scaffold pins by SHA-256 [X RUN-scaffold].

## 1. What the gate checks

The gate reads every lesson and drawer (`content/stages/S{n}/S{n}.L{k}.md`, `content/drawers/D-{nn}.md`) with the content build's own reader, and runs every Z3 cell, with or without a call, on both engines. Each finding names one check:

| Check | Fails when |
|---|---|
| `run` | the cell does not run to its end on an engine: it raises, the watchdog stops it, or the engine dies or answers with no checks. The checks it made before raising are still judged. Also a check the gate could not record (its own bookkeeping never raises into the cell; it says what it could not record) |
| `divergence` | native and Pyodide disagree: the number of checks, a verdict, the reason of an `unknown`, or an optimum. A model's values are never compared: they are not canonical [X RUN-z3-bv64-pyodide] |
| `witness` | a `sat` model does not satisfy its query, on either engine: an assertion Z3's own evaluation finds false (with model completion, on a copy of the model, so the cell's own model stays as Z3 gave it), or a quantifier the evaluator leaves unreduced that a fresh solver finds false under the model; or cvc5 finds the query with that model's values asserted unsatisfiable (an SMT-LIB check, which shows no model: its query); or neither settles an assertion: Z3 cannot decide it under the model within the check's rlimit, and cvc5 does not find the witness query satisfiable with every symbol the assertion mentions pinned by the model |
| `cvc5` | an `unsat` both engines agree on is not confirmed by cvc5: cvc5 says `sat` or `unknown`, cannot read the query, does not finish within its limit, or answers with an error line or more than one verdict |
| `key` | the call's first check does not give what the key option claims, on either engine |
| `key-read` | the key option names no verdict the gate reads, or names two, and is no number |
| `value-query` | a value key sits on a query with no single optimum: a plain solver check, or an Optimize with several objectives or soft ones |
| `optimum` | cvc5 does not confirm a value key's optimum: a value beyond it is satisfiable, the optimum is unattainable, or cvc5 cannot settle either |
| `no-check` | a call whose cell makes no solver check |
| `cell-code` | a call whose cell has no code, or an INS-z3 cell, call or free run, whose code is in a language Z3 does not run (Python and SMT-LIB run; a ```` ```py ```` free run would otherwise never be reproduced). A cell with no code at all and no call is not run |
| `instrument` | a call on an instrument with no engine here: Spectacle lands with W3-T08 and the interpreter with W2-T08; a Lean call (INS-goal-replay) is deferred to the nightly lane, where it fails until W2-T03 brings its engine; an instrument the gate does not know fails |
| `pin` | an engine is not at its pin: a Z3 engine by the versions it reports; cvc5 by its SHA-256 when it is set up, where one that is not the pinned binary stops the gate with exit 2 |
| `page` | a page cannot be read in full: its file cannot be read, or it has no front matter, so its cells cannot be seen, or two of its cells share a number, so they share a ref and cannot be told apart (those cells are left out, the rest of the page is checked) |

`--lane nightly` judges the Lean calls; the fast lane lists them as deferred. The conformance pair applies the checks between the two Z3 engines only (`run`, `divergence`, `witness` by Z3's evaluation, `key`, `key-read`, `value-query`, `no-check`, `cell-code`, `pin`, `page`), on every Z3 cell and, once the Z3 families exist, on every live template of every family that consults z3. An assertion Z3 cannot settle under a model is a note there, since settling it is cvc5's part.

## 2. Writing a cell the gate can check

For the authors of S1.L0 (W1-T09), S1.L1–S1.L5 (W1-T27, W1-T28), the drawers (W1-T11) and every later Z3 cell:

1. **The key names its verdict.** The gate reads the key option the way GATE-items does (it imports `verdictOf` from `scripts/verify-items.mjs`), so the two gates never disagree: `` `sat` ``, `` `unsat` `` or `` `unknown` `` in code, or the words proved, holds, verified, counterexample, violated, refuted, fails, broken, no verdict, can't tell, inconclusive. "Yes: some inputs get past the guard." names no verdict; Boot's key in `fixtures/s1/content/stages/S1/S1.L0.md` adds "so a counterexample exists" for that reason. Once lesson@1 carries a per-option `verdict` (`violated`, `holds`, `unknown` or `value`, requested from W1-T36 by W1-T39), the gate reads it first, as GATE-items does, and option text may stay as the curriculum words it.
2. **A value key is a number and nothing else** (`` `1` ``), and the cell's first check is an Optimize with exactly one `minimize` or `maximize`. The optimum is canonical; a model's values are not (spine section 8.4), so a value key on a plain `Solver` fails. A bit-vector objective is minimized and maximized as an unsigned number, and its key is that unsigned value (`harness.test.mjs` runs three).
3. **The call is about the cell's first check.** Call It is committed on the first run, and the first result shown is the one called. A cell that runs several queries puts the called one first: `fixtures/s1/content/stages/S1/S1.L3.md` runs S1.L3 cell 2's query (ii) before (i) and (iii).
4. **Every check runs under an rlimit:** the cell's own, else 5000000, the budget every S1 run used (`RLIMIT` in `runs/inputs/S1/`; for example [X RUN-z3-boot-variant]). A cell sets its own with `s.set('rlimit', N)` on a `Solver`, `o.set('rlimit', N)` on an `Optimize` or `set_param('rlimit', N)`, by position or by keyword, or with `(set-option :rlimit N)` in SMT-LIB; the gate's applies to a `Solver`, an `Optimize` and an SMT-LIB cell alike. Do not rely on `timeout`, which never returned under Pyodide [X RUN-z3-budget-pyodide]. The tab's default budget for an authored cell should be the same figure (a request to W1-T06).
5. **The code runs to its end on both engines.** `print(s.model())` after an `unsat` raises "model is not available", a `run` finding.
6. **An SMT-LIB cell** (a ` ```smt2 ` fence) runs through Z3's command interpreter, one command at a time in one context, which prints what the whole script prints, save the positions its error lines name (`harness.test.mjs` compares them). Its checks are the verdicts of its `check-sat` commands in order (an `(echo "unsat")` prints a verdict word and is no check), and an `(error ...)` line is output the learner reads, not a failure (D-13 shows one). A cell may make several queries, with several `(check-sat)` commands or `(push)` and `(pop)`. Z3 goes on past a command it rejects, and the rejected command has no effect; the pinned cvc5 stops at a parse or sort error (an undeclared symbol, a term that is no Boolean, a command it does not know, a `pop` past the stack) and goes on past a command that fails (a `get-model` after `unsat`), as `cvc5.test.mjs` shows. So cvc5 never reads the cell's text: for each check the harness cuts a query of its own, the commands Z3 ran without an error before it, less those that only print (`get-model`, `get-value`, `get-info`, `echo` and the like), the other checks and Z3's `(set-option :rlimit N)`, then the check itself. A Z3-only command left in such a query (`check-sat-using`, `minimize`) fails the cross-check of an `unsat` it precedes. A script the gate cannot split into commands (a `)` that closes nothing, a string that never ends) runs whole, and an `unsat` it shows fails `cvc5`.
7. **Free runs are run too:** a drawer's cells and `call=false` cells have no key to check, but their `unsat`s are cross-checked and the two engines must agree on them. So an INS-z3 free run is written in ` ```python ` or ` ```smt2 `, like a call; any other fence fails `cell-code`.
8. **An `unsat` must be one cvc5 can read.** The gate hands cvc5 the query as Z3 prints it in SMT-LIB, with the tracking literals of `assert_and_track` asserted. A query that comes back `unsat` with a construct cvc5 does not read (a power with a variable exponent, pseudo-Boolean constraints, a recursive function as Z3 prints it) cannot be cross-checked, and fails `cvc5`.
9. **Never key a call on a model value.** Native and Pyodide can return different models for the same query: two of RUN-z3-btc2010's queries did, in its browser configurations [X RUN-z3-btc2010].
10. **Number every cell of a page once.** The gate keys each engine's reply by the cell's ref (`cell:S1.L3#2`), so two cells with one number fail `page` (the content build fails the page too).
11. **Quantified queries are checked by their models too.** Z3's evaluator leaves a quantifier unreduced under a model (D-03 section D's `ForAll(k, k*k != y)` with y = 2, sat [X RUN-z3-unknown-pow], evaluates to `ForAll(k, Not(k*k == 2))`), so the harness asks a fresh solver, under the check's rlimit, whether what is left holds: it holds when its negation is unsatisfiable, and fails when it is unsatisfiable. One it cannot settle passes only when cvc5 finds the witness query satisfiable and the model pins every symbol the assertion mentions; otherwise it fails `witness`. A quantifier over a large or nonlinear domain under a small rlimit can end there.

## 3. Engines and cvc5

Both Z3 engines run `lib/harness.py`, one long-lived server each (`lib/engines.mjs`), so a batch of cells costs one engine start. A cell runs in a fresh Python namespace and a fresh Z3 context, so its results never depend on the cells before it; its own output is captured. Every `check()` of a `Solver` or an `Optimize` is intercepted and recorded. Each cell has a 30 s watchdog [D]: a cell that outlives it is reported, the server is restarted, and the other cells keep their results.

| Engine | From, first match wins |
|---|---|
| native | `STATESPACE_Z3_PYTHON`; `python3` or `python` on `PATH` if it carries the pinned z3; the virtual environment W1-T42's `prepareNative()` builds in the engine cache from the checked wheel |
| Pyodide | `STATESPACE_PYODIDE_DIR`; `node_modules/pyodide` at the pinned version (314.0.7 [X RUN-z3-starter-pyodide]); the cached tarball, extracted by W1-T42's `preparePyodide()`; the wheel from `STATESPACE_Z3_WASM_WHEEL` or the cache, checked by SHA-256 |
| cvc5 | `STATESPACE_CVC5`, which must hash to RUN-scaffold's pin; `cvc5` on `PATH` if it does (another one is passed over, and the report says so); else the release asset RUN-scaffold names, downloaded once into the engine cache, checked against the asset's SHA-256, and the binary taken out of it and checked against the binary's (Linux x86_64 only). Its version line must be the recorded one |

The pins and the cache (`.cache/statespace-engines`, or `STATESPACE_ENGINE_CACHE`) are W1-T42's (`scripts/spikes/W1-T42/lib/engines.mjs`), so every gate fetches and checks the same files once. cvc5's pin is read from `runs/RUN-scaffold.json` (configuration `bench-cvc5-version`) at run time, not repeated here. A query runs as `cvc5 --lang smt2 --incremental --produce-models --tlimit=20000 query.smt2` [D], from a scratch folder of its own, once per distinct query text. Every query ends in one check (section 2 item 6), and `--incremental` is there for the `push` and `pop` an SMT-LIB check's query may hold: without it the pinned cvc5 refuses them, "cannot push when not solving incrementally" (and, given several `(check-sat)` commands, "cannot make multiple queries unless incremental solving is enabled"); `cvc5.test.mjs` runs the pinned binary without the flag and shows both refusals. Only a single verdict with no error line counts as cvc5's answer: the pinned cvc5 stops at a parse or sort error, where Z3 goes on, and goes on past a command that fails, so an answer with an error line is not an answer to the query Z3 checked (`cvc5.test.mjs` runs both kinds). The file is named relative to its folder, so a parse error quotes `query.smt2`, never a machine path. An engine or cvc5 that cannot be set up stops the gate with exit 2, never a pass, and so does a `--root` that names no directory or, for the gate, a directory with no `content/` in it (the pair's tree may hold generator families alone).

Then one tracks its assertions for an unsat core, and one checks under an assumption (`s.check(guard)`), so they hold only while the export asserts the tracking literals and the assumptions; one is an SMT-LIB call with two queries and one an SMT-LIB free run with `push` and `pop`, whose second query's `unsat` cvc5 must confirm; one keys a bit-vector optimum (`6`), which cvc5 must confirm from both sides; one reads Z3's global parameters after an SMT-LIB cell set `(set-option :rlimit 100)`, so it holds only while every cell starts with them reset; D-03's quantified query keyed `sat`, a negated quantifier and a violation quantified over accounts, whose witnesses cvc5 must confirm, and D-03's query again with cvc5 not settling them, so it holds only while the harness settles the quantifier itself; an SMT-LIB free run with error lines before and between its two `unsat`s, and an SMT-LIB call with an `(echo "unsat")` before its first query and `get-model` and `get-info` between its two, whose `unsat`s cvc5 must confirm, so they hold only while each check's query leaves out what Z3 rejected and what only prints; an SMT-LIB free run whose string, comment and quoted symbol hold `(`, `)`, `;` and `""`, whose `unsat` cvc5 must confirm on a query cut as Z3 reads the script; an SMT-LIB free run with a check after `(exit)`, which must make exactly one check; and a cell that asserts its model leaves out a constant Z3 left out, so it holds only while the evaluation completes a copy of the model.

- **Coverage.** Every check of the judge must be some case's expected check, or the gate fails.

`weakenings.mjs` builds weakened copies of the gate, each with one rule removed or loosened (101 of them: the judge's rules, a divergence or a key excused for one verdict, cvc5's answer read past an error line or from several verdicts, cvc5's own output read without its error lines or past its first verdict, cvc5's pin at setup, the reading of keys and of each number form, page files that cannot be read, both engines and their pins, cvc5's incremental mode, the harness's budget for each kind of check and each way a cell sets its own, its recording of reasons, maximize objectives and checks it cannot record, its global-parameter reset and exports of tracked literals, assumptions, witnesses, optima and bit-vector optima, its evaluation of witnesses, settling of quantifiers and pinning of their symbols, and its splitting of SMT-LIB scripts and cutting of their queries), and `weakenings.test.mjs` requires the self-check of every copy to fail.

## 5. The conformance pair and the engine port

`node scripts/conformance/z3-pyodide-native.mjs --json` follows GATE-conformance's protocol (`scripts/verify-conformance.mjs`): one JSON object `{pair, ok, compared, equal, differences, notes}`, exit 0 when the pair holds, 1 when it differs, 2 when it cannot run. It compares every Z3 cell of the tree and, for every family that consults z3, every live template at 8 seeds per band [D] through a port that sends each request to both engines. Each run also plants a verdict flipped in a cell's reply, a decided check turned `unknown` in either engine's reply, and a request the two engines answer differently, which must all be caught, with the S1 cells as controls.

`createPorts()` returns `{ z3: EnginePort }` over Pyodide's Z3, the tab's engine, in the shapes of `packages/generators/src/core/port.ts`. GATE-generators loads it by default when a family needs z3. The request and reply, until `packages/bus` (W1-T35) publishes the z3 engine's input type:

| Field | Holds |
|---|---|
| `engine`, `version` | `'z3'` and the pinned version, `'5.3.1'` [X RUN-z3-starter-pyodide]; another version is refused (`version-mismatch`) |
| `input` | `{smtlib}`: declarations and assertions, parsed by Z3's own parser, checked as a conjunction (an option is refused, because the budget comes from the request); or `{python}`: z3py whose first check is the answer |
| `budget` | `rlimit` on every check (by default the gate's, section 2 item 4), `wallMs` the watchdog |
| reply `verdict` | `{kind: 'sat'}`, `{kind: 'unsat'}` or `{kind: 'unknown', reason}`; an rlimit stop is `unknown` with reason `canceled` |
| reply `witness` | for `sat`, the model's constants as strings (bit-vectors as Z3 prints them, unsigned) |
| reply `stats`, `provenance` | `{ms, bound: 'rlimit N'}`; `{engine, version, build, budget}` |
| errors | an Error with `code`: `terminated` (the watchdog, which the framework's `ask()` reads as a budget stop), `invalid-input`, `engine-crashed`, `version-mismatch`, `unknown-engine` |

The port starts nothing until its first request and holds no reference on the event loop while idle, so the process that borrowed it exits when its own work is done.

## 7. Decisions [D]

1. **The call is about the first check** (section 2 item 3). The content format has no field that names the called query, and the first result is the one a learner sees after calling.
2. **Value keys only for one optimum.** A value key on a model value cannot be reproduced, because models are not canonical; an Optimize objective's optimum is, and cvc5 confirms it from both sides.
3. **A fresh Z3 context and Z3's global parameters reset for every cell,** so a cell's results never depend on the cells before it. The reset matters: an SMT-LIB cell's `(set-option :rlimit N)` sets a global parameter that a fresh context alone does not clear, and so would reach the cells after it. A planted control reads Z3's global parameters right after such a cell, and `harness.test.mjs` checks a cell run with no budget of its own after one.
4. **cvc5 confirms witnesses and optima too.** A witness cvc5 refutes fails; a witness cvc5 does not settle is a note when Z3's evaluation on each engine has settled every assertion under the model; an assertion Z3 could not settle must be settled by cvc5, or the witness fails (section 2 item 11). Every `unsat`, and the bound of an optimum, must be confirmed.
5. **The gate reads GATE-items' verdict reading** rather than its own, so a call means the same to both gates.
6. **Unknown instruments fail closed,** and a call on an instrument whose engine has not landed fails, naming the task that brings it: a call no engine reproduces is never a pass.
7. **SMT-LIB cells:** interpreter error lines are output, not failures; a Python exception is a failure. cvc5 answers each check on its own query, cut from the commands Z3 ran (section 2 item 6), never on the cell's text, because it stops where Z3 goes on.
8. **The planted fixtures run on every invocation,** like GATE-items', so the lane proves on each run that the gate still trips; a separate self-check row adds only the per-case detail.
