## Before the proof (4 min)

Stage 3 now has a language: syntax, a typing judgment, and an evaluator that returns every outcome as a value. This lesson proves the first thing about all of it at once. **If a well-typed command takes a successful step from a state that satisfies the invariant, the new state satisfies it too.** Two questions first.

## A worked proof (14 min)

An invariant is a property of every state a system can reach. You do not prove it by running the system. You prove two things: it holds in the starting state, and every step that can happen next keeps it. In your own system the starting state is an empty table and the steps are the code paths that write to it. Here the property is `Inv`, and the steps are Mini-Plinth's five operations.

`Inv s := WF s ∧ total s = 0 ∧ ∀ p ∈ s.bals, p.1 ≠ mint → 0 ≤ p.2`

Read it as three parts. The account keys are unique. The balances add up to zero, because the `mint` account holds minus everything it has created. And every account except `mint` is at or above zero. The statement you are building towards is:

`step_preserves_inv : p.WellTyped → Inv s → exec p c s = .ok (s′, o, es) → Inv s′`

It speaks only of successful steps. An error returns no state, so there is nothing to keep.

Every operation is built from one primitive. `post s x y n` debits `x` by `n`, then credits `y` by `n`, reading the state the debit left. The two postings cancel, so the total stays at zero for every operation with no work per command. Only the third part of `Inv` can fail, and only at a debit. The whole stage reduces to one lemma:

`post_inv : 0 < n → (x = mint ∨ n ≤ bal s x) → Inv s → Inv (post s x y n)`

Each hypothesis has a job. Name the job before you see the step that uses it: zero-sum pairs keep the total, coverage pays the debit, positivity protects the credit, and unique keys keep `total` honest.[^s2b1-1]

[^s2b1-1]: Drawer D-07 collects the Lean errors you are likely to meet while writing proofs like this one.

```lean
-- From the template: State, bal, setBal, total, WF, NonNeg and Inv, with
--   setBal_wf     : WF s → WF (s.setBal a v)
--   total_setBal  : WF s → total (s.setBal a v) = total s - s.bal a + v
--   nonneg_setBal : NonNeg s → (a = .mint ∨ 0 ≤ v) → NonNeg (s.setBal a v)
--   bal_nonneg    : NonNeg s → a ≠ .mint → 0 ≤ s.bal a

def post (s : State) (x y : Acct) (n : Int) : State :=
  let s1 := s.setBal x (s.bal x - n)
  s1.setBal y (s1.bal y + n)

theorem post_inv (s : State) (x y : Acct) (n : Int)
    (hn : 0 < n) (hcov : x = .mint ∨ n ≤ s.bal x) (hs : Inv s) :
    Inv (post s x y n) := by
  obtain ⟨hwf, htot, hnn⟩ := hs
  unfold Inv post
  dsimp only
  have hdebit : x = .mint ∨ 0 ≤ s.bal x - n := by
    rcases hcov with h | h
    · exact Or.inl h
    · exact Or.inr (by omega)
  have hnn1 := nonneg_setBal hnn hdebit
  have hcredit : y = .mint ∨ 0 ≤ (s.setBal x (s.bal x - n)).bal y + n := by
    by_cases hy : y = .mint
    · exact Or.inl hy
    · exact Or.inr (by have := bal_nonneg hnn1 hy; omega)
  refine ⟨setBal_wf (setBal_wf hwf), ?_, nonneg_setBal hnn1 hcredit⟩
  rw [total_setBal (setBal_wf hwf), total_setBal hwf]
  omega
```

## Fading the support (14 min)

`post_inv` is the whole argument. Each operation's lemma only has to show that its postings meet the lemma's hypotheses, and the five differ in where coverage comes from.

| Operation | Debits | Where coverage comes from |
|---|---|---|
| `deposit n to a` | `mint` | the left side of `x = mint ∨ …`: the mint is exempt |
| `move n from x to y` | `x` | the guard, through R-cover |
| `hold n on x` | `x`, into escrow `h` | the guard, through R-cover |
| `capture h to y` | escrow `h` | a run-time check that the hold is open and its escrow covers it |
| `release h` | escrow `h` | the same run-time check |

Positivity is the same everywhere, because an amount is an `Amount`: a capture or a release credits the hold's stored amount, which is one too.

You will read the same kind of proof three times with less support each time. In `move_inv` the last step is blank. In `hold_inv` two steps are blank. In `capture_inv` only the case split is shown. No blank has a prompt, and every step you do see still asks which principle it uses. Three right answers in a row move you up a rung, one miss moves you down one, and Today sets your next rung.

## Assembling the theorem (13 min)

Now put the lemmas together. `step_preserves_inv` splits on the command's one statement.

- An operation statement calls its lemma. For `move` and `hold` the coverage comes from typing. R-cover forced a guard conjunct `balance(x) >= n`, and a successful `exec` got past the guard, so the guard evaluated to true. `covers_sound` turns that into `n ≤ bal s x`.
- A `set f(x) := e` statement writes a scalar field and never a balance, because R-set has no rule for assigning a resource.

Nothing here depends on how you decide the edge cases in the next lesson. A silent rejection and a zero no-op both return the unchanged state, and a bounded overflow returns an error. None of them can break `Inv`.

A proof can build before it is finished. Leave one lemma as `sorry` and Lean still builds, so a green build is not a finished proof. The gap shows in the axioms.

Last, tie the language to something you proved in Stage 2. That ledger had two fields. Pick two existing accounts `u₁` and `u₂` and read them as the ledger: `toLedger s := ⟨bal s u₁, bal s u₂⟩`.
