**Ideas taught.**

- The model takes a step the database refuses (22003)

## Recall before you wire (3 min)

Your runtime sits between your compiler and PostgreSQL. For every failure it decides whether to run the command again or to hand the failure back to the caller. That decision is yours, and a wrong one either hides a real fault or retries a doomed command forever.

**Question** (before the segment):

Your runtime retries whole commands on 40001 and 40P01. A credit fails with SQLSTATE 22003. What should it do?

- A. Retry it, like a serialization failure.
- B. Return a typed error without retrying: the model took a step the database refuses.
- C. Clamp the balance at the `bigint` maximum and commit.

## Re-run your gate (6 min)

A runtime is a compiler, an isolation level and a retry policy, wired together. The gate from Stage 6 runs the whole differential suite through that runtime and requires that no outcome class diverges from the interpreter (LAB-6.c8). It also reads back the isolation level of every session and requires `serializable`, and it names the deferred reconciliation triggers that re-stamp CL-6.4.

The retry policy is where a runtime goes wrong most quietly. It retries the decision, never the statement: after a failure, the whole command starts again from the beginning and reads again. The cell replays one conflict from the Stage 6 catalog. Two sessions each read 100 available and insert a hold of 80, and the second one's commit fails.

**Cell 1** (INS-bench-pg)

The recorded run replays one history. Session a commits, session b's first attempt fails at its commit, and b's retry begins a new transaction.

```text
-- holds at SERIALIZABLE: both sessions read 100 available and insert a hold of 80
setup {
  CREATE TABLE acct (id int PRIMARY KEY, bal bigint NOT NULL);
  CREATE TABLE holds (acct int, amt bigint);
  INSERT INTO acct VALUES (1, 100);
}

session a
step a_begin  { BEGIN ISOLATION LEVEL SERIALIZABLE; }
step a_avail  { SELECT bal - coalesce((SELECT sum(amt) FROM holds WHERE acct = 1), 0) FROM acct WHERE id = 1; }
step a_hold   { INSERT INTO holds VALUES (1, 80); }
step a_commit { COMMIT; }

session b
step b_begin   { BEGIN ISOLATION LEVEL SERIALIZABLE; }
step b_avail   { SELECT bal - coalesce((SELECT sum(amt) FROM holds WHERE acct = 1), 0) FROM acct WHERE id = 1; }
step b_hold    { INSERT INTO holds VALUES (1, 80); }
step b_commit  { COMMIT; }                               -- this commit fails
step b_begin2  { BEGIN ISOLATION LEVEL SERIALIZABLE; }   -- the retry: the whole command, from BEGIN
step b_avail2  { SELECT bal - coalesce((SELECT sum(amt) FROM holds WHERE acct = 1), 0) FROM acct WHERE id = 1; }
step b_hold2   { INSERT INTO holds VALUES (1, 80); }     -- only if the read returned 80 or more
step b_commit2 { COMMIT; }

permutation a_begin a_avail b_begin b_avail a_hold b_hold a_commit b_commit b_begin2 b_avail2 b_hold2 b_commit2
```

Recorded run: RUN-pg-catalog (postgres 18.6).

Text that follows the first run is left out here.

Decide by error code, and write the decision down as data. The codes are PostgreSQL's (run RUN-pg-claims).

| What the runtime sees | What it does |
|---|---|
| 40001, a serialization failure | Retry the whole command from the start, and decide again. |
| 40P01, a deadlock | The same. |
| 22003, a value out of range | Return a typed error. The same input fails the same way. |
| A typed refusal such as `Insufficient` | Return it. It is an outcome of the command, not a fault. |

Retries are bounded, and "retries terminate" stays an assumption with a reason, never a result (CL-6.5). The runs you carry into the report are two tests: CL-6.1, compiled transfers matching the interpreter on outcome classes, with n and generator statistics, and CL-6.2, the conditional-UPDATE compilation under concurrent READ COMMITTED, with n histories and the assumptions it rests on.
