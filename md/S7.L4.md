# S7.L4 · Row-level security as enforcement

> Draft: first-learner pass pending.

**Format.** Full lesson, about 45 minutes.

**Objective.** Compile the read rule to row-level security policies, test them per user against the access matrix, find the owner bypass and fix it with FORCE, and exhibit an integrity-check channel as a pair of worlds.

**Ideas taught.**

- `USING` filters silently, `WITH CHECK` errors, owners bypass unless `FORCE`
- Counts, sizes and integrity checks as channels

**Segments.**

1. From rules to rows
2. Compile the rule
3. The differential, and the owner
4. A channel the policy cannot see
5. Exit

## From rules to rows (2 min)

Your policy has been facts and rules. Now the database has to enforce it, one row at a time.

**Question** (before the segment):

A row fails the `USING` clause of every policy that applies to a user's `SELECT`. What does the user get?

- A. An error naming the policy.
- B. Nothing: the row is silently left out.
- C. It depends on `WITH CHECK`.

**Question** (before the segment):

Every row a user can see passes the read policy. Can the user still learn that a row they cannot see exists?

- A. No: they never see it.
- B. Only if a policy is missing.
- C. Yes: some checks run against every row, whoever may see it.

## Compile the rule (13 min)

A worked example first. The lab template gives you the schema `documents(id, slug UNIQUE, team_id, title, body, internal_notes, shared_team_ids int[])`, with `memberships` and `shares`, and `user_teams(u)`, a function that returns a user's team closure from a recursive query, independent of the Datalog engine. For a user on no team it returns an empty array, never NULL. Your three rules become three policies.

Read them with three facts in mind. Permissive policies combine with OR, as your three rules did. When row security is on and no policy applies, a default-deny policy is used, so no row is visible. And a policy whose `USING` expression is NULL hides the row, as `WHERE` skipped NULL rows in S6, so an unset `app.user` fails closed.

**Cell 1** (INS-pglite)

The cell loads the template world, creates your policies, and then runs frank's statement.

```sql
SET search_path = app;

-- the three read rules, as policies
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
CREATE POLICY read_team ON documents FOR SELECT
  USING (team_id = ANY (user_teams(current_setting('app.user', true))));
CREATE POLICY read_shared ON documents FOR SELECT
  USING (EXISTS (SELECT 1 FROM shares s
                 WHERE s.doc_id = documents.id
                   AND s.user_name = current_setting('app.user', true)
                   AND NOT s.revoked));
CREATE POLICY read_team_shared ON documents FOR SELECT
  USING (shared_team_ids && user_teams(current_setting('app.user', true)));

-- frank, a viewer on Growth, changes a row he cannot see
SET ROLE frank;
SELECT set_config('app.user', 'frank', false);
UPDATE documents SET title = 'x' WHERE id = 'q3-plan';
```

**Your call before the first run:**

frank (Growth, viewer) holds the UPDATE privilege and runs `UPDATE documents SET title = 'x' WHERE id = 'q3-plan'`, a row invisible to him. What comes back?

- A. An error naming row security
- B. `UPDATE 0`, with no error
- C. The update succeeds, because UPDATE checks only `WITH CHECK`

## The differential, and the owner (14 min)

How do you know the policies say what the rules say? Run a differential. For each user, switch to that user's role, name the user in the setting the policies read, list the visible ids, and compare them with that user's row of the matrix:

```sql
SET ROLE dana;
SELECT set_config('app.user', 'dana', false);
SELECT id FROM documents;
```

`SET app.user = 'dana'` does not parse, because `user` is a reserved word; `set_config` names the same setting (run RUN-pglite-rls). Zero disagreements over n generated worlds earns two stamps: [E] · RLS on `documents`, and [T] · n worlds × users, with the engine named. PostgreSQL on the Bench stays authoritative, and the tab reruns the differential on PGlite. A differential is a test. For the conjunctive fragment there is a proof alternative, query containment.[^s3b1-1]

[^s3b1-1]: Drawer D-17 holds query containment.

Many applications are built another way: one connection as the table's owner, with `app.user` set for each request. In the tab the connection is a superuser, which bypasses row security even on a forced table (run RUN-pglite-rls), so every RLS statement follows a `SET ROLE`, and the owner probe is `SET ROLE app_owner`. On the Bench you connect as the real owner.

## A channel the policy cannot see (12 min)

Every read so far was filtered. Now look at a write. Slugs are globally unique in this schema, so a slug names a row for everyone, including rows a user cannot see.

**Your call before the first run:**

frank inserts a document with the slug 'layoffs-memo' into Growth. Birch already has a private document with that slug, invisible to frank. What happens?

- A. The insert succeeds, because RLS hides Birch's row from the constraint
- B. A unique-violation error

Recorded run: RUN-pg-rls-covert (postgresql 18.6).

Text that follows the first run is left out here.

Every read was filtered, and frank still learned a bit. The channel is the error class: a unique violation against a successful insert. It is one bit, not the slug's owner or value, and the manual tells schema designers to avoid exactly this "covert channel" through integrity checks (section 5.9). There are three cures: a constraint per tenant, `UNIQUE (tenant_id, slug)`; opaque identifiers; or a recorded release, which S7.L7 teaches. S7.L5 names what you just found: enforcing the read rule is not the same as noninterference.

One more channel, seen only on the Bench. A policy that reads another table can race with a change to that table. In the recorded run, a locking read returns the new text at READ COMMITTED and fails with a serialization error at the two stricter levels, so the race is prevented by failure, not by returning nothing (run RUN-pg-catalog).
