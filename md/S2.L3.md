**Ideas taught.**

- Predict the goal a tactic produces

**Segments.**

1. Predict each goal

## Predict each goal (14 min)

**Question** (before the segment):

A goal contains `if c then x else y`. After `split`, what is there?

- A. One goal, with the `if` removed
- B. Two goals: one with `c` as a hypothesis and `x` in place of the `if`, one with `¬c` and `y`
- C. No goals
- D. Two goals with no new hypotheses

A tactic is a command that changes the goal. You do not write a proof from its last line backwards: you state the theorem, and each tactic turns the current goal into zero, one or several new ones. The proof ends when no goal is left. To read a proof you track the goal, not the code, and this lesson trains that skill: before each tactic is shown, you predict the goal it produces.

Three tactics carry most ledger proofs. `unfold` replaces a name by its definition. `split` breaks an `if` into two goals, one per branch, each with its branch's condition as a hypothesis. A closing tactic such as `simp` or `omega` finishes the arithmetic. The proof below uses all three on `transferPos_conserves`: after any transfer, the total is unchanged. Every goal in a replay is read from real Lean at build time, through its language server (run RUN-lean-plaingoal), and never typed by hand.

| Tactic | Turns the goal into |
|---|---|
| `unfold f` | the same goal with `f` replaced by its definition |
| `split` | two goals, one per branch of an `if`, each with its condition in scope |
| `constructor` | one goal for each part of a conjunction |
| `exact t` | no goal at all, if `t` has the goal's type |

Predict the goal after `unfold transferPos total` and make your call. Then step through the rest, predicting each goal before you look.

**Cell 1** (INS-goal-replay)

Replay shows: the reference proof of `transferPos_conserves`, with the goal before each tactic. Predict the goal, then compare.

```lean
structure Ledger where
  a : Int
  b : Int
deriving Repr, DecidableEq

def total (s : Ledger) : Int := s.a + s.b

def transferPos (s : Ledger) (n : Int) : Ledger :=
  if 0 < n ∧ n ≤ s.a then { a := s.a - n, b := s.b + n } else s

theorem transferPos_conserves (s : Ledger) (n : Int) :
    total (transferPos s n) = total s := by
  unfold transferPos total
  split <;> simp <;> omega
```

**Your call before the first run:**

What will the replay show as the goal after `unfold transferPos total`?

- A. The `if … then … else …` of `transferPos` now appears inside a sum of fields
- B. The goal is closed
- C. The goal is unchanged
- D. A new hypothesis `0 < n ∧ n ≤ s.a` appears

**Question** (ends the segment):

`transferKeep s n` is `if 0 < n ∧ n < s.a then { a := s.a - n, b := s.b + n } else s`, so it never empties the sender. The goal is `0 < (transferKeep s n).a`, with `ha : 0 < s.a` in scope. After `unfold transferKeep` and `split`, what is the second goal?

- A. `ha : 0 < s.a` and `0 < n ∧ n < s.a`; the goal is about the debited balance `s.a - n`
- B. `ha : 0 < s.a` only; the goal is `0 < s.a`
- C. `ha : 0 < s.a` and `¬(0 < n ∧ n < s.a)`; the goal is `0 < s.a`
- D. No goals: `split` has proved it

## Exit (4 min)

**Question** (exit question):

The goal is `0 ≤ (transferPos s n).a ∧ 0 ≤ (transferPos s n).b`, with `ha` and `hb` in scope. After `constructor`, what remains?

- A. One goal, the same conjunction
- B. Two goals, one for each part, and `ha` and `hb` are used up
- C. No goals, because the facts in scope already close it
- D. Two goals, `0 ≤ (transferPos s n).a` and `0 ≤ (transferPos s n).b`, each with `ha` and `hb` in scope
