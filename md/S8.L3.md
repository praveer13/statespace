## Before you start (2 min)

Between a customer's click and a settled charge, your system takes five steps, and a crash can land between any two of them. In some gaps a crash only delays the charge. In others it double-charges, or loses the charge, or does nothing at all. You will place the crash yourself, then ask TLC.

## Place the crash (13 min)

A command's chain has four gaps where a crash matters. Call them windows.

| Window | A crash lands between | One crash here permits |
|---|---|---|
| CW1 | Commit and Dispatch | delay only: the intent waits in the outbox |
| CW2 | Dispatch and Accept | you place the crash |
| CW3 | Accept and Persist | you place the crash |
| CW4 | Persist and Ack | you place the crash |

CW1 is the worked example. Commit writes the command and its pending intent. The worker crashes before it sends anything. Recover restarts it, the intent is still pending, Dispatch sends one request, the provider accepts it, and one charge happens. The answer for CW1 is none. You complete the other three in the Theater, with provider idempotency off, and the table fills in as you go.

**Cell 1** (INS-theater)

Enable one window, crash, recover and continue by hand. The monitors count charges per command.

Scene asserts: no command is charged more than once. The monitor counts the provider's charges for each command as you play, and marks a second one.

```tla
InWindow(w, c) ==
  CASE w = "CW1" -> status[c] = "pending"
    [] w = "CW2" -> /\ status[c] = "inflight"
                    /\ \E r \in reqs : r.cmd = c
                    /\ ~\E r \in replies : r.cmd = c
    [] w = "CW3" -> /\ \E r \in replies : r.cmd = c
                    /\ c \notin durable
    [] w = "CW4" -> c \in durable /\ status[c] = "inflight"
    [] OTHER     -> FALSE

\* A crash empties the worker's memory. The database and the network are not the worker's to lose.
Crash == /\ up
         /\ CrashBudget
         /\ \E c \in committed, w \in CrashWindows : InWindow(w, c)
         /\ up' = FALSE
         /\ got' = {}
         /\ crashes' = IF MaxCrashes < 0 THEN crashes ELSE crashes + 1
         /\ UNCHANGED <<committed, status, durable, attempts, reqs, replies, charges, seen>>

\* Recovery returns every inflight intent without a stored result to pending.
Recover == /\ ~up
           /\ up' = TRUE
           /\ status' = [c \in Cmds |-> IF status[c] = "inflight" /\ c \notin durable
                                          THEN "pending" ELSE status[c]]
           /\ UNCHANGED <<committed, durable, attempts, got, reqs, replies, charges, seen, crashes>>
```

## A poller and a late commit (13 min)

A crash is not the only way an effect fails to leave. Many systems deliver outbox rows with a poller. It reads committed rows above a high-water mark, delivers them, and raises the mark to the highest id it read. Two writers take sequence ids when they INSERT, and they commit in either order.

**Cell 3** (INS-theater)

Drive the writers and the poller by hand and watch the mark.

Scene asserts: every committed row is delivered, and the mark never passes a committed row that was not delivered.

```tla
Insert(w) == /\ wpc[w] = "idle"
             /\ idOf' = [idOf EXCEPT ![w] = nextId]
             /\ nextId' = nextId + 1
             /\ wpc' = [wpc EXCEPT ![w] = "inserted"]
             /\ UNCHANGED <<committedIds, delivered, mark>>

CommitRow(w) == /\ wpc[w] = "inserted"
                /\ committedIds' = committedIds \cup {idOf[w]}
                /\ wpc' = [wpc EXCEPT ![w] = "committed"]
                /\ UNCHANGED <<nextId, idOf, delivered, mark>>

\* Design "mark": rows above the mark.  Design "status": rows not yet delivered.
Batch == IF Design = "mark" THEN {i \in committedIds : i > mark}
                            ELSE committedIds \ delivered

Poll == /\ Batch /= {}
        /\ delivered' = delivered \cup Batch
        /\ mark' = IF Design = "mark" THEN Max(Batch \cup {mark}) ELSE mark
        /\ UNCHANGED <<nextId, idOf, wpc, committedIds>>

MarkInv == \A i \in committedIds : i <= mark => i \in delivered
```

**Your call before the first run:**

Writer 1 takes id 1. Writer 2 takes id 2 and commits first. The poller delivers row 2 and sets its mark to 2. Then writer 1 commits. Will row 1 be delivered?

- A. No, never.
- B. Yes, on the next poll.
- C. Yes, after the worker restarts.

Recorded run: RUN-tlc-lost-effect (tlc 2026.10.20.183001).

Text that follows the first run is left out here.

Poll by status, not by id. Claim pending rows with `FOR UPDATE SKIP LOCKED`, and delivery stays at-least-once. The [PostgreSQL 18 documentation](https://www.postgresql.org/docs/18/sql-select.html) says that skipping locked rows "provides an inconsistent view of the data": it claims rows, and it never promises completeness.

**Question** (ends the segment):

A poller claims pending rows by status instead of by id. Two writers insert and commit in either order, and polls run in between. Can a committed row be skipped forever?

- A. Yes: writer 2 commits first, a poll delivers row 2, then row 1 commits below the mark.
- B. No: a committed row stays pending until a poll claims it, whatever the commit order.
- C. Only when the writers commit in id order.
