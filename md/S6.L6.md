## Before you replay (2 min)

Your compiler from S6.L2 turns a debit into SQL. This lesson asks what happens when two sessions run that SQL at the same time, and the answer depends on how you compiled it. If you already know the isolation levels and the anomalies they allow, a finished concurrency lesson in tablespace counts as evidence of the basics, and drawer D-11 is a one-page recap if you want it.

**Question** (before the segment):

- A. How each withdrawal is compiled.
- B. The isolation level alone.
- C. Whether the sessions share a connection.
- D. How far apart in time they run.

- A. No: one fails with a serialization failure.
- B. No: they deadlock.
- C. Only if the holds are on different accounts.
- D. Yes.

## Two withdrawals, two compilations (15 min)

You have met this bug in a model. In Stage 5 you split a transfer into a read and a write, and TLC found two withdrawals of 80 that both went through against a balance of 100 (run RUN-tlc-doublespend). Making the guard and the write one atomic action removed the bug (run RUN-tlc-atomic). SQL gives you the same two shapes, and the isolation level does not choose between them for you. Your compiler does.

Here are two compilations of one debit of 80 from account 1.

```sql
-- Compilation 1: read-modify-write
SELECT bal FROM acct WHERE id = 1;          -- the application reads 100
-- the application checks 100 >= 80 and computes 20
UPDATE acct SET bal = 20 WHERE id = 1;      -- and writes the constant it computed

-- Compilation 2: conditional UPDATE
UPDATE acct SET bal = bal - 80 WHERE id = 1 AND bal >= 80;
```

The schema, the amount, the level and the two sessions are the same in both. Two PostgreSQL facts decide what happens when both sessions run at once. An UPDATE locks the row it changes, so a second UPDATE of that row waits until the first transaction ends. And under READ COMMITTED, when that wait ends in a commit, the waiting statement does not simply carry on: the manual says "The search condition of the command (the WHERE clause) is re-evaluated to see if the updated version of the row still matches" (§13.2.1, read 2026-10-23).

Every outcome on this page was recorded on PostgreSQL 18.6. Make your call on the conditional UPDATE first. The cell then lets you replay the read-modify-write beside it.

**Cell 1** (INS-history)

Both compilations at READ COMMITTED, one account holding 100, two sessions each debiting 80. The first permutation replays the conditional UPDATE. The second replays the read-modify-write.

Replay shows: the same two debits compiled two ways. In both, the second session's write waits for the first session's row lock. Compare what each second session is told when its wait ends.

```text
-- level: READ COMMITTED; account 1 holds 100; each session debits 80
setup { CREATE TABLE acct (id int PRIMARY KEY, bal bigint NOT NULL); INSERT INTO acct VALUES (1, 100); }

-- compilation 2: conditional UPDATE, the guard and the write in one statement
session a
step a_begin  { BEGIN ISOLATION LEVEL READ COMMITTED; }
step a_debit  { UPDATE acct SET bal = bal - 80 WHERE id = 1 AND bal >= 80; }
step a_commit { COMMIT; }

session b
step b_begin  { BEGIN ISOLATION LEVEL READ COMMITTED; }
step b_debit  { UPDATE acct SET bal = bal - 80 WHERE id = 1 AND bal >= 80; }   -- waits for a's row lock
step b_commit { COMMIT; }

-- compilation 1: read-modify-write, the client computes the new balance
session c
step c_begin  { BEGIN ISOLATION LEVEL READ COMMITTED; }
step c_read   { SELECT bal FROM acct WHERE id = 1; }
step c_write  { UPDATE acct SET bal = 20 WHERE id = 1; }   -- the client checked 100 >= 80 and computed 20
step c_commit { COMMIT; }

session d
step d_begin  { BEGIN ISOLATION LEVEL READ COMMITTED; }
step d_read   { SELECT bal FROM acct WHERE id = 1; }
step d_write  { UPDATE acct SET bal = 20 WHERE id = 1; }   -- the same constant, from its own read
step d_commit { COMMIT; }

permutation a_begin a_debit b_begin b_debit a_commit b_commit
permutation c_begin c_read d_begin d_read c_write d_write c_commit d_commit
```

**Your call before the first run:**

In the conditional UPDATE, txn B's statement waits on txn A's row lock. Txn A commits. Txn B then:

- A. Fails with a serialization failure.
- B. Deadlocks with txn A, and one of them is aborted.
- C. Re-checks `bal >= 80` against the new row version and updates 0 rows.
- D. Applies its debit to the value it first saw.

## The predicate nobody locks (15 min)

A conditional UPDATE guards one row, and the row lock does the rest. Now guard against something that is not a row. A hold sets money aside, as a row in `holds(acct, amt)`. What is available on an account is its balance less the sum of its holds, and a new hold may be placed only while enough is available. Compiled, that is a read followed by an insert.

```sql
SELECT bal - coalesce((SELECT sum(amt) FROM holds WHERE acct = 1), 0)
FROM acct WHERE id = 1;                  -- available: the application reads 100
-- the application checks 100 >= 80
INSERT INTO holds VALUES (1, 80);        -- and sets 80 aside
```

Two sessions run this at once. Each reads 100 available, and each inserts a hold of 80. The two inserts write two different new rows, so no row is written twice and there is no row for a lock to protect. Yet each read depends on what the other writes: `sum(amt)` is a question about the whole set of holds, and each insert changes the answer to the other's question. That is write skew. Two transactions each read something the other writes, and each writes something the other read, on different rows.

REPEATABLE READ in PostgreSQL is snapshot isolation, and snapshot isolation only checks whether two concurrent transactions wrote the same row. Here they did not, so nothing is checked. Make your call, then replay all three levels.

**Cell 2** (INS-history)

The holds compilation: read what is available, then insert a hold of 80. The first permutation runs at REPEATABLE READ.

Replay shows: both sessions read the available amount before either inserts, then each inserts a hold of 80 and commits. The level changes with the permutation.

```text
-- compilation: predicate read, then insert
-- account 1 holds 100; holds records money set aside; each session sets aside 80
setup {
  CREATE TABLE acct  (id int PRIMARY KEY, bal bigint NOT NULL);
  CREATE TABLE holds (acct int, amt bigint);
  INSERT INTO acct VALUES (1, 100);
}

session a
step a_rc     { BEGIN ISOLATION LEVEL READ COMMITTED; }
step a_rr     { BEGIN ISOLATION LEVEL REPEATABLE READ; }
step a_ser    { BEGIN ISOLATION LEVEL SERIALIZABLE; }
step a_avail  { SELECT bal - coalesce((SELECT sum(amt) FROM holds WHERE acct = 1), 0) FROM acct WHERE id = 1; }
step a_hold   { INSERT INTO holds VALUES (1, 80); }   -- only if a_avail returned 80 or more
step a_commit { COMMIT; }

session b
step b_rc     { BEGIN ISOLATION LEVEL READ COMMITTED; }
step b_rr     { BEGIN ISOLATION LEVEL REPEATABLE READ; }
step b_ser    { BEGIN ISOLATION LEVEL SERIALIZABLE; }
step b_avail  { SELECT bal - coalesce((SELECT sum(amt) FROM holds WHERE acct = 1), 0) FROM acct WHERE id = 1; }
step b_hold   { INSERT INTO holds VALUES (1, 80); }   -- only if b_avail returned 80 or more
step b_commit { COMMIT; }

permutation a_rr  a_avail b_rr  b_avail a_hold b_hold a_commit b_commit
permutation a_rc  a_avail b_rc  b_avail a_hold b_hold a_commit b_commit
permutation a_ser a_avail b_ser b_avail a_hold b_hold a_commit b_commit
```

**Your call before the first run:**

Txn A and txn B each read 100 available and each insert a hold of 80, at REPEATABLE READ. Outcome?

- B. Both commit: 160 is held against a balance of 100.
- C. Txn B waits for txn A, then sees 20 available.
- D. One transaction fails with a deadlock.

## Opposite directions (12 min)

The last pattern is a transfer compiled as two UPDATEs, debit first. Txn A moves 10 from account 1 to account 2. Txn B moves 10 from account 2 to account 1. Each debits its own account first, so each holds one row lock, and each then asks for the lock the other holds. Make your call, then replay. The cell's second permutation takes locks in one order instead.

**Cell 3** (INS-history)

Two transfers in opposite directions, interleaved after both debits, at READ COMMITTED. The second permutation has both sessions touch account 1 first, at REPEATABLE READ.

Replay shows: in the first permutation each session takes its debit lock, then each asks for the other's row. In the second, txn B's first statement waits for txn A, and txn B's next statement is ignored once an error arrives.

```text
-- compilation: two UPDATEs per transfer
-- accounts 1 and 2 hold 100 each; a moves 10 from 1 to 2, b moves 10 from 2 to 1
setup { CREATE TABLE acct (id int PRIMARY KEY, bal bigint NOT NULL); INSERT INTO acct VALUES (1, 100), (2, 100); }

session a
step a_rc     { BEGIN ISOLATION LEVEL READ COMMITTED; }
step a_rr     { BEGIN ISOLATION LEVEL REPEATABLE READ; }
step a_debit  { UPDATE acct SET bal = bal - 10 WHERE id = 1 AND bal >= 10; }   -- locks row 1
step a_credit { UPDATE acct SET bal = bal + 10 WHERE id = 2; }                 -- wants row 2
step a_commit { COMMIT; }

session b
step b_rc     { BEGIN ISOLATION LEVEL READ COMMITTED; }
step b_rr     { BEGIN ISOLATION LEVEL REPEATABLE READ; }
step b_debit  { UPDATE acct SET bal = bal - 10 WHERE id = 2 AND bal >= 10; }   -- locks row 2
step b_credit { UPDATE acct SET bal = bal + 10 WHERE id = 1; }                 -- wants row 1
step b_commit { COMMIT; }

-- opposite lock orders: each session debits first
permutation a_rc a_debit b_rc b_debit a_credit b_credit a_commit b_commit
-- one lock order: b credits account 1 first, as a debits it first
permutation a_rr a_debit b_rr b_credit a_credit a_commit b_debit b_commit
```

- C. Both fail with a serialization failure.

## Exit (8 min)

Here is the lesson in one table. Every cell is a recorded result (run RUN-pg-claims) (run RUN-pg-catalog). Read it by row first: the compilation sets the row, and the level sets the cell.

| Compilation | READ COMMITTED | REPEATABLE READ | SERIALIZABLE |
|---|---|---|---|
| read-modify-write | both commit; 160 spent from 100 | txn B fails with a serialization failure | one session fails in every interleaving except the two serial orders |
| conditional UPDATE | txn B waits, then updates 0 rows | txn B fails with a serialization failure | txn B fails with a serialization failure |
| predicate read, then insert (holds) | both commit; 160 held against 100 | both commit; 160 held against 100 | txn B fails at COMMIT with a serialization failure |
| opposite-order moves | one fails with a deadlock error | the same interleavings deadlock | the same interleavings deadlock |

No level cures every row. REPEATABLE READ turns the lost update into a failure and misses write skew. SERIALIZABLE catches write skew and still deadlocks on opposite-order moves. The conditional UPDATE needs a retry the moment you raise the level. In Stage 5 the double spend had two remedies, an atomic action and isolation. This table is the second one, and it shows that the first is available in SQL as a single statement.

You can already claim something from the conditional UPDATE's row. Under concurrent READ COMMITTED sessions it never overspends: in every recorded interleaving of two debits, the final balance is not negative, the debits that committed total at most the starting balance, and each refusal came back as zero rows. That claim is TESTED [T] · n histories, where n counts the recorded histories: every interleaving of two debits, over a grid of amounts (run RUN-pg-conditional-concurrent). It carries one assumption, ASSUMED [A]: PostgreSQL behaves as its manual documents. And it has a gap, NOT COVERED [N]: guards that span several rows, like the holds.

**Claim card CL-6.2** is minted here, prefilled from the results above.

The SERIALIZABLE column rests on one more assumption that these recordings cannot test for you: that PostgreSQL's SERIALIZABLE gives serializable outcomes for committed SERIALIZABLE transactions. The course plants that as a seam here, carries it on the claim you will mint in S6.L8, and re-runs PostgreSQL's own regression spec for it on a schedule. S6.L9 shows what it rests on.
