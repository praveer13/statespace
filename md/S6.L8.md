## Before you check (2 min)

Until now you compared outcomes: the interpreter said one thing, PostgreSQL said another, and you counted the cases where they differed. This lesson asks for something sharper. You will write a relation between the states of your reference semantics and the states of the database, then check that every step the database takes is matched by a step the semantics could take.

## One square at a time (15 min)

The two kinds of state do not look alike. An abstract state S maps account ids to balances. A database state D is tables of rows, with NULLs and, since S6.L5, postings. R(S, D) says which databases stand for which abstract states, in two parts.

- `wf(D)` says a database state means something at all: every `bal` is non-null and at least 0, and each balance matches its postings.
- `α(D)` is the abstract state that a well-formed D stands for: the map from each account id to its `bal`.
- `R(S, D)` holds when `wf(D)` holds and `S = α(D)`.

A state with a NULL balance has no S at all, because `wf` fails. That is why the `NOT NULL` of S6.L2 keeps every reachable D inside R.

The simulation square checks one transaction t at a time. Start from R(S, D). Let c be the command t was running, and let D → D′ be what t did to the database. What the semantics must say depends on how t ended.

| How t ended | What the reference semantics must say |
|---|---|
| Committed | `interp(c, S)` is `Ok(S′, out)`, with `S′ = α(D′)` and `out` equal to the old and new pairs t reported |
| Refused by its guard, with a typed outcome | `interp(c, S)` is `Err e`, with `D′ = D` and `e` the typed outcome t returned |
| Aborted and retried, or `GaveUp` | No abstract step: `D′ = D`, a stutter |

Here are two recorded transactions through the square, with account 1 at 100 and account 2 at 50.

| Transaction | α(D) before | The interpreter from S | α(D′) after | Square |
|---|---|---|---|---|
| `Transfer(1, 2, 30)` commits; pairs `1: 100 → 70` and `2: 50 → 80` | `{1: 100, 2: 50}` | `Ok`, `S′ = {1: 70, 2: 80}`, same pairs | `{1: 70, 2: 80}` | holds |
| `Transfer(1, 2, 500)`: the debit matched 0 rows on an account that exists | `{1: 70, 2: 80}` | `Err Insufficient` | `{1: 70, 2: 80}`, since `D′ = D` | holds |

Now a third transaction, which you call before the checker does. Account 3 holds the largest `bigint`, and the reference semantics has unbounded integers.

## Some serial order (15 min)

A single transaction's square is easy: one step of the database, one step of the semantics. Concurrency breaks that. When transactions overlap there is no single D to start each one from, and the database has not told you in which order to explain them. So the question changes from "is this step matched?" to "is there some order in which the steps could have run one at a time and given everyone the outputs they actually got?"

That is abstract serializability, and the check is a search. It takes the committed transactions, tries serial orders, and replays each through the reference semantics from `α(D₀)`. An order passes when every transaction's replayed output equals the output it committed with: its old and new pairs from `RETURNING`, and its typed outcome. Aborted attempts are stutters and are skipped. Two things keep the search small: the write order that old and new values reveal (a transaction that read 100 and wrote 20 came before one that read 20), and what each transaction read from whom. The search is still bounded: it handles at most 8 transactions and prints that bound with every verdict.

Read the two answers differently. A rejection shows an anomaly in this history, because no order explains it. An acceptance shows only that this history had a serial explanation. It does not show that the database will always provide one.

Take the history from S6.L6 where both withdrawals went through at READ COMMITTED. Make your call, then replay.

The read-modify-write history from S6.L6, as the serial-order checker reads it.

```text
-- the abstract command of each transaction: Debit(1, 80)

```

## Two orders for one history (12 min)

One more thing to unlearn is that the serial order is the order in which transactions committed. With two-phase locking the two usually agree. PostgreSQL's SERIALIZABLE is built on snapshots, so a transaction can read an old state, commit last, and still belong first in the serial order.

Take a report that reads two accounts while a transfer commits between the two reads. At SERIALIZABLE the report's snapshot is taken at its first read, so it sees the state from before the transfer for both accounts. It is a consistent report of an older state, and it commits after the transfer. Make your call, then replay.

**Cell 3** (INS-history)

A report and a transfer at SERIALIZABLE (catalog row H04). Accounts 1 and 2 hold 100 each.

Check asserts: some serial order, replayed through the reference semantics, gives each transaction the output it committed with. The checker also replays the commit order and reports what it finds.

```text
-- history: report before transfer, SERIALIZABLE; every committed state totals 200

txn A (report)    read acct 1 -> 100
txn B (transfer)  move 50 from 1 to 2;  pairs  acct 1: 100 -> 50,  acct 2: 100 -> 150
txn B             COMMIT                           -- txn B commits first
txn A (report)    read acct 2 -> 100               -- still read from its snapshot
txn A             COMMIT                           -- txn A commits last

search  serial orders of the 2 committed transactions, each replayed from alpha(D0) = {1: 100, 2: 100}
bound   at most 8 transactions
```

**Your call before the first run:**

Replayed in commit order, txn B then txn A, does the checker accept the history?

- A. Yes: commit order is the serial order.
- B. No: the history has a lost update.
- C. No: the report fits only an order with the report first.
- D. No: PostgreSQL must have aborted txn A.
