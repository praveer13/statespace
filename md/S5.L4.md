# S5.L4 · The holds lifecycle

> Draft: first-learner pass pending.

**Format.** Short lesson with reading, about 18 minutes.

**Objective.** Write a hold's lifecycle in TLA+ with a counter for resolutions, state that a hold never resolves twice as an invariant, and give a behavior for each outcome and a step the spec forbids.

**Ideas taught.**

- Available → Held → Captured or Released

**Segments.**

1. One hold
2. Exit

## One hold (14 min)

**Question** (before the segment):

Which formula says "a hold never resolves twice"?

- A. `<>(res >= 1)`, read as a property of the whole behavior
- B. `~(hst = "captured" /\ hst = "released")`, read as an invariant
- C. `res <= 1` as an invariant (`res` counts resolutions)

A hold reserves funds for a payment. `Place` takes it from available to held. From held it is either captured, and the money moves, or released, and the funds go back. In the spec these are three system actions on one hold, and the property to state is that it never resolves twice.

A state cannot say that. It holds one value for `hst` and remembers nothing about how it got there. So add a history variable, `res`, that counts resolutions: every `Capture` and every `Release` adds 1. Then the sentence is an ordinary invariant, `res <= 1`.

A second kind of statement is about a step, not a state. `StaysResolved` says that from a captured or released hold the next state is the same. It is an action property, so TLC checks it on the Bench, and the tab checks invariants. The implication is in parentheses because TLA+'s own parser rejects the bare form, although Spectacle's accepts it (run RUN-spectacle-s5s8).

**Cell 1** (INS-spectacle)

Model asserts: `TypeOK` and `NeverTwice` hold in every reachable state. A resolved hold has nothing left to do, so this model turns the deadlock check off.

```tla
---- MODULE HoldsLifecycle ----
EXTENDS Naturals
VARIABLES hst, res
vars == <<hst, res>>

TypeOK == /\ hst \in {"available", "held", "captured", "released"}
          /\ res \in 0..2

Init == hst = "available" /\ res = 0

Place   == hst = "available" /\ hst' = "held"     /\ UNCHANGED res
Capture == hst = "held"      /\ hst' = "captured" /\ res' = res + 1
Release == hst = "held"      /\ hst' = "released" /\ res' = res + 1

Next == Place \/ Capture \/ Release
Spec == Init /\ [][Next]_vars

NeverTwice == res <= 1
\* An action property: a resolved hold stays resolved. TLC checks it on the Bench.
StaysResolved == [][(hst \in {"captured", "released"}) => hst' = hst]_hst
====
\* INIT Init, NEXT Next, INVARIANT TypeOK, INVARIANT NeverTwice, deadlock check off
```

**Your call before the first run:**

Can `res` reach 2 in this lifecycle?

- A. No.
- B. Yes: `Capture` and `Release` are both enabled in held, so both fire.
- C. It depends on the scheduler.

**Question** (ends the segment):

A variant lets `Release` fire from `captured` as well as from `held`. Which prefix is the first to break `res <= 1`?

- A. `Place`, `Release`
- B. `Place`, `Capture`, `Release`
- C. `Place`, `Capture`, then a step that changes nothing

## Exit (4 min)

**Question** (exit question):

In the lifecycle's state `hst = "captured"`, `res = 1`, which actions are enabled?

- A. `Release`: it gives the money back to the payer.
- B. None: the behavior ends once the hold has resolved.
- C. None: the behavior stays here and stutters forever.
