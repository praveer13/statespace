## What your checker did not see (17 min)

In S6.L8 you minted a claim from what your checker saw. This lesson is about what it did not see.

**Question** (before the segment):

Your checker accepted all n recorded SERIALIZABLE histories. What does that establish about production?

- A. Only that these n histories were serializable.
- B. That production is serializable.
- C. That PostgreSQL has no isolation bugs.
- D. That PostgreSQL behaves as its manual documents.

Three histories show where the claim is thin. First, read skew.

**Cell 1** (INS-history)

Read skew at READ COMMITTED (catalog row H04).

Replay shows: txn A reads account 1, txn B's transfer commits, and txn A reads account 2. Add up what txn A saw.

```text
-- accounts 1 and 2 hold 100 each, so every committed state totals 200
-- txn A only reads; txn B moves 50 from account 1 to account 2
session a
step a_begin  { BEGIN ISOLATION LEVEL READ COMMITTED; }
step a_read1  { SELECT bal FROM acct WHERE id = 1; }
step a_read2  { SELECT bal FROM acct WHERE id = 2; }
step a_commit { COMMIT; }

session b
step b_begin  { BEGIN ISOLATION LEVEL READ COMMITTED; }
step b_move   { UPDATE acct SET bal = bal - 50 WHERE id = 1; UPDATE acct SET bal = bal + 50 WHERE id = 2; }
step b_commit { COMMIT; }

permutation a_begin a_read1 b_begin b_move b_commit a_read2 a_commit
```

Second, mixed levels.

**Cell 2** (INS-history)

Mixed levels (catalog row H10). Txn A runs SERIALIZABLE and txn B runs READ COMMITTED.

Replay shows: both sessions read the team total before either debits, then each debits and commits.

```text
-- two accounts of 100 form a team; each session reads the team total (200)
-- and debits 150 from its own account if the total stays at least 0
session a
step a_begin  { BEGIN ISOLATION LEVEL SERIALIZABLE; }
step a_total  { SELECT sum(bal) FROM acct WHERE team = 1; }
step a_debit  { UPDATE acct SET bal = bal - 150 WHERE id = 1; }   -- only if a_total allowed it
step a_commit { COMMIT; }

session b
step b_begin  { BEGIN ISOLATION LEVEL READ COMMITTED; }
step b_total  { SELECT sum(bal) FROM acct WHERE team = 1; }
step b_debit  { UPDATE acct SET bal = bal - 150 WHERE id = 2; }   -- only if b_total allowed it
step b_commit { COMMIT; }

permutation a_begin a_total b_begin b_total a_debit b_debit a_commit b_commit
```

Your claim rests on three clauses. Give each the strongest stamp it can carry.

1. **Every writer is SERIALIZABLE.** The guarantee has a condition: "If the Serializable transaction isolation level is used for all writes and for all reads which need a consistent view of the data" (§13.4.1, read 2026-10-23). Set `default_transaction_isolation = serializable` and read it back from each session: CONFIGURED [C]. Add a check in each transaction, as the manual suggests with "checks of the transaction isolation level in triggers": ENFORCED [E].
2. **PostgreSQL behaves as documented.** ASSUMED [A]. You can narrow it: the regression spec for the bug Jepsen found, `update-conflict-out.spec`, passes on the version you pin (run RUN-pg-catalog) (row H21), and the course re-runs it on a schedule. One history is evidence, not a stamp.
3. **Nothing reads a replica.** ASSUMED [A]. The protection "does not yet extend to hot standby mode … or logical replicas" (§13.4.1), and SERIALIZABLE "is not yet available in hot standby" (§26.4.5). A report served from a standby is outside your claim. The course plants this clause as a seam here, and S7.L8 is where it cracks.

If you built kernelspace's pool conformance, re-stamp it the same way: a lockstep run over one deterministic traffic script is TESTED [T] · n ticks · 1 script.

**Question** (ends the segment):

A claim's strip has three segments: the proposition of the model, the correspondence, and the requirement fit. Every session of your pool reads back `default_transaction_isolation = serializable`. Where does that evidence go, and with which stamp?

- A. Proposition of the model: `TESTED [T] · n histories`

## Exit (4 min)

**Question** (exit question):

Which statement is true?

- A. A claim that assumes no replica reads still covers a report served from a standby.
