## Two kinds of witness (15 min)

An agent reviews your hold model and writes: "The hold resolves exactly once." That one sentence makes two promises, and a model checker treats them in different ways. This lesson pulls them apart.

**Question** (before the segment):

Which can a finite log refute: "a hold never resolves twice" or "a hold eventually resolves"?

- A. Only the first.
- B. Both.
- C. Only the second.

**Question** (before the segment):

"Every hold resolves before its deadline", with the deadline counted on a clock variable, is...

- A. safety
- B. liveness
- C. both at once

A property makes a claim about whole behaviors, and two questions sort almost every property you will write.

**Can a finite log refute it?** Then it is **safety**. There is a bad thing, and once it has happened no continuation repairs it. "A hold never resolves twice" is safety: a log with two resolutions shows the bad thing, and nothing later can undo it.

**Can no finite log ever refute it?** Then it is **liveness**. Every finite prefix can still be extended into a behavior that satisfies the property, so a good thing that has not happened yet may still happen. "A hold eventually resolves" is liveness. A log that ends with the hold held proves nothing, because the next step may resolve it.

Most promises mix the two. "A hold resolves exactly once" is both: "at most once" is safety and "at least once" is liveness. Every property splits this way, into a safety part and a liveness part.[^s1b4-1]

[^s1b4-1]: Alpern and Schneider proved the split in "Defining Liveness" (Information Processing Letters, 1985). The paper is optional reading.

See a safety witness by breaking the lifecycle on purpose. Let `Release` also run from `captured`:

```tla
Release == hst \in {"held", "captured"} /\ hst' = "released" /\ res' = res + 1
```

Now Place, Capture, Release is a behavior with `res = 2`, and `NeverTwice` fails. Those three steps are the whole witness, and every way of continuing them fails too. Keep that picture and look at the other kind of property.

**Cell 1** (INS-theater)

Spec asserts: one hold is placed, then captured or released, once. The property asks: whenever the hold is held, is it later resolved? Play the graph by choosing enabled actions, and try to build a finite prefix that no continuation can repair.

```tla
---- MODULE Lifecycle ----
EXTENDS Naturals
VARIABLES hst, res
vars == <<hst, res>>

Init == hst = "available" /\ res = 0

Place   == hst = "available" /\ hst' = "held"     /\ UNCHANGED res
Capture == hst = "held"      /\ hst' = "captured" /\ res' = res + 1
Release == hst = "held"      /\ hst' = "released" /\ res' = res + 1

Next == Place \/ Capture \/ Release
Spec == Init /\ [][Next]_vars

Resolved == hst \in {"captured", "released"}
NeverTwice == res <= 1
EventuallyResolves == (hst = "held") ~> Resolved
====
```

- B. Yes, if the prefix is long enough.
- C. No.

Sort a property by asking for its witness. Here is the list for your hold model:

| A promise about a hold | Kind | What shows it failed |
|---|---|---|
| A hold never resolves twice: `[](res <= 1)` | safety | a finite prefix with two resolutions |
| A resolved hold stays resolved | safety | a finite prefix with one step out of `captured` or `released` |
| A hold eventually resolves | liveness | a behavior that never resolves: a lasso |
| A hold resolves before its deadline | safety | a finite prefix in which the clock passes the deadline with the hold unresolved |
| A hold resolves exactly once | both | whichever half fails |

A common slip: "before its deadline" sounds like "eventually", so it feels like liveness. Ask for the witness instead. Once the clock has passed the deadline with the hold unresolved, no continuation repairs the behavior, so a finite prefix is enough. TLA+ formulas cannot see stuttering steps, so "within k steps" needs a clock variable in the spec, and with the clock it is safety.

**Question** (ends the segment):

With `Release` also enabled from `captured`, which finite prefix of the lifecycle violates `NeverTwice`?

- A. `Place`, `Capture`
- B. `Place`, `Release`
- C. `Place`, `Capture`, `Release`
- D. None: a finite prefix cannot violate a property about what happens over time.

## Lassos (15 min)

A safety violation is a finite trace. A liveness violation cannot be, because no finite prefix refutes it: you need a whole infinite behavior in which the good thing never comes. A model with finitely many states makes that practical. An infinite behavior over finitely many states must come back to a state it has already visited, so it can be drawn as a finite **stem** followed by a **cycle** that repeats forever. That shape is a **lasso**, and TLC reports one when a temporal property fails.

Here is a second model, a hold with a retrying worker, which you will meet again in the next lesson. `Try` moves `held` to `pending`. From `pending`, the provider answers `Busy`, which moves back to `held`, or accepts (`Capture`, to `captured`). From `held`, the hold may time out (`Timeout`, to `released`). The variable `tries` flips between 0 and 1 on each `Try` and does nothing else, except make cycles longer.

**Cell 2** (INS-lasso)

Spec asserts: the retrying hold with no fairness conjunct at all. The check asks whether `<>Resolved` holds on every behavior of `Spec`. A violation comes back as a lasso: a stem, then a cycle that repeats forever.

```tla
---- MODULE Hold ----
\* A hold that a worker keeps retrying to capture; the provider may keep answering "busy".
EXTENDS Naturals
VARIABLES st, tries
vars == <<st, tries>>
Init == st = "held" /\ tries = 0
Try     == st = "held"    /\ st' = "pending"  /\ tries' = (tries + 1) % 2
Busy    == st = "pending" /\ st' = "held"     /\ UNCHANGED tries
Capture == st = "pending" /\ st' = "captured" /\ UNCHANGED tries
Timeout == st = "held"    /\ st' = "released" /\ UNCHANGED tries
Next == Try \/ Busy \/ Capture \/ Timeout
Spec == Init /\ [][Next]_vars          \* no fairness conjunct
Resolved == st \in {"captured", "released"}
EventuallyResolves == <>Resolved
====
```

**Your call before the first run:**

With no fairness conjunct, does this model satisfy `EventuallyResolves`?

- A. Yes: `Timeout` and `Capture` exist.
- B. No.
- C. Yes, for the states TLC explored.

Reading a lasso takes three tests, and the checker in this page applies them to every lasso you build. It must be a path: each step is an action that is enabled where it is taken. It must close: the last step returns to a state already on the lasso. And the property must fail on it: for `<>Resolved`, no state on the lasso is resolved.

Try one by hand. Start at `held` with `tries` at 0. `Try` gives `pending` with `tries` at 1. `Busy` gives `held` with `tries` at 1. `Try` gives `pending` with `tries` back at 0, and `Busy` returns to the state you started in. The path closes and no state on it is resolved, so it is a second lasso, made of real steps instead of one stuttering step.

**Question** (ends the segment):

The retrying hold has no fairness conjunct. Which behavior is a lasso that violates `EventuallyResolves`?

- A. `Try`, `Capture`, then stuttering forever in `captured`.
- B. `Try`, then `Try` again, then back to the first state.
- C. `Try`, `Busy`, `Try`, `Busy`, then back to the first state, repeated forever.
- D. None: `Capture` and `Timeout` exist, so the hold always resolves.

## Writing it (12 min)

Three operators carry most of the temporal logic you will write.

- `[]P` (always): P holds in every state of the behavior from here on.
- `<>P` (eventually): P holds in at least one state from here on.
- `P ~> Q` (leads to): whenever P holds, Q holds then or later. It is shorthand for `[](P => <>Q)`.

Two combinations are worth knowing on sight. `[]<>P` says P keeps happening forever. `<>[]P` says P eventually holds for good.

**Cell 3** (INS-lasso)

Config asks: `SPECIFICATION Spec` and `PROPERTY Avail`, where `Avail == hst = "available"`. The check reads `Avail` as TLC reads it. A violation would be a behavior of `Spec` on which `Avail` fails.

```tla
---- MODULE Lifecycle ----
EXTENDS Naturals
VARIABLES hst, res
vars == <<hst, res>>
Init == hst = "available" /\ res = 0
Place   == hst = "available" /\ hst' = "held"     /\ UNCHANGED res
Capture == hst = "held"      /\ hst' = "captured" /\ res' = res + 1
Release == hst = "held"      /\ hst' = "released" /\ res' = res + 1
Next == Place \/ Capture \/ Release
Spec == Init /\ [][Next]_vars

Resolved == hst \in {"captured", "released"}
Avail == hst = "available"
\* Then try, one at a time:  []Avail   <>Avail   <>Resolved
Responds == (hst = "held") ~> Resolved
====
```

Two habits follow. First, `INVARIANT Inv` means the property `[]Inv`, so use `INVARIANT` for "never" and write `PROPERTY` for what an invariant cannot say, with the operators spelled out. Second, write "exactly once" as `NeverTwice /\ EventuallyResolves`, two properties, never as one eager `<>`, which says only "at least once". For example, `Responds == (hst = "held") ~> Resolved` says that every held hold is later resolved.

Writing a formula from English goes wrong about twice as often as reading one back into English, in studies of students learning temporal logic. The exit items practice the harder direction.

## Exit (3 min)

**Question** (exit question):

Which of these promises about a hold is both a safety property and a liveness property joined together?

- A. A hold is never both captured and released.
- B. Every held hold is eventually resolved.
- C. A resolved hold stays resolved, and every held hold is eventually resolved.

**Question** (exit question):

A job moves `queued`, then `running` (`Start`), then `done` (`Finish`). There is no fairness conjunct. Which behavior is a lasso that violates `<>(state = "done")`?

- A. `Start`, `Finish`, then stuttering forever in `done`.
- B. `Start`, then stuttering forever in `running`.
- C. `Start`, `Finish`, then back to `queued`, repeated forever.
- D. None: `Start` and `Finish` are always enabled, so the job finishes.

**Question** (exit question):

Which formula says "whenever a hold is held, it is eventually resolved"?

- A. `[] (hst = "held" => Resolved)`
