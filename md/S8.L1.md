# S8.L1 · Commits are not sends

> Draft: first-learner pass pending.

**Format.** Short lesson with reading, about 16 minutes.

**Objective.** For send-then-commit, commit-then-send and an outbox, each crashed at a marked point, say which guarantees hold at the provider and which hold only in your database.

**Ideas taught.**

- Recording intent is not performing an effect

**Segments.**

1. Three designs, one crash each
2. Exit

## Three designs, one crash each (12 min)

An agent opens a pull request with this note. Nothing has reviewed it:

> We call the provider right after COMMIT returns, so every charge happens exactly once. All tests green.

Tests run on a good day. Here the process dies at one marked line, and you read what is left.

**Question** (before the segment):

Your handler commits a capture, then calls the provider. The process dies between the two. After restart, what is true?

- A. The database shows the capture; the provider was never called.
- B. The provider will be called on restart, because the capture committed.
- C. Neither happened: the transaction covers the call, so both roll back.

Three handlers pair a database write with a provider call. They differ only in order, and the order decides what a crash leaves behind.

**Cell 1** (INS-theater)

Place the crash at the marked point and watch the monitors.

Scene asserts: the end state after one crash at the marked line. Each monitor labels it an effect with no record, a record with no effect, or an intent waiting. A monitor reports what this scene did; it earns no stamp.

```text
A  send, then commit      B  commit, then send      C  outbox
   call the provider         COMMIT the capture        COMMIT the capture and an intent row
   COMMIT the capture        call the provider         (a worker, later)
                                                        read the intent, call the provider,
                                                        mark the intent done
```

**Your call before the first run:**

In design C the crash lands right after COMMIT. After restart, what does the outbox guarantee?

- A. The intent survives, and a worker sends it at least once if it recovers.
- B. The effect will happen exactly once, because the intent is a single row.
- C. The effect is lost unless the client retries the whole request.

Recorded run: RUN-tlc-outbox-safety (tlc 2026.10.20.183001).

Text that follows the first run is left out here.

**Question** (ends the segment):

Design C again. The worker sent the request, the provider performed the effect, and the worker crashed before it marked the intent done. The provider ignores keys. After restart, judge five statements. (1) A durable record of the intent exists. (2) The provider performed the effect. (3) The record shows the effect happened. (4) The worker sends again once it recovers. (5) The effect happens exactly once. Which option judges all five rightly?

- A. True: 1, 2, 4 and 5. False: 3.
- B. True: 1, 2, 3 and 4. False: 5.
- C. True: 1, 2 and 4. False: 3 and 5.
- D. True: 1 and 2. False: 3, 4 and 5.

## Exit (4 min)

**Question** (exit question):

A handler calls the provider, then commits. The process dies between the two. What can the end state be?

- A. A record with no effect.
- B. An effect with no record.
- C. Neither: the rollback undoes the call.
