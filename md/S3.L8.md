## A question first (3 min)

Lean accepts a function only if it can see that the function stops. That raises a question for any evaluator: what stops it?

**Question** (before the segment):

A fueled runner returns `outOfFuel` after 1,000 steps. What do you know about the program?

- A. It loops forever, past all 1,000 steps.
- B. No verdict was reached within 1,000 steps.
- C. It has a bug that a longer run would show.

## Total by construction (12 min)

A function that could loop forever would let you prove false things. If `bad n = bad n + 1` were accepted, subtracting `bad n` from both sides would prove `0 = 1`. So every Lean definition passes a termination check, and there are two ways through. In **structural recursion** each recursive call is on a smaller piece of the input, and Lean sees that by itself. The kernel can also run such a definition by plain unfolding. In **well-founded recursion** you name a measure that shrinks, and Lean proves it does. The definition then stays opaque to the kernel's own evaluation, so it is not necessarily equal to its value by computation.

Mini-Plinth v0 sits in the easy case. A command body is one statement, and `exec` recurses on the syntax of expressions, so it is structural and needs no fuel. That is why a golden, `theorem g : exec p c s = r := by decide`, can be decided: the kernel computes the left side.

**Cell 1** (INS-goal-replay)

Two definitions of one function.

The replay shows what Lean says to each `decide`.

```lean
def countdown : Nat → Nat
  | 0 => 0
  | n + 1 => countdown n

def countdownWF (n : Nat) : Nat :=
  if n = 0 then 0 else countdownWF (n - 1)
termination_by n

theorem g0 : countdown 3 = 0 := by decide
theorem g : countdownWF 3 = 0 := by decide
```

**Your call before the first run:**

`theorem g : countdownWF 3 = 0 := by decide`, where `countdownWF` uses well-founded recursion. What happens?

- A. It proves `g` by computing the value.
- B. It fails: the equation is false.
- C. It fails to reduce: no verdict.

Some programs would not fit the structural mould, such as a loop you add later. For those the runner takes **fuel**, a counter that drops at every step. At zero it stops with `outOfFuel`, so the runner is total by construction. `outOfFuel` is no verdict. It says the bound ran out, not that the program loops, and it is not an error the program raised. Your own system has the same shape: a request that times out tells you the deadline passed, not whether the work would have finished.

**Cell 2** (INS-goal-replay)

A counted loop outside v0, run with two bounds.

One program, two bounds.

```lean
inductive Run where
  | done (n : Nat)
  | outOfFuel
  deriving DecidableEq

def runFuel : Nat → Nat → Run
  | 0, _ => .outOfFuel
  | fuel + 1, n => if n = 0 then .done 0 else runFuel fuel (n - 1)

theorem fuel3   : runFuel 3 10 = .outOfFuel := by decide
theorem fuel100 : runFuel 100 10 = .done 0 := by decide
```

**Your call before the first run:**

With fuel 3 the runner says `outOfFuel`, and with fuel 100 it finishes. Did the program's meaning change?

- A. No: fuel bounds the runner, not the program.
- B. Yes: with fuel 3 it is a failing program.

**Question** (ends the segment):

Which statement is true?

- A. `outOfFuel` is an error the v0 program raised.
- B. A golden whose right side is `outOfFuel` states a fact about the v0 program.

## Exit (4 min)

**Question** (exit question):

A golden `theorem g : exec p c s = r := by decide` fails because your `exec` uses well-founded recursion and the kernel cannot reduce it. What kind of result is this?

- A. A failed golden: the equation is false.
- B. No verdict: nothing is established either way.
- C. A passing golden: Lean reported no mismatch.
