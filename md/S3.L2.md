## Before you type (4 min)

Your Stage 2 transfer had no assignment: it computed new balances from old ones, and every theorem followed from that. Give a language assignment and a command can write any number into a balance. This lesson is the set of rules that stops that before a command ever runs, and the two questions below are the ones those rules exist for.

**Question** (before the segment):

Draft 0 lets a command assign balances: `set balance(x) := e`. Which single command can mint money?

- A. `set balance(a) := balance(a) + 1`
- B. A transfer from an account to itself (a self-transfer of 1).
- C. None: Transfer conserves, so the language conserves.
- D. A transfer between two very large balances (above 2⁶³).

**Question** (before the segment):

Amounts are plain `Int`. Which guarded command can drive an account negative?

- A. `move amount from from to to` under its guard, with amount -5.
- B. None: the guard checks the balance (`balance(from) >= amount`).
- C. A transfer of 5 from an account to itself.

## The judgment (13 min)

A typing judgment says when a command is well-formed, before any state exists. It is written Γ ⊢ c ok: in a context Γ that lists the parameters and their types, the command c is accepted. This course writes it as a function, `typecheck : Ctx → Cmd → Except TypeErr Unit`, and defines `HasType Γ c` as `typecheck Γ c = .ok ()`. Every rejection then names the rule that fired, and a rule you got wrong shows up as a failing check you can read.[^s2b1-1]

[^s2b1-1]: Harper's *Practical Foundations for Programming Languages*, chapter 4, draws the same rules as inference rules.

| Rule | Requires | Rejection | Protects |
|---|---|---|---|
| R-param | distinct parameter names, each with a declared type | `dupParam` | well-formedness |
| R-var | every variable is a parameter | `unknownParam` | well-formedness |
| R-expr | `balance(e)` and `frozen(e)` take an account; arithmetic and `>=` take numbers; the guard is a bool | `wrongType` | no expression gets stuck |
| R-cover | a `move n from x ...` or `hold n on x` needs a top-level guard conjunct `balance(x) >= n` | `unguardedDebit` | non-negativity of the debited account |

R-cover is the rule that ties a guard to a body. `Covers g x n` holds when `g` is `balance(x) >= n`, or when `g` is `g₁ && g₂` and either side covers. A disjunction never covers. The rule is sound and incomplete: `balance(x) >= n + fee` implies coverage without covering syntactically, and Stage 4's obligations prove what the rule cannot see.

```lean
/-- `covers g x n`: some top-level conjunct of `g` is `balance(x) >= n`. -/
def covers : Expr → Expr → Expr → Bool
  | .ge (.balance y) m, x, n => y == x && m == n
  | .and g₁ g₂,         x, n => covers g₁ x n || covers g₂ x n
  | _,                  _, _ => false

/-- The R-cover clause of `typecheck`: a debit needs a covering guard. -/
def checkBody (g : Expr) : Stmt → Except TypeErr Unit
  | .op (.move n x _) => if covers g x n then .ok () else .error .unguardedDebit
  | .op (.hold n x)   => if covers g x n then .ok () else .error .unguardedDebit
  | _                 => .ok ()
```

## Five operations, ten postings (13 min)

An operation never edits a balance. It posts a pair of entries: a debit from one account and a credit of the same amount to another, so every operation is zero-sum. `mint` is the account that creates money, `sink` absorbs it, and a hold parks money in an escrow account. Write `bal s x` for the balance of account `x` in state `s`.

| Operation | Postings (debit to credit) | Run-time checks |
|---|---|---|
| `deposit n to a` | `mint` to `a` | `a` exists |
| `move n from x to y` | `x` to `y` | `x` and `y` exist |
| `hold n on x` | `x` to escrow `h` | `x` exists; `h` is the next hold number |
| `capture h to y` | escrow `h` to `y` | the hold exists, is open and is covered |
| `release h` | escrow `h` to the hold's owner | the same |

The invariant `Inv` says that keys are unique, the total of all balances is 0, and every account except `mint` is non-negative. A zero-sum pair keeps the total at 0 whatever a guard says, so conservation costs no proof per command. Only a debit can push a balance below zero, so non-negativity is the per-command obligation: R-cover pays it for `move` and `hold`, and a run-time check pays it for `capture` and `release`.

Three more rules keep a command from sidestepping the pairs.

| Rule | Requires | Rejection | Protects |
|---|---|---|---|
| R-set | `set f(x) := e` needs a scalar field `f`; `balance` is a resource and has no assignment rule | `assignsResource` | conservation |
| R-amount | an operation's amount is an `amount` parameter or a positive literal | `nonPositive` | the direction of every posting |
| R-hold | `capture h to y` and `release h` need `h : hold`, and `y : account` or `sink` | `wrongType` | no stuck statement |

R-amount matters because `move -5 from x to y` credits `x` and debits `y`, and no guard mentions `y`.

## Positivity as a type (12 min)

R-amount asks every amount to be positive, and a type can promise that once instead of each operation checking it. A subtype packs a value with a proof: `Amount := {n : Int // 0 < n}` is an integer together with a proof that it is positive. Lean checks the proof when the value is built, and no operation has to look again. Values of Mini-Plinth's `amount` type are `Amount`s.

Raw input is the catch. A call arrives with plain integers, and the boundary that decodes them has to build an `Amount` from each one.

**Cell 3** (INS-goal-replay)

Goal Replay shows the goal at each step: the proof of positivity that a value must carry.

```lean
abbrev Amount := { n : Int // 0 < n }

example : Amount := ⟨30, by decide⟩    -- goal: 0 < 30

example : Amount := ⟨0, by decide⟩     -- goal: 0 < 0

def Amount.add (a b : Amount) : Amount :=
  ⟨a.val + b.val, by
    have ha := a.property
    have hb := b.property
    omega⟩
```
