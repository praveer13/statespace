## Read the claim, then your invariants (13 min)

A proposal arrives as a command and a claim. Treat the claim as text under test: quote it, and say what kind of property it states before you run anything. The kind picks the checker.

| The claim says | Its kind | Who decides it |
|---|---|---|
| "No account goes negative" | A property of every reachable state | An obligation in Z3, then the induction check |
| "A self-transfer leaves the balance unchanged" | A property of one step, a state and its successor | An obligation over both states, in Z3 |
| "No tenant sees another's data" | A property of two runs together | Self-composition through your generator (LAB-7.5) |
| "Every hold is eventually resolved" | Something that eventually happens | Not Z3: a model check with its fairness stated |

The evidence the agent offers is a second thing to read, apart from the claim. "200 tests green" gives at best TESTED [T] · 200 with its generator statistics, and it does not say what was claimed. A tool's name gives nothing. An agent's assertion is never stamped, whatever it cites.

Then read your own invariants, before you read the command. The agent's claim is one property. Your Core holds a set of them, here conservation and a non-negative sender, and a true claim can still be too weak to protect that set. So the pipeline checks the agent's claim and your invariants side by side.

Your typechecker reads the command first, and a typed rejection is a valid outcome of triage. The command in the cell has no guard, so rule R-cover would turn it away before any solver ran. Read the cell as the question your checker asks of any version that gets past typing: what does this claim establish, and what does it leave out?

**Cell 1** (INS-z3)

The proposal is `command Transfer(from, to, amount) do move amount from from to to`, with no guard. The claim is "conserves money".

Query asserts: for any two `Int` balances and any amount, the negation of the agent's claim. `sat` means some input violates it. `unsat`, which `prove` prints as `proved`, means no input does, in this encoding. A second query asks the same of your own invariant, that the sender stays non-negative, and minimizes the amount.

```python
from z3 import *

a, b, amount = Ints('a b amount')        # two balances and the amount, as plain Int

# The agent's claim: the command conserves money.
print('conservation:')
prove((a - amount) + (b + amount) == a + b)

# Your other invariant: the sender never goes negative. The command has no guard.
o = Optimize()
o.add(a >= 0, b >= 0, amount > 0, a - amount < 0)
o.minimize(amount)
print('sender stays non-negative:', o.check())
print('smallest amount that breaks it:', o.model()[amount])
```

## Witness, then decide (13 min)

A checker result is not yet a decision. Eliminative argumentation (Goodenough, Weinstock and Klein, 2015) names three ways to make counterevidence irrelevant, and they are the three decisions open to you:

- Change the system: fix the command, so that the witness no longer happens.
- Change the specification: narrow the claim honestly to a stated fragment. This is the roadmap's restricted obligation.
- Attack the counterevidence: a witness that does not replay is invalid, so suspect the encoding.

Two answers are not refutations at all. `unknown` fails closed, so you enforce at commit and do not guess (S4.L7). And a `sat` inductive step is not yet a bug, because its pre-state may be unreachable (S4.L6).

The agent now proposes a hold-capture command, with the claim that a capture never overdraws. Your invariant is `bal >= 0`, and its inductive step is satisfiable. A search from `Init` runs to a bound N that you print. Make your call before you run the cell, then try the twin: change the guard of `Hold` to `n <= bal` and run it again.

**Cell 2** (INS-z3)

Query asserts: first, a state with `bal ≥ 0`, one step of the model and `bal < 0` afterwards. Then, for each k up to the bound, a run of k steps from `Init` that ends with `bal < 0`. Last, the same three checks for a stronger invariant: its step, `Init`, and that it implies `bal ≥ 0`. `sat` on the step query means a counterexample to induction exists. `sat` on a search query means a real run breaks the invariant.

```python
from z3 import *

N = 6                                            # the search bound, which you print

def step(s, t, n):                               # the agent's commands: one step from s to t
    (bal, held), (bal2, held2) = s, t
    return And(n > 0, Or(
        And(n <= bal - held, held2 == held + n, bal2 == bal),    # Hold(n)
        And(n <= held, held2 == held - n, bal2 == bal - n),      # Capture(n)
        And(n <= held, held2 == held - n, bal2 == bal)))         # Release(n)

bal, held, bal2, held2, n = Ints('bal held bal2 held2 n')

# 1. The inductive step for bal >= 0: from any state that meets it, can one step break it?
q = Solver()
q.add(bal >= 0, step((bal, held), (bal2, held2), n), bal2 < 0)
print('step of bal >= 0:', q.check())
m = q.model()
print('  the pre-state has held above bal:', m[held].as_long() > m[bal].as_long())

# 2. A search from Init: a run of k steps that ends with bal < 0, for k up to N.
found = None
for k in range(N + 1):
    s = [(Int(f'bal{i}'), Int(f'held{i}')) for i in range(k + 1)]
    search = Solver()
    search.add(s[0][0] >= 0, s[0][1] == 0)                       # Init
    for i in range(k):
        search.add(step(s[i], s[i + 1], Int(f'n{i}')))
    search.add(s[k][0] < 0)                                      # the invariant fails at step k
    if search.check() == sat:
        found = k
        break
print('violation reachable within', N, 'steps:', 'no' if found is None else f'yes, at step {found}')

# 3. Strengthen the invariant to 0 <= held <= bal, and check that it closes.
inv = lambda b, h: And(0 <= h, h <= b)
q2 = Solver()
q2.add(inv(bal, held), step((bal, held), (bal2, held2), n), Not(inv(bal2, held2)))
print('step of the strengthened invariant:', q2.check())
i0 = Solver()
i0.add(bal >= 0, held == 0, Not(inv(bal, held)))
print('Init implies the strengthened invariant, as a violation query:', i0.check())
sf = Solver()
sf.add(inv(bal, held), Not(bal >= 0))
print('the strengthened invariant implies bal >= 0, as a violation query:', sf.check())
```

## From the checker to PostgreSQL (13 min)

A proved command is one claim of three. The command's claim is the obligation, proved for a stated fragment. The compiler's claim is that the SQL it emits means what the command means. The runtime's claim is that PostgreSQL behaves as documented under your retries. Each has its own stamp, and they stay apart (Stage 9).

That is why CL-10.1 is a composite. It lists REFUTED [R] or PROVED [P] for the command, TESTED [T] with n and generator statistics for the compiled runs, and TESTED [T] with its seeds for the simulation. It takes no single stamp, least of all the stamp of its strongest part.

The corrected self-transfer from the worked example shows the gap. Compile it two ways and run both on PostgreSQL, with account 1 at 100 and a self-transfer of 30. The cell is a recorded run, shown with its run ID. Make your call first.

CREATE TABLE acct (id int PRIMARY KEY, bal bigint NOT NULL CHECK (bal >= 0));

UPDATE acct
   SET bal = CASE WHEN id = 1 THEN bal - 30
                  WHEN id = 1 THEN bal + 30 END

-- reset, then compilation 2: two statements
UPDATE acct SET bal = 100 WHERE id = 1;
UPDATE acct SET bal = bal - 30 WHERE id = 1 AND bal >= 30;
UPDATE acct SET bal = bal + 30 WHERE id = 1;
