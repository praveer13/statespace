## Retry the decision, not the statement (17 min)

SERIALIZABLE makes concurrent transactions behave as if they ran one at a time (§13.2.3, read 2026-10-23). It does that by aborting a transaction that would break the illusion, and your application sees an error. Retrying is a design decision: which errors, how often, and what you tell the caller when you stop.

**Question** (before the segment):

Txn B's hold insert failed at COMMIT with a serialization failure. What should the runtime retry?

- A. The COMMIT, where the failure was raised.
- B. The whole command from BEGIN, deciding again.
- C. The INSERT alone, keeping the earlier reads.
- D. Nothing: the failure means the command is wrong.

Replay S6.L6's holds history at SERIALIZABLE, with txn B retrying after its failure. Make your call first.

**Cell 1** (INS-history)

The holds history at SERIALIZABLE, with txn B retried from BEGIN (catalog row H23).

Replay shows: txn A commits, txn B's first attempt fails at COMMIT, and its retry begins a new transaction.

```text
-- holds, SERIALIZABLE: both sessions read 100 available and insert a hold of 80
-- txn B's COMMIT fails; b then runs the whole command again from BEGIN
setup {
  CREATE TABLE acct (id int PRIMARY KEY, bal bigint NOT NULL);
  CREATE TABLE holds (acct int, amt bigint);
  INSERT INTO acct VALUES (1, 100);
}

session a
step a_begin  { BEGIN ISOLATION LEVEL SERIALIZABLE; }
step a_avail  { SELECT bal - coalesce((SELECT sum(amt) FROM holds WHERE acct = 1), 0) FROM acct WHERE id = 1; }
step a_hold   { INSERT INTO holds VALUES (1, 80); }   -- only if a_avail returned 80 or more
step a_commit { COMMIT; }

session b
step b_begin   { BEGIN ISOLATION LEVEL SERIALIZABLE; }
step b_avail   { SELECT bal - coalesce((SELECT sum(amt) FROM holds WHERE acct = 1), 0) FROM acct WHERE id = 1; }
step b_hold    { INSERT INTO holds VALUES (1, 80); }
step b_commit  { COMMIT; }                      -- fails here
step b_begin2  { BEGIN ISOLATION LEVEL SERIALIZABLE; }   -- the retry: the whole command, from BEGIN
step b_avail2  { SELECT bal - coalesce((SELECT sum(amt) FROM holds WHERE acct = 1), 0) FROM acct WHERE id = 1; }
step b_hold2   { INSERT INTO holds VALUES (1, 80); }
step b_commit2 { COMMIT; }

permutation a_begin a_avail b_begin b_avail a_hold b_hold a_commit b_commit b_begin2 b_avail2 b_hold2 b_commit2
```

**Your call before the first run:**

Txn B retries the whole command from BEGIN. The retry now returns:

- A. Committed: a second hold of 80.
- B. A serialization failure again.
- C. A deadlock.
- D. Refused by its own guard; nothing is written.

Recorded run: RUN-pg-catalog (postgres 18.6).

Text that follows the first run is left out here.

Decide by error code, and write the decision down as data. The codes are PostgreSQL's SQLSTATEs (https://www.postgresql.org/docs/18/errcodes-appendix.html).

| Error | What it means | What the runtime does |
|---|---|---|
| 40001 | serialization failure | Retry the whole command from BEGIN. |
| 40P01 | deadlock detected | Retry the whole command from BEGIN. |
| 23505, 23P01 | unique or exclusion violation | Retry only inside a command that re-reads the key before it writes, a bounded number of times. Never re-send the same blind insert. |
| 22003 | value out of range | Never retry: the same input fails again. |
| `Insufficient`, `NoSuchAccount` | typed refusals | Never retry: they are outcomes. |

The rule for unique and exclusion violations is this course's choice, because the code alone does not say whether the condition persists. The manual warns they "might represent persistent error conditions rather than transient failures" (§13.5).

Under SERIALIZABLE a retry that re-checked the key ended without an error, and a blind retry failed with the same code again (rows H12a and H12b (run RUN-pg-catalog)).

Bound the attempts by k, with a jittered pause. When k is spent, return `GaveUp`, an outcome your reference semantics lacks, which S6.L8's relation has to place. Let nothing leave your system before COMMIT: data read is not valid "until the transaction which read it has successfully committed" (§13.2.3).

Does a retry loop end? The manual does not promise it: "Transaction retry does not guarantee that the retried transaction will complete; multiple retries may be needed" (§13.5). So "retries terminate" is a claim you can state and cannot establish. Stamp it ASSUMED [A], with its reason: contention is assumed finite and below the budget. Attempt logs support it on the runs they cover.

**Question** (ends the segment):

A command's attempt log: attempt 1 ended in a deadlock error, attempt 2 in an out-of-range error. What does the policy do next?

- A. Retry: both might clear on a new attempt.
- B. Stop: the out-of-range error is final, and the runtime returns it.
- C. Retry once more, then `GaveUp`.
- D. Retry only the failed statement.

## Exit (4 min)

**Question** (exit question):

An attempt log over n commands shows at most m attempts per command, always below the budget, and no `GaveUp`. The claim: retries terminate. Which stamp fits?

- A. `PROVED [P] · retries terminate for every command`
- B. `TESTED [T] · n commands`
- C. `MODEL-CHECKED [M] · retry loop, bound m`
- D. `ASSUMED [A] · contention assumed finite`
