# S9.L1 · A stack machine, proved

> Draft: first-learner pass pending.

**Format.** Short lesson with reading, about 21 minutes.

**Objective.** Prove that compiling an arithmetic expression to a stack machine preserves its value, by induction on the expression with the stack left arbitrary, and name the hypothesis the plus case needs.

**Ideas taught.**

- A compiler-correctness proof by structural induction
- Generalize the hypothesis over the state before induction

## Before the proof (3 min)

The validator you ran in LAB-9.1 checked one compiled command. A proof checks every program a compiler can produce. Start with the smallest compiler there is: arithmetic over account balances, compiled to a stack machine. Isabelle's HOL-IMP library proves this theorem in a few lines, and the port below reads balances with `bal a`.

**Question** (before the segment):

- A. The theorem never uses the stack.
- B. The code for the second operand runs on a stack that already holds the first operand's value.
- C. It only makes the automation faster.
- D. The induction is on the stack, not on the expression.

## The proof, then the slip (14 min)

The machine keeps a stack of integers. `loadi v` pushes a constant, `load a` pushes the balance of account `a`, and `add` pops two values and pushes their sum. The compiler emits the code for the first operand, then the code for the second, then `add`. The theorem: running `comp e` on any stack pushes `aval e s`, the expression's value in store `s`, and leaves the rest of the stack alone.

Two lemmas carry it. `exec_append` says that running two programs back to back is running one and then the other. `exec_comp` is the theorem. `add` on a stack with fewer than two values returns it unchanged, a junk case that compiled code never reaches.

**Cell 1** (INS-goal-replay)

Replay shows: `exec_comp` one tactic at a time, with the goal after each, then `exec_comp_narrow`, the same induction with `generalizing stk` removed. Compare the stack each hypothesis talks about with the stack the goal needs.

```lean
abbrev Acct := Nat
abbrev Store := Acct → Int

inductive AExp where
  | n (v : Int)
  | bal (a : Acct)
  | plus (e₁ e₂ : AExp)

def aval : AExp → Store → Int
  | .n v, _ => v
  | .bal a, s => s a
  | .plus e₁ e₂, s => aval e₁ s + aval e₂ s

inductive Instr where
  | loadi (v : Int)
  | load (a : Acct)
  | add

def exec1 (s : Store) : Instr → List Int → List Int
  | .loadi v, stk => v :: stk
  | .load a, stk => s a :: stk
  | .add, j :: i :: stk => (i + j) :: stk
  | .add, stk => stk

def exec (s : Store) : List Instr → List Int → List Int
  | [], stk => stk
  | i :: is, stk => exec s is (exec1 s i stk)

def comp : AExp → List Instr
  | .n v => [.loadi v]
  | .bal a => [.load a]
  | .plus e₁ e₂ => comp e₁ ++ comp e₂ ++ [.add]

theorem exec_append (s : Store) (p q : List Instr) (stk : List Int) :
    exec s (p ++ q) stk = exec s q (exec s p stk) := by
  induction p generalizing stk with
  | nil => rfl
  | cons i is ih => simp [exec, ih]

theorem exec_comp (s : Store) (e : AExp) (stk : List Int) :
    exec s (comp e) stk = aval e s :: stk := by
  induction e generalizing stk with
  | n v => rfl
  | bal a => rfl
  | plus e₁ e₂ ih₁ ih₂ =>
    simp only [comp]
    rw [exec_append, exec_append, ih₁, ih₂]
    rfl

-- the same induction with `generalizing stk` left out
theorem exec_comp_narrow (s : Store) (e : AExp) (stk : List Int) :
    exec s (comp e) stk = aval e s :: stk := by
  induction e with
  | n v => rfl
  | bal a => rfl
  | plus e₁ e₂ ih₁ ih₂ =>
    simp only [comp]
    rw [exec_append, exec_append, ih₁, ih₂]
    rfl
```
