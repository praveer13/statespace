## From rules to rows {minutes=2 kcs=KC-7.rls-semantics,KC-7.side-channels}

Your policy has been facts and rules. Now the database has to enforce it, one row at a time.

:::item role=prequestion family=GEN-find-the-witness template=t1 kcs=KC-7.rls-semantics
@choice key=B
A row fails the `USING` clause of every policy that applies to a user's `SELECT`. What does the user get?

- A. An error naming the policy.
  - why: `USING` hides rows; it does not refuse the query.
  - mis: dp:A10
- B. Nothing: the row is silently left out.
  - why: The manual says such rows are "silently suppressed; no error is reported".
- C. It depends on `WITH CHECK`.
  - why: `WITH CHECK` governs new rows from `INSERT` and `UPDATE`.
  - mis: dp:A10
:::

:::item role=prequestion family=GEN-find-the-witness template=t4 kcs=KC-7.side-channels
@choice key=C
Every row a user can see passes the read policy. Can the user still learn that a row they cannot see exists?

- A. No: they never see it.
  - why: A hidden row can still change an outcome.
  - mis: dp:A4
- B. Only if a policy is missing.
  - why: A complete policy still leaves those checks in place.
  - mis: dp:A4
- C. Yes: some checks run against every row, whoever may see it.
  - why: Uniqueness and foreign-key checks bypass row security.
:::

## Compile the rule {minutes=13 kcs=KC-7.rls-semantics}

A worked example first. The lab template gives you the schema `documents(id, slug UNIQUE, team_id, title, body, internal_notes, shared_team_ids int[])`, with `memberships` and `shares`, and `user_teams(u)`, a function that returns a user's team closure from a recursive query, independent of the Datalog engine. For a user on no team it returns an empty array, never NULL. Your three rules become three policies.

Read them with three facts in mind. Permissive policies combine with OR, as your three rules did. When row security is on and no policy applies, a default-deny policy is used, so no row is visible. And a policy whose `USING` expression is NULL hides the row, as `WHERE` skipped NULL rows in S6, so an unset `app.user` fails closed.

:::instrument ins=INS-pglite cell=1 recorded=RUN-pg-rls-semantics
```sql editable
SET search_path = app;

-- the three read rules, as policies
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
CREATE POLICY read_team ON documents FOR SELECT
  USING (team_id = ANY (user_teams(current_setting('app.user', true))));
CREATE POLICY read_shared ON documents FOR SELECT
  USING (EXISTS (SELECT 1 FROM shares s
                 WHERE s.doc_id = documents.id
                   AND s.user_name = current_setting('app.user', true)
                   AND NOT s.revoked));
CREATE POLICY read_team_shared ON documents FOR SELECT
  USING (shared_team_ids && user_teams(current_setting('app.user', true)));

-- frank, a viewer on Growth, changes a row he cannot see
SET ROLE frank;
SELECT set_config('app.user', 'frank', false);
UPDATE documents SET title = 'x' WHERE id = 'q3-plan';
```

@direction
The cell loads the template world, creates your policies, and then runs frank's statement.

@call key=B run=RUN-pg-rls-semantics surprise=yes
frank (Growth, viewer) holds the UPDATE privilege and runs `UPDATE documents SET title = 'x' WHERE id = 'q3-plan'`, a row invisible to him. What comes back?

- A. An error naming row security
  - why: `USING` filters before the update; it does not refuse the statement.
  - mis: dp:A10
- B. `UPDATE 0`, with no error
  - why: Such rows "will not be available for modification", and the manual's own example prints `UPDATE 0`.
- C. The update succeeds, because UPDATE checks only `WITH CHECK`
  - why: `WITH CHECK` tests the new row, and `USING` tests the existing ones.
  - mis: dp:A10

@after
The row was filtered out before the update saw it, so nothing changed and nothing failed {{run:RUN-pg-rls-semantics}}. Now edit the cell: as dana, an editor, move q3-plan to Growth, where she is not an editor. That trips `WITH CHECK` and raises an error. `USING` filters rows that exist; `WITH CHECK` refuses rows that would be written.
:::

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-7.rls-semantics
@choice key=A
A variant of `read_team_shared` says `shared_team_ids <@ user_teams(...)` where yours says `&&`. On W0, for which (user, document) pair do the policies and the matrix disagree?

- A. (frank, contract)
  - why: contract has no team shares, so its array is empty, and the empty array is contained in every array. frank now sees it.

  - mis: dp:A5

## The differential, and the owner {minutes=14 kcs=KC-7.rls-semantics}

How do you know the policies say what the rules say? Run a differential. For each user, switch to that user's role, name the user in the setting the policies read, list the visible ids, and compare them with that user's row of the matrix:

```sql
SET ROLE dana;
SELECT set_config('app.user', 'dana', false);
SELECT id FROM documents;
```

`SET app.user = 'dana'` does not parse, because `user` is a reserved word; `set_config` names the same setting {{run:RUN-pglite-rls}}. Zero disagreements over n generated worlds earns two stamps: [E] · RLS on `documents`, and [T] · n worlds × users, with the engine named. PostgreSQL on the Bench stays authoritative, and the tab reruns the differential on PGlite. A differential is a test. For the conjunctive fragment there is a proof alternative, query containment.[^1]

[^1]: Drawer D-17 holds query containment.

Many applications are built another way: one connection as the table's owner, with `app.user` set for each request. In the tab the connection is a superuser, which bypasses row security even on a forced table {{run:RUN-pglite-rls}}, so every RLS statement follows a `SET ROLE`, and the owner probe is `SET ROLE app_owner`. On the Bench you connect as the real owner.

:::instrument ins=INS-pglite cell=2 recorded=RUN-pg-rls-owner
```sql editable
SET search_path = app;

-- the application connects as the table's owner and names the user per request
SET ROLE app_owner;
SELECT set_config('app.user', 'frank', false);
SELECT id FROM documents ORDER BY id;
```

@direction
The cell loads the template world with your policies unchanged, and then runs the application's query.

@call key=C run=RUN-pg-rls-owner surprise=yes
RLS is enabled and your policies are unchanged. The application connects as the owner of `documents` and sets `app.user` to frank. What does frank's query return?

- A. frank's row of the matrix
  - why: The owner is not bound unless the table is forced.
  - mis: dp:A11
- B. No rows, by default deny
  - why: Default deny applies to the roles row security binds, and the owner is not one yet.
  - mis: dp:A11
- C. Every row
  - why: The manual: "Table owners normally bypass row security as well, though a table owner can choose to be subject to row security with ALTER TABLE ... FORCE ROW LEVEL SECURITY".

@after
Every document came back {{run:RUN-pg-rls-owner}}. Run it again after `ALTER TABLE documents FORCE ROW LEVEL SECURITY;` as the owner, and frank's row returns. FORCE is configuration, so you read it back from `pg_class` with the time, and stamp it [C]. Three more facts about who row security binds. A policy limited `TO app_users` leaves the forced owner with nothing, since no policy applies to it. Superusers and roles with `BYPASSRLS` always bypass. And `app.user` is trusted only because no end user runs SQL, which the claim carries as an assumption [A].
:::

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-7.rls-semantics
@choice key=A
Which connection shows frank a document his policies deny him?

- A. The table's owner, with RLS enabled and not forced.
  - why: Owners bypass row security unless the table is forced.
- B. A member of `app_users`, with RLS enabled.
  - why: The policies bind members of `app_users`, forced or not.
  - mis: dp:A11
- C. The table's owner, with `FORCE ROW LEVEL SECURITY` on.
  - why: Forcing binds the owner to the same policies as everyone else.
  - mis: dp:A11
:::

## A channel the policy cannot see {minutes=12 kcs=KC-7.side-channels}

Every read so far was filtered. Now look at a write. Slugs are globally unique in this schema, so a slug names a row for everyone, including rows a user cannot see.

:::instrument ins=INS-pglite cell=3 recorded=RUN-pg-rls-covert
```sql editable
SET search_path = app;

-- world 1: Birch already has a private document with the slug 'layoffs-memo'
SET ROLE frank;
SELECT set_config('app.user', 'frank', false);
INSERT INTO documents (id, slug, team_id) VALUES ('f1', 'layoffs-memo', 2);

-- world 2, after your call: Birch has no such row. Remove the -- marks and run again.
-- RESET ROLE;
-- DELETE FROM documents WHERE id = 'layoffs-memo';
-- SET ROLE frank;
-- SELECT set_config('app.user', 'frank', false);
-- INSERT INTO documents (id, slug, team_id) VALUES ('f1', 'layoffs-memo', 2);
```

@direction
The cell loads the template world with your policies, and then runs frank's insert.

@call key=B run=RUN-pg-rls-covert surprise=yes
frank inserts a document with the slug 'layoffs-memo' into Growth. Birch already has a private document with that slug, invisible to frank. What happens?

- A. The insert succeeds, because RLS hides Birch's row from the constraint
  - why: Constraint checks see every row.
  - mis: dp:A4
- B. A unique-violation error
  - why: The manual: "Referential integrity checks, such as unique or primary key constraints and foreign key references, always bypass row security to ensure that data integrity is maintained".
- C. An error naming row security
  - why: The refusal comes from the constraint, not from a policy.
  - mis: dp:A10

@after
The insert fails on the unique constraint {{run:RUN-pg-rls-covert}}, and the error carries no key: under row security the DETAIL line that would name the slug is withheld {{run:RUN-pglite-rls}}. In the paired world, where Birch has no such row, the insert succeeds. Two worlds differ only in Birch's private row, and frank tells them apart.
:::

Every read was filtered, and frank still learned a bit. The channel is the error class: a unique violation against a successful insert. It is one bit, not the slug's owner or value, and the manual tells schema designers to avoid exactly this "covert channel" through integrity checks (section 5.9). There are three cures: a constraint per tenant, `UNIQUE (tenant_id, slug)`; opaque identifiers; or a recorded release, which S7.L7 teaches. S7.L5 names what you just found: enforcing the read rule is not the same as noninterference.

One more channel, seen only on the Bench. A policy that reads another table can race with a change to that table. In the recorded run, a locking read returns the new text at READ COMMITTED and fails with a serialization error at the two stricter levels, so the race is prevented by failure, not by returning nothing {{run:RUN-pg-catalog}}.

:::item role=segment family=GEN-find-the-witness template=t4 kcs=KC-7.side-channels
@choice key=A
frank inserts a document with the slug 'budget' into Growth. Which pair of worlds, differing only in Birch's private rows, lets him tell them apart by the outcome?

- A. Birch has a private document with the slug 'budget' in one world and none in the other.
  - why: One insert fails on the unique constraint and the other succeeds.
- B. Birch's private document layoffs-memo has a different body in each world.
  - why: No constraint the insert touches reads a body, so the outcomes match.
  - mis: dp:A4
- C. Birch has a private document with the slug 'budget-2' in one world and none in the other.
  - why: A different slug collides with nothing, so the outcomes match.
  - mis: dp:A4
:::

:::item role=exit family=GEN-find-the-witness template=t1 kcs=KC-7.rls-semantics
@choice key=C
A table has row security enabled and forced, with one policy limited `TO app_users`. Its owner, who is not a member of `app_users`, connects and lists the rows. What does the owner see?

- A. Every row
  - why: Forcing binds the owner, so the bypass is gone.
  - mis: dp:A11
- B. The rows the policy allows
  - why: The policy applies to `app_users`, and the owner is not one.
  - mis: dp:A11
- C. No rows
  - why: Forced, the owner is bound, and no policy applies to it, so default deny leaves nothing.
:::

:::item role=exit family=GEN-find-the-witness template=t4 kcs=KC-7.side-channels
@choice key=B
Which of frank's commands reveals whether Birch has a private document with the slug 'layoffs-memo'?

- A. `SELECT count(*) FROM documents WHERE slug = 'layoffs-memo'`

  - mis: dp:A4
- B. `INSERT INTO documents (id, slug, team_id) VALUES ('f1', 'layoffs-memo', 2)`
  - why: It fails on the unique constraint when Birch has the row, and succeeds when it does not.
- C. `UPDATE documents SET title = 'x' WHERE slug = 'layoffs-memo'`
  - why: A hidden row is not available for modification, so it affects no row either way.
  - mis: dp:A4
