## Before you start {minutes=2 kcs=KC-8.deterministic-simulation,KC-8.trace-validation}

Your simulator can replay any failure from a seed, and your spec says which steps are allowed. This lesson joins them. The simulator writes a log, TLC checks that the log is a behavior of your spec, and a mutant that passes every test in the course's suite fails on its first wrong line.

:::item role=prequestion family=GEN-find-the-witness template=t2 kcs=KC-8.deterministic-simulation
@choice key=A
Two runs of your simulator with the same seed produce different traces. Where do you look first?

- A. At anything not derived from the seed: a clock, an unseeded random source, a host-chosen order.
  - why: Determinism means every choice comes from the seed and the inputs.
- B. At the seed: it is too small, so two runs of the same seed can drift apart.
  - why: Any seed replays exactly if every random choice derives from it.
  - mis: dp:E8
- C. Nowhere: faults are random, so two runs of one seed are bound to differ.
  - why: Seeded randomness is reproducible. That is what a seed is for.
  - mis: dp:E8
:::

:::item role=prequestion family=GEN-trace-allowed template=t3 kcs=KC-8.trace-validation
@choice key=C
Trace validation accepts the traces of n seeds. What does that establish?

- A. Your implementation is right on every input.
  - why: It covers these n traces, at the logged detail, against the spec you wrote.
  - mis: dp:E9
- B. Your implementation agrees with a reference implementation.
  - why: That is differential testing. Here the oracle is a spec that allows many behaviors.
  - mis: dp:E9
- C. Each of those n traces is a behavior of your spec, at the logged detail.
  - why: It is membership, trace by trace, and says nothing about traces never run.
- D. Your spec is right about your system.
  - why: The spec and the code can share one misreading.
  - mis: dp:X4
:::

## One seed, one behavior {minutes=13 kcs=KC-8.deterministic-simulation}

Your machine is sans-I/O: `step(&mut self, input) -> Vec<Output>`. It has no clock, no randomness and no network, and the zero-import ABI gives it no way to reach them. The harness owns time, faults, the simulated world and the log. So a run is a function of the machine and the seed: replay it and you get the same trace, byte for byte.

:::instrument ins=INS-sim cell=1 recorded=RUN-sim-determinism
Run the reference machine on recorded seed 1 twice. The cell prints both trace hashes. Then run a harness variant that draws its faults from an unseeded host source.

```rust
// machine.rs: sans-I/O. Everything the machine knows arrives as an input.
pub enum Input  { Commit(Cmd), Tick, Reply(Reply), Restarted }
pub enum Output { Send { cmd: Cmd, key: Key, att: u32 }, Store(Cmd), Ack(Cmd), Arm(Timer) }

impl Machine {
    pub fn step(&mut self, input: Input) -> Vec<Output> { /* your code */ }
}

// harness/faults.rs: the harness owns every choice a fault makes.
fn next_fault(rng: &mut Seeded) -> Fault { rng.pick(&FAULTS) }
// the planted variant: not derived from the seed
// fn next_fault(_: &mut Seeded) -> Fault { host_random_pick(&FAULTS) }
```

@direction
Run asserts: the same seed gives the same trace. Equal hashes mean byte-identical traces.

@call key=C surprise=no run=RUN-sim-determinism
With the planted variant, which component can make two runs of seed 1 differ?

- A. The machine, because it ran twice.
  - why: With no imports, the same inputs give the same outputs, step after step.
  - mis: dp:E8
- B. TLC, because it checked both runs.
  - why: TLC reads traces. It does not produce them.
  - mis: dp:E9
- C. The harness's fault plan.
  - why: It chose faults from a source the seed does not control.

@after
The reference traces are byte-identical, and the variant's traces differ at a reported line {{run:RUN-sim-determinism}}. A failing seed is now a bug report: replay it exactly, then shrink the fault schedule until every remaining fault matters. WebAssembly has nondeterminism of its own (NaN bit patterns, resource exhaustion); this lab's integer-only machine stays clear of it.
:::

Two runs of seed 7 write the same first three lines. Line 4 is `Timeout c1` in one run and `Receive c1` in the other. The harness fires a timer when the host clock passes a threshold. What is the first diverging line, and what is its source?

  - mis: dp:E8
- B. Line 4, a timer input driven by the wall clock.
  - why: The host clock is not derived from the seed, so two runs fire the timer at different points.

## The log as a constraint {minutes=14 kcs=KC-8.trace-validation}

Model checking asks whether some behavior of a spec violates a property. Trace validation turns that around: it asks whether some behavior of the spec produces your log. The method is Cirstea, Kuppe, Loillier and Merz's: "The problem is reduced to a constrained model checking problem, realized using the TLC model checker" ([arXiv 2404.16075](https://arxiv.org/abs/2404.16075), v2, 2024-09-17). A trace is accepted when some behavior of the spec consumes every line.

The course supplies the trace module's skeleton: a line counter `l`, `IsEvent`, a stuttering disjunct for implementation-only events, and the acceptance check. Logs record updates to spec variables only, so a step the log omits, such as the provider's Accept, is searched for by TLC. Here is a log from the reference machine:

```text
{"event":"Commit","cmd":"c1"}
{"event":"Dispatch","cmd":"c1","key":["c1",0],"att":1}
{"event":"TimerArmed","cmd":"c1"}
{"event":"Receive","cmd":"c1"}
{"event":"Persist","cmd":"c1"}
{"event":"Ack","cmd":"c1"}
{"event":"End"}
```

Worked example: the `IsDispatch` disjunct below applies the spec's `Dispatch(c)` and requires the logged key and attempt to match the request it adds. Write `IsAck` yourself before you read on, then compare it with the module.

:::instrument ins=INS-bench-tlc cell=2 recorded=RUN-tlc-trace-validation
```tla
\* run: statespace trace validate spec/Outbox.tla traces/seed-1.ndjson
---- MODULE OutboxTrace ----
EXTENDS Outbox, TraceValidation

IsCommit   == IsEvent("Commit") /\ Line.cmd \in Cmds /\ Commit(Line.cmd)

IsDispatch == /\ IsEvent("Dispatch")
              /\ Line.cmd \in Cmds
              /\ Dispatch(Line.cmd)
              /\ \E r \in reqs' \ reqs :
                    /\ Logged("key") => r.key = Line.key
                    /\ Logged("att") => r.att = Line.att

IsReceive  == IsEvent("Receive") /\ Line.cmd \in Cmds /\ Receive(Line.cmd)
IsPersist  == IsEvent("Persist") /\ Line.cmd \in Cmds /\ Persist(Line.cmd)
IsAck      == IsEvent("Ack")     /\ Line.cmd \in Cmds /\ Ack(Line.cmd)
IsCrash    == IsEvent("Crash")   /\ Crash
IsRecover  == IsEvent("Recover") /\ Recover

\* An implementation-only line is a stuttering step: no spec variable changes.
IsTimer    == IsEvent("TimerArmed") /\ UNCHANGED vars
IsEnd      == IsEvent("End") /\ IsLast /\ UNCHANGED vars

\* The provider's Accept is not logged, so TLC searches for it.
ProviderStep == Unlogged /\ \E r \in reqs : Accept(r)

TraceInit == Init /\ l = 1
TraceNext == \/ IsCommit \/ IsDispatch \/ IsReceive \/ IsPersist \/ IsAck
             \/ IsCrash \/ IsRecover \/ IsTimer \/ IsEnd \/ ProviderStep
TraceSpec == TraceInit /\ [][TraceNext]_<<vars, l>>
====
```

@direction
Check asserts: the log is a behavior of the spec. Accepted means some behavior consumes every line. Rejected names the first line that no behavior consumes.

@call key=A surprise=yes run=RUN-tlc-trace-validation
A log line records a timer being armed between Dispatch and Accept. Is the trace accepted?

- A. Accepted: the line is a stuttering step.
  - why: Specs allow stuttering so that steps the spec cannot see are permitted.
- B. Rejected: every line must be a spec action.
  - why: The stuttering disjunct matches the line with every spec variable unchanged.
  - mis: dp:E9
- C. Accepted only if the deadlock check is on.
  - why: The deadlock check decides whether a stuck state is reported. Acceptance means every line was consumed.
  - mis: dp:T9

@after
Two cautions from the paper. Too little logged information causes state explosion or wrongly accepted traces (§4.5). And a rejection yields no counterexample, only a maximal matching behavior (§4.2), so the tool reports the highest line any behavior reached. TLC's search depth equals that line only when every step consumes one, and the provider's unlogged steps consume none {{run:RUN-tlc-tracemodule}}. TLC's trace-loading option is not needed: it replays traces that TLC itself wrote, not an implementation's log, and the pinned jar's `Json` module reads the log through `ndJsonDeserialize` {{run:RUN-tlc-tracemodule}}.
:::

:::item role=segment family=GEN-trace-allowed template=t3 kcs=KC-8.trace-validation
@choice key=C
A log reads: 1 Commit c1; 2 Dispatch c1; 3 TimerArmed; 4 Persist c1; 5 End. Which description is right?

- A. Line 3 is the first line no behavior matches: a timer is not a spec action.
  - why: The stuttering disjunct matches line 3 with every spec variable unchanged.
  - mis: dp:T7
- B. Every line is a spec action or a stuttering step, so the log is accepted.
  - why: A line that fits on its own can still fail in order. Persist has no reply to store.
  - mis: dp:E9
- C. Line 3 is a stuttering step, and line 4 is the first line no behavior matches.
  - why: Persist needs a received reply, and the log shows no Receive. TLC can add the provider's Accept but not the worker's Receive.
:::

## A mutant and the suite {minutes=13 kcs=KC-8.trace-validation,KC-8.deterministic-simulation}

A mutant of the reference simulator marks the intent done before it stores the provider's result. The course's end-state suite checks that every committed intent is acknowledged and that an idempotent provider is never double-charged. The mutant passes it on every recorded seed. Then trace validation reads the same seeds' traces.

:::instrument ins=INS-bench-tlc cell=3 recorded=RUN-tlc-trace-validation
```text
statespace trace validate spec/Outbox.tla traces/mutant-seed-1.ndjson

{"event":"Commit","cmd":"c1"}
{"event":"Dispatch","cmd":"c1","key":["c1",0],"att":1}
{"event":"TimerArmed","cmd":"c1"}
{"event":"Receive","cmd":"c1"}
{"event":"Ack","cmd":"c1"}
{"event":"Persist","cmd":"c1"}
{"event":"End"}
```

@direction
Check asserts: the log is a behavior of the spec. Rejected names the first line that no behavior consumes.

@call key=B surprise=yes run=RUN-tlc-trace-validation
The mutant passes the suite on every recorded seed. Will trace validation accept its fault-free traces?

- A. Accepted: no crash, no harm.
  - why: The spec orders Persist before Ack, and the order is wrong on every trace, crash or no crash.
  - mis: dp:X1
- B. Rejected at the first Ack line.
  - why: Ack is not enabled before the result is stored, so no behavior matches that line.
- C. Rejected only on seeds that crash between Ack and Persist.
  - why: That is how a test would find it. Trace validation checks the steps, not their consequences.
  - mis: dp:E9

@after
The suite checks outcomes, and outcomes agree whenever no crash lands between the two steps. Trace validation checks the order of steps on every trace, so it sees the drift before a crash makes it costly. This is specimen SP-8.4 {{run:RUN-tlc-trace-validation}}. It also mints CL-8.3: TESTED [T] · n seeds, composed with the spec's MODEL-CHECKED [M] result. The simulated environment stays ASSUMED [A].
:::

:::item role=segment family=GEN-find-the-witness template=t2 kcs=KC-8.trace-validation
@choice key=A
Which is the first line no behavior of the spec matches, and which drift is it?

- A. Line 6: a new key for the second attempt.
  - why: The spec's key names the intent, so the re-send must carry the key of line 2.
- B. Line 3: a Receive with no Accept logged before it.
  - why: The provider's Accept is not logged, so TLC searches for it. A Receive after a Dispatch is allowed.
  - mis: dp:E9
- C. Line 4: the crash.
  - why: A reply is in flight and unstored, so a crash is enabled. The environment's steps are in the spec.
  - mis: dp:T15
- D. None: the end state is fine, so the log conforms.
  - why: The outcome agrees, but the key does not. A test that checks outcomes would miss it.
  - mis: dp:X1
:::

## Exit {minutes=4 kcs=KC-8.deterministic-simulation,KC-8.trace-validation}

:::item role=exit family=GEN-trace-allowed template=t3 kcs=KC-8.trace-validation
@choice key=A
A log reads: 1 Commit c1; 2 Dispatch c1; 3 Receive c1; 4 TimerArmed; 5 Persist c1; 6 Ack c1; 7 End. Which description is right?

- A. Line 4 is a stuttering step, and the log is accepted.
  - why: Line 3 fits because TLC adds the provider's Accept before it. Every other line is a spec action or a stuttering step, in order.
- B. Line 3 is the first line no behavior matches: no Accept is logged.
  - why: The provider's Accept is unlogged, and TLC searches for it.
  - mis: dp:E9
- C. Line 4 is the first line no behavior matches: a timer is not a spec action.
  - why: A step that changes no spec variable is a stuttering step.
  - mis: dp:T7
:::

:::item role=exit family=GEN-find-the-witness template=t2 kcs=KC-8.deterministic-simulation
@choice key=B
Two runs of seed 9 write the same lines, except that after a crash and a recovery the replies for c1 and c2 appear as c1 then c2 in one run and c2 then c1 in the other. The harness delivers the batch from a hash map. What is the source?

- A. The machine reordered its outputs.
  - why: With no imports, the same inputs give the same outputs.
  - mis: dp:E8
- B. A host-ordered delivery of a reply batch.
  - why: The map's iteration order is chosen by the host, not derived from the seed.
- C. TLC explored the replies in another order.
  - why: TLC reads the traces. It does not produce them.
  - mis: dp:E9
:::
