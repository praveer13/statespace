## Before you start {minutes=2 kcs=KC-8.crash-windows,KC-8.at-least-once}

Between a customer's click and a settled charge, your system takes five steps, and a crash can land between any two of them. In some gaps a crash only delays the charge. In others it double-charges, or loses the charge, or does nothing at all. You will place the crash yourself, then ask TLC.

One prediction first. In the time stage you wrote the claim CL-5.2, and its model sent the provider request in the same step that changed the hold. When those two steps come apart, which part of that claim cracks: the proposition of the model, the correspondence, the requirement fit, or an assumption record? Keep your answer. The lesson returns to it.

:::item role=prequestion family=GEN-find-the-witness template=t2 kcs=KC-8.at-least-once
@choice key=B run=RUN-tlc-double-charge
No crash happens. Your worker's timer fires before the provider's reply arrives, and it sends again. The provider ignores keys. Can the charge happen twice?

- A. No: without a crash there is nothing to retry.
  - why: Timers retry too, and a slow reply looks exactly like a lost one.
  - mis: dp:E6
- B. Yes.
  - why: Both copies can be accepted. At-least-once delivery duplicates by design.
- C. Only if the network duplicates the message.
  - why: Your own re-send creates the duplicate. The network need not.
  - mis: dp:E6
:::

:::item role=prequestion family=GEN-trace-allowed template=t2 kcs=KC-8.crash-windows
@choice key=C
Your worker stored the provider's result, then crashed before it marked the intent done. On restart, what should it do?

- A. Send again: the intent is not acknowledged.
  - why: The stored result proves the effect happened. Sending again turns this window into a double charge.
  - mis: dp:E1
- B. Drop it: the provider already has it.
  - why: The intent would stay inflight forever, and nothing would record that it finished.
  - mis: dp:E3
- C. Acknowledge it from the stored result.
  - why: Recovery reads what is durable before it acts.
:::

## Place the crash {minutes=13 kcs=KC-8.crash-windows,KC-8.at-least-once}

A command's chain has four gaps where a crash matters. Call them windows.

| Window | A crash lands between | One crash here permits |
|---|---|---|
| CW1 | Commit and Dispatch | delay only: the intent waits in the outbox |
| CW2 | Dispatch and Accept | you place the crash |
| CW3 | Accept and Persist | you place the crash |
| CW4 | Persist and Ack | you place the crash |

CW1 is the worked example. Commit writes the command and its pending intent. The worker crashes before it sends anything. Recover restarts it, the intent is still pending, Dispatch sends one request, the provider accepts it, and one charge happens. The answer for CW1 is none. You complete the other three in the Theater, with provider idempotency off, and the table fills in as you go.

:::instrument ins=INS-theater cell=1 recorded=RUN-tlc-double-charge
Enable one window, crash, recover and continue by hand. The monitors count charges per command.

```tla
InWindow(w, c) ==
  CASE w = "CW1" -> status[c] = "pending"
    [] w = "CW2" -> /\ status[c] = "inflight"
                    /\ \E r \in reqs : r.cmd = c
                    /\ ~\E r \in replies : r.cmd = c
    [] w = "CW3" -> /\ \E r \in replies : r.cmd = c
                    /\ c \notin durable
    [] w = "CW4" -> c \in durable /\ status[c] = "inflight"
    [] OTHER     -> FALSE

\* A crash empties the worker's memory. The database and the network are not the worker's to lose.
Crash == /\ up
         /\ CrashBudget
         /\ \E c \in committed, w \in CrashWindows : InWindow(w, c)
         /\ up' = FALSE
         /\ got' = {}
         /\ crashes' = IF MaxCrashes < 0 THEN crashes ELSE crashes + 1
         /\ UNCHANGED <<committed, status, durable, attempts, reqs, replies, charges, seen>>

\* Recovery returns every inflight intent without a stored result to pending.
Recover == /\ ~up
           /\ up' = TRUE
           /\ status' = [c \in Cmds |-> IF status[c] = "inflight" /\ c \notin durable
                                          THEN "pending" ELSE status[c]]
           /\ UNCHANGED <<committed, durable, attempts, got, reqs, replies, charges, seen, crashes>>
```

@direction
Scene asserts: no command is charged more than once. The monitor counts the provider's charges for each command as you play, and marks a second one.

@call key=C surprise=yes run=RUN-tlc-double-charge
Window CW2: the crash lands after your worker sent the request and before the provider accepted it. Can a double charge follow?

- A. No: the provider never saw the first request.
  - why: It has not seen it yet. That copy is still in flight and can arrive after the re-send.
  - mis: dp:E6
- B. Only if the provider crashes too.
  - why: The provider stays up in this scene. Delay alone is enough.
  - mis: dp:T15
- C. Yes: both copies can be accepted.
  - why: Recovery re-sends, and the old copy is still deliverable.

@after
TLC finds the same thing: `NoDoubleCharge` fails in CW2, and the run records the witness and its length in actions {{run:RUN-tlc-double-charge}}. The provider accepted nothing before the crash, yet the retry still double-charges, because the first copy was never lost. Try CW3 and CW4 the same way, and fill in the rest of the table.
:::

:::item role=segment family=GEN-find-the-witness template=t2 kcs=KC-8.crash-windows,KC-8.at-least-once

Provider idempotency off, one command, one crash, allowed only in CW3. Which is the shortest trace to a double charge?

- A. Commit, Dispatch, Accept, Receive, Crash, Recover, Dispatch, Accept.
  - why: It double-charges, but Receive is not needed, so a shorter trace exists.
  - mis: dp:T6
- B. Commit, Dispatch, Accept, Crash, Recover, Dispatch, Accept.
  - why: The worker crashed before it stored the reply, so recovery treats the intent as unanswered and re-sends. The provider has no memory of the key and performs the effect again.
- C. Commit, Dispatch, Accept, Crash, Recover, Accept.
  - why: A second charge needs a second request, and only the worker's re-send makes one.
  - mis: dp:E6
- D. None: the provider performed the effect only once.
  - why: One accepted request is one charge. The re-send after recovery is the second.
  - mis: dp:E4
:::

## The same model under TLC {minutes=13 kcs=KC-8.crash-windows,KC-8.at-least-once}

Now ask TLC the same question. The Bench runs TLC on the same model with one worker and the deadlock check off, because a finished command is not a deadlock. On a phone you see the recorded run with its id.

Run CW3 with provider idempotency off first. TLC reports that `NoDoubleCharge` fails and prints a trace like the one you just built {{run:RUN-tlc-double-charge}}. That trace is specimen SP-8.1: the first copy was accepted, the worker crashed before it stored the reply, and the re-send made a second charge.

Then run the full design: every window, two crashes, and a provider that honors one stable key per intent.

@direction

@call key=B surprise=no run=RUN-tlc-outbox-safety
`NoLostIntent`, `AckedIsDurable` and `NoDoubleCharge`: what does TLC report?

- A. A violation: some window still double-charges.
  - why: One stable key plus the provider's idempotency closes CW2 and CW3, and recovery closes CW4. The provider's idempotency is part of this model.
  - mis: dp:E4
- B. No error, and the exploration completes.
  - why: Every reachable state satisfies all three, at these constants.
- C. It stops early and reports a deadlock.
  - why: This configuration turns the deadlock check off on purpose.
  - mis: dp:T9

@after
TLC reports no error and finishes exploring. The stamp is MODEL-CHECKED [M] · constants · complete {{run:RUN-tlc-outbox-safety}}. Read the constants beside it: one command, two crashes, a provider that honors keys and never prunes them. Change one of those and you have a different claim.
:::

Compare the run with the answer you kept. SP-8.1 cracks an assumption you wrote in the time stage: that the provider request left in the same step as the hold's commit. This is SEAM-4, and it was never true of a system that calls an outside service. `res <= 1` still holds on the old model. What fails is the assumption that the effect left with the commit, so the part that cracks is an assumption record. Three remedies follow: an outbox, built here; inbound keys, next lesson; and the provider's idempotency, stated as an assumption in CL-8.2.

NoLostIntent, checked with crash actions on, is your first claim of this stage. It rests on two assumptions: the command and its intent commit together, and a crash loses memory only.

- A. Dispatch and Ack.
  - why: Recovery returned only intents without a stored result to pending. This one stays inflight.

## A poller and a late commit {minutes=13 kcs=KC-8.crash-windows}

A crash is not the only way an effect fails to leave. Many systems deliver outbox rows with a poller. It reads committed rows above a high-water mark, delivers them, and raises the mark to the highest id it read. Two writers take sequence ids when they INSERT, and they commit in either order.

:::instrument ins=INS-theater cell=3 recorded=RUN-tlc-lost-effect
Drive the writers and the poller by hand and watch the mark.

```tla
Insert(w) == /\ wpc[w] = "idle"
             /\ idOf' = [idOf EXCEPT ![w] = nextId]
             /\ nextId' = nextId + 1
             /\ wpc' = [wpc EXCEPT ![w] = "inserted"]
             /\ UNCHANGED <<committedIds, delivered, mark>>

CommitRow(w) == /\ wpc[w] = "inserted"
                /\ committedIds' = committedIds \cup {idOf[w]}
                /\ wpc' = [wpc EXCEPT ![w] = "committed"]
                /\ UNCHANGED <<nextId, idOf, delivered, mark>>

\* Design "mark": rows above the mark.  Design "status": rows not yet delivered.
Batch == IF Design = "mark" THEN {i \in committedIds : i > mark}
                            ELSE committedIds \ delivered

Poll == /\ Batch /= {}
        /\ delivered' = delivered \cup Batch
        /\ mark' = IF Design = "mark" THEN Max(Batch \cup {mark}) ELSE mark
        /\ UNCHANGED <<nextId, idOf, wpc, committedIds>>

MarkInv == \A i \in committedIds : i <= mark => i \in delivered
```

@direction
Scene asserts: every committed row is delivered, and the mark never passes a committed row that was not delivered.

@call key=A surprise=yes run=RUN-tlc-lost-effect
Writer 1 takes id 1. Writer 2 takes id 2 and commits first. The poller delivers row 2 and sets its mark to 2. Then writer 1 commits. Will row 1 be delivered?

- A. No, never.
  - why: Ids are allocated at INSERT and become visible at COMMIT, so id order is not commit order. Row 1 sits below the mark.
- B. Yes, on the next poll.
  - why: The next poll reads ids above 2, and row 1 is below the mark.
  - mis: dp:E11
- C. Yes, after the worker restarts.
  - why: The mark is stored, and a restart reads it back.
  - mis: dp:E11

@after
The mark invariant fails. With weak fairness on the poller, eventual delivery fails too, on a lasso that stutters after the last poll {{run:RUN-tlc-lost-effect}}. This is specimen SP-8.2. PostgreSQL records the same late commit: poll 1 delivers id 2 and moves the mark to 2, the first transaction then commits, and poll 2 returns no rows, at every isolation level (row H20 {{run:RUN-pg-catalog}}).
:::

Poll by status, not by id. Claim pending rows with `FOR UPDATE SKIP LOCKED`, and delivery stays at-least-once. The [PostgreSQL 18 documentation](https://www.postgresql.org/docs/18/sql-select.html) says that skipping locked rows "provides an inconsistent view of the data": it claims rows, and it never promises completeness.

:::item role=segment family=GEN-find-the-witness template=t2 kcs=KC-8.crash-windows
@choice key=B
A poller claims pending rows by status instead of by id. Two writers insert and commit in either order, and polls run in between. Can a committed row be skipped forever?

- A. Yes: writer 2 commits first, a poll delivers row 2, then row 1 commits below the mark.
  - why: That trace belongs to the mark design. This poller has no mark to fall behind.
  - mis: dp:E11
- B. No: a committed row stays pending until a poll claims it, whatever the commit order.
  - why: Pending is a property of the row, not of its id, so a late commit is claimed by the next poll.
- C. Only when the writers commit in id order.
  - why: Commit order does not matter here. Status decides what a poll claims.
  - mis: dp:E11
:::

## Exit {minutes=3 kcs=KC-8.crash-windows,KC-8.at-least-once}

:::item role=exit family=GEN-find-the-witness template=t2 kcs=KC-8.at-least-once
@choice key=A
Provider idempotency off, timers on, crashes off, one command. Which is the shortest trace to a double charge?

- A. Commit, Dispatch, Timeout, Dispatch, Accept, Accept.
  - why: The timer returns the unanswered intent to pending, and the worker sends again while the first copy is in flight.
- B. None: with no crash, nothing is sent twice.
  - why: A timer fires on a slow reply just as it does on a lost one.
  - mis: dp:E6
- C. Commit, Dispatch, Accept, Accept.
  - why: Each request copy is accepted once. A second accept needs a second request.
  - mis: dp:E6
:::

:::item role=exit family=GEN-trace-allowed template=t1 kcs=KC-8.crash-windows
@choice key=C
Two commands, c1 and c2, one crash, allowed only in CW4. The provider ignores keys. Which trace is a behavior of the model?

- A. Commit c1, Dispatch c1, Accept, Receive c1, Persist c1, Crash, Recover, Dispatch c1.
  - why: Recovery does not return an intent with a stored result to pending, so Dispatch is not enabled.
  - mis: dp:E1
- B. Commit c1, Dispatch c1, Accept, Ack c1.
  - why: Ack needs a stored result, and only Persist writes one.
  - mis: dp:E3
- C. Commit c1, Commit c2, Dispatch c1, Accept, Receive c1, Persist c1, Crash, Recover, Ack c1.
  - why: The crash lands in CW4 for c1. Recovery leaves its stored result alone, so Ack is enabled.
- D. Dispatch c1, Commit c1, Accept, Receive c1, Persist c1, Ack c1.
  - why: Dispatch needs a pending intent, and only Commit writes one.
  - mis: dp:E5
:::
