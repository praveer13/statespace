## The chain as actions {minutes=14 kcs=KC-8.outbox-chain}

TLA+ has been idle since the time stage, so read this model once, slowly. Your chain has five steps: a command commits together with its outbox intent, a worker dispatches the intent, the provider performs the effect, the worker stores the reply, and the worker acknowledges. Each step is an action over variables. A crash is one more action.

:::item role=prequestion family=GEN-trace-allowed template=t1 kcs=KC-8.outbox-chain
@choice key=C
Which variables must survive a crash of the worker?

- A. All of them, including replies the worker has received.
  - why: A crash is not a pause. A reply held in memory is gone.
  - mis: dp:T13
- B. None: the worker can rebuild its state from the provider.
  - why: The provider is outside your trust boundary, and it may have pruned what it knew.
  - mis: dp:E7
- C. The committed commands, the outbox rows and the stored results.
  - why: They live in your database. Only the worker's memory is lost.
:::

Four parts own the variables. Your database keeps the committed commands, the outbox rows and the stored results. The worker's memory holds the replies it has received and not yet stored. The network holds requests and replies in flight. The provider holds its effects and its table of keys.[^1]

[^1]: Drawer D-09 shows the same actions in PlusCal beside TLA+. Spectacle reads TLA+ only.

:::instrument ins=INS-spectacle cell=1 recorded=RUN-spectacle-s5s8
Here is the chain as actions. Step through it with crashes off.

```tla
---- MODULE Outbox ----
EXTENDS OutboxIface
\* OutboxIface declares the variables, by who owns them:
\*   your database, kept across a crash: committed, status, durable, attempts
\*   the worker's memory, emptied by a crash: got
\*   the network: reqs, replies         the provider: charges, seen
\*   the environment: up, crashes
\* and supplies Accept, the provider's step, and the properties.

Init == /\ committed = {}
        /\ status = [c \in Cmds |-> "none"]
        /\ durable = {}
        /\ attempts = [c \in Cmds |-> 0]
        /\ got = {}
        /\ reqs = {}
        /\ replies = {}
        /\ charges = [c \in Cmds |-> 0]
        /\ seen = {}
        /\ up = TRUE
        /\ crashes = 0

\* The client's transaction: the command and its outbox intent commit together.
Commit(c) == /\ c \notin committed
             /\ committed' = committed \cup {c}
             /\ status' = [status EXCEPT ![c] = "pending"]
             /\ UNCHANGED <<durable, attempts, got, reqs, replies, charges, seen, up, crashes>>

\* The worker sends the intent with its key.
Dispatch(c) == /\ up
               /\ status[c] = "pending"
               /\ attempts[c] < MaxAttempts
               /\ LET a == attempts[c] + 1
                  IN /\ attempts' = [attempts EXCEPT ![c] = a]
                     /\ reqs' = reqs \cup {[cmd |-> c, key |-> Key(c, a), att |-> a]}
               /\ status' = [status EXCEPT ![c] = "inflight"]
               /\ UNCHANGED <<committed, durable, got, replies, charges, seen, up, crashes>>

\* A timer returns an unanswered intent to pending.
Timeout(c) == /\ Timeouts
              /\ up
              /\ status[c] = "inflight"
              /\ c \notin got
              /\ c \notin durable
              /\ status' = [status EXCEPT ![c] = "pending"]
              /\ UNCHANGED <<committed, durable, attempts, got, reqs, replies, charges, seen, up, crashes>>

\* The worker buffers a reply, then stores it.
Receive(c) == /\ up
              /\ status[c] = "inflight"
              /\ c \notin got
              /\ c \notin durable
              /\ \E r \in replies : r.cmd = c
              /\ got' = got \cup {c}
              /\ UNCHANGED <<committed, status, durable, attempts, reqs, replies, charges, seen, up, crashes>>

Persist(c) == /\ up
              /\ c \in got
              /\ durable' = durable \cup {c}
              /\ got' = got \ {c}
              /\ UNCHANGED <<committed, status, attempts, reqs, replies, charges, seen, up, crashes>>

\* The worker acknowledges. It needs a stored result.
Ack(c) == /\ up
          /\ c \in durable
          /\ status[c] = "inflight"
          /\ status' = [status EXCEPT ![c] = "acked"]
          /\ UNCHANGED <<committed, durable, attempts, got, reqs, replies, charges, seen, up, crashes>>

\* The windows, Crash and Recover are the next lesson. With MaxCrashes = 0 they never fire.
InWindow(w, c) ==
  CASE w = "CW1" -> status[c] = "pending"
    [] w = "CW2" -> /\ status[c] = "inflight"
                    /\ \E r \in reqs : r.cmd = c
                    /\ ~\E r \in replies : r.cmd = c
    [] w = "CW3" -> /\ \E r \in replies : r.cmd = c
                    /\ c \notin durable
    [] w = "CW4" -> c \in durable /\ status[c] = "inflight"
    [] OTHER     -> FALSE

CrashBudget == MaxCrashes < 0 \/ crashes < MaxCrashes

Crash == /\ up
         /\ CrashBudget
         /\ \E c \in committed, w \in CrashWindows : InWindow(w, c)
         /\ up' = FALSE
         /\ got' = {}
         /\ crashes' = IF MaxCrashes < 0 THEN crashes ELSE crashes + 1
         /\ UNCHANGED <<committed, status, durable, attempts, reqs, replies, charges, seen>>

Recover == /\ ~up
           /\ up' = TRUE
           /\ status' = [c \in Cmds |-> IF status[c] = "inflight" /\ c \notin durable
                                          THEN "pending" ELSE status[c]]
           /\ UNCHANGED <<committed, durable, attempts, got, reqs, replies, charges, seen, crashes>>

Next == \/ \E c \in Cmds : Commit(c)
        \/ \E c \in Cmds : Dispatch(c)
        \/ \E c \in Cmds : Timeout(c)
        \/ \E c \in Cmds : Receive(c)
        \/ \E c \in Cmds : Persist(c)
        \/ \E c \in Cmds : Ack(c)
        \/ Crash
        \/ Recover
        \/ \E r \in reqs : Accept(r)
        \/ \E k \in seen : Forget(k)

Spec == Init /\ [][Next]_vars
====
```

@direction
Model asserts: the chain for one command, with crashes and timers off. A trace is a behavior when every step is an action whose guard holds in the state before it. Spectacle lists the enabled actions in each state.

@call key=A surprise=yes run=RUN-tlc-outbox-safety
Is Commit, Dispatch, Receive a behavior of this model?

- A. No.
  - why: Receive is enabled only when a reply for the command exists, and a reply exists only after the provider's Accept.
- B. Yes: the worker sent the request, so it can receive.
  - why: The provider's step belongs in the trace. Sending a request creates no reply.
  - mis: dp:E7

@after
Each guard names what its action needs. `Dispatch` needs a pending intent, `Receive` needs a reply, `Persist` needs a received reply, and `Ack` needs a stored result. A trace is a behavior when every guard holds in turn. Step the prefix again in Spectacle: after Dispatch, only the provider's Accept is enabled.
:::

:::item role=segment family=GEN-trace-allowed template=t1 kcs=KC-8.outbox-chain
@choice key=D
Crashes and timers off. Which sequence of actions is a behavior of this model from Init?

- A. Commit, Dispatch, Receive, Accept, Persist, Ack.
  - why: Receive needs a reply, and none exists before Accept. The grader names that step as the first non-edge.
  - mis: dp:E7
- B. Commit, Dispatch, Accept, Ack.
  - why: Ack needs a stored result, and only Persist writes one.
  - mis: dp:E3
- C. Dispatch, Commit, Accept, Receive, Persist, Ack.
  - why: Dispatch needs a pending intent, and only Commit writes one.
  - mis: dp:E5
- D. Commit, Dispatch, Accept, Receive, Persist, Ack.
  - why: Each action's guard holds in the state before it, so every step is an edge of the state graph.
:::

## Exit {minutes=4 kcs=KC-8.outbox-chain}

:::item role=exit family=GEN-trace-allowed template=t3 kcs=KC-8.outbox-chain
@choice key=A
A log shows an implementation-only step, a timer being armed, between Dispatch and Accept. Is that a behavior of the spec?

- A. Yes: it is a stuttering step, which a spec allows.
  - why: The box in the next-state relation permits steps that leave every variable unchanged.
- B. No: every step must be one of the spec's actions.
  - why: That reads the next-state relation without its box. Stuttering steps are part of every behavior.
  - mis: dp:T7
- C. It depends on the flags TLC is run with.
  - why: Run options change what TLC checks, not which behaviors a spec allows.
  - mis: dp:T9
:::
