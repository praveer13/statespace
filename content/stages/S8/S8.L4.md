## The key and the commit {minutes=10 kcs=KC-8.idempotency-keys}

A reply is input from outside your trust boundary, even when your worker sent the request it answers. Check it, and make repeating it harmless.

:::item role=prequestion family=GEN-find-the-witness template=t2 kcs=KC-8.untrusted-replies,KC-8.idempotency-keys
@choice key=A
Two copies of a reply arrive for one intent and key: `ok`, cost 80, against a hold of 100; then `ok`, cost 120. What should your handler do?

- A. Capture 80 once; discard the second copy by key, and record its mismatch for reconciliation.
  - why: The key makes the second copy a no-op, validation keeps the bad value out, and the mismatch is evidence worth keeping.
- B. Capture 80, then raise the capture to 120: the latest reply from the provider wins.
  - why: A cost above the hold is invalid however it arrives.
  - mis: dp:E7
- C. Capture both: they are two replies from the provider, so they are two charges.
  - why: One intent, one key, one effect.
  - mis: dp:E2
:::

:::instrument ins=INS-pglite cell=1 recorded=RUN-pglite-inbound-key
PGlite has one connection, so deliveries cannot race here. Deliver the same valid reply twice.

```sql editable
create table holds (intent text primary key, amount int not null, status text not null);
create table captures (intent text primary key, cost int not null);
create table inbound_keys (key text primary key);
insert into holds values ('i1', 100, 'held');

create function handle(k text, i text, c int) returns text language plpgsql as $$
declare n int;
begin
  insert into inbound_keys (key) values (k) on conflict do nothing;
  get diagnostics n = row_count;
  if n = 0 then return 'duplicate: already applied'; end if;
  update holds set status = 'captured'
   where intent = i and status = 'held' and amount >= c;
  get diagnostics n = row_count;
  if n = 0 then raise exception 'reply rejected for %', i; end if;
  insert into captures values (i, c);
  return 'captured';
end $$;

select handle('k1', 'i1', 80);
select handle('k1', 'i1', 80);
select count(*) as captures from captures;
```

@direction
Script asserts: a reply captures at most once. The key row and the capture are one transaction, so a handler that raises takes its key row with it.

@call key=A surprise=no run=RUN-pglite-inbound-key
The same valid reply is delivered twice, one after the other. How many captures?

- A. One.
  - why: The second key insert touches no row, so the handler stops before the capture.
- B. Two.
  - why: A second delivery acts twice only if nothing durable remembers the first.
  - mis: dp:E2

@after
The key row commits with the capture, so a duplicate cannot pass the guard. Two sessions racing to insert one key under SERIALIZABLE fail differently: a unique violation for blind inserts, and a serialization failure where both checked first. The recorded race is {{run:RUN-pg-catalog}} (row H12a), and LAB-6.6's retry policy handles both.
:::

If the connection drops during COMMIT, you do not know which state you are in. Run the handler again with the same key: "captured" means the first attempt did not commit, and "duplicate" means it did. The key needs no retention window.

:::item role=segment family=GEN-find-the-witness template=t4 kcs=KC-8.idempotency-keys
@choice key=C
A connection drops while your handler runs COMMIT for key k1. Which states can it leave, and which query tells them apart?

- A. The key row exists and the capture does not. Look for the capture.
  - why: That needs the key row committed on its own. Here it rolls back with the capture.
  - mis: dp:E5
- B. Neither exists: a dropped COMMIT always rolls back, so no query is needed.
  - why: A dropped connection hides the outcome. The commit may already have happened.
  - mis: dp:E3
- C. The key row and the capture both exist, or neither does. Look for the key row.
  - why: They commit in one transaction, so a commit applies both and a failed one applies neither. The key row is the evidence.
:::

## Replies you did not write {minutes=11 kcs=KC-8.untrusted-replies,KC-8.idempotency-keys}

The rest of the handler is four more checks: the reply's status, its cost against the hold, its key, and whether the hold is still held.

:::instrument ins=INS-spectacle cell=2 recorded=RUN-tlc-outbox-safety
A timer released the hold. Then a valid `ok` reply arrives.

```tla
\* The handler captures on any reply that passes the checks switched on.
Handle(r) == /\ r \in inbox
             /\ captures < 2
             /\ CheckStatus => r.status = "ok"
             /\ CheckCost => r.cost <= Hold
             /\ CheckKey => r.key \notin handled
             /\ CheckLate => hst = "held"
             /\ hst' = "captured"
             /\ handled' = handled \cup {r.key}
             /\ captures' = captures + 1
             /\ last' = r
             /\ UNCHANGED <<inbox, released>>

NoCaptureAfterRelease == ~(released /\ hst = "captured")
\* Here: CheckStatus = TRUE, CheckCost = TRUE, CheckKey = FALSE, CheckLate = FALSE
```

@direction
Model asserts: no capture after release, one capture per intent, a charge within the hold, and status ok.

@call key=C surprise=yes run=RUN-tlc-outbox-safety
Your handler checks status and cost only. What happens?

- A. Nothing: the hold is already released.
  - why: A handler that never reads the hold's state captures it anyway.
  - mis: dp:E7
- B. The provider undoes the charge on its own.
  - why: The provider did what you asked. Undoing it is your reconciliation, not its default.
  - mis: dp:T15
- C. It captures a released hold.
  - why: Lateness is a check of its own, and this handler lacks it.

@after
Reject the late reply, keep the release, and record a reconciliation: the provider may have charged after you gave up, and the record makes that loss visible. Drawer D-19 frames the timer as a durable obligation.
:::

:::instrument ins=INS-spectacle cell=3 recorded=RUN-tlc-fresh-key
Your worker re-sends after a crash in CW3 and mints a new key for each attempt.

```tla
\* The key names the intent when FreshKey is FALSE, and the attempt when it is TRUE.
Key(c, a) == IF FreshKey THEN <<c, a>> ELSE <<c, 0>>
\* Dispatch sends [cmd |-> c, key |-> Key(c, a), att |-> a]
\* Here: Dedup = TRUE, FreshKey = TRUE, CrashWindows = {"CW3"}
```

@direction
Model asserts: no command is charged more than once, with a provider that honors keys.

@call key=B surprise=yes run=RUN-tlc-fresh-key
The provider honors keys. Can the charge happen twice?

- A. No: the provider deduplicates.
  - why: Deduplication is per key, and the second attempt carries a new one. The key must name the intent, not the attempt.
  - mis: dp:E2
- B. Yes.
  - why: Two keys, two effects.

@after
Mint the key once, with the intent, in the command's transaction, and send it on every attempt. The [PostgreSQL 18 documentation](https://www.postgresql.org/docs/18/functions-uuid.html) lists `uuidv7()`, which "Generates a version 7 (time-ordered) UUID" (read 2026-10-23). Whether PGlite supports it is part of {{run:RUN-pglite-inbound-key}}.
:::

:::item role=segment family=GEN-find-the-witness template=t2 kcs=KC-8.untrusted-replies
@choice key=D
A handler checks status, cost and key, but not lateness. Which reply sequence breaks an invariant?

- A. An `ok` reply for cost 80 arrives twice, one copy after the other.
  - why: The key check discards the second copy.
  - mis: dp:E2
- B. A `declined` reply arrives while the hold is still held.
  - why: The status check rejects it.
  - mis: dp:E7
- C. An `ok` reply for cost 120 arrives against a hold of 100.
  - why: The cost check rejects it against the hold of 100.
  - mis: dp:E7
- D. The timer releases the hold, then a valid `ok` reply for cost 80 arrives.
  - why: Nothing stops the capture, so it lands on a released hold.
:::

## Exit {minutes=3 kcs=KC-8.untrusted-replies,KC-8.idempotency-keys}

:::item role=exit family=GEN-find-the-witness template=t2 kcs=KC-8.idempotency-keys
@choice key=B
A handler writes its key row in a separate transaction, after the capture committed. Which sequence captures twice?

- A. The same reply arrives twice in a row, with no crash between the two deliveries.
  - why: The first delivery wrote its key row, so the second is discarded.
  - mis: dp:E2
- B. The capture commits, the worker crashes before writing the key row, and the reply arrives again.
  - why: The key row is missing, so the second copy passes the key check and captures again.
- C. A reply for cost 120 arrives, against a hold that is still held.
  - why: The cost check rejects it.
  - mis: dp:E7
:::
