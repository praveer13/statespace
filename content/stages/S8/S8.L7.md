## Four ways to forget a key {minutes=12 kcs=KC-8.provider-horizon,KC-8.at-least-once}

An outbox plus a provider that honors keys looks like exactly-once. It is two promises, made by two parties, and the second has a time limit.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-8.provider-horizon
@choice key=B
Your worker's first attempt was charged, but its reply was lost. Then the worker was down for two days. Your provider documents that keys may be pruned once at least 24 hours old. On restart, the worker re-sends with the same key. What happens?

- A. The provider returns the saved result, because it remembers the key.
  - why: The retention did not cover the outage.
  - mis: dp:E10
- B. A second charge: a reused key after pruning is a new request.
  - why: The key is gone, so the provider treats the request as new.
- C. The provider rejects the reused key as a duplicate.
  - why: There is no key left to reject. The provider fails open and charges again.
  - mis: dp:T15
:::

:::instrument ins=INS-spectacle cell=1 recorded=RUN-tlc-key-ttl
The full design, with timers on, and a provider that prunes keys under a stated policy.

```tla
\* The provider prunes a key from its table under a stated policy.
CanForget(k) ==
  CASE Forgets = "never"      -> FALSE
    [] Forgets = "anytime"    -> TRUE
    [] Forgets = "afterAck"   -> status[k[1]] = "acked"
    [] Forgets = "afterDrain" -> /\ status[k[1]] = "acked"
                                 /\ ~\E r \in reqs : r.key = k
    [] OTHER                  -> FALSE
\* Here: Dedup = TRUE, FreshKey = FALSE, Timeouts = TRUE, Forgets = "afterAck"
```

@direction
Model asserts: no command is charged more than once, with a provider that honors keys until it prunes them.

@call key=A surprise=yes run=RUN-tlc-key-ttl
The provider prunes a key as soon as your worker has acknowledged its intent. Is a double charge possible?

- A. Yes.
  - why: A copy of an earlier attempt can still be in flight. When it arrives the key is gone, and the provider performs the effect again.
- B. No: an acknowledged intent is never sent again.
  - why: Your worker stops sending. Its earlier copies do not stop.
  - mis: dp:E10

@after
The timer sent a second copy while the first was in flight. The worker acknowledged on the first reply, the provider pruned the key, and the late copy was charged as new.
:::

:::instrument ins=INS-spectacle cell=2 recorded=RUN-tlc-key-ttl
The same design, with a stricter provider.

```tla
    [] Forgets = "afterDrain" -> /\ status[k[1]] = "acked"
                                 /\ ~\E r \in reqs : r.key = k
\* Here: Dedup = TRUE, FreshKey = FALSE, Timeouts = TRUE, Forgets = "afterDrain"
```

@direction
Model asserts: no command is charged more than once, with a provider that honors keys until it prunes them.

@call key=B surprise=no run=RUN-tlc-key-ttl
Now the provider prunes only once the intent is acknowledged and no copy is in flight. Is a double charge possible?

- A. Yes.
  - why: Once no copy remains, no request can carry the key again.
  - mis: dp:E10
- B. No.
  - why: Every copy that could reuse the key has been delivered or dropped.

@after
Never pruning holds too. Pruning at any time double-charges when an outage outlives the retention. That is specimen SP-8.5 {{run:RUN-tlc-key-ttl}}.
:::

:::card variant=dated-incident title="Stripe: documented key pruning"
Stripe's API reference, [Idempotent requests](https://docs.stripe.com/api/idempotent_requests) (read 2026-10-21; re-read 2026-10-23). For API v1, keys can be removed "after they're at least 24 hours old", and "We generate a new request if a key is reused after the original is pruned." Retries with the same key "return the saved response, including 500 errors." A request that conflicts with another "executing concurrently" is not saved and can be retried. API v2 behaves differently. Trace three questions on the page as you read it: API v1's retention, a retry after a saved 500, and a concurrent request with the same key. Pins: {{run:RUN-twin-pins}}.
:::

Write the claim as two parts. Yours: every committed intent is dispatched at least once, carrying the key minted at commit (CL-8.1 and CL-8.5). The provider's: a reused key within its retention returns the saved result, ASSUMED [A], in your trusted base. Together they give no double charge (CL-8.2), while every copy of every attempt is delivered or dropped before the key can be pruned. That last clause is SEAM-12, and you write it in LAB-8.8, with the provider, the API version, the retention and the date you read it.

## Exit {minutes=4 kcs=KC-8.provider-horizon,KC-8.at-least-once}

:::item role=exit family=GEN-call-it template=t4 kcs=KC-8.at-least-once,KC-8.provider-horizon
@choice key=B
Five statements about "exactly once". (1) An outbox alone gives exactly-once effects. (2) A provider that honors one stable key per intent prevents a second charge while it still holds the key. (3) Pruning a key as soon as the intent is acknowledged cannot double-charge. (4) The provider's deduplication belongs in your trusted assumptions, with its retention stated. (5) The retention only has to outlast your retry loop. Which option judges all five rightly?

- A. True: 2, 4 and 5. False: 1 and 3.
  - why: A copy of an earlier attempt can arrive after your retry loop ends, so the retention must outlast every copy.
  - mis: dp:E10
- B. True: 2 and 4. False: 1, 3 and 5.
  - why: Copies of earlier attempts can outlive your retry loop, so 3 and 5 fail. An outbox makes the intent durable, not the effect single.
- C. True: 1, 2 and 4. False: 3 and 5.
  - why: An outbox makes the intent durable. The effect is single only with the provider's help.
  - mis: dp:E1
- D. True: 2. False: 1, 3, 4 and 5.
  - why: You rely on the provider's deduplication, so your claim states it as an assumption.
  - mis: dp:E4
:::
