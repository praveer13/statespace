## Lassos under stated fairness {minutes=13 kcs=KC-8.progress-needs-recovery}

In the time stage you checked that a hold eventually resolves under weak fairness, and wrote it as CL-5.3. Crashes now join that model. Before you read on, decide which part of that claim cracks, and keep your answer.

:::item role=prequestion family=GEN-lasso-or-not template=t1 kcs=KC-8.progress-needs-recovery
@choice key=C
A check of "every committed command is eventually acknowledged" passes. Its configuration has no Crash action. What did it establish about your system with crashes?

- A. The property holds with crashes too, because the check passed.
  - why: Crashes were outside the model, so the check is silent about them.
  - mis: dp:E3
- B. It holds if crashes are rare, since the check passed without any.
  - why: The model has no notion of rare. One crash at the wrong moment is a behavior.
  - mis: dp:E3
- C. Nothing about crashes: they are NOT COVERED [N].
  - why: A model without an action cannot speak about behaviors that need it.
:::

The outbox has two progress properties. `EventuallyDispatched` says a committed command leads to a request. `EventuallyAcked` says it leads to an acknowledgement. Each is checked under fairness you state. A refutation is a lasso: a stem, then a cycle that breaks no stated fairness conjunct and never reaches the goal.

:::instrument ins=INS-lasso cell=1 recorded=RUN-tlc-crash-liveness
Crashes on, at most two. The worker's actions and the provider's are weakly fair, and Recover has no fairness.

```tla
WorkerFair   == \A c \in Cmds : /\ WF_vars(Dispatch(c)) /\ WF_vars(Receive(c))
                                /\ WF_vars(Persist(c))  /\ WF_vars(Ack(c))
ProviderFair == WF_vars(\E r \in reqs : Accept(r))
LiveSpec     == Init /\ [][Next]_vars /\ WorkerFair /\ ProviderFair

EventuallyDispatched == \A c \in Cmds : (c \in committed) ~> (attempts[c] > 0)
EventuallyAcked      == \A c \in Cmds : (c \in committed) ~> (status[c] = "acked")
\* Here: MaxCrashes = 2
```

@direction
Check asserts: EventuallyAcked holds on every behavior that satisfies the fairness. A violation is a lasso that satisfies it and never acknowledges.

@call key=B surprise=no run=RUN-tlc-crash-liveness
EventuallyAcked?

- A. Holds: weak fairness keeps the worker going.
  - why: Fairness applies to enabled actions. A crashed worker has none, and nothing obliges Recover.
  - mis: dp:E3
- B. Violated by a lasso.
  - why: Stuttering after a crash is a behavior, and the lasso is fair to every stated action.

@after
The lasso ends with a crash, then the worker down and stuttering, and the lasso checker accepts it as fair. With the crash actions switched off, the same property passes {{run:RUN-tlc-crash-liveness}}. That is specimen SP-8.6: a liveness check that passes only because the model left crashes out. Compare with the answer you kept. CL-5.3's check still passes on its own model. What cracks is the assumption that the worker keeps running, SEAM-8: an assumption record.
:::

:::instrument ins=INS-lasso cell=2 recorded=RUN-tlc-recovery
Crashes unlimited, with no bound on sends. Recover is now weakly fair too.

```tla
RecoverFair == WF_vars(Recover)
LiveSpec2   == Init /\ [][Next]_vars /\ WorkerFair /\ ProviderFair /\ RecoverFair
\* Here: MaxCrashes = -1, which means no bound on crashes
```

@direction
Check asserts: EventuallyAcked holds on every behavior that satisfies the fairness.

@call key=C surprise=yes run=RUN-tlc-recovery
EventuallyAcked?

- A. Holds: the worker always comes back.
  - why: It comes back and crashes again before acting. Weak fairness needs an action continuously enabled, and each crash disables Dispatch.
  - mis: dp:T14
- B. It would hold with strong fairness on Recover.
  - why: Recover is already enabled the whole time the worker is down, so strong fairness on it changes nothing. Dispatch is the starved action.
  - mis: dp:T14
- C. Violated by a crash and recover cycle.
  - why: The cycle is fair to every stated action, yet Dispatch never fires.

@after
Weak fairness cannot see an action that is enabled only between a recovery and the next crash.
:::

:::instrument ins=INS-lasso cell=3 recorded=RUN-tlc-recovery
Crashes unlimited. The worker's actions are now strongly fair; Recover and the provider stay weakly fair.

```tla
WorkerStrong == \A c \in Cmds : /\ SF_vars(Dispatch(c)) /\ SF_vars(Receive(c))
                                /\ SF_vars(Persist(c))  /\ SF_vars(Ack(c))
LiveSpec3    == Init /\ [][Next]_vars /\ WorkerStrong /\ ProviderFair /\ RecoverFair
\* Here: MaxCrashes = -1
```

@direction
Check asserts: EventuallyAcked holds on every behavior that satisfies the fairness.

@call key=A surprise=yes run=RUN-tlc-recovery
EventuallyAcked?

- A. Holds.
  - why: Strong fairness takes an action enabled infinitely often, so some window between a recovery and the next crash is eventually used.
- B. Violated by a crash and recover cycle.
  - why: That cycle starved weak fairness only.
  - mis: dp:T14

@after
There are two honest ways to say that the worker recovers: crashes eventually stop (a finite budget, with Recover fair), or the worker's actions get strong fairness. Write yours as an assumption. The provider's recovery is a separate assumption, needed for EventuallyAcked only. Provider idempotency serves safety, not progress.
:::

Worked example: EventuallyDispatched needs a worker that recovers and nothing from the provider, so its fairness is `WorkerFair` plus recovery. Write the fairness that EventuallyAcked needs, then compare it with the table. Safety needs no fairness at all.

| Property | Kind | The worker recovers | The provider replies | Provider idempotency |
|---|---|---|---|---|
| NoLostIntent | safety | no | no | no |
| NoDoubleCharge | safety | no | no | yes, one key per intent |
| EventuallyDispatched | liveness | yes | no | no |
| EventuallyAcked | liveness | yes | yes | no |

:::item role=segment family=GEN-lasso-or-not template=t1 kcs=KC-8.progress-needs-recovery
@choice key=A
EventuallyDispatched. Crashes are unlimited, Recover is weakly fair, and the worker's actions are weakly fair. Which lasso refutes it, or is there none?

- A. Commit, then Crash and Recover forever: the worker is never up long enough to Dispatch.
  - why: Dispatch is enabled only while the worker is up, so weak fairness does not force it, and the cycle is fair to Recover.
- B. None: weak fairness forces Dispatch because the intent stays pending.
  - why: Weak fairness forces an action only if it stays enabled. Each crash disables Dispatch.
  - mis: dp:T14
- C. Commit, Crash, then stutter forever with the worker down.
  - why: Recover is weakly fair and stays enabled while the worker is down, so this lasso breaks a stated conjunct.
  - mis: dp:T14
:::

## Exit {minutes=3 kcs=KC-8.progress-needs-recovery}

:::item role=exit family=GEN-lasso-or-not template=t2 kcs=KC-8.progress-needs-recovery
@choice key=C
EventuallyAcked. Crashes are finite, Recover and the worker's actions are weakly fair, and the provider has no fairness. Is there a fair cycle that never acknowledges?

- A. No: the worker's weak fairness forces the acknowledgement of every stored result.
  - why: The worker cannot acknowledge a result the provider never sent.
  - mis: dp:T15
- B. No: a finite crash budget brings the worker back, and that is enough.
  - why: A finite budget recovers the worker. It does not make the provider answer.
  - mis: dp:E3
- C. Yes: the provider never replies, and the worker waits and stutters.
  - why: Nothing obliges the provider to act, and the stuttering cycle breaks no stated conjunct.
:::
