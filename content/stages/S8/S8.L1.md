## Three designs, one crash each {minutes=12 kcs=KC-8.commit-not-send}

An agent opens a pull request with this note. Nothing has reviewed it:

> We call the provider right after COMMIT returns, so every charge happens exactly once. All tests green.

Tests run on a good day. Here the process dies at one marked line, and you read what is left.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-8.commit-not-send
@choice key=A
Your handler commits a capture, then calls the provider. The process dies between the two. After restart, what is true?

- A. The database shows the capture; the provider was never called.
  - why: Commit-then-send leaves a record with no effect, and nothing durable remembers that a call is owed.
- B. The provider will be called on restart, because the capture committed.
  - why: No durable row says a call is owed. A committed record is not a promise of an effect.
  - mis: dp:E1
- C. Neither happened: the transaction covers the call, so both roll back.
  - why: A transaction spans your database only. The provider sits outside it.
  - mis: dp:E5
:::

Three handlers pair a database write with a provider call. They differ only in order, and the order decides what a crash leaves behind.

:::instrument ins=INS-theater cell=1 recorded=RUN-tlc-outbox-safety
Place the crash at the marked point and watch the monitors.

```text
A  send, then commit      B  commit, then send      C  outbox
   call the provider         COMMIT the capture        COMMIT the capture and an intent row
   COMMIT the capture        call the provider         (a worker, later)
                                                        read the intent, call the provider,
                                                        mark the intent done
```

@direction
Scene asserts: the end state after one crash at the marked line. Each monitor labels it an effect with no record, a record with no effect, or an intent waiting. A monitor reports what this scene did; it earns no stamp.

@call key=A surprise=yes run=RUN-tlc-outbox-safety
In design C the crash lands right after COMMIT. After restart, what does the outbox guarantee?

- A. The intent survives, and a worker sends it at least once if it recovers.
  - why: The intent committed with the command, so it is durable. Delivery is at least once, and it needs a worker that comes back.
- B. The effect will happen exactly once, because the intent is a single row.
  - why: The outbox makes the intent durable, not the effect single. Sending can repeat after later crashes.
  - mis: dp:E1
- C. The effect is lost unless the client retries the whole request.
  - why: That is design B, where the intent lived in memory. Here it committed with the command.
  - mis: dp:E5

@after
The outbox scene keeps its intent through the crash. Design B loses it, and the check `NoLostIntent` fails there {{run:RUN-tlc-outbox-safety}}. One crash at the marked line leaves:

| Design | At the provider | In your database |
|---|---|---|
| A. send, then commit | the effect happened | nothing: an effect with no record |
| B. commit, then send | nothing | the record: a record with no effect |
| C. outbox | nothing yet | the record and its intent: an intent waiting |

A commit records that you intend something. Only the provider's own step makes it happen, so a guarantee about the effect lives at the provider, and a guarantee about the intent lives in your database. The outbox makes the intent durable; it does not make the effect single, because the worker may send again.
:::

:::item role=segment family=GEN-call-it template=t4 kcs=KC-8.commit-not-send
@choice key=C
Design C again. The worker sent the request, the provider performed the effect, and the worker crashed before it marked the intent done. The provider ignores keys. After restart, judge five statements. (1) A durable record of the intent exists. (2) The provider performed the effect. (3) The record shows the effect happened. (4) The worker sends again once it recovers. (5) The effect happens exactly once. Which option judges all five rightly?

- A. True: 1, 2, 4 and 5. False: 3.
  - why: Sending again to a provider that ignores keys performs the effect twice.
  - mis: dp:E1
- B. True: 1, 2, 3 and 4. False: 5.
  - why: An inflight row says a request went out. It cannot say that a reply came back.
  - mis: dp:E3
- C. True: 1, 2 and 4. False: 3 and 5.
  - why: The intent row is still inflight with no stored result, so recovery sends again. The row records intent, not outcome, and a second send repeats the effect.
- D. True: 1 and 2. False: 3, 4 and 5.
  - why: Recovery returns the unanswered intent to pending, so the worker does send again.
  - mis: dp:E5
:::

## Exit {minutes=4 kcs=KC-8.commit-not-send}

:::item role=exit family=GEN-call-it template=t1 kcs=KC-8.commit-not-send
@choice key=B
A handler calls the provider, then commits. The process dies between the two. What can the end state be?

- A. A record with no effect.
  - why: That is commit-then-send. Here the order is reversed.
  - mis: dp:E5
- B. An effect with no record.
  - why: The call happened and the commit did not, so nothing remembers the charge.
- C. Neither: the rollback undoes the call.
  - why: A rollback covers your database only. The provider keeps what it did.
  - mis: dp:E5
:::
