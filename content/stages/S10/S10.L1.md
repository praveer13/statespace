## Recall before you wire {minutes=3 kcs=KC-3.typing-judgment,KC-3.resource-postings,KC-3.abstract-syntax}

You wrote your parser and typechecker in Stage 3, months ago, and a gate held them to the course's goldens. The Core now puts them in front of everything else, and some of the commands they read will come from an agent. Recalling a rule and trusting it as a component are different acts, so answer from memory first.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-3.typing-judgment,KC-3.resource-postings,KC-3.abstract-syntax
@choice key=B
Your typechecker accepts an agent's command that assigns a number to `balance(from)`. What follows?

- A. It type-checks, so it keeps your invariants as they were.
  - why: Typing rules out ill-formed commands. A well-formed command can still break an invariant.
  - mis: dp:S4
- B. It has drifted from `HasType`'s resource rule: re-run the goldens.
  - why: The rule forbids assigning a resource field (S3.L2), so acceptance means your Rust mirror disagrees with the Lean judgment.
- C. Nothing yet: the obligation checker will catch what typing misses.
  - why: Typing and obligation checking make different claims, and the checker assumes a well-typed IR.
  - mis: dp:P3
:::

## Re-run your gate {minutes=6 kcs=KC-3.typing-judgment,KC-3.resource-postings,KC-3.abstract-syntax}

Your parser turns the toy syntax into the JSON IR, the one format that Stages 3, 6 and 9 share. Your typechecker reads that IR and either accepts a command or names the rule that rejects it. Everything after it assumes a well-typed command: the checker does not re-examine typing, and the compiler does not either. A typechecker that accepts too much is not caught downstream. It is trusted downstream.

The gate from Stage 3 holds each half to the course's fixtures.

| Half | Gate | Passing means |
|---|---|---|
| Parser | LAB-3.c8 | The IR your parser emits equals the Lean export on every golden. |
| Typechecker | LAB-3.c9 | On fresh seeds drawn when the gate runs, your verdict, accept or the name of the rule, equals the typing golden's. |

Run both on your current code before you wire anything. The cell below holds the agent's command from the question. Rule R-set rejects a command like it with `assignsResource` (S3.L2), the typing goldens hold that verdict {{run:RUN-interp-goldens}}, and your typechecker should return it too.

:::instrument ins=INS-lane-a cell=1 recorded=RUN-interp-goldens call=false
```text
command Settle(from: account, to: account, amount: amount)
  requires balance(from) >= amount
  do set balance(from) := balance(from) - amount
```

@direction
Your parser reads this text into IR, and your typechecker returns accept or the name of a rule. No state is involved, so nothing here can overdraw an account. The only question is whether the command is well-formed.

@after
Your typechecker should reject the command under rule R-set, with `assignsResource`. If it accepted the command, it has drifted from `HasType`, and the typing check of the gate fails on this fixture too. If it rejected the command under a different rule, the verdict class matches but the gate compares rule names, so the gate still fails.
:::

When the gate fails, name the first fixture that disagrees and say whether the parser or the typechecker produced the difference, before you change any code. The earlier you find a disagreement, the fewer components you have to suspect.

:::
