## Before you type {minutes=4 kcs=KC-3.resource-postings,KC-3.typing-judgment,KC-3.refined-types}

Your Stage 2 transfer had no assignment: it computed new balances from old ones, and every theorem followed from that. Give a language assignment and a command can write any number into a balance. This lesson is the set of rules that stops that before a command ever runs, and the two questions below are the ones those rules exist for.

:::item role=prequestion family=GEN-find-the-witness template=t1 kcs=KC-3.resource-postings,KC-3.typing-judgment
@choice key=A
Draft 0 lets a command assign balances: `set balance(x) := e`. Which single command can mint money?

- A. `set balance(a) := balance(a) + 1`
  - why: An assignment can write any value, so it can write one more than was there.
- B. A transfer from an account to itself.
  - why: Sequential updates conserve on a self-transfer. Stage 2's mint came from computing both balances from the old state.
  - mis: dp:S1
- C. None: Transfer conserves, so the language conserves.
  - why: One conserving command says nothing about a language that also has assignment.
  - mis: dp:S10
- D. A transfer between two very large balances.
  - why: Lean's `Int` does not overflow.
  - mis: dp:Z4
:::

:::item role=prequestion family=GEN-find-the-witness template=t1 kcs=KC-3.refined-types
@choice key=A
Amounts are plain `Int`. Which guarded command can drive an account negative?

- A. `move amount from from to to` under `requires balance(from) >= amount`, with amount -5.
  - why: A negative move debits `to`, and no guard mentions `to`.
- B. None: the guard checks the balance.
  - why: A guard covers the account it names, not the other one.
  - mis: dp:S9
- C. Only a transfer from an account to itself.
  - why: A positive self-transfer nets to zero.
  - mis: dp:S1
:::

## The judgment {minutes=13 kcs=KC-3.typing-judgment}

A typing judgment says when a command is well-formed, before any state exists. It is written Γ ⊢ c ok: in a context Γ that lists the parameters and their types, the command c is accepted. This course writes it as a function, `typecheck : Ctx → Cmd → Except TypeErr Unit`, and defines `HasType Γ c` as `typecheck Γ c = .ok ()`. Every rejection then names the rule that fired, and a rule you got wrong shows up as a failing check you can read.[^1]

[^1]: Harper's *Practical Foundations for Programming Languages*, chapter 4, draws the same rules as inference rules.

| Rule | Requires | Rejection | Protects |
|---|---|---|---|
| R-param | distinct parameter names, each with a declared type | `dupParam` | well-formedness |
| R-var | every variable is a parameter | `unknownParam` | well-formedness |
| R-expr | `balance(e)` and `frozen(e)` take an account; arithmetic and `>=` take numbers; the guard is a bool | `wrongType` | no expression gets stuck |
| R-cover | a `move n from x ...` or `hold n on x` needs a top-level guard conjunct `balance(x) >= n` | `unguardedDebit` | non-negativity of the debited account |

R-cover is the rule that ties a guard to a body. `Covers g x n` holds when `g` is `balance(x) >= n`, or when `g` is `g₁ && g₂` and either side covers. A disjunction never covers. The rule is sound and incomplete: `balance(x) >= n + fee` implies coverage without covering syntactically, and Stage 4's obligations prove what the rule cannot see.

```lean
/-- `covers g x n`: some top-level conjunct of `g` is `balance(x) >= n`. -/
def covers : Expr → Expr → Expr → Bool
  | .ge (.balance y) m, x, n => y == x && m == n
  | .and g₁ g₂,         x, n => covers g₁ x n || covers g₂ x n
  | _,                  _, _ => false

/-- The R-cover clause of `typecheck`: a debit needs a covering guard. -/
def checkBody (g : Expr) : Stmt → Except TypeErr Unit
  | .op (.move n x _) => if covers g x n then .ok () else .error .unguardedDebit
  | .op (.hold n x)   => if covers g x n then .ok () else .error .unguardedDebit
  | _                 => .ok ()
```

## Five operations, ten postings {minutes=13 kcs=KC-3.resource-postings}

An operation never edits a balance. It posts a pair of entries: a debit from one account and a credit of the same amount to another, so every operation is zero-sum. `mint` is the account that creates money, `sink` absorbs it, and a hold parks money in an escrow account. Write `bal s x` for the balance of account `x` in state `s`.

| Operation | Postings (debit to credit) | Run-time checks |
|---|---|---|
| `deposit n to a` | `mint` to `a` | `a` exists |
| `move n from x to y` | `x` to `y` | `x` and `y` exist |
| `hold n on x` | `x` to escrow `h` | `x` exists; `h` is the next hold number |
| `capture h to y` | escrow `h` to `y` | the hold exists, is open and is covered |
| `release h` | escrow `h` to the hold's owner | the same |

The invariant `Inv` says that keys are unique, the total of all balances is 0, and every account except `mint` is non-negative. A zero-sum pair keeps the total at 0 whatever a guard says, so conservation costs no proof per command. Only a debit can push a balance below zero, so non-negativity is the per-command obligation: R-cover pays it for `move` and `hold`, and a run-time check pays it for `capture` and `release`.

Three more rules keep a command from sidestepping the pairs.

| Rule | Requires | Rejection | Protects |
|---|---|---|---|
| R-set | `set f(x) := e` needs a scalar field `f`; `balance` is a resource and has no assignment rule | `assignsResource` | conservation |
| R-amount | an operation's amount is an `amount` parameter or a positive literal | `nonPositive` | the direction of every posting |
| R-hold | `capture h to y` and `release h` need `h : hold`, and `y : account` or `sink` | `wrongType` | no stuck statement |

R-amount matters because `move -5 from x to y` credits `x` and debits `y`, and no guard mentions `y`.

:::instrument ins=INS-interp cell=2 recorded=RUN-interp-goldens
Three operations in a row, from a small state.

```text
start    mint -100 · a 100 · sink 0
1   hold 30 on a
2   capture h to sink
3   release h
```

@direction
The posting view lists the balances before and after each step. `h` is the hold that step 1 creates.

@call key=B run=RUN-interp-goldens surprise=no
After `hold 30 on a` and `capture h to sink`, what does `release h` do?

- A. It returns 30 to `a`.
  - why: Capture emptied the escrow and closed the hold.
  - mis: dp:S11
- B. It fails with `holdNotOpen h`.
  - why: A run-time check refuses a second resolution. No typechecker knows a hold's status.
- C. It is rejected before it runs, as ill-typed.
  - why: `release h` with `h : hold` is well-typed. This is a run-time outcome.
  - mis: dp:S7

@after
Every step moved money in pairs, so the total stayed at 0 throughout. The third step was refused at run time, as `holdNotOpen`, because the hold was already resolved {{run:RUN-interp-goldens}}. A typechecker reads a command, and a hold's status lives in the state, so no typing rule can make this check. Your own system draws the same line: a missing check is visible in the code, and an already-resolved hold is visible only in the data.
:::

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-3.resource-postings
@choice key=A
A variant checker drops R-set. Which command does it now accept, and which part of `Inv` does the command break?

- A. `set balance(a) := balance(a) + 1`, which breaks conservation.
  - why: The total becomes 1, and no posting pair balances it.
- B. `set balance(a) := balance(a) + 1`, which breaks non-negativity.
  - why: The balance grew, so it did not go negative. The total is what changed.
  - mis: dp:S10
- C. `move 5 from a to b` under `requires balance(a) >= 5`, which breaks non-negativity.
  - why: The guard covers the debit, so both checkers accept it and `Inv` holds.
  - mis: dp:S9
- D. `move 5 from a to a`, which breaks conservation.
  - why: A self-move debits and credits one account, so the total is unchanged.
  - mis: dp:S1
:::

## Positivity as a type {minutes=12 kcs=KC-3.refined-types}

R-amount asks every amount to be positive, and a type can promise that once instead of each operation checking it. A subtype packs a value with a proof: `Amount := {n : Int // 0 < n}` is an integer together with a proof that it is positive. Lean checks the proof when the value is built, and no operation has to look again. Values of Mini-Plinth's `amount` type are `Amount`s.

Raw input is the catch. A call arrives with plain integers, and the boundary that decodes them has to build an `Amount` from each one.

:::instrument ins=INS-goal-replay cell=3 recorded=RUN-lean-golden-harness
Three ways to build an `Amount`.

```lean
abbrev Amount := { n : Int // 0 < n }

example : Amount := ⟨30, by decide⟩    -- goal: 0 < 30

example : Amount := ⟨0, by decide⟩     -- goal: 0 < 0

def Amount.add (a b : Amount) : Amount :=
  ⟨a.val + b.val, by
    have ha := a.property
    have hb := b.property
    omega⟩
```

@direction
Goal Replay shows the goal at each step: the proof of positivity that a value must carry.

@call key=A run=RUN-lean-golden-harness surprise=no
Can the boundary turn the argument 0 into an `Amount`?

- A. No: there is no proof of `0 < 0`, so the boundary must reject zero or treat it specially.
  - why: A subtype value carries its proof, checked once at construction. Zero becomes a boundary decision.
- B. Yes: Lean raises an error later, when the amount is used.
  - why: There is no later check. The value cannot be built at all.
  - mis: dp:S14

@after
`decide` tries to prove `0 < 0` and reports that the proposition is false {{run:RUN-lean-golden-harness}}. The proof is part of the value, so no zero `Amount` exists to catch later. What the boundary does with a zero argument is a decision, and you make it in S3.L7. The third step, `Amount.add`, uses the proofs both inputs carry, which `omega` combines.
:::
