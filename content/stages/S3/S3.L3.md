## Failure as a value {minutes=12 kcs=KC-3.big-step-errors}

A big-step evaluator takes a program, a call and a state, and returns the whole outcome at once. Mini-Plinth's returns `Except Err (State × Output × List Effect)`: either a named error, or a new state with an output and the effects to emit. Every failure is a value the caller can match on. That is what explicit errors means.

The evaluator checks in a fixed order, and the first check that fails decides the outcome:

1. The command exists, else `unknownCommand`.
2. The arguments decode, with positive amounts, else `badArgument`.
3. Every account argument exists, else `unknownAccount`.
4. A self-transfer is allowed or rejected, as your policy says.
5. The guard holds, else `guardFailed`.
6. A hold's checks pass, else `unknownHold` or `holdNotOpen`.
7. The postings run, then the effects and output are built.

The reference's default policy rejects a zero amount, allows a self-transfer, returns an error for a failed guard and lets balances grow without bound. S3.L7 makes each of those your decision. Here is the idea in a few lines.

```lean
abbrev State := List (String × Int)

def bal (s : State) (a : String) : Int := (s.lookup a).getD 0

def setBal (s : State) (a : String) (v : Int) : State :=
  s.map fun p => if p.1 = a then (a, v) else p

inductive Err where
  | badArgument (p : String)
  | unknownAccount (a : String)
  | guardFailed (c : String)
  deriving DecidableEq, Repr

/-- Debit, then credit, reading the updated state: a self-transfer changes nothing. -/
def post (s : State) (x y : String) (n : Int) : State :=
  let s₁ := setBal s x (bal s x - n)
  setBal s₁ y (bal s₁ y + n)

/-- Four of the reference's checks, as a function that returns every outcome as a value. -/
def transfer (s : State) (x y : String) (n : Int) : Except Err State :=
  if n ≤ 0 then .error (.badArgument "amount")
  else if (s.lookup x).isNone then .error (.unknownAccount x)
  else if (s.lookup y).isNone then .error (.unknownAccount y)
  else if bal s x < n then .error (.guardFailed "Transfer")
  else .ok (post s x y n)
```

:::instrument ins=INS-interp cell=1 recorded=RUN-lean-golden-harness
A transfer from an account to itself, under the default policy.

```text
start    mint -10 · a 10
Transfer(a, a, 5)
```

@direction
The evaluator view shows the outcome, the step of the order that produced it, and the balances after.

@call key=A run=RUN-lean-golden-harness surprise=yes
From a = 10, `Transfer(a, a, 5)`. What is a's balance afterwards?

- A. 10
  - why: The postings debit and then credit the same account, reading the updated state.
- B. 15
  - why: Stage 2's specimen computed both balances from the old state {{run:RUN-lean-selftransfer}}. Postings do not.
  - mis: dp:S1
- C. 5
  - why: That is the debit without the credit.
  - mis: dp:S1
- D. An error.
  - why: The default policy allows self-transfers. S3.L7 makes that your decision.
  - mis: dp:S12

@after
The debit takes 5 from `a` and the credit puts 5 back, reading the state the debit left. The outcome is a commit with the state unchanged, and the effects notify `a`, who is both sender and recipient {{run:RUN-lean-golden-harness}}.
:::

:::instrument ins=INS-interp cell=2 recorded=RUN-lean-golden-harness
A transfer of zero.

```text
start    mint -100 · a 100 · b 0
Transfer(a, b, 0)
```

@direction
The same view. Watch for the step that decides the outcome.

@call key=A run=RUN-lean-golden-harness surprise=no
`Transfer(a, b, 0)`: what is the outcome?

- A. `badArgument "amount"`
  - why: Zero is not an `Amount`, so the boundary rejects it with a typed error.
- B. It commits and changes nothing.
  - why: That is the decision `zero = noop`, which is not the default.
  - mis: dp:S12
- C. The evaluator crashes.
  - why: A total evaluator always returns a value.
  - mis: dp:S6

@after
Zero never reaches the account checks: it fails to decode at step 2 {{run:RUN-lean-golden-harness}}. A silent no-op and an error are different outcomes. The no-op tells the caller the request succeeded, and the error tells the caller it was refused.
:::

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-3.big-step-errors
@choice key=A
From a = 100 and b = 0 under the default policy, which call returns `unknownAccount`, and at which step of the order?

- A. `Transfer(a, ghost, 30)`, at step 3.
  - why: `ghost` is not in the state, and the account check comes before the guard.
- B. `Transfer(a, b, 130)`, at step 3.
  - why: The accounts exist. The guard fails at step 5, as `guardFailed`.
  - mis: dp:S12
- C. `Transfer(a, a, 30)`, at step 4.
  - why: Self-transfers are allowed by default, so this commits.
  - mis: dp:S1
- D. `Transfer(a, b, 0)`, at step 2.
  - why: Zero fails to decode at step 2, as `badArgument`.
  - mis: dp:S12
:::

## Exit {minutes=4 kcs=KC-3.big-step-errors}

:::item role=exit family=GEN-find-the-witness template=t1 kcs=KC-3.big-step-errors
@choice key=A
From a = 100 and b = 0 under the default policy, which call returns `guardFailed "Transfer"`?

- A. `Transfer(a, b, 130)`
  - why: Both accounts exist and the amount decodes, so step 5 finds the guard false.
- B. `Transfer(a, b, 100)`
  - why: The guard is `>=`, so 100 passes and the call commits.
  - mis: dp:Z5
- C. `Transfer(a, ghost, 130)`
  - why: An unknown account is refused at step 3, before the guard is read.
  - mis: dp:S12
:::
