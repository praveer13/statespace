## Before the proof {minutes=4 kcs=KC-3.step-invariant}

Stage 3 now has a language: syntax, a typing judgment, and an evaluator that returns every outcome as a value. This lesson proves the first thing about all of it at once. **If a well-typed command takes a successful step from a state that satisfies the invariant, the new state satisfies it too.** Two questions first.

:::item role=prequestion family=GEN-proof-structure template=t3 kcs=KC-3.step-invariant
@choice key=B
Every Mini-Plinth operation is a zero-sum pair of postings. Which part of `Inv` needs the guard?

- A. Conservation: the total stays 0 after each operation.
  - why: A zero-sum pair keeps the total whatever the guard says.
  - mis: dp:S10
- B. Non-negativity: no account but the mint goes below 0.
  - why: Only a debit can push a balance below zero, so only a debit needs cover.
- C. Both parts: conservation and non-negativity.
  - why: The total is untouched by the guard. One part needs it, not both.
  - mis: dp:S10
:::

:::item role=prequestion family=GEN-proof-structure template=t3 kcs=KC-3.step-invariant
@choice key=A
Your evaluator returns `guardFailed` for every call. Can you prove `step_preserves_inv`?

- A. Yes, vacuously: no call succeeds and the theorem has nothing to check.
  - why: The theorem speaks only of successful steps. A later lesson's goldens are what catch an evaluator that never succeeds.
- B. No: the error results break the invariant of the state.
  - why: An error returns no state, so there is nothing for the invariant to fail on.
  - mis: dp:S7
- C. No: the statement needs at least one successful call to check.
  - why: A premise that is never met makes the implication true, so the statement holds without one.
  - mis: dp:G4
:::

## A worked proof {minutes=14 kcs=KC-3.step-invariant}

An invariant is a property of every state a system can reach. You do not prove it by running the system. You prove two things: it holds in the starting state, and every step that can happen next keeps it. In your own system the starting state is an empty table and the steps are the code paths that write to it. Here the property is `Inv`, and the steps are Mini-Plinth's five operations.

`Inv s := WF s ∧ total s = 0 ∧ ∀ p ∈ s.bals, p.1 ≠ mint → 0 ≤ p.2`

Read it as three parts. The account keys are unique. The balances add up to zero, because the `mint` account holds minus everything it has created. And every account except `mint` is at or above zero. The statement you are building towards is:

`step_preserves_inv : p.WellTyped → Inv s → exec p c s = .ok (s′, o, es) → Inv s′`

It speaks only of successful steps. An error returns no state, so there is nothing to keep.

Every operation is built from one primitive. `post s x y n` debits `x` by `n`, then credits `y` by `n`, reading the state the debit left. The two postings cancel, so the total stays at zero for every operation with no work per command. Only the third part of `Inv` can fail, and only at a debit. The whole stage reduces to one lemma:

`post_inv : 0 < n → (x = mint ∨ n ≤ bal s x) → Inv s → Inv (post s x y n)`

Each hypothesis has a job. Name the job before you see the step that uses it: zero-sum pairs keep the total, coverage pays the debit, positivity protects the credit, and unique keys keep `total` honest.[^1]

[^1]: Drawer D-07 collects the Lean errors you are likely to meet while writing proofs like this one.

:::instrument ins=INS-goal-replay cell=1 recorded=RUN-lean-step-invariant
The reference proof of `post_inv`. The template supplies the state, its lemmas and `Inv`. `post` is yours.

```lean
-- From the template: State, bal, setBal, total, WF, NonNeg and Inv, with
--   setBal_wf     : WF s → WF (s.setBal a v)
--   total_setBal  : WF s → total (s.setBal a v) = total s - s.bal a + v
--   nonneg_setBal : NonNeg s → (a = .mint ∨ 0 ≤ v) → NonNeg (s.setBal a v)
--   bal_nonneg    : NonNeg s → a ≠ .mint → 0 ≤ s.bal a

def post (s : State) (x y : Acct) (n : Int) : State :=
  let s1 := s.setBal x (s.bal x - n)
  s1.setBal y (s1.bal y + n)

theorem post_inv (s : State) (x y : Acct) (n : Int)
    (hn : 0 < n) (hcov : x = .mint ∨ n ≤ s.bal x) (hs : Inv s) :
    Inv (post s x y n) := by
  obtain ⟨hwf, htot, hnn⟩ := hs
  unfold Inv post
  dsimp only
  have hdebit : x = .mint ∨ 0 ≤ s.bal x - n := by
    rcases hcov with h | h
    · exact Or.inl h
    · exact Or.inr (by omega)
  have hnn1 := nonneg_setBal hnn hdebit
  have hcredit : y = .mint ∨ 0 ≤ (s.setBal x (s.bal x - n)).bal y + n := by
    by_cases hy : y = .mint
    · exact Or.inl hy
    · exact Or.inr (by have := bal_nonneg hnn1 hy; omega)
  refine ⟨setBal_wf (setBal_wf hwf), ?_, nonneg_setBal hnn1 hcredit⟩
  rw [total_setBal (setBal_wf hwf), total_setBal hwf]
  omega
```

## Fading the support {minutes=14 kcs=KC-3.step-invariant}

`post_inv` is the whole argument. Each operation's lemma only has to show that its postings meet the lemma's hypotheses, and the five differ in where coverage comes from.

| Operation | Debits | Where coverage comes from |
|---|---|---|
| `deposit n to a` | `mint` | the left side of `x = mint ∨ …`: the mint is exempt |
| `move n from x to y` | `x` | the guard, through R-cover |
| `hold n on x` | `x`, into escrow `h` | the guard, through R-cover |
| `capture h to y` | escrow `h` | a run-time check that the hold is open and its escrow covers it |
| `release h` | escrow `h` | the same run-time check |

Positivity is the same everywhere, because an amount is an `Amount`: a capture or a release credits the hold's stored amount, which is one too.

You will read the same kind of proof three times with less support each time. In `move_inv` the last step is blank. In `hold_inv` two steps are blank. In `capture_inv` only the case split is shown. No blank has a prompt, and every step you do see still asks which principle it uses. Three right answers in a row move you up a rung, one miss moves you down one, and Today sets your next rung.

@call key=A run=RUN-lean-step-invariant surprise=no
In `capture_inv` the debited account is the escrow. What pays for the debit?

- A. The run-time check that the hold is open and covers the amount.
  - why: `capture` makes that check before it posts, as the table of operations shows.
- B. The command's guard on the escrow account's balance.
  - why: No guard names an escrow account, because a command cannot name one.
  - mis: dp:S9
- C. Nothing: escrow accounts may go negative without harm.
  - why: `Inv` exempts only the mint.
  - mis: dp:S10

@after
A guard cannot cover an escrow: commands never name escrow accounts, so the check has to live inside the operation. In reachable states it never fails, and keeping it makes each lemma local. Stage 4 shows how an inductive "every escrow covers its hold" lets it go {{run:RUN-lean-step-invariant}}.

:::item role=segment family=GEN-proof-structure template=t2 kcs=KC-3.step-invariant
@choice key=A
`release_inv` must show `Inv s′` after `release h` returns `.ok s′`. Here are six moves, in no order. Two of them do not belong in a proof.

- (a) Unfold `applyOp` and split on the hold lookup.
- (b) Dismiss the error branches: the hypothesis says the result is `.ok`.
- (c) Cover the escrow debit with the command's guard.
- (d) Apply `post_inv` to the escrow debit, covered by the run-time check.
- (e) Apply `release_inv` to the new state.
- (f) Note that marking the hold released changes no balance.

Which sequence is a proof?

- A. (a), (b), (d), (f)
  - why: Split first, drop the error branches, apply `post_inv` with the run-time check as coverage, and see that a status change leaves `Inv` alone.
- B. (a), (c), (d), (f)
  - why: No guard covers an escrow debit, so move (c) proves nothing.
  - mis: dp:S9
- C. (a), (b), (e), (f)
  - why: Move (e) uses the lemma being proved, which is circular.
  - mis: dp:L6
- D. (d), (a), (b), (f)
  - why: The coverage comes from the branch that move (a) opens, so `post_inv` cannot be applied first.
  - mis: dp:L2
:::

## Assembling the theorem {minutes=13 kcs=KC-3.step-invariant}

Now put the lemmas together. `step_preserves_inv` splits on the command's one statement.

- An operation statement calls its lemma. For `move` and `hold` the coverage comes from typing. R-cover forced a guard conjunct `balance(x) >= n`, and a successful `exec` got past the guard, so the guard evaluated to true. `covers_sound` turns that into `n ≤ bal s x`.
- A `set f(x) := e` statement writes a scalar field and never a balance, because R-set has no rule for assigning a resource.

Nothing here depends on how you decide the edge cases in the next lesson. A silent rejection and a zero no-op both return the unchanged state, and a bounded overflow returns an error. None of them can break `Inv`.

A proof can build before it is finished. Leave one lemma as `sorry` and Lean still builds, so a green build is not a finished proof. The gap shows in the axioms.

What you assemble in LAB-3.5 becomes your first claim card from this stage, that successful steps preserve the state invariant. Its method, tool and axioms arrive prefilled. You write the proposition, the assumptions and the correspondence. One assumption is dashed: "a correct step needs no observer." The proof says a successful step keeps the balances in order. It says nothing about who can see that the step happened, and nothing in this stage tests that. It is a seam, and Stage 7 is where it is tested.

Last, tie the language to something you proved in Stage 2. That ledger had two fields. Pick two existing accounts `u₁` and `u₂` and read them as the ledger: `toLedger s := ⟨bal s u₁, bal s u₂⟩`. The refinement says a positive Transfer from `u₁` to `u₂` either commits with `toLedger s′ = transfer (toLedger s) n`, where `transfer` is Stage 2's function, or fails its guard exactly when Stage 2's `transfer` leaves the ledger unchanged {{run:RUN-lean-postings-refine}}. Zero lies outside this square: Stage 2's guard admits `n = 0`, and Stage 3's `Amount` is positive. The proof needs one hypothesis beyond the ones it shares with the lemmas above.

:::item role=segment family=GEN-proof-structure template=t3 kcs=KC-3.step-invariant
@choice key=C
Which hypothesis does the refinement proof need?

- A. `frozen u₁ = false`
  - why: Transfer's guard never reads a frozen flag, so the proof never meets one.
  - mis: dp:L4
- B. `n ≤ bal s u₁`
  - why: The statement already splits on the guard. When it fails, Stage 2's ledger is unchanged too, so no coverage is assumed.
  - mis: dp:S7
- C. `u₁ ≠ u₂`
  - why: With one account there are not two fields. Stage 2's `transfer` would move `n` from one field to the other, while Stage 3's self-transfer changes nothing.
- D. `Inv s`
  - why: The refinement is about two balances. It does not need the whole invariant, and the invariant does not supply it.
  - mis: dp:S4
:::

## Exit {minutes=4 kcs=KC-3.step-invariant}

:::item role=exit family=GEN-proof-structure template=t3 kcs=KC-3.step-invariant
@choice key=C
In the `move` branch of `step_preserves_inv`, `post_inv` needs `n ≤ bal s x` for the debited account. Which hypothesis supplies it?

- A. `Inv s`, the invariant before the step
  - why: `Inv s` says balances are non-negative now. It does not say the debit leaves them so.
  - mis: dp:G9
- B. `0 < n`, the amount's positivity
  - why: Positivity protects the credited account. It says nothing about the debit.
  - mis: dp:L4
- C. `HasType`, through `covers_sound`.
  - why: R-cover demands a guard conjunct for `x`, the step got past the guard, and `covers_sound` turns that into coverage.
- D. The successful result `exec … = .ok …` on its own.
  - why: Success only helps through the guard that typing put there. Without typing, the guard need not mention `x` at all.
  - mis: dp:S9
:::
