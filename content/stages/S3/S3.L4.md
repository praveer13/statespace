## A question first {minutes=3 kcs=KC-3.small-step-stuck}

The evaluator you just met answers every call. This lesson asks what that hides.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-3.small-step-stuck
@choice key=A
Your Lean evaluator is total: it returns a value on every input. Can a Mini-Plinth program still go wrong?

- A. Yes: a total evaluator must answer even where the semantics has no rule.
  - why: A total function must answer even for `balance(30)`. The small-step relation honestly has no rule for it.
- B. No: a total evaluator returns a value on every input, so nothing can go wrong.
  - why: Total means it always answers, not that the answer means anything.
  - mis: dp:S6
- C. Only if the program loops, because only a loop can go wrong.
  - why: Mini-Plinth has no loops. Going wrong here means a missing rule.
  - mis: dp:S8
:::

## One step at a time {minutes=11 kcs=KC-3.small-step-stuck}

Big-step evaluation gives only the final outcome. Small-step evaluation gives the journey: a relation that takes one step from a configuration to the next. A configuration is a program part-way through a run. A call moves through `bind` (arguments meet parameters), `checked`, `guard` and `run`, and ends in `done`, with a state, an output and effects, or in `err`, with a name. Expressions step left to right, and `balance(acct a)` steps to the literal `bal s a`.

`done` and `err` are final. A non-final configuration with no step is stuck: the relation has no rule for it. Stuck is not an error. An error is a defined outcome with a rule, and stuck is the absence of a rule.

A total evaluator hides the difference, because it must answer anyway: asked for `balance(30)`, a big-step lookup can read 0 and look fine. A relation cannot fake it, so it says honestly where the semantics stops, and typing's job is to keep programs away from that edge.

```lean
abbrev State := List (String × Int)

def bal (s : State) (a : String) : Int := (s.lookup a).getD 0

inductive E where
  | num  : Int → E
  | acct : String → E
  | bal  : E → E
  | ge   : E → E → E
  | tt   : E
  | ff   : E

/-- One small step of an expression, left to right. -/
inductive Step (s : State) : E → E → Prop
  | bal_acct (a : String) : Step s (.bal (.acct a)) (.num (bal s a))
  | bal_cong {e e' : E} : Step s e e' → Step s (.bal e) (.bal e')
  | ge_left {e₁ e₁' e₂ : E} : Step s e₁ e₁' → Step s (.ge e₁ e₂) (.ge e₁' e₂)
  | ge_right {n : Int} {e₂ e₂' : E} : Step s e₂ e₂' → Step s (.ge (.num n) e₂) (.ge (.num n) e₂')
  | ge_num (m n : Int) : Step s (.ge (.num m) (.num n)) (if n ≤ m then .tt else .ff)

/-- `balance(30)`: no rule applies, so there is no next expression. -/
theorem balance_num_stuck (s : State) (n : Int) : ∀ e', ¬ Step s (.bal (.num n)) e' := by
  intro e' h
  cases h with
  | bal_cong h' => cases h'
```

:::instrument ins=INS-interp cell=1 recorded=RUN-lean-stuck
A command whose guard reads the balance of an amount, called with typing bypassed.

```text
command Odd(from: account, to: account, amount: amount)
  requires balance(amount) >= amount
  do move amount from from to to

call Odd(a, b, 30)        -- typing bypassed
```

@direction
The trace view steps the call one rule at a time. Typing is bypassed, so nothing turns the program away before it runs.

@call key=B run=RUN-lean-stuck surprise=no
What does the relation do with `balance(30) >= 30`?

- A. It steps to `0 >= 30`: an unknown account reads as 0.
  - why: That default belongs to the big-step lookup, not to a rule.
  - mis: dp:S6
- B. Nothing: no rule applies.
  - why: `balance` steps only on an account value.
- C. It steps to `err unknownAccount`.
  - why: An error is a defined outcome with a rule, and here there is none.
  - mis: dp:S7

@after
The first step would have to evaluate `balance(30)`, and no rule covers a number there {{run:RUN-lean-stuck}}. The configuration is stuck. Typing's rule for `balance`, R-expr, would have turned the program away as `wrongType` before it ran.
:::

:::instrument ins=INS-interp cell=2 recorded=RUN-lean-bigsmall
A well-typed transfer that the guard refuses, under the first draft of the relation.

```text
start    mint -100 · a 100 · b 0
Transfer(a, b, 130)       -- draft relation: no rule yet for a false guard
```

@direction
The same view, on a program that passes typing. The guard is simply false.

@call key=B run=RUN-lean-bigsmall surprise=yes
Under the draft relation, where does this trace end?

- A. `err (guardFailed "Transfer")`
  - why: That is the big-step answer. The draft has no rule for a false guard, so the two semantics disagree.
  - mis: dp:S6
- B. Stuck at `guard false`.
  - why: The fix is a rule from `guard false` to `err (guardFailed ...)`, plus rules that carry an error outward.
- C. `done`, with a at -30.
  - why: A false guard never runs the body.
  - mis: dp:S9

@after
The program is well-typed and the guard is false, yet the draft relation has nowhere to go: the trace is stuck at `guard false` {{run:RUN-lean-bigsmall}}. The big-step evaluator answered `guardFailed` for the same call, so two semantics of one language disagree. The repair adds a rule from `guard false` to an `err` configuration, and rules that pass an error up.
:::

## Exit {minutes=4 kcs=KC-3.small-step-stuck}

:::item role=exit family=GEN-call-it template=t1 kcs=KC-3.small-step-stuck
@choice key=B
A well-typed call runs `release h` with `h` = 9, in a state that has no hold 9. How does the configuration end under the reference relation?

- A. It steps to `done`: releasing nothing is a no-op.
  - why: The run-time check for the hold comes first and refuses the call.
  - mis: dp:S12
- B. It ends in `err (unknownHold 9)`.
  - why: A missing hold is a checked run-time outcome with its own rule.
- C. It is stuck: there is no hold to release.
  - why: An error is a defined outcome, not the absence of a rule.
  - mis: dp:S7
:::
