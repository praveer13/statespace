## A question first {minutes=3 kcs=KC-3.abstract-syntax}

Stage 3 gives Mini-Plinth a meaning of its own, independent of SQL, Rust and any screen. The roadmap's toy syntax is `entity Account; command Transfer(from, to, amount); requires balance(from) >= amount; do move amount from from to to.` You will give programs like this a meaning without ever parsing them.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-3.abstract-syntax
@choice key=A
You skip parsing and build programs directly as AST values. Which problem can such a value never have?

- A. A missing closing parenthesis.
  - why: A tree has no parentheses, so no value can lack one.
- B. An amount used where an account is expected.
  - why: `balance(e)` takes any expression, so a typing rule has to reject this.
  - mis: dp:S5
- C. Two commands with the same name.
  - why: A list can repeat a name, so a well-formedness rule has to catch it.
  - mis: dp:S5
- D. A guard that is never true.
  - why: It is well-formed and well-typed. Only the semantics, or a search, shows it.
  - mis: dp:G4
:::

## Programs as trees {minutes=9 kcs=KC-3.abstract-syntax}

A parser turns text into a tree, and the semantics only reads the tree. Parsing adds no meaning, so you build the tree directly, as a Lean value. The Rust front end you write later parses the roadmap's text into this same tree.

Each kind of thing in Mini-Plinth is an inductive type: a closed list of the ways to make one.

```lean
inductive Ty where
  | account | amount | hold | int | bool

inductive Expr where
  | lit     : Int → Expr
  | var     : String → Expr
  | balance : Expr → Expr
  | frozen  : Expr → Expr
  | add     : Expr → Expr → Expr
  | sub     : Expr → Expr → Expr
  | ge      : Expr → Expr → Expr
  | eq      : Expr → Expr → Expr
  | and     : Expr → Expr → Expr
  | not     : Expr → Expr

inductive ResourceOp where
  | deposit : Expr → Expr → ResourceOp          -- deposit n to a
  | move    : Expr → Expr → Expr → ResourceOp   -- move n from x to y
  | hold    : Expr → Expr → ResourceOp          -- hold n on x
  | capture : Expr → Expr → ResourceOp          -- capture h to y
  | release : Expr → ResourceOp                 -- release h

inductive Stmt where
  | op  : ResourceOp → Stmt
  | set : String → Expr → Expr → Stmt           -- set f(x) := e

structure Cmd where
  name   : String
  params : List (String × Ty)
  guard  : Expr
  body   : Stmt
```

Lean checks the shape of what you build: `move` takes exactly three expressions, so a `move` with two is not a value. Mini-Plinth's own types, such as "this is an account", are a separate judgment, which you write next lesson.

Draft 0 of the state keeps each balance as a `Nat`, with a dashed note: ASSUMED [A], balances cannot go negative. The course offers it as a default; keep it or replace it.

The roadmap's Transfer as a tree, beside draft 0's state.

```lean
def transfer : Cmd :=
  { name   := "Transfer"
    params := [("from", .account), ("to", .account), ("amount", .amount)]
    guard  := .ge (.balance (.var "from")) (.var "amount")
    body   := .op (.move (.var "amount") (.var "from") (.var "to")) }

structure State0 where   -- draft 0
  balances : List (String × Nat)
```

@direction
The view draws `transfer` as a tree: what it relates, and what it leaves out.

@call key=A surprise=no
Can this AST represent `Transfer(a, a, 30)`, a transfer from an account to itself?

- A. Yes.
  - why: No syntax relates `from` to `to`. Allowing a self-transfer is a decision for the semantics.
- B. No: the AST forbids it.
  - why: The syntax cannot say "distinct". Two parameters are two names.
  - mis: dp:S5
- C. Only if the parser allows it.
  - why: There is no parser here. The tree is built directly.
  - mis: dp:S5

@after
Nothing in the tree says `from` and `to` differ. Whether a self-transfer commits, fails or does nothing is a decision for the semantics, and S3.L7 is where you make it.
:::

:::item role=segment family=GEN-call-it template=t4 kcs=KC-3.abstract-syntax
@choice key=A
Which statement about an AST-only design is true?

- A. A `deposit` with no amount cannot be built.
  - why: `deposit` takes two expressions, so a tree with one does not exist.
- B. A guard that compares an account with a number cannot be built.
  - why: `ge` takes two `Expr` values, and an account name is one. The typing rules, not the tree, tell them apart.
  - mis: dp:S5
- C. A `hold` on an account that does not exist cannot be built.
  - why: An account is a name in the tree. Whether the state has it is a run-time question.
  - mis: dp:S5
- D. A command that moves money from an account to itself cannot be built.
  - why: Nothing in the tree relates the two accounts, so the tree allows it.
  - mis: dp:S1
:::

## Shape is not meaning {minutes=8 kcs=KC-3.abstract-syntax}

A type index on `Expr` could make Lean reject `balance(amount)` itself, but then you could not see which Mini-Plinth rule fired. This course keeps the tree plain and writes the typing rules, so every rejection names its rule.

:::instrument ins=INS-goal-replay cell=2 recorded=RUN-lean-stuck
A command whose guard reads the balance of an amount.

```lean
def odd : Cmd :=
  { name   := "Transfer"
    params := [("from", .account), ("to", .account), ("amount", .amount)]
    guard  := .ge (.balance (.var "amount")) (.var "amount")
    body   := .op (.move (.var "amount") (.var "from") (.var "to")) }

#check odd
```

@direction
Lean elaborates `odd` against the types above, and the recorded output shows what it says.

@call key=A run=RUN-lean-stuck surprise=yes
Does Lean accept `balance(amount) >= amount` as a value of type `Expr`?

- A. Yes.
  - why: `balance` takes any `Expr`, and `amount` is one.
- B. No: `amount` is an amount, not an account.
  - why: That is Mini-Plinth's rule, not Lean's. Lean only checks the tree's shape.
  - mis: dp:S5

@after
Lean accepts it {{run:RUN-lean-stuck}}. The rule that `balance` takes an account is not Lean's to enforce here, so the tree stands. In S3.L4 this guard comes back as a program that cannot take a step.
:::

:::item role=segment family=GEN-call-it template=t4 kcs=KC-3.abstract-syntax
@choice key=C
A command's guard is `balance(amount) >= amount`. Which layer first has a rule that rejects it?

- A. Lean's elaborator, because the tree is not well-formed.
  - why: The tree is well-formed, as the cell showed.
  - mis: dp:S5
- B. A parser, because the text is not valid.
  - why: A grammar for expressions accepts `balance` of any expression.
  - mis: dp:S5
- C. The typechecker you write next lesson.
  - why: Its rule for `balance` asks for an account.
:::

:::item role=exit family=GEN-call-it template=t1 kcs=KC-3.abstract-syntax
@choice key=C
A command declares two parameters, both called `from`. In this course's rules, which layer rejects it?

- A. The AST's shape: a list cannot hold two entries with one name.
  - why: A list can repeat a name.
  - mis: dp:S5
- B. The parser: the text is misspelled.
  - why: The text is fine, and the tree has no text.
  - mis: dp:S5
- C. The typechecker: its parameter rule asks for distinct names.
  - why: Well-formedness is a judgment over the tree.
