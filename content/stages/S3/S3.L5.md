## A question first {minutes=3 kcs=KC-3.progress-preservation-scope}

Type safety is the headline result of most language courses. Here is what it is worth to a ledger.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-3.progress-preservation-scope
@choice key=B
Progress and preservation are proved for Mini-Plinth. Do those two theorems alone guarantee that well-typed Transfers keep balances non-negative?

- A. Yes: that is what type safety means.
  - why: Type safety is about steps and types, not about what a balance holds.
  - mis: dp:S4
- B. No: type safety rules out stuck states, not business violations.
  - why: The theorems speak of steps and types. R-cover and the step invariant carry balances.
- C. Only if the program terminates.
  - why: Termination is a separate property.
  - mis: dp:S8
:::

## Two theorems about steps {minutes=11 kcs=KC-3.progress-preservation-scope}

Type safety is two theorems. Progress says a well-typed configuration is either final or can take a step. Final means `done` or `err`, so a well-typed configuration is never stuck. Preservation says a step from a well-typed configuration lands on a well-typed one. Used together, a well-typed program is never stuck at any point of its run: each step keeps it well-typed, and a well-typed configuration that is not final always has a next step.

That is a real guarantee, and it has a precise edge. Both theorems are about steps and types. Neither mentions a balance, a hold's status or a guard's outcome. A well-typed call can still end in an error, because an error is a defined outcome and not a stuck state. The previous lesson drew that line.

The step invariant is a different kind of statement. It is about a state, and it needs R-cover, through a lemma named `covers_sound`, before it can say anything about a balance. Read the three side by side and ask what each one mentions.

:::instrument ins=INS-goal-replay cell=1 recorded=RUN-lean-progress
The statements, as the reference states them.

```lean
theorem progress     {c : Cfg}    : Typed c → Final c ∨ ∃ c', Step c c'
theorem preservation {c c' : Cfg} : Typed c → Step c c' → Typed c'

theorem step_preserves_inv :
    p.WellTyped → Inv s → exec p c s = .ok (s', o, es) → Inv s'
```

@direction
Goal Replay shows the statements read-only. None of them is yours to edit here.

@call key=C run=RUN-lean-progress surprise=yes
Delete R-cover from the typing rules. Which theorem stops being provable?

- A. `progress`, because an unguarded debit gets stuck.
  - why: An unguarded debit still steps. It only drives a balance negative.
  - mis: dp:S4
- B. `preservation`, because an unguarded debit loses its types.
  - why: An unguarded debit keeps its types.
  - mis: dp:S4
- C. Neither; only `step_preserves_inv` fails.
  - why: Only the step invariant mentions balances.
- D. Both, because both depend on R-cover.
  - why: Neither theorem depends on R-cover.
  - mis: dp:S9

@after
Without R-cover an unguarded debit still takes a step and its types still line up, so progress and preservation stand {{run:RUN-lean-progress}} {{run:RUN-lean-preservation}}. What breaks is `step_preserves_inv`: the move can drive a balance below zero, and that theorem alone speaks of balances.

Your own system has the same split. A typed API layer rules out whole families of mistakes before a request arrives, and a balance below zero is not one of them. That takes a guard, a check in the database or a proof like this stage's, and each is a separate piece of evidence. The overclaim to watch for is "the types check, so the ledger works."
:::

## Exit {minutes=4 kcs=KC-3.progress-preservation-scope}

:::item role=exit family=GEN-proof-structure template=t1 kcs=KC-3.progress-preservation-scope
@choice key=A run=RUN-lean-preservation
A preservation proof for the expression fragment goes by induction on the step. In the case where `balance(e)` steps to `balance(e')`, you hold `hstep : Step s e e'` and `ih : ∀ {t : Ty}, HasTy e t → HasTy e' t`, and you have introduced `ht : HasTy e.bal t`, with goal `HasTy e'.bal t`. After `cases ht with | bal h`, which goal is left?

- A. `h : HasTy e Ty.account ⊢ HasTy e'.bal Ty.int`
  - why: The typing rule for `balance` gives `h` for the inner expression and fixes the type to `Ty.int`. The goal stays about the stepped expression.
- B. `h : HasTy e Ty.account ⊢ HasTy e' Ty.int`
  - why: The stepped expression is still `balance(e')`, not `e'`.
  - mis: dp:L4
- C. `h : HasTy e Ty.account ⊢ HasTy e'.bal Ty.account`
  - why: `balance` returns a number, so the type is `Ty.int`.
  - mis: dp:L4
- D. `h : Step s e e' ⊢ HasTy e'.bal Ty.int`
  - why: `h` comes from the typing derivation, and `hstep` is the step.
  - mis: dp:L4
:::
