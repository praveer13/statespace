## Two questions first {minutes=4 kcs=KC-3.edge-cases-as-decisions,KC-3.nat-truncation}

Ask three engineers what a transfer does when the amount is zero, when sender and recipient are the same account, or when the sender cannot cover it, and you may get three confident answers. Your own system already has answers to these, chosen or not. This lesson makes them choices, and it shows what a quiet default can hide.

- A. The one that rejects.
  - why: "A self-transfer obviously works" assumes the answer. The sentence never says it.
  - mis: dp:L7

  - mis: dp:S1

## Four edge cases, four decisions {minutes=14 kcs=KC-3.edge-cases-as-decisions}

The roadmap's sentence says to move an amount from one account to another if the sender has enough. It does not say what happens when:

- the amount is zero;
- the sender and the recipient are the same account;
- the sender does not have enough;
- a balance outgrows what the integers can hold.

Each is an edge case, and each answer is a decision the sentence left open. The reference makes the decisions data. `Policy` has four fields:

| Field | Options | Reference default |
|---|---|---|
| `zero` | `reject`, `noop` | `reject` |
| `self` | `allow`, `reject` | `allow` |
| `guard` | `error`, `silent` | `error` |
| `overflow` | `unbounded`, `bounded maxBal` | `unbounded` |

Your evaluator implements one option per field and declares it as `Lab3.policy`. Because `exec` checks in a fixed order, you can answer any call from the semantics alone. The command exists. The arguments decode, and an amount must be positive: under `zero = noop`, a zero amount returns the unchanged state right here, before any account or guard is read. The accounts exist. A self-transfer is allowed or rejected. The guard holds or fails. The postings run, and under `bounded` a balance outside the bound is an `overflow`.

Read the defaults against what you know. Zero is a recorded change from Stage 2, whose guard admits `n = 0` as a transfer that changes nothing {{run:RUN-lean-ledger}}, while `Amount` is positive, so under `reject` a zero never reaches the guard. A self-transfer debits and then credits one account, reading the updated state, so `Transfer(a, a, 30)` leaves `a` alone. Stage 2's specimen computed both balances from the old state and turned 10 into 15 {{run:RUN-lean-selftransfer}}. The guard still runs first, so from `a = 10`, `Transfer(a, a, 15)` fails its guard. A failed guard is either an error value or a silent success that changes nothing. And an `Int` has no top, so by default nothing overflows. PostgreSQL's `bigint` does refuse an out-of-range step, with SQLSTATE {{run:RUN-pg-claims#values.e6_overflow_sqlstate}}.

Some questions the semantics never answers: how long a transfer waits for a lock, or how a screen rounds a balance. A semantics that answered them would stop being independent of the implementation. "The semantics does not decide this" is a real answer, and telling it apart from the four above is the test of this lesson.

## A seam under load {minutes=14 kcs=KC-3.nat-truncation}

In S3.L1 the course offered draft 0 with `Nat` balances and a dashed note: ASSUMED [A], balances cannot go negative. Everyone's cabinet keeps draft 0, so the note is there whatever you adopted. It is a seam, an assumption planted on purpose.

Before you run anything, say draft 0's claim from memory, in your own words: "balances are never negative, because they are `Nat`." Then call which part of a claim's strip would crack if that note were misleading.

:::item role=segment family=GEN-call-it template=t1 kcs=KC-3.nat-truncation
@choice key=B
If "balances are never negative, because they are `Nat`" turned out to mislead, which part of the claim's strip would crack?

- A. The proposition about the model.
  - why: The proposition stays true. In the model, no `Nat` balance is ever negative.
  - mis: dp:S2
- B. The correspondence between the model and money.
  - why: `Nat` is not the intended arithmetic, so the model stops corresponding to what the system does with money.
- C. The fit to the requirement.
  - why: The requirement still asks for non-negative balances. What fails is the model's picture of them.
  - mis: dp:S2
:::

This is an erosion: a seam you accepted in S3.L1 has cracked. The proposition still holds, and the requirement still asks for it. What cracks is the correspondence, because `Nat` subtraction is not the arithmetic of money: 30 - 50 is 0, not -20. Ask Z3 to show where the missing 20 goes. Model draft 0's payment with truncated subtraction over non-negative integers, and ask for a negative balance first.

:::instrument ins=INS-z3 cell=2 recorded=RUN-z3-nat-trunc
Draft 0's `Pay`: balances are non-negative, the amount is positive, and subtraction stops at 0.

```python
from z3 import *

a, b, n = Ints('a b n')
after_a = If(n <= a, a - n, 0)   # Nat subtraction stops at 0
after_b = b + n
base = [a >= 0, b >= 0, n > 0]   # Nat balances, a positive amount

s = Solver()
s.add(*base, Or(after_a < 0, after_b < 0))
print('negative balance:', s.check())

t = Solver()
t.add(*base, after_a + after_b != a + b)
print('total changed:   ', t.check())
```

@direction
Query asserts: a draft-0 payment after which some balance is negative. `sat` means such a payment exists. The second query asserts a payment after which the total moved.

@tap
no draft-0 payment leaves a balance below zero

@call key=B run=RUN-z3-nat-trunc surprise=yes
Z3 searches for a draft-0 `Pay` after which some balance is negative. What is its verdict?

- A. `sat`
  - why: Truncation makes a negative balance impossible, so the overdraft cannot show up as one.
  - mis: dp:S2
- B. `unsat`
  - why: Every balance after the payment is at or above zero, so no model exists. The overdraft hides in the total instead.
- C. `unknown`
  - why: A small linear integer query is decided outright.
  - mis: dp:Z2

@after
Z3 answered the first query in {{run:RUN-z3-nat-trunc}}, and the second is in the same run. The overdraft did not vanish. When the amount exceeds the balance, the sender gives up only what it holds and the recipient receives the whole amount, so the difference is created from nothing.[^1]

[^1]: A `sat` answer is graded by checking the witness's property, never its values. Your model may differ from the example of 50 from a balance of 30.
:::

The remedy has two parts: `Int` balances with a guard, as Stage 2's ledger had, and the refined `Amount` from S3.L2. With both, the changed-total query has no model, and a second solver, cvc5, agrees {{run:RUN-z3-nat-trunc}}.

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-3.nat-truncation

A witness for draft 0 is `Pay(from, to, 50)` from `from = 30`: the sender drops to 0, the recipient gains 50, and 20 is created. Which change removes every witness of this class, not just this one?

  - why: One witness dies and the class lives. `Pay(from, to, 31)` from 30 still creates 1.

- B. Keep `Nat` balances and guard every debit with `amount <= balance`.
  - why: `Pay` is fixed, but a `Nat` mint cannot go below 0. The first deposit truncates it at 0 and the total moves.

## Decisions travel {minutes=13 kcs=KC-3.edge-cases-as-decisions}

A decision is data, and it travels. The reference takes a `Policy`. Your evaluator implements one, and the edge-case goldens select their expected outcomes by the policy you declare. Changing a decision changes outcomes and what a caller or an observer can see, and it changes what every later component must do: the Stage 6 compiler, the Rust interpreter you write for the capstone, and anyone reading the logs.

It does not change the theorem. Under `guard = silent` a rejected call returns the unchanged state, under `zero = noop` a zero returns it too, and under `bounded` an overflow is an error. None of these can break `Inv`, so `step_preserves_inv` holds under every policy.

LAB-3.7 asks for one short record per decision: the decision, the alternative you considered, the consequence, and what downstream components must do. Each record also carries a `choice:` line that must match the matching field of `Lab3.policy`. A record that disagrees with the evaluator is a bug in your documents, and so is an evaluator that disagrees with its declared policy.

after    zero = reject · self = allow · guard = silent · overflow = unbounded
