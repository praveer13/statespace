## The unsafe command {minutes=8 kcs=KC-3.step-invariant}

So far every command kept the invariant. Add one that does not: `force move n from x to y`, a move with no cover requirement, so R-cover has nothing to say about it. Admit it as well-typed and a successful step can leave `Inv`.

That ends `step_preserves_inv` for the extended language. The reference states its negation as `cex_force`, and `decide` closes it {{run:RUN-lean-unsafe-cmd}}. A counterexample the kernel checked settles the matter, so do not hunt for a cleverer proof. Keep the broken command in `broken/`, beside a fix that removes `force move` or demands a covering guard.

:::instrument ins=INS-interp cell=1 recorded=RUN-lean-unsafe-cmd
The unsafe command, called from an empty balance.

```text
command ForcePay(from, to, amount)
  do force move amount from from to to

start    mint 0 · a 0 · b 0
  ForcePay(a, b, 1)
```

@direction
The interpreter evaluates `Inv` on the outcome of a successful call and shows which part fails.

@call key=B run=RUN-lean-unsafe-cmd surprise=no
Admit `force move` as well-typed. Can `step_preserves_inv` still be proved?

- A. Yes, with a cleverer proof.
  - why: No proof exists once a kernel-checked counterexample does. Reading a violation as a proof difficulty is a mistake.
  - mis: dp:O3
- B. No: a counterexample exists.
  - why: `cex_force` proves the negation by `decide`.
- C. Unknown until someone tries.
  - why: The counterexample settles it.
  - mis: dp:Z2

@after
The call commits and leaves `a` at -1, so non-negativity fails while the total stays 0. Any amount above the balance does the same {{run:RUN-lean-unsafe-cmd}}.
:::

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-3.step-invariant
@choice key=A
Every balance is 0. Which call to `ForcePay` makes a successful step that leaves `Inv`?

- A. `ForcePay(a, b, 1)`
  - why: It debits `a` below zero with no cover. The class is any amount above the balance.
- B. `ForcePay(mint, a, 1)`
  - why: `Inv` exempts the mint, so debiting it leaves `Inv` intact.
  - mis: dp:S9
- C. `ForcePay(a, a, 1)`
  - why: Debit, then credit, on one account changes nothing.
  - mis: dp:S1
- D. `ForcePay(a, b, 0)`
  - why: A zero amount is rejected at the boundary, so no step succeeds.
  - mis: dp:S14
:::

## Goldens as theorems {minutes=9 kcs=KC-3.goldens-as-theorems}

Comparator accepted your proof against the pinned statement. That checks the statement's text. The statement mentions your evaluator, `exec`, and you wrote it. Redefine `exec` to return `guardFailed` for every call and `step_preserves_inv` still holds, vacuously, because no call succeeds. Comparator checks against a challenge that copies your definitions, so it passes.

Goldens close the gap. A golden is a theorem, `theorem golden_k : exec p c s₀ = r := by decide`, whose right side comes from the reference. It is a theorem and not printed output because a closed `decide` proof adds no axiom, `native_decide` adds a `_native` one {{run:RUN-lean-axioms}}, and `#eval` can disagree with the kernel through `implemented_by` {{run:RUN-lean-implemented-by}}.

:::instrument ins=INS-bench-lean cell=2 recorded=RUN-lean-golden-redef
An evaluator redefined to reject every call, with one golden.

```lean
def exec (p : Program) (c : Call) (s : State) :
    Except Err (State × Output × List Effect) :=
  .error (.guardFailed c.name)

theorem golden_transfer_ok :
    exec refProgram transferCall s0 = .ok (s1, [], [.notify b]) := by
  decide
```

@direction
The recorded receipt runs two checks on this source: comparator against the pinned statement, and the goldens.

@call key=A run=RUN-lean-golden-redef surprise=yes
This evaluator returns `guardFailed` for every call. Which checks pass?

- A. Comparator only.
  - why: The statement matches and holds vacuously. The first golden that expects a commit evaluates to false.
- B. Comparator and the goldens.
  - why: A vacuous theorem does not make a golden true.
  - mis: dp:G4
- C. Neither.
  - why: Comparator checks against the frozen challenge, which copied this evaluator.
  - mis: dp:L3

@after
The redefined evaluator passes comparator and fails the golden {{run:RUN-lean-golden-redef}}. The course makes the same kind of claim about the interpreter in this tab: that it agrees with the Lean reference on its goldens. That is a seam the course plants on itself, and it is tested the same way.
:::

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-3.goldens-as-theorems
@choice key=B
A mutant evaluator computes both posting balances from the old state. Under the default policy, which call separates it from the goldens?

- A. `Transfer(a, b, 5)` from `a = 10`, `b = 0`
  - why: With two accounts the old and new state agree, so both evaluators return the same state.
  - mis: dp:X1
- B. `Transfer(a, a, 5)` from `a = 10`
  - why: The reference leaves `a` at 10. The mutant credits from the old balance and returns 15.
- C. `Transfer(a, ghost, 5)`
  - why: Both return `unknownAccount ghost` before any posting runs.
  - mis: dp:X1
- D. `Transfer(a, b, 50)` from `a = 10`
  - why: Both fail the guard before any posting runs.
  - mis: dp:X1
:::
