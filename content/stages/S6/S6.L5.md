## The check runs at commit {minutes=18 kcs=KC-6.enforce-at-commit}

Your compiled Transfer writes two legs to `postings(cmd, acct, amt)`, and `acct.bal` is a cached balance. The invariant from S4 has two parts: each `bal` equals the sum of its postings, and each command's postings sum to zero. Transfer's proof obligation is discharged per command, as in S4. A command an agent proposes, such as "adjust this balance", has none, so you enforce the invariant when the transaction commits.

:::item role=prequestion family=GEN-find-the-witness template=t1 kcs=KC-6.enforce-at-commit
@choice key=C
`SELECT sum(amt) FROM postings WHERE acct = 3`, and account 3 has no postings. The result is:

- A. 0
  - why: The manual says "sum of no rows returns null, not zero as one might expect".
  - mis: dp:Q9
- B. No row at all, not even NULL.
  - why: Without GROUP BY, an aggregate returns exactly one row.
  - mis: dp:Q8
- C. NULL
  - why: An aggregate over no rows has no value to report, and `sum` reports NULL {{run:RUN-pg-sum-null}}.
- D. An error.
  - why: An empty input is not an error.
  - mis: dp:Q10
:::

A constraint trigger can run at commit. This one is `AFTER UPDATE`, `DEFERRABLE INITIALLY DEFERRED` and `FOR EACH ROW`: it fires per updated row, and PostgreSQL holds it until the end of the transaction. It raises when the new balance differs from the sum of the postings.

:::instrument ins=INS-pglite cell=1 recorded=RUN-pg-sum-null
Account 1 holds 100 with a posting to match. Account 3 holds 0 and has no postings. The command adjusts account 3 to 500 and writes no postings.

```sql
CREATE TABLE acct (id int PRIMARY KEY, bal bigint NOT NULL CHECK (bal >= 0));
CREATE TABLE postings (cmd int NOT NULL, acct int NOT NULL, amt bigint NOT NULL);
INSERT INTO acct VALUES (1, 100), (3, 0);
INSERT INTO postings VALUES (0, 1, 100);

CREATE FUNCTION check_balance() RETURNS trigger AS $$
BEGIN
  IF NEW.bal <> (SELECT sum(amt) FROM postings WHERE acct = NEW.id) THEN
    RAISE EXCEPTION 'balance % does not match its postings', NEW.bal;
  END IF;
  RETURN NULL;
END $$ LANGUAGE plpgsql;

CREATE CONSTRAINT TRIGGER acct_balance AFTER UPDATE ON acct
  DEFERRABLE INITIALLY DEFERRED FOR EACH ROW EXECUTE FUNCTION check_balance();

BEGIN;
UPDATE acct SET bal = 500 WHERE id = 3;
COMMIT;
SELECT id, bal FROM acct ORDER BY id;
```

@direction
Read what COMMIT reports and what the last SELECT shows for account 3.

@call key=D surprise=yes run=RUN-pg-sum-null
The adjust command sets account 3's balance to 500 and writes no postings. Account 3 never had any. At COMMIT the check:

- A. Raises, and the transaction rolls back.
  - why: This treats a missing sum as a mismatch. A missing sum is NULL, and a NULL comparison is unknown, not true.
  - mis: dp:Q9
- B. Does not fire, because no posting was inserted.
  - why: The trigger sits on `acct`, which the command updated, so it fires.
  - mis: dp:Q10
- C. Raises an out-of-range error on 500.
  - why: Nothing here overflows.
  - mis: dp:Q6
- D. Passes, and 500 is minted.
  - why: The subquery is NULL, `500 <> NULL` is unknown, and an unknown IF condition does not raise.

@after
The check ran, saw an unknown, and let the commit through. Account 3 now holds money that no posting backs. {{run:RUN-pg-sum-null}}
:::

The fix treats "no postings" as zero and never returns unknown: `NEW.bal IS DISTINCT FROM coalesce((SELECT sum(amt) ...), 0)`. A second deferred trigger, on `postings`, requires each command's postings to sum to zero. Together they are the invariant, written so that a NULL cannot hide a mismatch.

:::instrument ins=INS-pglite cell=2 call=false recorded=RUN-pg-enforce-commit
Free run. The same mint, a proper transfer, and a one-legged command.

```sql
CREATE TABLE acct (id int PRIMARY KEY, bal bigint NOT NULL CHECK (bal >= 0));
CREATE TABLE postings (cmd int NOT NULL, acct int NOT NULL, amt bigint NOT NULL);
-- command 0 is the opening deposit; every later command must net to zero
INSERT INTO acct VALUES (1, 100), (3, 0);
INSERT INTO postings VALUES (0, 1, 100);

CREATE FUNCTION check_balance() RETURNS trigger AS $$
BEGIN
  IF NEW.bal IS DISTINCT FROM coalesce((SELECT sum(amt) FROM postings WHERE acct = NEW.id), 0) THEN
    RAISE EXCEPTION 'balance % does not match its postings', NEW.bal;
  END IF;
  RETURN NULL;
END $$ LANGUAGE plpgsql;

CREATE FUNCTION check_zero_sum() RETURNS trigger AS $$
BEGIN
  IF NEW.cmd > 0 AND coalesce((SELECT sum(amt) FROM postings WHERE cmd = NEW.cmd), 0) <> 0 THEN
    RAISE EXCEPTION 'command % posts a nonzero total', NEW.cmd;
  END IF;
  RETURN NULL;
END $$ LANGUAGE plpgsql;

CREATE CONSTRAINT TRIGGER acct_balance AFTER UPDATE ON acct
  DEFERRABLE INITIALLY DEFERRED FOR EACH ROW EXECUTE FUNCTION check_balance();
CREATE CONSTRAINT TRIGGER postings_zero_sum AFTER INSERT ON postings
  DEFERRABLE INITIALLY DEFERRED FOR EACH ROW EXECUTE FUNCTION check_zero_sum();

-- adjust: set account 3 to 500 and write no postings
BEGIN;
UPDATE acct SET bal = 500 WHERE id = 3;
COMMIT;

-- a proper transfer: two legs, two balances
BEGIN;
INSERT INTO postings VALUES (1, 1, -30), (1, 3, 30);
UPDATE acct SET bal = bal - 30 WHERE id = 1;
UPDATE acct SET bal = bal + 30 WHERE id = 3;
COMMIT;

-- a one-legged command: a debit and its posting, no credit leg
BEGIN;
INSERT INTO postings VALUES (2, 1, -20);
UPDATE acct SET bal = bal - 20 WHERE id = 1;
COMMIT;

SELECT id, bal FROM acct ORDER BY id;
```

@direction
Free run. Read which statement raises for each command, and the final balances.
:::

A delta check is the inductive step run at commit. It examines only what this transaction changed, so it holds the invariant only if the invariant held before. That base case is an assumption, and your claim says so. The claim is stamped `ENFORCED [E]` with where it runs: deferred constraint triggers on `acct` and `postings`, at commit {{run:RUN-pg-enforce-commit}}. A check that balances stay non-negative across rows other transactions write has the check-then-write shape that S6.L6 takes apart, so it stays `NOT COVERED [N]`. S6.L6 and S6.L7 return to it with SERIALIZABLE and retries.

## Exit {minutes=3 kcs=KC-6.enforce-at-commit}

:::item role=exit family=GEN-find-the-witness template=t1 kcs=KC-6.enforce-at-commit
@choice key=A
Let `s` stand for `(SELECT sum(amt) FROM postings WHERE acct = NEW.id)`. A check raises when its expression is true. Which expression lets an unposted balance of 500 through?

- A. `NOT (NEW.bal = s)`
  - why: `500 = NULL` is unknown and `NOT unknown` is unknown, so it never raises.
- B. `NEW.bal IS DISTINCT FROM coalesce(s, 0)`
  - why: `500` is distinct from `0`, so it raises.
  - mis: dp:Q9
- C. `NEW.bal <> coalesce(s, 0)`
  - why: `coalesce` turns the missing sum into 0, so `500 <> 0` is true and it raises.
  - mis: dp:Q9
- D. `coalesce(NEW.bal <> s, true)`
  - why: `coalesce` turns the unknown into true, so it raises.
  - mis: dp:Q9
:::
