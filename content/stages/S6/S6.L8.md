## Before you check {minutes=2 kcs=KC-6.refinement-relation,KC-6.abstract-serializability}

Until now you compared outcomes: the interpreter said one thing, PostgreSQL said another, and you counted the cases where they differed. This lesson asks for something sharper. You will write a relation between the states of your reference semantics and the states of the database, then check that every step the database takes is matched by a step the semantics could take.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-6.refinement-relation
@choice key=C
For a committed transaction that takes the database from D to D′, which question does Stage 6 ask?

- A. Is D′ equal to S′, row for row, after the commit?
  - why: R relates states of different shape: rows, ids, NULLs, postings. D′ and S′ are never equal. The relation links them.
  - mis: dp:Q14
- B. Did every statement report one row?
  - why: Rowcounts feed the check, but they are not the relation.
  - mis: dp:Q10
- C. Is there a legal abstract step from S to S′ with R(S′, D′)?
  - why: That is the roadmap's question: some legal step of the reference semantics, from a state related to D, ends in a state related to D′.
- D. Does D′ satisfy every CHECK constraint?
  - why: Constraints restrict D and say nothing about S. A state can satisfy every CHECK and still not be what the semantics would have produced.
  - mis: dp:Q2
:::

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-6.abstract-serializability
@choice key=D
Two SERIALIZABLE transactions committed, txn B first, then txn A. In which order do you replay them through the reference semantics?

- A. Commit order, since commits are serialized.
  - why: Two-phase locking makes commit order match the apparent serial order. PostgreSQL's SERIALIZABLE is built on snapshots, and there the order need not match (Ports and Grittner, PVLDB 5(12), 2012, §7.2, read 2026-10-23).
  - mis: dp:Q13
- B. Start order, since snapshots begin there.
  - why: Start order is no better. A transaction that started first can still belong last.
  - mis: dp:Q13
- C. Both orders, which must agree.
  - why: One order is enough. The guarantee is "the same effect as if they were run one at a time" (§13.2.3, read 2026-10-23).
  - mis: dp:Q13
- D. Any order that reproduces every committed output.
  - why: That is the guarantee, checked: some serial order exists in which each transaction gets the output it actually returned.
:::

## One square at a time {minutes=15 kcs=KC-6.refinement-relation}

The two kinds of state do not look alike. An abstract state S maps account ids to balances. A database state D is tables of rows, with NULLs and, since S6.L5, postings. R(S, D) says which databases stand for which abstract states, in two parts.

- `wf(D)` says a database state means something at all: every `bal` is non-null and at least 0, and each balance matches its postings.
- `α(D)` is the abstract state that a well-formed D stands for: the map from each account id to its `bal`.
- `R(S, D)` holds when `wf(D)` holds and `S = α(D)`.

A state with a NULL balance has no S at all, because `wf` fails. That is why the `NOT NULL` of S6.L2 keeps every reachable D inside R.

The simulation square checks one transaction t at a time. Start from R(S, D). Let c be the command t was running, and let D → D′ be what t did to the database. What the semantics must say depends on how t ended.

| How t ended | What the reference semantics must say |
|---|---|
| Committed | `interp(c, S)` is `Ok(S′, out)`, with `S′ = α(D′)` and `out` equal to the old and new pairs t reported |
| Refused by its guard, with a typed outcome | `interp(c, S)` is `Err e`, with `D′ = D` and `e` the typed outcome t returned |
| Aborted and retried, or `GaveUp` | No abstract step: `D′ = D`, a stutter |

Here are two recorded transactions through the square, with account 1 at 100 and account 2 at 50.

| Transaction | α(D) before | The interpreter from S | α(D′) after | Square |
|---|---|---|---|---|
| `Transfer(1, 2, 30)` commits; pairs `1: 100 → 70` and `2: 50 → 80` | `{1: 100, 2: 50}` | `Ok`, `S′ = {1: 70, 2: 80}`, same pairs | `{1: 70, 2: 80}` | holds |
| `Transfer(1, 2, 500)`: the debit matched 0 rows on an account that exists | `{1: 70, 2: 80}` | `Err Insufficient` | `{1: 70, 2: 80}`, since `D′ = D` | holds |

Now a third transaction, which you call before the checker does. Account 3 holds the largest `bigint`, and the reference semantics has unbounded integers.

:::instrument ins=INS-interp cell=1 recorded=RUN-pg-claims
The three transactions through the square. The first two are the table above.

```text
alpha(D)  = the map from each account id to its bal
wf(D)     = every bal is not NULL and is at least 0
R(S, D)   = wf(D) and S = alpha(D)

semantics   the pinned reference: integers are unbounded
D0          acct 1: 100, acct 2: 50, acct 3: the largest bigint

t1  Transfer(1, 2, 30)    committed    pairs  acct 1: 100 -> 70,  acct 2: 50 -> 80
t2  Transfer(1, 2, 500)   refused      the debit matched 0 rows on an account that exists
t3  Transfer(1, 3, 10)    rolled back  the credit to account 3 raised an out-of-range error
```

@direction
Check asserts: for each transaction, the reference semantics' step from S matches what the database did, under the three rules of the square. The verdict for each transaction is `holds` or `fails`.

@call key=B surprise=no run=RUN-pg-claims
Under the pinned reference semantics, which verdict does the square give for t3?

- A. Holds: an abort matches a stutter.
  - why: The model commits this transfer, so there is no stutter on the abstract side to match the database's rollback.
  - mis: dp:P1
- B. Fails: the model takes a step the database refused.
  - why: With unbounded integers the interpreter commits, and the database raised an out-of-range error and rolled back. S′ has the credit, and α(D′) does not.
- C. Fails: the database took a step the model forbids.
  - why: The database took no step. It rolled back.
  - mis: dp:P1
- D. Skipped: aborted transactions are not checked.
  - why: Aborts are checked, as stutters, and this one fails the check.
  - mis: dp:P1

@after
The database refused the credit and left the balance as it was {{run:RUN-pg-claims}}, so `D′ = D`. The interpreter committed, so `S′` holds the credit and `α(D′)` does not: the square fails.

Two directions matter here, and it matters which one fails. First: every committed database step has a legal abstract step with matching outputs. That is the roadmap's question, and it says the implementation stays inside the model. Second: every abstract step that commits has a database step that commits, up to retryable aborts. That one is about availability, because the database must not refuse what the model allows. The out-of-range credit breaks the second. So does `GaveUp`, on purpose, and it says so: a command that runs out of retries is an outcome the semantics lacks, and R places it as a stutter.
:::

:::item role=segment family=GEN-find-the-witness template=t3 kcs=KC-6.refinement-relation
@choice key=C
You weaken R so that it compares only totals: it holds when the abstract balances and `α(D′)` have the same sum. Which sequential history does this weak R accept although the full R rejects it?

- A. `Transfer(1, 2, 30)` commits in both, with matching old and new pairs.
  - why: The full R accepts it too: `S′ = α(D′)` and the pairs match. A witness must pass the weak R and fail the full one.
  - mis: dp:Q14
- B. The database commits the debit of `Transfer(1, 2, 30)` and loses the credit, so 30 vanishes.
  - why: The total changes by 30, so the weak R rejects it as well. A witness has to slip past the totals.
  - mis: dp:Q14
- C. The database credits account 3 instead of account 2, and the total is unchanged.
  - why: The totals match, so the weak R accepts. `S′` has the credit on account 2 and `α(D′)` has it on account 3, so the full R rejects.
- D. The database rolls back a transfer that the model also refuses with `Insufficient`.
  - why: Both relations accept this: the refusal matches and `D′ = D`.
  - mis: dp:P1
:::

## Some serial order {minutes=15 kcs=KC-6.abstract-serializability}

A single transaction's square is easy: one step of the database, one step of the semantics. Concurrency breaks that. When transactions overlap there is no single D to start each one from, and the database has not told you in which order to explain them. So the question changes from "is this step matched?" to "is there some order in which the steps could have run one at a time and given everyone the outputs they actually got?"

That is abstract serializability, and the check is a search. It takes the committed transactions, tries serial orders, and replays each through the reference semantics from `α(D₀)`. An order passes when every transaction's replayed output equals the output it committed with: its old and new pairs from `RETURNING`, and its typed outcome. Aborted attempts are stutters and are skipped. Two things keep the search small: the write order that old and new values reveal (a transaction that read 100 and wrote 20 came before one that read 20), and what each transaction read from whom. The search is still bounded: it handles at most 8 transactions and prints that bound with every verdict.

Read the two answers differently. A rejection shows an anomaly in this history, because no order explains it. An acceptance shows only that this history had a serial explanation. It does not show that the database will always provide one.

Take the history from S6.L6 where both withdrawals went through at READ COMMITTED. Make your call, then replay.

:::instrument ins=INS-history cell=2 recorded=RUN-pg-claims
The read-modify-write history from S6.L6, as the serial-order checker reads it.

```text
-- history: read-modify-write at READ COMMITTED, one account holding 100
-- the abstract command of each transaction: Debit(1, 80)

txn A   read 100;  its UPDATE returned old 100, new 20;   committed
txn B   read 100;  its UPDATE returned old 20,  new 20;   committed

search  serial orders of the 2 committed transactions, each replayed from alpha(D0) = {1: 100}
bound   at most 8 transactions
```

@direction
Check asserts: some serial order, replayed through the reference semantics, gives each transaction the output it committed with. The checker prints its bound beside its verdict.

@call key=D surprise=no run=RUN-pg-claims
Txn A and txn B each read 100 and debited 80, and both committed. Does a serial order reproduce both outputs?

- A. Yes: txn A, then txn B, as committed.
  - why: Run txn A first and txn B meets a balance of 20. Its guard refuses the debit, yet txn B committed one.
  - mis: dp:Q13
- B. Yes: txn B, then txn A.
  - why: Whichever runs second meets a balance of 20 and is refused, yet both committed a debit.
  - mis: dp:Q13
- C. It cannot be told without commit timestamps.
  - why: Outputs decide, not clocks. The check never needs a timestamp.
  - mis: dp:Q11
- D. No: in either order the second debit is refused.
  - why: The history is rejected, so an anomaly is present. It is the lost update from S6.L6.

@after
The checker rejects the history, after trying both orders {{run:RUN-pg-claims}}. With txn A first, its debit takes the balance from 100 to 20. Txn B then meets 20, its guard fails, and the reference semantics refuses it, but txn B was told it updated a row. Txn B first fails the same way. The rejection is the anomaly: no serial explanation exists.
:::

:::item role=segment family=GEN-find-the-witness template=t3 kcs=KC-6.abstract-serializability
@choice key=A
The conditional UPDATE compilation at SERIALIZABLE, one account holding 100, two debits of 80. Txn A commits its debit, taking the balance to 20. Txn B's first attempt fails with a serialization failure. Txn B runs again from BEGIN: its statement updates 0 rows, and it commits. What does the checker answer?

- A. Txn A, then txn B: the retry is refused by its guard, as the reference semantics refuses it.
  - why: Txn B's failed attempt is a stutter and is skipped. In the order A, B the second debit meets 20 and is refused, which is what the committed retry reported.
- B. Txn B, then txn A, because txn B started first.
  - why: With txn B first its debit would succeed, but the retry reported 0 rows. Start order is not the serial order.
  - mis: dp:Q13
- C. None: the failed attempt leaves a hole that no order fills.
  - why: An aborted attempt changes nothing in the database, so the check treats it as a stutter.
  - mis: dp:P1
- D. None: both transactions touched the same row.
  - why: Many serializable histories touch one row. What matters is whether some order reproduces the outputs.
  - mis: dp:Q11
:::

## Two orders for one history {minutes=12 kcs=KC-6.abstract-serializability}

One more thing to unlearn is that the serial order is the order in which transactions committed. With two-phase locking the two usually agree. PostgreSQL's SERIALIZABLE is built on snapshots, so a transaction can read an old state, commit last, and still belong first in the serial order.

Take a report that reads two accounts while a transfer commits between the two reads. At SERIALIZABLE the report's snapshot is taken at its first read, so it sees the state from before the transfer for both accounts. It is a consistent report of an older state, and it commits after the transfer. Make your call, then replay.

:::instrument ins=INS-history cell=3 recorded=RUN-pg-catalog
A report and a transfer at SERIALIZABLE (catalog row H04). Accounts 1 and 2 hold 100 each.

```text
-- history: report before transfer, SERIALIZABLE; every committed state totals 200

txn A (report)    read acct 1 -> 100
txn B (transfer)  move 50 from 1 to 2;  pairs  acct 1: 100 -> 50,  acct 2: 100 -> 150
txn B             COMMIT                           -- txn B commits first
txn A (report)    read acct 2 -> 100               -- still read from its snapshot
txn A             COMMIT                           -- txn A commits last

search  serial orders of the 2 committed transactions, each replayed from alpha(D0) = {1: 100, 2: 100}
bound   at most 8 transactions
```

@direction
Check asserts: some serial order, replayed through the reference semantics, gives each transaction the output it committed with. The checker also replays the commit order and reports what it finds.

@call key=C surprise=yes run=RUN-pg-catalog
Replayed in commit order, txn B then txn A, does the checker accept the history?

- A. Yes: commit order is the serial order.
  - why: Replayed in commit order, the report would read 50 and 150 after the transfer. It reported 100 and 100.
  - mis: dp:Q13
- B. No: the history has a lost update.
  - why: Nothing was overwritten, because txn A only read.
  - mis: dp:Q16
- C. No: the report fits only an order with the report first.
  - why: Txn A reported 100 and 100, the state before the transfer. After the transfer it would read 50 and 150. The order A, B reproduces it, though txn B committed first.
- D. No: PostgreSQL must have aborted txn A.
  - why: Nothing was aborted. The history has a serial explanation that differs from its commit order.
  - mis: dp:Q13

@after
Both committed {{run:RUN-pg-catalog}} (row H04), and the checker accepts the history under the order txn A, then txn B. The commit order and the serial order are different things, and the checker searches for the second. A checker that replayed in commit order would reject a history that has a serial explanation. That is one of the ways your own relation can fail: it is a witness for the claim below.
:::

:::item role=segment family=GEN-anomaly-id template=t3 kcs=KC-6.abstract-serializability
@choice key=A
The same report and transfer, now at READ COMMITTED. Txn A reads account 1 (100). Txn B's transfer of 50 commits. Txn A reads account 2 (150) and commits. What class is this history, and what does the checker say?

- A. Read skew: no serial order reproduces what txn A reported.
  - why: Txn A saw 100 and 150, which is neither the state before the transfer (100 and 100) nor the state after it (50 and 150). The checker rejects the history.
- B. No anomaly: txn A, then txn B explains it.
  - why: In that order the report would read 100 and 100. It reported 150 for account 2.
  - mis: dp:Q13
- C. Lost update: txn B's write overwrote txn A's.
  - why: Txn A only read, so nothing of its was overwritten.
  - mis: dp:Q16
- D. Write skew: both transactions wrote rows the other had read.
  - why: Only txn B wrote.
  - mis: dp:Q16
:::

## Exit {minutes=8 kcs=KC-6.refinement-relation,KC-6.abstract-serializability}

Put the two checks together and you have R for a whole system: the square for each committed transaction of a sequential history, and the serial-order search for a concurrent one. Both are bounded, and the search prints its bound with every verdict. In LAB-6.7 you will write α, wf and R, run the checker over a fixed set of recorded histories {{run:RUN-serializability-fixtures}}, and mint the claim below: R holds on every checked history, TESTED [T] · n histories · the search bound. For a history nobody checked, the claim rests on two assumptions that S6.L9 writes out.

::claim template=CL-6.3

byzantine's linearizability checker searches for an order the same way, and drawer D-21 has a one-page sketch of it.

:::item role=exit family=GEN-call-it template=t1 kcs=KC-6.refinement-relation
@choice key=B
Suppose your system took remedy 2 from S6.L4: the semantics returns `Err Overflow` for a credit past the largest `bigint`. The database raises an out-of-range error on the same credit and rolls back. What does the square say?

- A. Fails on the first direction: the database committed a step with no legal abstract step.
  - why: The database committed nothing. It rolled back.
  - mis: dp:P1
- B. Holds: both sides refuse, `D′ = D`, and the typed outcome is the same on both.
  - why: The remedy moved the failure out of the square and into the outcome type. The interpreter says `Overflow`, and the compile maps the database's error to `Overflow`.
- C. Fails on the second direction: the model commits where the database refuses.
  - why: That was the verdict under unbounded integers. Under remedy 2 the model refuses too.
  - mis: dp:P1
- D. Skipped: the database aborted, so there is nothing to check.
  - why: Aborts are checked as stutters, and this one is a refusal with a typed outcome.
  - mis: dp:P1
:::

:::item role=exit family=GEN-find-the-witness template=t3 kcs=KC-6.abstract-serializability
@choice key=D
Two accounts hold 100 each, in one team. At REPEATABLE READ, txn A reads the team total, 200, and debits 150 from account 1. Txn B reads the same total and debits 150 from account 2. Both commit. Give a serial order that reproduces every committed output, or answer none.

- A. Txn A, then txn B.
  - why: Run txn B second and its guard sees a total of 50. It refuses the debit and updates nothing, yet it committed a debit.
  - mis: dp:Q13
- B. Txn B, then txn A.
  - why: The same problem, mirrored: whichever runs second would be refused.
  - mis: dp:Q13
- C. None: an aborted transaction leaves no order.
  - why: Nothing aborted here. Both transactions committed.
  - mis: dp:P1
- D. None: whichever runs second would be refused, yet both committed.
  - why: Each debit passed only because the other had not happened yet. No order lets both pass, so the history is rejected.
:::
