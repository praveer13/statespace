## Before you replay {minutes=2 kcs=KC-6.compilation-pattern,KC-6.anomaly-isolation}

Your compiler from S6.L2 turns a debit into SQL. This lesson asks what happens when two sessions run that SQL at the same time, and the answer depends on how you compiled it. If you already know the isolation levels and the anomalies they allow, a finished concurrency lesson in tablespace counts as evidence of the basics, and drawer D-11 is a one-page recap if you want it.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-6.compilation-pattern
@choice key=A
Two sessions each withdraw 80 from a balance of 100 under READ COMMITTED. What decides whether 160 can be spent?

- A. How each withdrawal is compiled.
  - why: At one level, a read-modify-write can spend 160 while a conditional UPDATE loses nothing. The recorded runs in this lesson show both.
- B. The isolation level alone.
  - why: The level is the same in both compilations, and the results differ.
  - mis: dp:Q4
- C. Whether the sessions share a connection.
  - why: Each session has its own connection, which is what makes the two concurrent. One shared connection would run the steps in a single order.
  - mis: dp:C1
- D. How far apart in time they run.
  - why: The order of the steps decides, at any speed. A fast pair and a slow pair with the same interleaving give the same result.
  - mis: dp:Q11
:::

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-6.anomaly-isolation
@choice key=D
Under REPEATABLE READ, two transactions each read "available = 100" and insert a hold of 80. Can both commit?

- A. No: one fails with a serialization failure.
  - why: REPEATABLE READ aborts conflicting writes to one row. These two inserts are different rows.
  - mis: dp:Q5
- B. No: they deadlock.
  - why: Nobody waits on a lock here, so there is nothing to deadlock on.
  - mis: dp:C2
- C. Only if the holds are on different accounts.
  - why: Both holds were on account 1, and both still committed.
  - mis: dp:Q4
- D. Yes.
  - why: Both committed, with 160 held against a balance of 100. Each transaction read a snapshot that did not include the other's hold.
:::

## Two withdrawals, two compilations {minutes=15 kcs=KC-6.compilation-pattern}

You have met this bug in a model. In Stage 5 you split a transfer into a read and a write, and TLC found two withdrawals of 80 that both went through against a balance of 100 {{run:RUN-tlc-doublespend}}. Making the guard and the write one atomic action removed the bug {{run:RUN-tlc-atomic}}. SQL gives you the same two shapes, and the isolation level does not choose between them for you. Your compiler does.

Here are two compilations of one debit of 80 from account 1.

```sql
-- Compilation 1: read-modify-write
SELECT bal FROM acct WHERE id = 1;          -- the application reads 100
-- the application checks 100 >= 80 and computes 20
UPDATE acct SET bal = 20 WHERE id = 1;      -- and writes the constant it computed

-- Compilation 2: conditional UPDATE
UPDATE acct SET bal = bal - 80 WHERE id = 1 AND bal >= 80;
```

The schema, the amount, the level and the two sessions are the same in both. Two PostgreSQL facts decide what happens when both sessions run at once. An UPDATE locks the row it changes, so a second UPDATE of that row waits until the first transaction ends. And under READ COMMITTED, when that wait ends in a commit, the waiting statement does not simply carry on: the manual says "The search condition of the command (the WHERE clause) is re-evaluated to see if the updated version of the row still matches" (§13.2.1, read 2026-10-23).

Every outcome on this page was recorded on PostgreSQL {{run:RUN-pg-claims#version}}. Make your call on the conditional UPDATE first. The cell then lets you replay the read-modify-write beside it.

:::instrument ins=INS-history cell=1 recorded=RUN-pg-claims
Both compilations at READ COMMITTED, one account holding 100, two sessions each debiting 80. The first permutation replays the conditional UPDATE. The second replays the read-modify-write.

```text
-- level: READ COMMITTED; account 1 holds 100; each session debits 80
setup { CREATE TABLE acct (id int PRIMARY KEY, bal bigint NOT NULL); INSERT INTO acct VALUES (1, 100); }

-- compilation 2: conditional UPDATE, the guard and the write in one statement
session a
step a_begin  { BEGIN ISOLATION LEVEL READ COMMITTED; }
step a_debit  { UPDATE acct SET bal = bal - 80 WHERE id = 1 AND bal >= 80; }
step a_commit { COMMIT; }

session b
step b_begin  { BEGIN ISOLATION LEVEL READ COMMITTED; }
step b_debit  { UPDATE acct SET bal = bal - 80 WHERE id = 1 AND bal >= 80; }   -- waits for a's row lock
step b_commit { COMMIT; }

-- compilation 1: read-modify-write, the client computes the new balance
session c
step c_begin  { BEGIN ISOLATION LEVEL READ COMMITTED; }
step c_read   { SELECT bal FROM acct WHERE id = 1; }
step c_write  { UPDATE acct SET bal = 20 WHERE id = 1; }   -- the client checked 100 >= 80 and computed 20
step c_commit { COMMIT; }

session d
step d_begin  { BEGIN ISOLATION LEVEL READ COMMITTED; }
step d_read   { SELECT bal FROM acct WHERE id = 1; }
step d_write  { UPDATE acct SET bal = 20 WHERE id = 1; }   -- the same constant, from its own read
step d_commit { COMMIT; }

permutation a_begin a_debit b_begin b_debit a_commit b_commit
permutation c_begin c_read d_begin d_read c_write d_write c_commit d_commit
```

@direction
Replay shows: the same two debits compiled two ways. In both, the second session's write waits for the first session's row lock. Compare what each second session is told when its wait ends.

@call key=C surprise=yes run=RUN-pg-claims
In the conditional UPDATE, txn B's statement waits on txn A's row lock. Txn A commits. Txn B then:

- A. Fails with a serialization failure and rolls back.
  - why: That is REPEATABLE READ's behaviour. This cell runs READ COMMITTED, where the statement carries on instead.
  - mis: dp:Q5
- B. Deadlocks with txn A, and one of them is aborted.
  - why: Only one lock is involved, and txn A has finished with it. A wait with no cycle is not a deadlock.
  - mis: dp:C2
- C. Re-checks `bal >= 80` on the new row version and updates 0 rows.
  - why: The WHERE clause is re-evaluated against the updated row. It now holds 20, so the guard fails and the statement updates nothing. Your compiler maps that zero to `Insufficient`.
- D. Applies its debit of 80 to the value it first saw.
  - why: The statement computes from the row it finds after the wait, not from anything read earlier. Debiting a stale value is the read-modify-write's mistake.
  - mis: dp:Q4

@after
Same level, two verdicts. In the conditional UPDATE, txn B's statement waited, re-checked its guard on the row txn A left and updated nothing. The single statement is Stage 5's atomic action: no other session can slip in between the guard and the write.

Now the second permutation. In the read-modify-write, txn B's write waited and then went through, and txn B committed. Both debits took effect, so {{run:RUN-pg-anomalies#values.rmw_rc_spent}} was spent from a balance of 100, and the account ends at 20 {{run:RUN-pg-claims}}. The re-check ran, but all it re-evaluated was `id = 1`, which still matched. The constant 20 came from txn B's old read, and the guard `100 >= 80` was checked against a value that went stale before the write.

Txn B's zero rows in the conditional UPDATE is not an error, and PostgreSQL does not say why it is zero, so your compile has to turn that zero into a named outcome, as in S6.L2. Under REPEATABLE READ and SERIALIZABLE the same conditional UPDATE behaves differently: txn B fails with a serialization failure after its wait {{run:RUN-pg-claims}}, and a whole-command retry then updates 0 rows (row H24 {{run:RUN-pg-catalog}}). A stricter level needs the retries of S6.L7.
:::

A debit therefore has two inputs to its verdict, and the level is only one of them. The pattern decides whether the guard can be separated from the write. The level decides what PostgreSQL does when two sessions touch one row. Read the pattern first, then the level.

@choice key=B
Replay in your head: the read-modify-write compilation at REPEATABLE READ, one account holding 100, two debits of 80. Txn A and txn B both read 100. Txn A writes 20 and commits while txn B's write waits for txn A's row lock. Txn B's write then ends in an error. Which class is this history?

- A. Lost update: both debits took effect, and 80 was lost.
  - why: Txn B's write failed, so only txn A's debit took effect. The same compilation lost an update at READ COMMITTED, and at this level it loses nothing.
  - mis: dp:Q4
- B. Serialization failure: txn B was aborted, and no money was lost.
  - why: At REPEATABLE READ txn B's write meets a row that changed after its snapshot, and the database aborts txn B instead of letting it overwrite. Txn B has to run again.
- C. Deadlock: txn A and txn B waited on each other.
  - why: Txn A held the lock and finished. Txn B waited on txn A, and txn A never waited on txn B, so there was no cycle.
  - mis: dp:Q11
- D. Write skew: each wrote a different row that the other one had read.
  - why: Both wrote the same row, account 1. Write skew needs different rows.
  - mis: dp:Q16

## The predicate nobody locks {minutes=15 kcs=KC-6.anomaly-isolation}

A conditional UPDATE guards one row, and the row lock does the rest. Now guard against something that is not a row. A hold sets money aside, as a row in `holds(acct, amt)`. What is available on an account is its balance less the sum of its holds, and a new hold may be placed only while enough is available. Compiled, that is a read followed by an insert.

```sql
SELECT bal - coalesce((SELECT sum(amt) FROM holds WHERE acct = 1), 0)
FROM acct WHERE id = 1;                  -- available: the application reads 100
-- the application checks 100 >= 80
INSERT INTO holds VALUES (1, 80);        -- and sets 80 aside
```

Two sessions run this at once. Each reads 100 available, and each inserts a hold of 80. The two inserts write two different new rows, so no row is written twice and there is no row for a lock to protect. Yet each read depends on what the other writes: `sum(amt)` is a question about the whole set of holds, and each insert changes the answer to the other's question. That is write skew. Two transactions each read something the other writes, and each writes something the other read, on different rows.

REPEATABLE READ in PostgreSQL is snapshot isolation, and snapshot isolation only checks whether two concurrent transactions wrote the same row. Here they did not, so nothing is checked. Make your call, then replay all three levels.

:::instrument ins=INS-history cell=2 recorded=RUN-pg-claims
The holds compilation: read what is available, then insert a hold of 80. The first permutation runs at REPEATABLE READ.

```text
-- compilation: predicate read, then insert
-- account 1 holds 100; holds records money set aside; each session sets aside 80
setup {
  CREATE TABLE acct  (id int PRIMARY KEY, bal bigint NOT NULL);
  CREATE TABLE holds (acct int, amt bigint);
  INSERT INTO acct VALUES (1, 100);
}

session a
step a_rc     { BEGIN ISOLATION LEVEL READ COMMITTED; }
step a_rr     { BEGIN ISOLATION LEVEL REPEATABLE READ; }
step a_ser    { BEGIN ISOLATION LEVEL SERIALIZABLE; }
step a_avail  { SELECT bal - coalesce((SELECT sum(amt) FROM holds WHERE acct = 1), 0) FROM acct WHERE id = 1; }
step a_hold   { INSERT INTO holds VALUES (1, 80); }   -- only if a_avail returned 80 or more
step a_commit { COMMIT; }

session b
step b_rc     { BEGIN ISOLATION LEVEL READ COMMITTED; }
step b_rr     { BEGIN ISOLATION LEVEL REPEATABLE READ; }
step b_ser    { BEGIN ISOLATION LEVEL SERIALIZABLE; }
step b_avail  { SELECT bal - coalesce((SELECT sum(amt) FROM holds WHERE acct = 1), 0) FROM acct WHERE id = 1; }
step b_hold   { INSERT INTO holds VALUES (1, 80); }   -- only if b_avail returned 80 or more
step b_commit { COMMIT; }

permutation a_rr  a_avail b_rr  b_avail a_hold b_hold a_commit b_commit
permutation a_rc  a_avail b_rc  b_avail a_hold b_hold a_commit b_commit
permutation a_ser a_avail b_ser b_avail a_hold b_hold a_commit b_commit
```

@direction
Replay shows: both sessions read the available amount before either inserts, then each inserts a hold of 80 and commits. The level changes with the permutation.

@call key=B surprise=yes run=RUN-pg-claims
Txn A and txn B each read 100 available and each insert a hold of 80, at REPEATABLE READ. Outcome?

- A. Txn A commits; txn B fails with a serialization failure.
  - why: No row is written twice, so snapshot isolation sees no conflict. That abort belongs to a different compilation.
  - mis: dp:Q5
- B. Both commit: 160 is held against a balance of 100.
  - why: Each transaction read a snapshot that did not include the other's hold, and neither wrote a row the other wrote. Nothing in REPEATABLE READ looks for that.
- C. Txn B waits for txn A, then sees 20 available.
  - why: Row locks do not cover a predicate. There is no row for txn B to wait on, so it never sees txn A's hold.
  - mis: dp:C2
- D. Deadlock: one transaction fails.
  - why: Nothing waits, so nothing can deadlock.
  - mis: dp:Q4

@after
Both committed. The run records it as: {{run:RUN-pg-claims#values.e3_holds_write_skew_rr}}.

Replay the other two permutations. At READ COMMITTED the same thing happens. At SERIALIZABLE, txn B's COMMIT fails with a serialization failure, and the database's message names read-write dependencies among transactions {{run:RUN-pg-claims}}. SERIALIZABLE watches for the cycle: txn A read what txn B wrote, and txn B read what txn A wrote, a cycle of read-write dependencies on different rows. When it finds one it aborts one of the transactions, and the application runs the whole command again (S6.L7).
:::

The same shape appears on existing rows. Two accounts hold 100 each, in one team. Each transaction reads the team total, 200, and debits 150 from a different account. At REPEATABLE READ both commit and the team total ends at {{run:RUN-pg-anomalies#values.write_skew_rr_team_total}}. At SERIALIZABLE one transaction is aborted instead {{run:RUN-pg-anomalies}}. Hermitage, a public suite of isolation anomaly tests, reports the same family of results for PostgreSQL; the reading card at the end links it.

## Opposite directions {minutes=12 kcs=KC-6.anomaly-isolation}

The last pattern is a transfer compiled as two UPDATEs, debit first. Txn A moves 10 from account 1 to account 2. Txn B moves 10 from account 2 to account 1. Each debits its own account first, so each holds one row lock, and each then asks for the lock the other holds. Make your call, then replay. The cell's second permutation takes locks in one order instead.

:::instrument ins=INS-history cell=3 recorded=RUN-pg-claims
Two transfers in opposite directions, interleaved after both debits, at READ COMMITTED. The second permutation has both sessions touch account 1 first, at REPEATABLE READ.

```text
-- compilation: two UPDATEs per transfer
-- accounts 1 and 2 hold 100 each; a moves 10 from 1 to 2, b moves 10 from 2 to 1
setup { CREATE TABLE acct (id int PRIMARY KEY, bal bigint NOT NULL); INSERT INTO acct VALUES (1, 100), (2, 100); }

session a
step a_rc     { BEGIN ISOLATION LEVEL READ COMMITTED; }
step a_rr     { BEGIN ISOLATION LEVEL REPEATABLE READ; }
step a_debit  { UPDATE acct SET bal = bal - 10 WHERE id = 1 AND bal >= 10; }   -- locks row 1
step a_credit { UPDATE acct SET bal = bal + 10 WHERE id = 2; }                 -- wants row 2
step a_commit { COMMIT; }

session b
step b_rc     { BEGIN ISOLATION LEVEL READ COMMITTED; }
step b_rr     { BEGIN ISOLATION LEVEL REPEATABLE READ; }
step b_debit  { UPDATE acct SET bal = bal - 10 WHERE id = 2 AND bal >= 10; }   -- locks row 2
step b_credit { UPDATE acct SET bal = bal + 10 WHERE id = 1; }                 -- wants row 1
step b_commit { COMMIT; }

-- opposite lock orders: each session debits first
permutation a_rc a_debit b_rc b_debit a_credit b_credit a_commit b_commit
-- one lock order: b credits account 1 first, as a debits it first
permutation a_rr a_debit b_rr b_credit a_credit a_commit b_debit b_commit
```

@direction
Replay shows: in the first permutation each session takes its debit lock, then each asks for the other's row. In the second, txn B's first statement waits for txn A, and txn B's next statement is ignored once an error arrives.

@call key=A surprise=no run=RUN-pg-claims
In the first permutation, each transaction holds its debit row and wants the other's. Outcome?

- A. One fails with a deadlock error and the other commits.
  - why: The database finds the cycle of lock waits and aborts one transaction. The survivor finishes its transfer.
- B. Both commit, one after the other finishes.
  - why: Each is waiting for a lock the other holds, so neither can finish first.
  - mis: dp:C1
- C. Both fail with a serialization failure and both roll back.
  - why: A serialization failure reports a conflict between snapshots. This is a cycle of lock waits, which PostgreSQL reports with a different error.
  - mis: dp:Q4
- D. Both wait forever, each holding the other's row.
  - why: PostgreSQL checks for lock cycles after a short wait and aborts one transaction, so the waiting ends.
  - mis: dp:C2

@after
One transaction was aborted with {{run:RUN-pg-claims#values.e4_sqlstate}}, "deadlock detected", and the other committed. In the recorded run it was txn A that failed {{run:RUN-pg-claims}}. A deadlock costs availability, not money: the aborted transfer did not happen, and nothing was lost or created.

The usual cure is a lock order. In the second permutation every statement is issued in ascending account order, so both sessions take account 1's lock first and no cycle can form. That removed the deadlock, and it did not remove the failure. At READ COMMITTED both transfers commit in every interleaving of this pair. At REPEATABLE READ and SERIALIZABLE, four of the six interleavings still end with a serialization failure for one of them, because txn B's first write finds a row that txn A changed after txn B's snapshot (row H22b {{run:RUN-pg-catalog}}). Order the locks, and retry what remains.
:::

:::item role=segment family=GEN-anomaly-id template=t4 kcs=KC-6.anomaly-isolation
@choice key=D
Replay in your head: two transfers between accounts 1 and 2, at REPEATABLE READ, each taking account 1's lock first. Txn A debits account 1 and credits account 2. Txn B credits account 1 first, so it waits for txn A, then would debit account 2. Txn A credits account 2 and commits. Txn B's waiting statement then ends in an error. What does the history end with?

- A. Deadlock: the two transactions waited on each other's locks.
  - why: Both took account 1 first, so only txn B ever waited. A wait with no cycle cannot deadlock.
  - mis: dp:C2
- B. Both commit: one lock order prevents every failure here.
  - why: That holds at READ COMMITTED. At REPEATABLE READ the waiting write meets a row changed after its snapshot, and the database aborts it.
  - mis: dp:C3
- C. Lost update: txn A's credit was overwritten by txn B.
  - why: Txn B's write never took effect, so nothing was overwritten. The database aborted txn B first.
  - mis: dp:Q4
- D. Serialization failure: a row changed after txn B's snapshot.
  - why: Ordering the locks removed the cycle and not the conflict. Txn B has to run the whole command again.

## Exit {minutes=8 kcs=KC-6.compilation-pattern,KC-6.anomaly-isolation}

Here is the lesson in one table. Every cell is a recorded result {{run:RUN-pg-claims}} {{run:RUN-pg-catalog}}. Read it by row first: the compilation sets the row, and the level sets the cell.

| Compilation | READ COMMITTED | REPEATABLE READ | SERIALIZABLE |
|---|---|---|---|
| read-modify-write | both commit; 160 spent from 100 | txn B fails with a serialization failure | one session fails in every interleaving except the two serial orders |
| conditional UPDATE | txn B waits, then updates 0 rows | txn B fails with a serialization failure | txn B fails with a serialization failure |
| predicate read, then insert (holds) | both commit; 160 held against 100 | both commit; 160 held against 100 | txn B fails at COMMIT with a serialization failure |
| opposite-order moves | one fails with a deadlock error | the same interleavings deadlock | the same interleavings deadlock |

No level cures every row. REPEATABLE READ turns the lost update into a failure and misses write skew. SERIALIZABLE catches write skew and still deadlocks on opposite-order moves. The conditional UPDATE needs a retry the moment you raise the level. In Stage 5 the double spend had two remedies, an atomic action and isolation. This table is the second one, and it shows that the first is available in SQL as a single statement.

You can already claim something from the conditional UPDATE's row. Under concurrent READ COMMITTED sessions it never overspends: in every recorded interleaving of two debits, the final balance is not negative, the debits that committed total at most the starting balance, and each refusal came back as zero rows. That claim is TESTED [T] · 126 histories {{run:RUN-pg-conditional-concurrent#values.histories}}: every interleaving of two debits that can run, over a grid of nine balance and amount pairs. The other interleavings ask a session for a step while it waits on the other's row lock, so no execution has them {{run:RUN-pg-conditional-concurrent}}. It carries one assumption, ASSUMED [A]: PostgreSQL behaves as its manual documents. And it has a gap, NOT COVERED [N]: guards that span several rows, like the holds.

::claim template=CL-6.2

The SERIALIZABLE column rests on one more assumption that these recordings cannot test for you: that PostgreSQL's SERIALIZABLE gives serializable outcomes for committed SERIALIZABLE transactions. The course plants that as a seam here, carries it on the claim you will mint in S6.L8, and re-runs PostgreSQL's own regression spec for it on a schedule. S6.L9 shows what it rests on.

The holds compilation at SERIALIZABLE. Both sessions read 100 available and insert a hold of 80, and txn A commits first. What does PostgreSQL record for txn B?

  - mis: dp:Q5
- B. Txn B waits for txn A, then updates 0 rows.
  - why: That is the conditional UPDATE at READ COMMITTED. The holds compilation has no row for txn B to wait on.
  - mis: dp:C2

  - why: The database finds the read-write cycle when the second transaction commits, and the later committer is the one aborted.
