## A credit at the edge {minutes=17 kcs=KC-6.overflow-refusal}

Your model's balance is a whole number with no bound. The database's is eight bytes. Stage 1 set that mismatch up as a seam, and this lesson is where it breaks.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-6.overflow-refusal
@choice key=B
Recall S1.L5's table of what 64 bits mean. Which row does PostgreSQL's `bigint` take when a credit would pass the largest value it holds?

- A. It never overflows; it keeps counting, like whole numbers.
  - why: `bigint` is eight bytes with a largest value. It does not grow.
  - mis: dp:Z4
- B. It raises an out-of-range error and the statement fails.
  - why: The manual says attempts to store values outside the allowed range "will result in an error", and the recorded run raised SQLSTATE {{run:RUN-pg-claims#values.e6_overflow_sqlstate}} {{run:RUN-pg-claims}}.
- C. It wraps, like Z3's signed BitVec 64.
  - why: BitVec 64 wraps {{run:RUN-z3-bv64}}. PostgreSQL takes a different row of the table.
  - mis: dp:Q6
- D. It saturates at the maximum, then commits.
  - why: The manual's rule is an error, not a clamp.
  - mis: dp:Q6
:::

:::instrument ins=INS-pglite cell=1 recorded=RUN-pg-claims
Account 1 holds the largest `bigint` and account 2 holds 5. The credit is 1.

```sql
CREATE TABLE acct (id int PRIMARY KEY, bal bigint NOT NULL CHECK (bal >= 0));
INSERT INTO acct VALUES (1, 9223372036854775807), (2, 5);
-- the model: whole numbers with no bound
SELECT (bal::numeric + 1)::text AS model_balance FROM acct WHERE id = 1;
-- the database: the same credit
UPDATE acct SET bal = bal + 1 WHERE id = 1;
SELECT id, bal::text AS bal FROM acct ORDER BY id;
-- the total over both accounts
SELECT sum(bal)::text AS total, pg_typeof(sum(bal)) AS total_type FROM acct;
```

@direction
The first SELECT is your model's step: the same credit in numbers with no bound. The UPDATE is the database's. Compare what each does.

@call key=D surprise=no run=RUN-pg-claims
Your model credits 1 to an account holding the largest `bigint`, and the database does the same credit. What outcome classes do they report?

- A. Both committed: the model and PostgreSQL agree.
  - why: The database cannot store the result.
  - mis: dp:Z4
- B. Both refused: the model and PostgreSQL raise an error.
  - why: The model has no bound, so nothing refuses on its side.
  - mis: dp:Q6
- C. The model refused with `Insufficient`, while PostgreSQL committed it.
  - why: This reverses the direction of the failure. The model's guard passes.
  - mis: dp:P1
- D. The model committed, and PostgreSQL raised an out-of-range error.
  - why: The model takes a step the database refuses.

@after
The model's credit gave a balance one past the largest `bigint`. The database refused the same credit with SQLSTATE {{run:RUN-pg-claims#values.e6_overflow_sqlstate}} and left the balance as it was. The total over both accounts is a `numeric`, and it fits, although no single balance could hold it. {{run:RUN-pg-claims}}
:::

## Exit {minutes=4 kcs=KC-6.overflow-refusal}

The model's theorem still holds. What broke is the match between model and database, and the failure is a refusal, not a wrap. It is not retryable like a serialization failure either, because the same input fails again. Your claim from S6.L3, CL-6.1, gains a defeater too: its statistics showed the largest balance reached was far from the boundary.

Record one remedy as a decision, as you did in LAB-3.7. Each changes a different artifact.

1. **Bounded semantics.** The guard adds `bal(to) + amt <= 2^63 - 1`, and the S2 and S3 lemmas are re-proved. This changes the model.
2. **`Except Overflow`.** The database's out-of-range error maps to `Err Overflow`, and both sides report "refused: overflow". This changes the outcome type, and with it the relation R(S, D) that you define in S6.L8.
3. **`numeric` with a stated bound.** A `numeric(19,0)` column holds the balance `bigint` refuses and raises at its own declared bound {{run:RUN-pg-numeric-bound}}, so the bound must still appear in the semantics, or as an assumption. This changes the schema.

Drawer D-30, on Kani, is deferred. It appears in Today for the Rust `i64` path of your system, where `checked_add` returns `None` {{run:RUN-rust-i64}}. Nothing waits on it.
