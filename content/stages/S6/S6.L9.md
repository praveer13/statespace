## What your checker did not see {minutes=17 kcs=KC-6.db-as-assumption}

In S6.L8 you minted a claim from what your checker saw. This lesson is about what it did not see.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-6.db-as-assumption
@choice key=A
Your checker accepted all n recorded SERIALIZABLE histories. What does that establish about production?

- A. That these n histories were serializable.
  - why: It is a `TESTED [T]` result over the histories it saw. Production rests on clauses no history covers.
- B. That production is serializable.
  - why: That generalizes from tests to every transaction.
  - mis: dp:X1
- C. That PostgreSQL has no isolation bugs.
  - why: A release of PostgreSQL once had one, as the dated incident below shows.
  - mis: dp:G8
- D. That PostgreSQL behaves as its manual documents.
  - why: A serializable history is consistent with the manual, and shows nothing about other histories.
  - mis: dp:Q7
:::

Three histories show where the claim is thin. First, read skew.

:::instrument ins=INS-history cell=1 recorded=RUN-pg-read-skew call=false
Read skew at READ COMMITTED.

```text
-- accounts 1 and 2 hold 100 each, so every committed state totals 200
-- txn A only reads; txn B moves 50 from account 1 to account 2
session a
step a_begin  { BEGIN ISOLATION LEVEL READ COMMITTED; }
step a_read1  { SELECT bal FROM acct WHERE id = 1; }
step a_read2  { SELECT bal FROM acct WHERE id = 2; }
step a_commit { COMMIT; }

session b
step b_begin  { BEGIN ISOLATION LEVEL READ COMMITTED; }
step b_move   { UPDATE acct SET bal = bal - 50 WHERE id = 1; UPDATE acct SET bal = bal + 50 WHERE id = 2; }
step b_commit { COMMIT; }

permutation a_begin a_read1 b_begin b_move b_commit a_read2 a_commit
```

@direction
Replay shows: txn A reads account 1, txn B's transfer commits, and txn A reads account 2. Add up what txn A saw.

@after
Txn A saw 100 and then 150, a total of 250 {{run:RUN-pg-read-skew#values.read_committed.reader_total}}, though every committed state totals 200. Your checker rejects that report. READ COMMITTED takes a new snapshot for each statement, so a reader that spans two statements can see two committed states.
:::

Second, mixed levels.

:::instrument ins=INS-history cell=2 recorded=RUN-pg-mixed-levels
Mixed levels. Txn A runs SERIALIZABLE and txn B runs READ COMMITTED.

```text
-- two accounts of 100 form a team; each session reads the team total (200)
-- and debits 150 from its own account if the total stays at least 0
session a
step a_begin  { BEGIN ISOLATION LEVEL SERIALIZABLE; }
step a_total  { SELECT sum(bal) FROM acct WHERE team = 1; }
step a_debit  { UPDATE acct SET bal = bal - 150 WHERE id = 1; }   -- only if a_total allowed it
step a_commit { COMMIT; }

session b
step b_begin  { BEGIN ISOLATION LEVEL READ COMMITTED; }
step b_total  { SELECT sum(bal) FROM acct WHERE team = 1; }
step b_debit  { UPDATE acct SET bal = bal - 150 WHERE id = 2; }   -- only if b_total allowed it
step b_commit { COMMIT; }

permutation a_begin a_total b_begin b_total a_debit b_debit a_commit b_commit
```

@direction
Replay shows: both sessions read the team total before either debits, then each debits and commits.

@call key=C surprise=yes run=RUN-pg-mixed-levels
Does SERIALIZABLE abort either transaction?

- A. Yes: txn B fails with a serialization failure.
  - why: Only SERIALIZABLE transactions are tracked for read-write cycles, and txn B is not one.
  - mis: dp:Q4
- B. Yes: txn A fails with a serialization failure.
  - why: The guarantee covers a set of SERIALIZABLE transactions, and this set has one member.
  - mis: dp:Q4
- C. No: both commit, and the team total goes below zero.
  - why: The manual's guarantee covers "any set of successfully committed concurrent Serializable transactions" (§13.2.3, read 2026-10-23). Txn B is outside that set.
- D. They deadlock, and one is aborted.
  - why: Nothing waits on a lock.
  - mis: dp:C2

@after
Both committed; the team sank to -100 {{run:RUN-pg-mixed-levels#values.mixed.team_total}}. One writer at a weaker level removes the protection from every cycle it joins.
:::

Third, a toy history shaped like the cycle Jepsen reported (see the dated incident below).

:::instrument ins=INS-history cell=3 recorded=RUN-history-g2item call=false
A toy G2-item history at SERIALIZABLE.

```text
-- items x and y both start at 0
txn A   read x -> 0;   write y = 1;   committed
txn B   read y -> 0;   write x = 1;   committed

search  serial orders of the 2 committed transactions
bound   at most 8 transactions
```

@direction
Check asserts: some serial order gives each transaction the reads it reported.

@after
The checker rejects it {{run:RUN-history-g2item}}. With txn A first, txn B would have read y = 1. With txn B first, txn A would have read x = 1. A SERIALIZABLE database must never commit this pair.
:::

Your claim rests on three clauses. Give each the strongest stamp it can carry.

1. **Every writer is SERIALIZABLE.** The guarantee has a condition: "If the Serializable transaction isolation level is used for all writes and for all reads which need a consistent view of the data" (§13.4.1, read 2026-10-23). Set `default_transaction_isolation = serializable` and read it back from each session: CONFIGURED [C]. Add a check in each transaction, as the manual suggests with "checks of the transaction isolation level in triggers": ENFORCED [E].
2. **PostgreSQL behaves as documented.** ASSUMED [A]. You can narrow it: the regression spec for the bug Jepsen found, `update-conflict-out.spec`, passes on the version you pin {{run:RUN-pg-catalog}} (row H21), and the course re-runs it on a schedule. One history is evidence, not a stamp.
3. **Nothing reads a replica.** ASSUMED [A]. The protection "does not yet extend to hot standby mode … or logical replicas" (§13.4.1), and SERIALIZABLE "is not yet available in hot standby" (§26.4.5). A report served from a standby is outside your claim. The course plants this clause as a seam here, and S7.L8 is where it cracks.

If you built kernelspace's pool conformance, re-stamp it the same way: a lockstep run over one deterministic traffic script is TESTED [T] · n ticks · 1 script.

:::item role=segment family=GEN-which-stamp template=t3 kcs=KC-6.db-as-assumption
@choice key=B
A claim's strip has three segments: the proposition of the model, the correspondence, and the requirement fit. Every session of your pool reads back `default_transaction_isolation = serializable`. Where does that evidence go, and with which stamp?

- A. Proposition of the model: `TESTED [T] · n histories`
  - why: That is what the checker's runs earn. A setting says nothing about histories.
  - mis: dp:P3
- B. Correspondence: `CONFIGURED [C] · read back from each session`
  - why: It says how the running system relates to the model, and a setting read back from the system is CONFIGURED [C], with its source.
- C. Requirement fit: `ASSUMED [A] · fit for purpose is a judgment`
  - why: Requirement fit does stay assumed, but a setting read back is evidence about the running system: the correspondence.
  - mis: dp:P3
- D. Correspondence: `ENFORCED [E] · in PostgreSQL`
  - why: A setting alone blocks nothing: a client can still start a transaction at a weaker level.
  - mis: dp:X2
:::

## Exit {minutes=4 kcs=KC-6.db-as-assumption}

:::item role=exit family=GEN-call-it template=t4 kcs=KC-6.db-as-assumption
@choice key=C
Which statement is true?

- A. A claim that assumes no replica reads still covers a report served from a standby.
  - why: A standby is exactly what the clause excludes.
  - mis: dp:P3
- B. Reading `serializable` back from every session shows every transaction ran SERIALIZABLE.
  - why: That is CONFIGURED [C]. A client can start a transaction at a weaker level.
  - mis: dp:X2
- C. With one writer at READ COMMITTED, the SERIALIZABLE guarantee does not cover that writer's transactions.
  - why: The guarantee covers a set of SERIALIZABLE transactions, as the mixed-levels cell showed.
- D. Jepsen's 2020 finding means the SERIALIZABLE of the version you pin cannot be trusted at all.
  - why: The bug was fixed, and its regression spec passes on your version.
  - mis: dp:G8
:::
