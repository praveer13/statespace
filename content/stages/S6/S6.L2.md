## Before you compile {minutes=2 kcs=KC-6.rowcount-as-guard,KC-6.null-guards}

A transfer is two UPDATEs. In your model each step either happens or the command is refused with a reason. In SQL an UPDATE that matches no row succeeds and changes nothing, and the row count is the only place the database says so. If typed error outcomes are new to you, drawer D-23 is one page on them.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-6.rowcount-as-guard
@choice key=C
Your debit `UPDATE acct SET bal = bal - $2 WHERE id = $1 AND bal >= $2` reports 0 rows on a table where `bal` may be NULL. What could have happened?

- A. Only insufficient funds; the other causes raise errors.
  - why: Three other causes give the same zero, and none of them raises an error.
  - mis: dp:Q3
- B. A serialization failure from a concurrent writer.
  - why: A serialization failure raises an error. It never returns 0 rows.
  - mis: dp:Q11
- C. Any of four: low funds, a missing account, a NULL balance, a NULL amount.
  - why: All four returned 0 rows with no error in the recorded run {{run:RUN-pg-claims}}.
- D. Nothing: an UPDATE that matches no row, for any reason at all, raises an error.
  - why: Matching no row is a success with a count of 0.
  - mis: dp:Q10
:::

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-6.null-guards
@choice key=A
Now declare `bal NOT NULL`. Which causes of a 0-row debit remain?

- A. Three: all but the NULL balance.
  - why: `NOT NULL` constrains stored rows. It does not constrain parameters or missing rows {{run:RUN-pg-claims}}.
- B. All four, NULL balance included.
  - why: A NULL balance can no longer be stored.
  - mis: dp:Q2
- C. Two: low funds and a missing account.
  - why: A NULL amount still makes the guard unknown, so it still selects nothing.
  - mis: dp:Q9
- D. Only low funds, not a NULL amount.
  - why: A missing account still matches nothing.
  - mis: dp:Q10
:::

## Why a debit reports zero rows {minutes=14 kcs=KC-6.rowcount-as-guard}

Run five statements on a table where `bal` may be NULL: four debits that fail in four different ways, then a credit to an account that does not exist.

:::instrument ins=INS-pglite cell=1 recorded=RUN-pg-claims
Account 1 holds 100 and account 2 holds NULL.

```sql
CREATE TABLE acct (id int PRIMARY KEY, bal bigint CHECK (bal >= 0));
INSERT INTO acct VALUES (1, 100), (2, NULL);
-- low funds
UPDATE acct SET bal = bal - 150 WHERE id = 1 AND bal >= 150;
-- no such account
UPDATE acct SET bal = bal - 10 WHERE id = 999 AND bal >= 10;
-- a NULL balance
UPDATE acct SET bal = bal - 10 WHERE id = 2 AND bal >= 10;
-- a NULL amount
UPDATE acct SET bal = bal - CAST(NULL AS bigint)
 WHERE id = 1 AND bal >= CAST(NULL AS bigint);
-- a credit to an account that does not exist
UPDATE acct SET bal = bal + 30 WHERE id = 999;
SELECT id, bal FROM acct ORDER BY id;
```

@direction
Read the row count each UPDATE reports, and whether any statement raises an error.

@call key=D surprise=yes run=RUN-pg-claims
`UPDATE acct SET bal = bal + 30 WHERE id = 999`, and no row 999 exists. PostgreSQL returns:

- A. A new row 999 with balance 30.
  - why: UPDATE never inserts.
  - mis: dp:Q10
- B. Success, 1 row.
  - why: No row matches, so no row is counted.
  - mis: dp:Q10
- C. An error naming the missing row.
  - why: SQL reports a count, not a missing key.
  - mis: dp:Q10
- D. Success, 0 rows.
  - why: The statement succeeds and changes nothing.

@after
All four debits and the credit reported the same thing: zero rows, no error {{run:RUN-pg-claims}}. If your plan ignores the credit's zero, the debit commits and 30 leaves the system.
:::

A plan that cannot miss a zero declares how many rows each UPDATE expects and turns every zero into a named outcome inside the transaction. Here is the reference plan. Read it once before the witness question.

```text
schema  acct(id int PRIMARY KEY, bal bigint NOT NULL CHECK (bal >= 0))
plan Transfer(from, to, amt)          -- amt > 0 by type
  if from = to and your decision rejects it: Err SelfTransfer   -- before any SQL
  BEGIN
  s1  UPDATE acct SET bal = bal - $amt WHERE id = $from AND bal >= $amt
      RETURNING old.bal, new.bal      -- expect exactly 1 row
      0 rows: SELECT 1 FROM acct WHERE id = $from
              none -> Err NoSuchAccount(from); some -> Err Insufficient; ROLLBACK
  s2  UPDATE acct SET bal = bal + $amt WHERE id = $to
      RETURNING old.bal, new.bal      -- expect exactly 1 row
      0 rows -> Err NoSuchAccount(to); ROLLBACK
  SQLSTATE 22003 -> the decision of S6.L4; ROLLBACK
  COMMIT -> Ok(the two old/new pairs)
```

`RETURNING old.bal, new.bal` returns each row's balance before and after the update, as the recorded run on PostgreSQL {{run:RUN-pg-sql-semantics#version}} shows {{run:RUN-pg-sql-semantics}}. Each pair is one row's concrete step from D to D′, which S6.L8 uses. Expectations are equalities, never "at least one". If your decision allows a self-transfer, the two UPDATEs handle it: the guard still runs, so one above the balance is refused as `Insufficient`.

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-6.rowcount-as-guard
@choice key=A
A plan matches the reference except in one place: its credit declares no expectation, so a credit that updates zero rows goes unnoticed. Which initial state and command make its outcome differ from the reference's?

- A. Account 1 holds 100, account 2 is missing; transfer 30 from 1 to 2.
  - why: The debit commits, the credit updates no row, and the plan returns success. The reference refuses with `NoSuchAccount(to)` and rolls back.
- B. Accounts 1 and 2 hold 100 each; transfer 30 from 1 to 2.
  - why: Both plans commit the same two changes.
  - mis: dp:Q10
- C. Account 1 holds 20 and account 2 holds 0; transfer 30 from 1 to 2.
  - why: The debit's guard fails in both plans, so both refuse with `Insufficient` and the credit never runs.
  - mis: dp:Q3
- D. Account 1 does not exist and account 2 holds 0; transfer 30 from 1 to 2.
  - why: The debit's own expectation catches a missing `from` in both plans.
  - mis: dp:Q10
:::

## The schema is part of the compile {minutes=13 kcs=KC-6.rowcount-as-guard,KC-6.null-guards}

Look at the schema line of the plan: `NOT NULL CHECK (bal >= 0)`. It is part of the compile. Without `NOT NULL` a NULL balance can be stored and the guard skips it. With `NOT NULL` that cause is gone, but a NULL amount and a missing account still give zero rows. A second question: if the schema keeps the `CHECK`, does the plan still need its guard?

:::instrument ins=INS-pglite cell=2 recorded=RUN-pg-sql-semantics
The debit has no guard. The schema keeps `CHECK (bal >= 0)`.

```sql
CREATE TABLE acct (id int PRIMARY KEY, bal bigint NOT NULL CHECK (bal >= 0));
INSERT INTO acct VALUES (1, 50);
UPDATE acct SET bal = bal - 80 WHERE id = 1;
SELECT id, bal FROM acct;
```

@direction
Debit 80 from a balance of 50 with no guard in the statement. Read what the UPDATE reports and what the SELECT shows.

@call key=B surprise=no run=RUN-pg-sql-semantics
No guard; the schema keeps `CHECK (bal >= 0)`. Debit 80 from a balance of 50. PostgreSQL:

- A. Commits, leaving a balance of -30.
  - why: A false result is rejected. Only NULL slips through.
  - mis: dp:Q2
- B. Fails with a check violation on `bal >= 0`.
  - why: The new row would make the constraint false, so the statement errors.
- C. Skips the row and updates 0 rows.
  - why: A constraint does not filter rows the way WHERE does.
  - mis: dp:Q3
- D. Commits, clamping the balance at 0.
  - why: Nothing clamps. The database refuses or stores the value.
  - mis: dp:Q6

@after
The balance is unchanged, the same as after a guarded refusal. The outcome is not the same: your semantics says `Insufficient`, and the database raises a check violation (SQLSTATE {{run:RUN-pg-sql-semantics#values.check_only_overdraft.sqlstate}} {{run:RUN-pg-sql-semantics}}). A harness that compares final balances alone calls the two equal.
:::

:::item role=segment family=GEN-call-it template=t4 kcs=KC-6.null-guards,KC-6.rowcount-as-guard
@choice key=D
Which statement is true?

- A. With `CHECK` alone, an overdraft's outcome equals the semantics' `Insufficient`.
  - why: The database raises a check violation, a different outcome class.
  - mis: dp:Q2
- B. A debit that updates 0 rows says which account was missing.
  - why: Zero rows says only that nothing matched. One more query tells low funds from a missing account.
  - mis: dp:Q10
- C. `RETURNING old.bal, new.bal` still returns a row when the guard matches nothing.
  - why: `RETURNING` reports updated rows only, so zero updated rows returns nothing.
  - mis: dp:Q10
- D. With `NOT NULL` and the guard, a NULL amount still yields 0 rows.
  - why: `bal >= NULL` is unknown, so the guard selects nothing and no write happens {{run:RUN-pg-claims}}.
:::

## One row, two roles {minutes=12 kcs=KC-6.rowcount-as-guard}

S2's self-transfer bug (SP-2.1) comes back in SQL. Your decision record from LAB-3.7 says what a self-transfer means, and the compiler has to act on it. If you have not recorded that decision yet, use the reference's: a self-transfer is allowed and changes nothing. Here is the compile that saves a round trip: one statement with a CASE, then the two-UPDATE version.

:::instrument ins=INS-pglite cell=3 recorded=RUN-pg-claims
Account 1 holds 100. The command moves 30 from account 1 to account 1.

```sql
CREATE TABLE acct (id int PRIMARY KEY, bal bigint NOT NULL CHECK (bal >= 0));
INSERT INTO acct VALUES (1, 100);
-- one statement, from = to = 1, amount 30
UPDATE acct
   SET bal = CASE WHEN id = 1 THEN bal - 30
                  WHEN id = 1 THEN bal + 30 END
 WHERE id IN (1, 1);
SELECT id, bal FROM acct;
-- reset, then two statements
UPDATE acct SET bal = 100 WHERE id = 1;
UPDATE acct SET bal = bal - 30 WHERE id = 1 AND bal >= 30;
UPDATE acct SET bal = bal + 30 WHERE id = 1;
SELECT id, bal FROM acct;
```

@direction
The first UPDATE is the one-statement plan with `$from`, `$to` and `$amt` filled in. Compare the two SELECTs.

@call key=C surprise=yes run=RUN-pg-claims
One statement: `SET bal = CASE WHEN id = $from THEN bal - $amt WHEN id = $to THEN bal + $amt END WHERE id IN ($from, $to)`, with from = to = 1 and amount 30. Afterwards:

- A. Balance 100, 2 rows updated.
  - why: One row matches, and only the first true CASE arm applies.
  - mis: dp:L7
- B. An error: one row updated twice.
  - why: The single matching row is updated once, and nothing reports the overlap.
  - mis: dp:Q10
- C. Balance 70, 1 row updated.
  - why: The debit arm wins and 30 disappears. The two-UPDATE plan leaves 100.
- D. Balance 130, 1 row updated.
  - why: CASE takes the first true arm, not the last.
  - mis: dp:S1

@after
The one-statement plan ended at {{run:RUN-pg-claims#values.e7_case_self_transfer_final}}, and the two-UPDATE plan ended at {{run:RUN-pg-claims#values.e7_two_updates_final}}.
:::

The compile assumed `from` and `to` are different accounts. With exact expectations the CASE plan would have expected two rows, received one and rolled back, so the rowcount check catches it. Without them it commits and destroys 30.

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-6.rowcount-as-guard

A one-statement CASE plan and the two-UPDATE plan both keep `NOT NULL CHECK (bal >= 0)`, and neither checks a rowcount. They give the same outcome on every command except one kind. Which kind?

- A. A transfer larger than the sender's balance.
  - why: Both plans raise the same check violation.
  - mis: dp:Q2
- B. A transfer from an account to itself.
  - why: The CASE plan applies only the debit arm, and the two-UPDATE plan leaves the balance unchanged.
- C. A transfer to an account that does not exist.
  - why: Both plans debit the sender and credit nothing.
  - mis: dp:Q10
- D. A transfer whose amount is NULL.
  - why: Both plans fail on the NOT NULL constraint.
