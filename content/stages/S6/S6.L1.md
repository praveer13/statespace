## Three truth values {minutes=16 kcs=KC-6.sql-not-algebra,KC-6.null-guards}

Your transfer lived in a model where a comparison is true or false. Stage 6 compiles it into SQL, and SQL has a third answer. Commit to one prediction before the first cell.

:::item role=prequestion family=GEN-call-it template=t4 kcs=KC-6.sql-not-algebra,KC-6.null-guards
@choice key=D
A table `t(id int, team int, bal bigint CHECK (bal >= 0))` holds rows. Which statement is true?

- A. Inserting a row whose `bal` is NULL is rejected.
  - why: The manual says a check constraint "is satisfied if the check expression evaluates to true or the null value".
  - mis: dp:Q2
- B. `SELECT count(bal)` counts the rows whose `bal` is NULL.
  - why: `count(expr)` counts non-null values. `count(*)` counts rows.
  - mis: dp:Q9
- C. `WHERE NOT (bal >= 10)` selects exactly the rows that `WHERE bal >= 10` skips.
  - why: A NULL row makes both predicates unknown, so it lands in neither.
  - mis: dp:Q9
- D. `SELECT team FROM t` can return the same value twice.
  - why: Tables and results are bags. A plain SELECT keeps duplicates.
:::

**How the cells work.** Every cell in this stage runs PostgreSQL in your browser tab through PGlite {{run:RUN-pglite-0511#version}}, whose `version()` names the same PostgreSQL release as the Bench server, {{run:RUN-pg-sql-semantics#version}} {{run:RUN-pglite-0511}}. A cell starts from an empty database, runs its statements in order, and prints each statement's rows, row count or error code. Nothing carries over to the next cell. The tab has one connection, so it cannot show two transactions at once; S6.L6 replays recorded histories for that. While the engine loads, a cell shows a recorded run with its ID.

:::instrument ins=INS-pglite cell=1 recorded=RUN-pg-anomalies
Two rows, one with a NULL balance and one with 50. The UPDATE debits 10 from every row whose balance is at least 10.

```sql
CREATE TABLE t (id int PRIMARY KEY, team int, bal bigint CHECK (bal >= 0));
INSERT INTO t VALUES (1, 1, NULL), (2, 1, 50);
UPDATE t SET bal = bal - 10 WHERE bal >= 10;
SELECT id, bal FROM t ORDER BY id;
```

@direction
The cell asserts nothing. It records what the database does: read the row count the UPDATE reports and the balances the SELECT shows.

@call key=A surprise=yes run=RUN-pg-anomalies
`UPDATE t SET bal = bal - 10 WHERE bal >= 10` runs over row 1 (balance NULL) and row 2 (balance 50). What happens?

- A. 1 row: row 2 becomes 40 and the NULL row is untouched.
  - why: `NULL >= 10` is unknown, WHERE keeps only true rows, and nothing reports the skip.
- B. 0 rows: the NULL row stops the statement.
  - why: WHERE filters row by row, so one unknown row does not fail the statement.
  - mis: dp:Q10
- C. 2 rows: row 1 stays NULL and row 2 becomes 40.
  - why: An unknown predicate is not true, so row 1 is never selected and never counted.
  - mis: dp:Q9
- D. An error: NULL cannot be compared with 10.
  - why: Comparing with NULL gives unknown, never an error.
  - mis: dp:Q3

@after
The INSERT put a NULL balance past `CHECK (bal >= 0)`, and the UPDATE skipped that row without a word. SQL has three truth values. A constraint lets unknown through; a filter throws it away. Neither tells you. {{run:RUN-pg-anomalies}}
:::

A `CHECK` accepts a row when its expression is true or unknown. A `WHERE` keeps a row only when its expression is true. So one NULL balance gets past the constraint, and then every guard you write skips it. Two more departures from the algebra you learned: a table is a bag, so a result can repeat a row, and `count(bal)` skips NULLs where `count(*)` does not.

:::instrument ins=INS-pglite cell=2 call=false recorded=RUN-pg-sql-semantics
Run it and check each result against the rule above.

```sql
CREATE TABLE t (id int PRIMARY KEY, team int, bal bigint CHECK (bal >= 0));
INSERT INTO t VALUES (1, 1, NULL), (2, 1, 50), (3, 2, 5);
-- every row lands in exactly one of three groups
SELECT count(*) FILTER (WHERE bal >= 10)           AS p,
       count(*) FILTER (WHERE NOT (bal >= 10))     AS not_p,
       count(*) FILTER (WHERE (bal >= 10) IS NULL) AS unknown,
       count(*)                                    AS all_rows
FROM t;
-- NULL equals nothing, itself included
SELECT id FROM t WHERE bal = NULL;
SELECT id FROM t WHERE bal IS NULL;
-- a NULL amount in the guard
UPDATE t SET bal = bal - CAST(NULL AS bigint)
 WHERE id = 2 AND bal >= CAST(NULL AS bigint);
-- a table is a bag
SELECT team FROM t ORDER BY id;
```

@direction
Free run. Predicate, negation and IS NULL together account for every row; the NULL amount selects nothing; `team` repeats.
:::

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-6.null-guards,KC-6.sql-not-algebra
@choice key=B
A table `t(bal bigint, frozen boolean)` may hold any of the rows below, written `(bal, frozen)`. Which row is selected by neither `WHERE bal >= 10 OR frozen` nor `WHERE NOT (bal >= 10 OR frozen)`?

- A. `(NULL, true)`
  - why: `unknown OR true` is true, so the first query selects it.
  - mis: dp:Q9
- B. `(5, NULL)`
  - why: `false OR unknown` is unknown, and so is its negation. Neither query keeps the row.
- C. `(50, NULL)`
  - why: `true OR unknown` is true, so the first query selects it.
  - mis: dp:Q9
- D. `(5, false)`
  - why: `false OR false` is false, so the second query selects it.
  - mis: dp:Q3
:::

## Exit {minutes=3 kcs=KC-6.sql-not-algebra,KC-6.null-guards}

:::item role=exit family=GEN-call-it template=t4 kcs=KC-6.sql-not-algebra,KC-6.null-guards
@choice key=D
Which statement is true?

- A. `bal = NULL` is true for a NULL `bal`, just as `1 = 1` is true.
  - why: `=` with a NULL operand is unknown. Ask `bal IS NULL`.
  - mis: dp:Q1
- B. `UNION` keeps duplicate rows, as `UNION ALL` does.
  - why: `UNION` removes duplicates. `UNION ALL` keeps them.
  - mis: dp:Q8
- C. `count(*)` skips rows whose balance is NULL, as `count(bal)` does.
  - why: `count(*)` counts rows. `count(bal)` skips NULL balances.
  - mis: dp:Q9
- D. `2 NOT IN (1, NULL)` is unknown and keeps nothing in a `WHERE`.
  - why: `NOT IN` becomes `NOT (2 = 1 OR 2 = NULL)`, which is `NOT unknown`.
:::
