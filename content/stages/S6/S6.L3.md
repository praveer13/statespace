## What a suite reaches {minutes=18 kcs=KC-6.differential-testing}

Your compiler runs. The next question is what a test of it can tell you. A differential suite feeds the same generated commands to a reference and to the compiled plan on a real database, then compares outcome classes: committed, refused for a named reason, or an error code.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-6.differential-testing
@choice key=D
A suite ran n generated transfers through the reference interpreter and the compiled plan on a database, and found no divergence. Which stamp fits?

- A. `PROVED [P] · n runs · no divergence`
  - why: Many passing runs are still runs.
  - mis: dp:X1
- B. `MODEL-CHECKED [M] · bound n · complete`
  - why: No bounded space was explored exhaustively.
  - mis: dp:T5
- C. `ENFORCED [E] · in PostgreSQL, at commit`
  - why: Nothing checks production at run time.
  - mis: dp:Q7
- D. `TESTED [T] · n · generator statistics`
  - why: The qualifier says how many commands were run and what kind.
:::

The cell below is a small harness in SQL. Its reference is a rule standing in for the course's interpreter: it rejects a self-transfer, refuses an overdraft and commits everything else. The plan under test is the one-statement CASE compile from S6.L2. The generator draws accounts 1 to 3 with `from` and `to` different, and amounts 1 to 200.

:::instrument ins=INS-pglite cell=1 recorded=RUN-drt-transfers
```sql editable
CREATE TABLE mut (id int PRIMARY KEY, bal bigint NOT NULL CHECK (bal >= 0));

CREATE FUNCTION plan_case(f int, t int, amt bigint) RETURNS text AS $$
DECLARE n int;
BEGIN
  UPDATE mut
     SET bal = CASE WHEN id = f THEN bal - amt ELSE bal + amt END
   WHERE id IN (f, t) AND (SELECT bal FROM mut WHERE id = f) >= amt;
  GET DIAGNOSTICS n = ROW_COUNT;
  RETURN CASE WHEN n = 0 THEN 'refused' ELSE 'committed' END;
END $$ LANGUAGE plpgsql;

CREATE FUNCTION suite(n int, self_pct int)
RETURNS TABLE (commands int, self_transfers int, largest_balance bigint,
               first_divergence int, reference text, plan text) AS $$
DECLARE
  i int; f int; t int; amt bigint; bal_f bigint;
  want text; got text; selfs int := 0; big bigint := 500;
BEGIN
  DELETE FROM mut;
  INSERT INTO mut VALUES (1, 500), (2, 500), (3, 500);
  PERFORM setseed(0.42);
  FOR i IN 1..n LOOP
    f := 1 + floor(random() * 3)::int;
    IF random() * 100 < self_pct THEN
      t := f; selfs := selfs + 1;
    ELSE
      t := 1 + (f + floor(random() * 2)::int) % 3;
    END IF;
    amt := 1 + floor(random() * 200)::bigint;
    SELECT bal INTO bal_f FROM mut WHERE id = f;
    want := CASE WHEN f = t OR bal_f < amt THEN 'refused' ELSE 'committed' END;
    got := plan_case(f, t, amt);
    SELECT greatest(big, max(bal)) INTO big FROM mut;
    IF got <> want THEN
      RETURN QUERY SELECT i, selfs, big, i, want, got;
      RETURN;
    END IF;
  END LOOP;
  RETURN QUERY SELECT n, selfs, big, NULL::int, NULL::text, NULL::text;
END $$ LANGUAGE plpgsql;

SELECT * FROM suite(300, 0);
SELECT * FROM suite(300, 5);
```

@direction
Each `suite(n, self_pct)` call runs n commands, with `self_pct` percent of them self-transfers, and prints its statistics and its first divergence, if any. Edit the numbers and run again.

@call key=B surprise=yes run=RUN-drt-transfers
Before you run it: will `suite(300, 0)` report a divergence from the CASE plan within its commands?

- A. Yes, within a few hundred commands.
  - why: The generator never draws `from = to`, so the bug is unreachable however many commands run.
  - mis: dp:G8
- B. No: the suite passes.
  - why: Its statistics line shows no self-transfers. A test finds only what its generator reaches.
- C. The run cannot finish.
  - why: Nothing in the plan stops execution.
  - mis: dp:Q10

@after
The default generator found nothing, and its statistics line says why. With a 5 percent self-transfer quota the first divergence appears, with its command number and both outcome classes. {{run:RUN-drt-transfers}}
:::

A passing run earns `TESTED [T]` with its qualifier: how many commands ran, and the generator's statistics, meaning each outcome class's share, the self-transfer share and the largest balance reached. The last one returns in S6.L4. Engines belong in the stamp too. PGlite reports PostgreSQL 18.6 {{run:RUN-pglite-0511}}, so agreement on PGlite and on a Bench server is one semantics checked twice. The claim below keeps that assumption visible as a seam, drawn dashed: one database's agreement stands for the compiler. A later stage tests it.

::claim template=CL-6.1

:::item role=segment family=GEN-which-stamp template=t2 kcs=KC-6.differential-testing
@choice key=C
A receipt for a differential run shows 300 commands, no divergence, PGlite and a Bench server both named, the share of each outcome class, a self-transfer share of 0 percent, and the largest balance reached. Which line stamps it?

- A. `PROVED [P] · 300 commands · no divergence`
  - why: A run is not a proof, however clean.
  - mis: dp:X1
- B. `TESTED [T] · 300 commands`
  - why: A count with no statistics hides what the generator never reached.
  - mis: dp:G8
- C. `TESTED [T] · 300 commands · class shares and self-transfer share · both engines named`
  - why: The qualifier carries the count, what the generator drew and where it ran.
- D. `TESTED [T] · two independent engines agree`
  - why: Both engines report one server code base, so agreement is one check, not two.
  - mis: dp:Q15
:::

## Exit {minutes=3 kcs=KC-6.differential-testing}

:::item role=exit family=GEN-call-it template=t4 kcs=KC-6.differential-testing
@choice key=A
Which statement is true?

- A. A class of command the generator never draws is untested.
  - why: The suite can only diverge on commands it runs.
- B. The compiled plan matches the interpreter on every possible command.
  - why: A run covers the commands it drew, and nothing more.
  - mis: dp:X1
- C. PGlite and a real server agreeing is two independent checks.
  - why: They share one code base, so a common-mode bug passes both.
  - mis: dp:Q15
- D. Comparing final balances alone would catch a plan that overdrafts through the CHECK.
  - why: Balances can match while the outcome differs, as the CHECK-only plan shows.
  - mis: dp:Q14
:::
