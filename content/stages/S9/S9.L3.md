## Before the compiler {minutes=3 kcs=KC-9.target-ir}

Your compiler needs somewhere to compile to. The IR here is small: reads, writes, asserts and aborts, one transaction's worth. Its semantics and your compiler are LAB-9.3. First, what a careless scheme does to money.

:::item role=prequestion family=GEN-find-the-witness template=t1 kcs=KC-9.target-ir
@choice key=B
`move balance(a) from a to b`, with a = 5 and b = 0. A compiler debits a by balance(a), then credits b by balance(a), reading balance(a) a second time for the credit. What does b end with?

- A. 5
  - why: The source evaluates the amount once. This compile evaluates it again, after the debit.
  - mis: dp:S1
- B. 0
  - why: The second read sees the debited balance, 0, so the 5 leaves the system.
- C. 10
  - why: No write adds a second 5.
  - mis: dp:L7
:::

## Semantics, then a scheme {minutes=13 kcs=KC-9.target-ir}

The IR has seven instructions. `ldi` loads a constant, `read` loads a balance, `arith` computes, and `write` stores a balance. `assertGe` aborts with an error unless one register is at least another, and `abort` aborts outright. `writeIf` writes only when its condition holds, like an UPDATE whose WHERE matches no row, with the rowcount ignored. A run ends committed with a store, or aborted with an error, and an abort discards every write of the run, as a ROLLBACK does.

`exec` is a function: one program and one starting state give one outcome. State that anyway, as `exec_deterministic`. Forward simulation needs it (S9.L5), and a database under concurrency does not meet it. LLVM's IR is not deterministic (`undef`), so Alive2 checks refinement instead of equality.

The compile scheme makes two decisions. The amount is computed once, before the first write, and saved in a register. The credit reads the store the debit left, so a self-transfer nets to zero.

| Source | IR |
|---|---|
| `require e₁ e₂ err` | `e₁` into `r0`, `e₂` into `r1`, then `assertGe r0 r1 err` |
| `move amt src dst` | `amt` into `r0`; `read r1 src`; `sub r1 r1 r0`; `write src r1`; `read r1 dst`; `add r1 r1 r0`; `write dst r1` |
| `seq c₁ c₂` | the code for `c₁`, then the code for `c₂` |
| `abort err` | `abort err` |

:::instrument ins=INS-interp cell=1 recorded=RUN-tv-reference
```text
store (a0, a1) = (5, 0)

program 1
  ldi      r0 9
  write    a0 r0
  abort    denied

program 2
  ldi      r0 1
  ldi      r1 2
  assertGe r0 r1 insufficient
  ldi      r2 9
  write    a0 r2

program 3
  ldi      r0 1
  ldi      r1 2
  ldi      r2 9
  writeIf  r0 r1 a0 r2
```

@direction
Each program runs from the store above. The view shows what a client observes: committed with a store, or aborted with an error and the store the client sees.

@call key=B run=RUN-tv-reference surprise=no
Program 1 writes 9 to account 0, then executes `abort denied`. What does a client observe?

- A. Committed: balances (9, 0)
  - why: `abort` is not `skip`. The run ends in an error.
  - mis: dp:P4
- B. Aborted with `denied`: balances (5, 0)
  - why: An abort discards every write of the run, as ROLLBACK does.
- C. Aborted with `denied`: balances (9, 0)
  - why: That would be an IR whose aborts keep earlier writes. S9.L7 shows what that breaks.
  - mis: dp:P4

@after
Program 1 aborts with its error and its write is discarded {{run:RUN-tv-reference}}. Program 2 returns `insufficient` before it reaches its write. Program 3's condition fails, so it changes nothing and the run commits: a failed `writeIf` is silent, the same trap as S6's unchecked rowcount.
:::

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-9.target-ir
@choice key=B
A compile scheme reads both balances first and writes both after. Which command and store expose it?

- A. `transfer 5 a1 a2` from (10, 0)
  - why: With two accounts, both schemes end at (5, 5).
  - mis: dp:L7
- B. `transfer 5 a1 a1` from (10, 0)
  - why: The source nets to zero. The scheme writes the debit from the old balance, then the credit from the same old balance, and ends five higher.
- C. `transfer 5 a1 a2` from (3, 0)
  - why: Both abort with `insufficient` before any write.
  - mis: dp:X2
- D. None of these commands
  - why: Reading first matches writing in order only when no two writes name one account.
  - mis: dp:L7
:::

## Exit {minutes=4 kcs=KC-9.target-ir}

:::item role=exit family=GEN-call-it template=t4 kcs=KC-9.target-ir
@choice key=C
Which statement about the IR is true?

- A. `abort` keeps the writes made before it, and discards the rest.
  - why: An abort discards every write of the run.
  - mis: dp:P4
- B. Because `exec` is a function, the database under concurrency is deterministic too.
  - why: `exec` models one transaction. A database running many at once is another system.
  - mis: dp:P3
- C. A failing `assertGe` ends the run with its error, and the store is as it started.
  - why: A failed assert aborts, and an abort discards every write.
- D. A failing `writeIf` aborts the run with an error code.
  - why: It writes nothing and the run goes on.
  - mis: dp:Q3
:::
