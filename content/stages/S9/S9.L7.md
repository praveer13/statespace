## A write above its guard {minutes=12 kcs=KC-9.bad-optimization}

An agent reads your compiler's output for `transfer` and suggests a speed-up: debit first, check the guard after. Your preservation proof covers the compiler you wrote. It says nothing about the one the agent edited.

:::item role=prequestion family=GEN-find-the-witness template=t1 kcs=KC-9.bad-optimization
@choice key=C
Moving a write above an `assert`: when does it preserve meaning?

- A. Always, because aborts roll back.
  - why: Rollback hides a write after a failed guard. It cannot fix a guard that reads the written account after the write.
  - mis: dp:S1
- B. Never.
  - why: One cell of the table below is a sound move.
  - mis: dp:X3
- C. When the guard read its operands first, the write clobbers neither, and aborts roll back.
  - why: A failed guard then leaves nothing behind, and a passed guard saw the original values.
- D. Only when aborts keep earlier writes.
  - why: Kept writes leak whenever the guard fails.
  - mis: dp:P4
:::

Four cases, side by side:

| | Aborts roll back (this IR) | Aborts keep earlier writes |
|---|---|---|
| The guard read its operands before the write | preserved | broken: a failed guard leaves the write behind |
| The guard reads the written account after the write | broken: it tests the new value | broken |

:::instrument ins=INS-interp cell=1 recorded=RUN-lean-hoist
The agent's output for `transfer 1 a1 a2`.

```text
source    transfer 1 a1 a2
store     (a1, a2) = (1, 0)

hoisted: the debit block moved above the guard's read and assert
(the positivity check is unchanged and left out)
  ldi      r0 1
  read     r1 a1
  sub      r1 r1 r0
  write    a1 r1            # the debit, moved up
  read     r0 a1            # the guard now reads the debited balance
  ldi      r1 1
  assertGe r0 r1 insufficient
  ...                       # the credit, as before
```

@direction
The view runs the source and the hoisted program from the store above, and shows each outcome and the balances.

@call key=A run=RUN-lean-hoist surprise=yes
The source commits this transfer. What does the hoisted code do?

- A. Aborts with `insufficient`.
  - why: The guard now reads the debited balance, 0, and the amount is 1.
- B. Commits with the same balances.
  - why: That is the source's outcome. The hoist changed which balance the guard reads.
  - mis: dp:S1
- C. Commits and overdraws.
  - why: The guard got stricter, not weaker.
  - mis: dp:S1

@after
From the same store the source commits and the hoisted code aborts {{run:RUN-lean-hoist}}. The write moved above the guard's read, so the guard tests the debited balance. This is SP-9.1.
:::

::specimen id=SP-9.1

SP-9.1 is an erosion. Before it fires, restate CL-4.2 from memory: your checker's obligations hold for the source commands. Its strip has three segments: the proposition of the model, the correspondence between model and code, and the requirement fit.

:::item role=segment family=GEN-call-it template=t1 kcs=KC-9.bad-optimization
@choice key=B
The running code is compiled with the hoisted write. Which segment of CL-4.2's strip cracks?

- A. The proposition of the model.
  - why: Your proof about the source commands still stands. Nothing in the source changed.
  - mis: dp:P3
- B. The correspondence.
  - why: The obligation is still true of the source, and the code no longer follows the source.
- C. The requirement fit.
  - why: The requirement is unchanged. What broke is the link from model to code.
  - mis: dp:X4
- D. None: the hoisted code never commits a negative balance.
  - why: True, and beside the point. It now needs twice the amount to commit, so it refuses transfers the source allows, and your argument no longer describes it.
  - mis: dp:P3
:::

## From the stuck goal to the class {minutes=8 kcs=KC-9.bad-optimization}

Your preservation proof breaks in the sequence arm. The source's guard held, `amt ≤ bal src`, and the arm needs the guard the hoisted code tests, `amt ≤ bal src − amt`. Hand that reduced goal to Lean.

:::instrument ins=INS-bench-lean cell=2 recorded=RUN-lean-hoist
```lean
-- The sequence arm of the hoisted compile, reduced to arithmetic.
example (amt bal : Int) (h : amt ≤ bal) : amt ≤ bal - amt := by
  omega
```

@direction
Replay runs the tactic on the goal. The hypothesis is the source's guard, and the goal is the guard the hoisted code tests.

@call key=B run=RUN-lean-hoist surprise=moderate
What does `omega` do with this goal?

- A. Proves it.
  - why: The goal needs the balance to be at least twice the amount, and the hypothesis gives only `amt ≤ bal`.
  - mis: dp:L2
- B. Fails, and reports constraints that a counterexample must meet.
  - why: A failed `omega` describes a possible counterexample, as a negated query would in S1.
- C. Fails without saying why.
  - why: `omega` decides goals of this kind, so a failure comes with the constraints that defeat it.
  - mis: dp:X2

@after
The stuck goal is false: `omega` reports `a - 2*b ≤ -1` and `a - b ≥ 0`, with `a := bal` and `b := amt` {{run:RUN-lean-hoist}}. Pick values that meet them and replay them in the interpreter: the source commits where the hoisted code aborts. The smallest member is balance 1 with amount 1, the witness of SP-9.1.
:::

That witness belongs to a class, `amt ≤ bal src < 2·amt`. A fix that handles only balance 1 with amount 1 passes this test and misses balance 7 with amount 4, so check a non-minimal member too.

Two remedies: a preservation proof, which this compiler cannot have, or per-command translation validation, which rejects this output. The sound hoist rewrites the guard by substitution, as in S4.L2: after `src := src − amt`, the guard `amt ≤ src` becomes `src ≥ 0`.

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-9.bad-optimization
@choice key=D
The agent now hoists the debit and rewrites the guard to `balance ≥ 0`, tested on the debited balance. Which start separates the source from the rewrite?

- A. Balance 1, amount 1.
  - why: The old witness. The rewritten guard tests 0 ≥ 0 and commits, as the source does.
  - mis: dp:X3
- B. Balance 7, amount 4.
  - why: A non-minimal member of the old class. Both commit.
  - mis: dp:X3
- C. Balance 0, amount 1.
  - why: Both abort with `insufficient`, and the abort rolls the debit back.
  - mis: dp:P4
- D. None: the rewrite agrees with the source on every start.
  - why: Substitution moved the guard with the write. It aborts exactly when the amount exceeds the balance, and the abort undoes the debit.
:::

## Exit {minutes=3 kcs=KC-9.bad-optimization}

:::item role=exit family=GEN-find-the-witness template=t1 kcs=KC-9.bad-optimization
@choice key=B
A different agent hoists the credit above the guard. Which start separates the source from that code?

- A. Transfer 1 from a1 to a2, balances (1, 0).
  - why: Both commit with the same balances. That is the first witness, not this one.
  - mis: dp:X3
- B. Transfer 1 from a1 to a1, balance 0.
  - why: The source aborts, since 0 cannot cover 1. The hoisted credit makes the balance 1 before the guard reads it, so the code commits.
- C. Transfer 1 from a1 to a2, balances (0, 5).
  - why: Both abort, and the abort undoes the credit.
  - mis: dp:P4
- D. None: aborts roll back, so a hoisted write is always sound.
  - why: Rollback only hides a write after the guard has failed. Here the write changes what the guard reads.
  - mis: dp:S1
:::
