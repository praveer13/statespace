## The statement and what to generalize {minutes=13 kcs=KC-9.preservation-proof}

The theorem is CompCert's template, written for this fragment: if `compile c = some p`, then for every store and register file, the observation of the compiled run equals the observation of the source run. You do not prove it head on. You prove a stronger statement about related states, and read the theorem off it at the end.

`R` is the relation you froze in LAB-9.4. `Follows` says what it means for a target run to follow a source outcome. A source run that commits is followed by a target run that commits, in states R relates again. A source run that aborts is followed by a target run that aborts with the same error. Every other pairing is `False`, which is how aborts stay observable: a compiled program that commits where the source aborts follows nothing.

`SimR c p` says that from any related states, with any registers, the outcome of `c` is followed by the run of `p`. The induction proves `compile c = some p → SimR c p`, one case per kind of command. Look at `seq c₁ c₂`, whose program is `p₁ ++ p₂`. The second half runs in the store, and with the registers, that the first half left.

:::instrument ins=INS-goal-replay cell=1 recorded=RUN-lean-preservation-frag
Two versions of one statement, and the start of the sequence case for each. `R` is your relation from LAB-9.4, and the rest comes from the template.

```lean
def Follows (o : Outcome) (t : Except Err (Regs × Store)) : Prop :=
  match o, t with
  | .committed s', .ok (regs', st') => R s' regs' st'
  | .aborted e, .error e' => e = e'
  | _, _ => False

-- The statement you prove: from any related states, with any registers.
def SimR (c : Cmd) (p : List Instr) : Prop :=
  ∀ (s : Store) (regs : Regs) (st : Store), R s regs st →
    Follows (runS c s) (exec p regs st)

-- A variant that reads like the same statement, with the registers fixed.
def SimZero (c : Cmd) (p : List Instr) : Prop :=
  ∀ (s : Store) (st : Store), R s (fun _ => 0) st →
    Follows (runS c s) (exec p (fun _ => 0) st)

theorem seq_start (c₁ c₂ : Cmd) (p₁ p₂ : List Instr)
    (h₁ : SimR c₁ p₁) (h₂ : SimR c₂ p₂) : SimR (.seq c₁ c₂) (p₁ ++ p₂) := by
  intro s regs st hR
  rw [exec_append]
  sorry

theorem seq_start_zero (c₁ c₂ : Cmd) (p₁ p₂ : List Instr)
    (h₁ : SimZero c₁ p₁) (h₂ : SimZero c₂ p₂) : SimZero (.seq c₁ c₂) (p₁ ++ p₂) := by
  intro s st hR
  rw [exec_append]
  sorry
```

## A lemma for expressions, then one posting {minutes=14 kcs=KC-9.preservation-proof}

Every case compiles some expression, so every case leans on one lemma about expression code. `compE_correct` says three things about the code for `e` compiled at register `r`: the value of `e` lands in register `r`; the store is unchanged; and every register below `r` keeps its value. The last clause is a frame condition, as in S4. The guard case depends on it: the guard keeps one operand in register 0 while it evaluates the other into register 1, and without the frame clause the second evaluation could overwrite the first.

A sibling shows the shape of every case without giving the lab's away. `post a e` adds the value of `e` to account `a` and does nothing else. It is last lesson's posting with an expression for its amount. It compiles to the code for `e` at register 0, then three instructions: read the balance of `a`, add register 0, write the sum back. The proof makes four moves: split the code with the append law, run the expression code by its lemma, run the three instructions, and show R again. Goal Replay hides the last moves. Rung 2 hides the last two, rung 3 hides all but the first, and the blanks carry no prompt.

-- From the template: compE_correct, exec_append and a reference R

-- Rung 2: the last two moves are blank.
theorem post_sim (a : Acct) (e : Expr) (s : Store) (regs : Regs) (st : Store)

  rw [exec_append]

## Sequences, aborts and the assembled theorem {minutes=14 kcs=KC-9.preservation-proof}

The sequence case has two branches, and they use different things. If `c₁` commits, its simulation gives related states and registers, and `c₂`'s simulation is applied at the store `c₁` left, with the registers `c₁`'s code left. If `c₁` aborts, the compiled first half aborts with the same error, the append law's bind passes the error along, and `c₂`'s code never runs. That is why `seq_abort` takes no hypothesis about `c₂`. A proof that reaches for one is treating an abort as an ordinary step.

The same shape appears in two postings in a row. Run the cell and see which store the second posting's lemma is applied at.

:::instrument ins=INS-bench-lean cell=3 recorded=RUN-lean-preservation-frag
Two postings in a row, the sibling of the sequence case, on your Bench.

```lean
-- post_sim is the sibling lemma from the last cell.
theorem post_post_sim (a b : Acct) (e f : Expr) (s : Store) (regs : Regs) (st : Store)
    (hR : R s regs st) :
    ∃ regs' st', exec (compPost a e ++ compPost b f) regs st = .ok (regs', st') ∧
      R (runPost b f (runPost a e s)) regs' st' := by
  rw [exec_append]
  obtain ⟨regs₁, st₁, h₁, hR₁⟩ := post_sim a e s regs st hR
  rw [h₁]
  exact post_sim b f _ _ _ hR₁

#print axioms post_post_sim
```

Assembling the theorem takes three moves. Induction on `c`, with the program generalized, gives the sequence case both hypotheses, and the five case lemmas give `compile_correct`. Then `preservation`: `R_init` says the starting states are related, `SimR` gives a `Follows` for the run, and `R_obs` turns related final states into equal observations. Last comes what you do not prove by hand: `#print axioms preservation` must list only the standard three, and the comparator checks your proof against the pinned statement {{run:RUN-lean-comparator}}. In the lab, manual mode keeps `omega` and `grind` off, and a step an automation closes is flagged on the receipt.

After LAB-9.6 the claim card for this theorem opens as PROVED modulo the cases you have not closed yet, each carried as ASSUMED [A]. It changes as each stage closes, and a goal you park at 90 minutes joins it as one more [A] case.

@choice key=D
The sequence case, `seq_commit` and `seq_abort` together. Here are six moves, in no order. Two of them do not belong in a proof.

- (a) Split the compiled code with the append law.
- (b) Case on how `c₁` ran: it committed or it aborted.
- (c) Committed: use `c₁`'s simulation, then `c₂`'s at the intermediate store, from the registers `c₁`'s code left.
- (d) Aborted: `c₁`'s code aborts with the same error, so `c₂`'s code never runs.
- (e) Aborted: use `c₂`'s simulation to show the second half aborts too.
- (f) Committed: use `c₂`'s simulation at the original store.

Which sequence is a proof?

- A. (a), (b), (f), (d)
  - why: Move (f) applies `c₂`'s simulation at the starting store, but `c₂` runs from the store `c₁` left.
  - mis: dp:S1
- B. (a), (b), (c), (e)
  - why: Move (e) treats an abort as one more step. When `c₁` aborts, `c₂`'s code never runs.
  - mis: dp:P4
- C. (c), (a), (b), (d)
  - why: Move (c) needs the branch that (b) opens and the code that (a) splits, so it cannot come first.
  - mis: dp:L6
- D. (a), (b), (c), (d)
  - why: Split, case, then each branch with what it has. The commit branch chains the two simulations, and the abort branch needs neither.

@choice key=C
The proof of `compile_correct` by induction on the command. Here are six moves, in no order. Two of them do not belong in a proof.

- (a) Induct on `c`, generalizing the program `p`.
- (b) In the `seq` case, read `compile (.seq c₁ c₂) = some p` to get `p₁` and `p₂`.

- (e) Assume `compile_complete`, so that no case meets `none`.
- (f) In the `seq` case, apply `preservation` to the two halves.

Which sequence is a proof?

- A. (b), (a), (c), (d)
  - why: The compile equation of a sub-command exists only inside the induction, so (a) comes first.
  - mis: dp:L5
- B. (a), (b), (e), (d)
