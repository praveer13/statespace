## One database is one instance {minutes=17 kcs=KC-9.sql-equivalence}

Your compiler turns each command into SQL, and an agent offers a faster rewrite of one statement. Your suite agrees with it. This lesson is about what that agreement establishes, and about checking the compiler's output one command at a time instead.

:::item role=prequestion family=GEN-find-the-witness template=t1 kcs=KC-9.sql-equivalence
@choice key=B
An agent rewrote your compiled credit as an upsert, `INSERT … ON CONFLICT (id) DO UPDATE`. The fixture database and your S6 suite agree with the original. What is established?

- A. PROVED [P]: the rewrite is equivalent.
  - why: Agreement on instances is a test.
  - mis: dp:X1
- B. TESTED [T]: it agrees on the fixture.
  - why: One instance is evidence, stamped as such.
- C. Equivalent whenever the accounts exist.
  - why: The instances tried are read as all the relevant ones, and the schema allows a missing account.
  - mis: dp:A6
- D. Nothing at all.
  - why: A matching instance is evidence, and the stamp says how much.
  - mis: dp:G8
:::

The validator compares outcome classes for each command: a commit with balances related by your R(S, D), a typed error, or a database error code. Evidence for a verdict comes in three kinds, and each earns its own stamp.

| Evidence | Tools, on your Bench | Stamp |
|---|---|---|
| A proof for a fragment | containment by homomorphism (drawer D-17), QED | [P] of the prover's encoding, uncertified |
| A bounded search | VeriEQL, databases up to a size | [M] · bound |
| Refutation and tests | Polygon, generated databases | [R] after replay, otherwise [T] · n |

A prover's NEQ is not [R]: only an instance that replays through both semantics refutes. A model's "equivalent" earns no stamp at all.

:::instrument ins=INS-pglite cell=1 recorded=RUN-pg-one-db
The original credit and the upsert, on a database that lacks the destination account. On the fixture database, where account 2 exists, the two agree.

```sql
CREATE TABLE acct (id int PRIMARY KEY, bal bigint NOT NULL CHECK (bal >= 0));
INSERT INTO acct VALUES (1, 100);
-- the compiled credit of a transfer of 30 to account 2
UPDATE acct SET bal = bal + 30 WHERE id = 2;
-- the agent's rewrite
INSERT INTO acct (id, bal) VALUES (2, 30)
  ON CONFLICT (id) DO UPDATE SET bal = acct.bal + 30;
SELECT id, bal FROM acct ORDER BY id;
```

@direction
Read the row count each statement reports, then the table. In your plan, a credit that touches zero rows becomes a typed error and a rollback.

@call key=C run=RUN-pg-one-db surprise=moderate
On a database that lacks the destination account, what happens?

- A. Both fail: no such destination account.
  - why: An upsert inserts the row when none matches, so it does not fail.
  - mis: dp:Q10
- B. Both commit, creating the missing account.
  - why: The UPDATE matches no row and reports `UPDATE 0` {{run:RUN-pg-one-db}}, and the plan's rowcount check rolls it back.
  - mis: dp:Q10
- C. The original rolls back, the upsert creates it.
  - why: One statement reports zero rows, the other inserts one.

@after
The credit reported `UPDATE 0`, which your plan turns into a typed error and a rollback. The upsert reported `INSERT 0 1` and left account 2 at 30 {{run:RUN-pg-one-db}}. On the fixture both leave account 2 at 80, so your suite saw nothing. This is SP-9.4, an erosion: SEAM-11 cracks, and CL-6.1's correspondence held only for the one instance it tried.
:::

::specimen id=SP-9.4

Restate CL-6.1 from memory: your suite's agreement says the compiler's SQL means what your commands mean. Its strip has three segments: the proposition of the model, the correspondence between model and database, and the requirement fit.

:::item role=segment family=GEN-call-it template=t1 kcs=KC-9.sql-equivalence
@choice key=B
A rewrite agrees with the original on your fixture and differs on a database without the destination account. Which segment of CL-6.1's strip cracks?

- A. The proposition of the model.
  - why: The source semantics did not change. The rewrite is not what it describes.
  - mis: dp:X2
- B. The correspondence.
  - why: One database's agreement stood for the compiler, and a second database disagrees.
- C. The requirement fit.
  - why: The requirement is unchanged. What broke is the link from model to database.
  - mis: dp:X4
- D. None: the suite still passes.
  - why: A passing suite is the evidence that missed it.
  - mis: dp:X1
:::

## Shape is not meaning {minutes=5 kcs=KC-9.sql-equivalence}

A shape check is the cheap alternative to a replay. Here is a mutant of the compiled transfer whose credit names the source account.

:::instrument ins=INS-lane-a cell=2 recorded=RUN-sql-shape-validator
```text
plan    transfer 30 from account 1 to account 2, with the credit naming account 1
  UPDATE acct SET bal = bal - 30 WHERE id = 1 AND bal >= 30    -- expects 1 row
  UPDATE acct SET bal = bal + 30 WHERE id = 1                  -- expects 1 row

check   shape      two UPDATEs, each WHERE id = <parameter>, each expecting one row
check   semantic   lift both sides to IR form, compare outcome classes, replay any rejection
```

@direction
The reference validator runs both checks on the plan, from a fixture where accounts 1 and 2 hold 100 and 0.

@call key=A run=RUN-sql-shape-validator surprise=no
Does the shape check accept the mutant?

- A. Accepts.
  - why: The shape is intact: two UPDATEs, each by id, each touching one row.
- B. Rejects.
  - why: A shape check cannot see which account a parameter names.
  - mis: dp:X2

@after
The shape check accepts it. The semantic check rejects it with an instance that replays: account 2 never receives the 30 {{run:RUN-sql-shape-validator}}. This is SP-9.2. The validator you build replays each plan on PGlite and the source on the interpreter, and rejects only with an instance whose outcome classes differ.
:::

::specimen id=SP-9.2

A counterexample must satisfy the schema, here `bal bigint NOT NULL CHECK (bal >= 0)`. An instance the database cannot insert is spurious and is discarded.

::claim template=CL-9.3

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-9.sql-equivalence
@choice key=C
A guard in your plan reads `WHERE id NOT IN (SELECT acct_id FROM holds)`. The agent rewrites it as `WHERE NOT EXISTS (SELECT 1 FROM holds h WHERE h.acct_id = acct.id)`, and `holds.acct_id` allows NULL. Which schema-valid instance separates them?

- A. `holds` is unpopulated, NULL-free.
  - why: Both guards let every account through, so they agree.
  - mis: dp:X1
- B. `holds` has one row, for account 1.
  - why: Both guards stop account 1 and let the others through.
  - mis: dp:X1
- C. `holds` has one row whose `acct_id` is NULL.
  - why: `id NOT IN (…, NULL)` is never true, so the original lets no account through. `NOT EXISTS` finds no match and lets them all through.
- D. An `acct` row whose balance is −5.
  - why: The CHECK refuses that row. An instance the database cannot insert is spurious.
  - mis: dp:X2
:::

## Exit {minutes=3 kcs=KC-9.sql-equivalence}

:::item role=exit family=GEN-which-stamp template=t1 kcs=KC-9.sql-equivalence
@choice key=B
A bounded checker finds no counterexample among all databases of up to 4 rows per table. Which stamp does the pair earn?

- A. PROVED [P] · prover, uncertified, unbounded
  - why: A bound limits the search. Databases of 5 rows were never tried.
  - mis: dp:X1
- B. MODEL-CHECKED [M] · up to 4 rows per table
  - why: Every database within the bound was checked, and the bound is part of the stamp.
- C. TESTED [T] · 1 fixture instance
  - why: It searched every database up to the bound, not one.
  - mis: dp:X2
- D. UNKNOWN [?] · search abandoned
  - why: The search finished, and a stamp that names its bound is available.
  - mis: dp:Z2
:::
