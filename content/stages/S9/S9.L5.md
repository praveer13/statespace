## Two questions first {minutes=2 kcs=KC-9.forward-simulation,KC-9.simulation-kinds}

A preservation theorem is proved by a simulation: a relation between source states and target states, and a diagram that says the relation survives each step. The direction of the diagram decides what the theorem rules out, and this lesson is about reading it.

:::item role=prequestion family=GEN-call-it template=t4 kcs=KC-9.forward-simulation,KC-9.simulation-kinds
@choice key=B
Forward simulation: every source behavior is a target behavior. Backward: every target behavior is a source behavior. Which one says "the compiled code never does what the source forbids"?

- A. Forward
  - why: Forward shows the target can match the source, not that it does nothing else.
  - mis: dp:P1
- B. Backward
  - why: Every target behavior is a source behavior, so the target has none that the source lacks.
- C. Both are needed
  - why: One direction carries that sentence.
  - mis: dp:P1
- D. Neither
  - why: A direction of simulation says exactly this.
  - mis: dp:X2
:::

:::item role=prequestion family=GEN-call-it template=t4 kcs=KC-9.simulation-kinds,KC-9.forward-simulation
@choice key=B
When does the easier direction, forward, give you the other?

- A. When the source is deterministic
  - why: A deterministic source does not stop the target from having extra behaviors.
  - mis: dp:P1
- B. When the target is deterministic
  - why: Leroy (CACM 2009, section 2.4) states it "provided the target language of the compiler has deterministic semantics". CompCert's `forward_to_backward_simulation` asks for a receptive source and a determinate target.
- C. Always
  - why: A target that may abort on any run is a counterexample.
  - mis: dp:P1
- D. Never
  - why: With a deterministic target, the one target behavior is the one that forward simulation matched.
  - mis: dp:P1
:::

## The diagram {minutes=13 kcs=KC-9.forward-simulation}

A simulation needs a matching relation R between a source store and the target's registers and store. Yours, from LAB-9.4, is small: R ignores registers, because they are dead between commands. Leroy puts it this way: "The gist of a proof by simulation is the definition of the ∼ relation" (CACM 2009, section 4.3).

Forward simulation for your fragment is a square. Start from related states. Run the source command and run the compiled code. The source's outcome must be matched: if it commits with a store, the code commits with registers and a store related to it, and if it aborts with an error, the code aborts with the same error.

The square below is drawn for a single posting, `post a v`, which adds `v` to account `a`. It sits outside your fragment, so the lab's cases stay yours. The compiled code loads the amount, reads the balance, adds, and writes.

:::instrument ins=INS-goal-replay cell=1 recorded=RUN-lean-preservation-frag
```lean
abbrev Acct := Nat
abbrev Store := Acct → Int
abbrev Regs := Nat → Int

def upd (f : Nat → Int) (k : Nat) (v : Int) : Nat → Int :=
  fun j => if j = k then v else f j

-- source: one posting adds v to account a
def postS (a : Acct) (v : Int) (s : Store) : Store := upd s a (s a + v)

inductive Instr where
  | ldi (r : Nat) (v : Int)
  | read (r : Nat) (a : Acct)
  | add (rd r₁ r₂ : Nat)
  | write (a : Acct) (r : Nat)

def step : Instr → Regs × Store → Regs × Store
  | .ldi r v, (regs, st) => (upd regs r v, st)
  | .read r a, (regs, st) => (upd regs r (st a), st)
  | .add rd r₁ r₂, (regs, st) => (upd regs rd (regs r₁ + regs r₂), st)
  | .write a r, (regs, st) => (regs, upd st a (regs r))

def run : List Instr → Regs × Store → Regs × Store
  | [], m => m
  | i :: is, m => run is (step i m)

-- target: load the amount, read the balance, add, write
def postT (a : Acct) (v : Int) : List Instr :=
  [.ldi 0 v, .read 1 a, .add 1 1 0, .write a 1]

-- the matching relation: the stores agree, registers are ignored
def R (s : Store) (_regs : Regs) (st : Store) : Prop := st = s

theorem post_sim (a : Acct) (v : Int) (s : Store) (regs : Regs) (st : Store)
    (h : R s regs st) :
    R (postS a v s) (run (postT a v) (regs, st)).1 (run (postT a v) (regs, st)).2 := by
  unfold R at h ⊢
  rw [h]
  simp [postT, run, step, postS, upd]
```

@direction
Replay shows: `post_sim` one tactic at a time, with the goal after each. The theorem says that from related states, the compiled code ends in a state related to the source's new store.

@tap
the compiled posting leaves the target related to the source

@call key=A run=RUN-lean-preservation-frag surprise=no
After `post`'s compiled code runs from related states, what must you re-establish?

- A. The target's store equals the source's new store.
  - why: R relates the source's new store to the target's final registers and store, and only the stores have to agree.
- B. The target's registers equal the source's.
  - why: The source has no registers. R forgets them, as Leroy's relation ignores dead registers.
  - mis: dp:P6
- C. Both.
  - why: Requiring equal registers would fail on every run, because the compiled code uses scratch registers.
  - mis: dp:P6
- D. Nothing: the relation carries over.
  - why: The store changed, so the relation has to be shown again at the new store.
  - mis: dp:X2

@after
The proof unfolds R, runs the four instructions and compares two stores {{run:RUN-lean-preservation-frag}}. Registers never appear, because R never mentions them. In the lab the amount is an expression, and its lemma `compE_correct` does the work of the first instruction.
:::

:::item role=segment family=GEN-proof-structure template=t1 kcs=KC-9.forward-simulation
@choice key=A
The proof of `post_sim` has run `unfold R at h ⊢` and then `rw [h]`, where `h : st = s`. What is the goal now?

- A. `(run (postT a v) (regs, s)).2 = postS a v s`
  - why: R compares stores, and `rw [h]` has replaced `st` by `s`.
- B. `(run (postT a v) (regs, s)).1 = regs`
  - why: R does not compare registers.
  - mis: dp:P6
- C. `(run (postT a v) (regs, s)).2 = s`
  - why: That relates the target's final store to the source's old store, but the posting changed it.
  - mis: dp:S1
- D. `R s regs s`
  - why: That relates the states before the posting. The goal is about the states after it.
  - mis: dp:X2
:::

## Which direction, when {minutes=13 kcs=KC-9.simulation-kinds,KC-9.forward-simulation}

Forward simulation says every source behavior is matched by a target behavior. Backward says every target behavior is a source behavior, and that is the direction users of a compiler care about. Forward is the easier proof: you follow the source and build the target's matching run. Leroy's rule is that forward gives backward when the target is deterministic. Bisimulation is both directions at once.

Your IR is deterministic, which is why S9.L3 states it. A database under concurrency is not: it may abort a transaction with a serialization failure on any run. The cell compares your IR with a variant whose step `maybeFail` may do exactly that.

:::instrument ins=INS-interp cell=2 recorded=RUN-tv-reference
```text
program
  ldi       r0 5
  ldi       r1 1
  assertGe  r0 r1 nonPositive
  read      r0 a1
  ldi       r1 5
  assertGe  r0 r1 insufficient
  ldi       r0 5
  read      r1 a1
  sub       r1 r1 r0
  write     a1 r1
  read      r1 a2
  add       r1 r1 r0
  write     a2 r1
  maybeFail serializationFailure    # does nothing, or aborts the run with this error

store (a1, a2) = (10, 0)
view  every outcome the program can reach
```

@direction
The run view lists every outcome the program can reach from the store above. `maybeFail` is a step with two possible results: nothing, or an abort.

@call key=C run=RUN-tv-reference surprise=moderate
This target may abort with a serialization failure on any run. You proved forward simulation. Is every target behavior a source behavior?

- A. Yes.
  - why: Forward simulation never rules out extra target behaviors.
  - mis: dp:P1
- B. Yes, once retries are added.
  - why: Retries move the problem into the runtime claim, where termination is assumed (CL-6.5).
  - mis: dp:P3
- C. No: the extra abort is a target behavior the source lacks.
  - why: By definition. The source never aborts with that error, and forward simulation says nothing about it.

@after
The run view lists two outcomes {{run:RUN-tv-reference}}: the committed transfer, and an abort that discards it. The committed outcome matches the source, so forward simulation holds. The abort has no source behavior to match, so backward simulation fails. This is why S9.L3 states the IR's determinism, and why serialization failures are outcome classes in S6 and S9.L8 rather than invisible {{run:RUN-pg-anomalies}} {{run:RUN-pg-claims}}.
:::

:::item role=segment family=GEN-call-it template=t4 kcs=KC-9.simulation-kinds
@choice key=B
Which description is a backward simulation?

- A. Every source run is matched by a target run with the same observation.
  - why: That starts from the source, so it is forward.
  - mis: dp:P1
- B. For every target run there is a source run with the same observation.
  - why: It starts from the target and finds a source run.
- C. Related states step to related states, in both directions.
  - why: That is bisimulation.
  - mis: dp:P1
- D. The compiled code agrees with the source on every one of n sampled commands.
  - why: That is a sampled check, not a simulation.
  - mis: dp:X1
:::

## One family, five methods {minutes=12 kcs=KC-9.simulation-kinds}

The correspondence checks you have met are one family. Each says how concrete runs relate to source behavior, over a different set of runs.

| Method | Direction | Over | Stamp |
|---|---|---|---|
| Preservation proof (CL-9.2) | forward, and backward when the target is deterministic | every program and store | [P] |
| Translation validation (S9.L2) | both, for one output | stores within a bound | [M] · bound |
| Differential testing (S6.L3, CL-6.1) | equal outcome classes | n sampled commands | [T] · n |
| Abstract serializability (S6.L8, CL-6.3) | backward: each history is explained by a serial source run | recorded histories | [T] · n · search bound |
| Trace validation (S8.L6, CL-8.3) | backward: each implementation trace is a behavior of the spec | n seeds | [T] · n seeds |

:::instrument ins=INS-receipt cell=3 recorded=RUN-serializability-fixtures
```text
receipt  CL-6.3   abstract serializability, over recorded histories
receipt  CL-8.3   trace validation, over n seeds
view     side by side: what each check starts from, and what it searches for
```

@direction
Two of your own receipts, side by side. Each check starts from one thing and searches for another, and which is which is the direction.

@call key=B surprise=yes
Your S6 checker accepted a history because some serial order of source commands reproduced every committed output. Which direction was that?

- A. Forward
  - why: Forward starts from a source run and builds the target's. This check starts from the recorded history.
  - mis: dp:P1
- B. Backward
  - why: It starts from the concrete history and searches for a source run that explains it.
- C. Bisimulation
  - why: It checked one direction, on recorded histories only.
  - mis: dp:P1

@after
Backward: the history is the starting point, and the search is for a source run behind it. Trace validation takes the same direction against a spec. Both are TESTED [T] over what was recorded, where a preservation proof is PROVED [P] over every program.
:::

:::item role=segment family=GEN-call-it template=t4 kcs=KC-9.simulation-kinds
@choice key=C
Which of these checks is trace validation?

- A. n sampled commands run through the compiled SQL and the source, with outcome classes compared.
  - why: That is differential testing, TESTED [T] · n.
  - mis: dp:X2
- B. Every store within a bound, enumerated for one compiled output.
  - why: That is translation validation, MODEL-CHECKED [M] · bound.
  - mis: dp:X2
- C. n seeded runs of the implementation, each checked as a behavior of the spec.
  - why: Each implementation trace has to be a behavior the spec allows. That is backward, and it earns TESTED [T] · n seeds.
- D. A Lean proof for every program and store.
  - why: That is a preservation proof, PROVED [P].
  - mis: dp:X2
:::

## Exit {minutes=5 kcs=KC-9.forward-simulation,KC-9.simulation-kinds}

:::item role=exit family=GEN-proof-structure template=t1 kcs=KC-9.forward-simulation
@choice key=A
The proof of `post_sim` has run `unfold R at h ⊢`, with `h : R s regs st` unfolded to `st = s`. Which goal comes next?

- A. `(run (postT a v) (regs, st)).2 = postS a v s`
  - why: R is unfolded in the conclusion, so the goal compares the two stores. `h` is still a hypothesis.
- B. `(run (postT a v) (regs, st)).1 = regs`
  - why: R does not compare registers.
  - mis: dp:P6
- C. `st = s`
  - why: That is the hypothesis, not the goal.
  - mis: dp:L6
- D. `R s regs st`
  - why: That is `h` before it was unfolded. The goal is the relation at the new store.
  - mis: dp:L6
:::

:::item role=exit family=GEN-call-it template=t4 kcs=KC-9.simulation-kinds
@choice key=A
Which statement is true?

- A. With a deterministic target, forward simulation gives backward simulation.
  - why: The one target behavior is the one that forward simulation matched.
- B. With a deterministic source, forward simulation gives backward simulation.
  - why: A deterministic source does not stop the target from having extra behaviors.
  - mis: dp:P1
- C. Forward simulation shows the compiled code never does what the source forbids.
  - why: That sentence is backward simulation.
  - mis: dp:P1
- D. A preservation proof and a differential test establish the same thing over different sample sizes.

:::
