## One output, not the compiler {minutes=3 kcs=KC-9.translation-validation}

In LAB-9.1 a validator accepted one compiled transfer and rejected another. This lesson says what each verdict established, and what it left open.

:::item role=prequestion family=GEN-which-stamp template=t1 kcs=KC-9.translation-validation
@choice key=B
A translation validator accepts one compiled command. What is established?

- A. The compiler preserves meaning for every command.
  - why: One output was checked. The next output is a new question.
  - mis: dp:P3
- B. This output agrees with the source on every store within the validator's bound.
  - why: The verdict is about one output and one bound.
- C. This output agrees with the source on every store.
  - why: Only an unbounded method says that, and then only about its own encoding.
  - mis: dp:X1
- D. This output has the same text as the reference compiler's.
  - why: The validator compares behavior, never text.
  - mis: dp:X2
:::

## Run the validator {minutes=13 kcs=KC-9.translation-validation}

Translation validation checks each output a compiler produces instead of the compiler. Pnueli, Siegel and Singerman introduced it in 1998, and Necula applied it to a production compiler in 2000. Leroy's CompCert paper states the move in one line: run untrusted code, then check its result with a validator that is itself proved.

The reference validator runs two semantics on every store within its bound, the source's and the IR's, and compares the outcomes. It reports either accepted within the bound, with the bound printed, or rejected, with a store on which the outcomes differ. Alive2 works this way for LLVM: bounded by design, and built to avoid false alarms.

The stamp depends on how the search went. Every store within a bound is MODEL-CHECKED [M] with the bound printed. Sampled stores are TESTED [T] with n. A symbolic encoding of straight-line code could be PROVED [P] of that encoding, uncertified. Whichever it is, the validator joins your trusted base in S9.L9.

IR programs here use registers `r0`, `r1`, … and numbered accounts `a1`, `a2`. `assertGe r1 r0 insufficient` aborts with `insufficient` unless r1 ≥ r0. The command is a transfer from an account to itself, the case behind SP-2.1 {{run:RUN-lean-selftransfer}}.

:::instrument ins=INS-lane-a cell=1 recorded=RUN-tv-reference
```text
validate transfer 5 a1 a1
output:
  ldi      r0 5
  ldi      r1 1
  assertGe r0 r1 nonPositive
  read     r0 a1
  ldi      r1 5
  assertGe r0 r1 insufficient
  ldi      r0 5            # the amount, saved before any write
  read     r1 a1           # credit first ...
  add      r1 r1 r0
  write    a1 r1
  read     r1 a1           # ... then debit; each write re-reads its account
  sub      r1 r1 r0
  write    a1 r1
```

@direction
The validator runs the source and this output on every store within its bound and compares outcomes. In the source, the debit comes first and the credit reads the debited balance.

@call key=A run=RUN-tv-reference surprise=yes
What does the validator report for the swapped writes?

- A. Accepted within the bound.
  - why: Two postings commute when each reads the current balance and the amount is fixed, a self-transfer included.
- B. Rejected: a self-transfer counterexample.
  - why: SP-2.1's mint needs both balances read before either write. This order re-reads.
  - mis: dp:L7
- C. Rejected: an insufficient-funds counterexample.
  - why: The guards and their asserts did not move.
  - mis: dp:S1

@after
Accepted, and the verdict carries the bound it covered {{run:RUN-tv-reference}}. The swapped output is a different program with the same meaning, which is why the validator compares outcomes and never text.
:::

:::instrument ins=INS-lane-a cell=2 recorded=RUN-tv-reference
```text
validate transfer 5 a1 a1 using the reference compiler's output

validate transfer 5 a1 a1 using this output, both balances read first:
  ldi      r0 5
  ldi      r1 1
  assertGe r0 r1 nonPositive
  read     r0 a1
  ldi      r1 5
  assertGe r0 r1 insufficient
  ldi      r0 5
  read     r1 a1
  read     r2 a1
  sub      r1 r1 r0
  add      r2 r2 r0
  write    a1 r1
  write    a1 r2
```

@direction
Two runs. The first checks the course's reference compiler on this command. The second checks an output that reads both balances before it writes either.

@call key=C run=RUN-tv-reference surprise=no
For the reference compiler's output, the validator enumerated every store within its bound and found no divergence. Which stamp does that earn?

- A. PROVED [P] · validator
  - why: Complete within a bound is not complete without one.
  - mis: dp:X1
- B. TESTED [T] · n
  - why: [T] is for sampled instances. This enumeration was exhaustive within its bound.
  - mis: dp:X2
- C. MODEL-CHECKED [M] · with the bound printed
  - why: Every store in the printed bound was checked, so the stamp names the bound and says complete within it.

@after
The first run earns [M] within its bound. The second output is rejected {{run:RUN-tv-reference}}: the credit's write lands after the debit's and was computed from the old balance, so the account ends higher than the source leaves it. The store the validator prints replays in both semantics, and then it is REFUTED [R].
:::

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-9.translation-validation
@choice key=C
An agent's output for `transfer 5 a1 a2` is the reference output with the `insufficient` assert dropped. Which store, as balances (a1, a2), separates the output from the source?

- A. (40, 0)
  - why: Both commit with the same balances. The dropped assert would have passed.
  - mis: dp:G4
- B. (5, 3)
  - why: Both commit. The balance covers the amount exactly.
  - mis: dp:O1
- C. (2, 0)
  - why: The source aborts with `insufficient`. The output has no assert, commits, and leaves account 1 negative.
- D. None
  - why: A dropped assert matters on exactly the stores where it would have fired, and (2, 0) is one.
  - mis: dp:X2
:::

## Exit {minutes=4 kcs=KC-9.translation-validation}

:::item role=exit family=GEN-which-stamp template=t2 kcs=KC-9.translation-validation
@choice key=A
A validator prints `accepted`, and its bound line names two accounts and balances from 0 to 40, with every store enumerated. Complete the stamp: MODEL-CHECKED [M] · …

- A. Complete within the bound: two accounts, balances 0 to 40.
  - why: The qualifier copies the bound and says the enumeration was exhaustive inside it.
- B. n sampled stores, with the generator's statistics.
  - why: Every store in the bound was enumerated, so nothing was sampled.
  - mis: dp:X2
- C. Every store, so no bound.
  - why: The bound stays on the stamp because the enumeration stopped there.
  - mis: dp:X1
- D. The compiler, for every command.
  - why: The verdict covers one output.
  - mis: dp:P3
:::
