## Two questions first {minutes=2 kcs=KC-9.observations}

A compiler's theorem says the compiled program behaves like the source. "Behaves" does all the work: it names what a client may see, and anything it leaves out can change without breaking the theorem. This lesson picks that list for the compiler you are building, and shows what a weak list lets through.

:::item role=prequestion family=GEN-leaks-to-observer template=t3 kcs=KC-9.observations
@choice key=B
A compiler turns a failed funds check into "change nothing, report success". Your theorem compares final balances only. Does it catch the bug?

- A. Yes.
  - why: The balances end equal either way. Only the outcome differs.
  - mis: dp:P1
- B. No.
  - why: A source that aborts leaves the balances as they were, and so does the compiled program that does nothing.
- C. Only on self-transfers.
  - why: Neither run writes anything.
  - mis: dp:S1
:::

:::item role=prequestion family=GEN-call-it template=t4 kcs=KC-9.observations
@choice key=C
Which is part of CompCert's observable behavior?

- A. Execution time, measured per run
  - why: The manual excludes it by name, together with memory consumption.
  - mis: dp:P5
- B. Memory consumption at each step
  - why: The manual excludes it by name, together with execution time.
  - mis: dp:P5
- C. Its input and output trace, and how it ends
  - why: Termination, divergence or going wrong, plus the trace of input and output (Leroy 2009, section 2.1).
- D. The generated assembly, instruction by instruction
  - why: It is an artifact, not a behavior.
  - mis: dp:X2
:::

## What a client sees {minutes=13 kcs=KC-9.observations}

A client of your system sends a command and sees an outcome: the command committed, or it aborted with an error code. An observation is a function of the starting store and that outcome. Two runs are observationally equivalent when no observation tells them apart. The weaker the observation, the more programs count as equal, and the easier the theorem is to prove.

Take the compiler of SP-9.3. It turns the funds check into conditional writes, `writeIf`, that match nothing when funds are short, so a transfer that should abort commits and changes nothing. Run it on a store with balance 0 and a transfer of 1, under two observers: balances only, and the outcome, which is the committed balances or the error code.

:::instrument ins=INS-pairs cell=1 recorded=RUN-lean-abort-blind
```text
source    transfer 1 a1 a2
store     (a1, a2) = (0, 0)

compiled by SP-9.3's scheme (the positivity check is unchanged and left out):
  ldi      r0 1
  read     r1 a1
  sub      r2 r1 r0
  writeIf  r1 r0 a1 r2     # debit only when the balance covers the amount
  read     r3 a2
  add      r3 r3 r0
  writeIf  r1 r0 a2 r3     # credit only when the same condition holds

observers  balances only | outcome
```

@direction
Each observer is applied to the source's run and to the compiled run. The pair view lists what each observer sees in both, and marks the observers that tell them apart.

@call key=C run=RUN-lean-abort-blind surprise=moderate
Which observers tell these two runs apart?

- A. Neither of the two
  - why: One run aborts and the other commits.
  - mis: dp:P1
- B. The balances-only observer
  - why: Both runs leave the balances unchanged.
  - mis: dp:P1
- C. The outcome observer
  - why: It sees an abort in one run and a commit in the other.
- D. Both of the observers
  - why: The balances-only observer equates the two runs.
  - mis: dp:X2

@after
The balances are equal, so the balances-only observer equates the runs, and the outcome observer does not {{run:RUN-lean-abort-blind}}. This is S6's unchecked rowcount one level up: an observer that cannot see aborts lets a proof pass over that bug.
:::

:::item role=segment family=GEN-leaks-to-observer template=t3 kcs=KC-9.observations
@choice key=B
An observer merges error codes: an abort reports only "failed". A compiler reports `insufficient` for a non-positive amount, where the source says `nonPositive`. Which command and store give runs that the observer equates and a client tells apart?

- A. `transfer 5 a1 a2` from (10, 0)

  - mis: dp:X2
- B. `transfer 0 a1 a2` from (10, 0)
  - why: The source aborts with `nonPositive` and the compiled program with `insufficient`. Merged codes equate the runs, and a client that reads the code does not.
- C. `transfer 5 a1 a2` from (3, 0)
  - why: Both abort with `insufficient`, so the runs agree on the code too.

  - mis: dp:P1
:::

## The template {minutes=13 kcs=KC-9.observations,KC-1.implication-vacuity}

CompCert states what it proves in one sentence: if the compiler produces the code, then the observable behavior of that code improves on one of the allowed observable behaviors of the source (manual, section 1.2). In Coq it is one line, `transf_c_program p = OK tp -> backward_simulation (Csem.semantics p) (Asm.semantics tp)` (`driver/Compiler.v`, read 2026-10-23). "Improves on" matters when the source can go wrong, because undefined behavior lets the compiler pick any behavior. Your fragment has none, since errors are outcomes, so "improves on" becomes equality. The theorem for your fragment:

```lean
theorem preservation (c : Cmd) (p : List Instr) :
    compile c = some p →
    ∀ (s : Store) (regs : Regs), obs s (runT p regs s) = obs s (runS c s)
```

The premise `compile c = some p` says the compiler produced `p`. A compiler that never produces anything never meets it.

:::instrument ins=INS-goal-replay cell=2 recorded=RUN-lean-preservation-frag
```lean
def Preserves {Cmd Prog Obs : Type} (compile : Cmd → Option Prog)
    (obsS : Cmd → Obs) (obsT : Prog → Obs) : Prop :=
  ∀ c p, compile c = some p → obsT p = obsS c

-- a "compiler" that refuses every command
def refuse {Cmd Prog : Type} : Cmd → Option Prog := fun _ => none

theorem refuse_preserves {Cmd Prog Obs : Type} (obsS : Cmd → Obs) (obsT : Prog → Obs) :
    Preserves (refuse : Cmd → Option Prog) obsS obsT := by
  unfold Preserves
  intro c p h
  simp [refuse] at h
```

@direction
Replay shows: `Preserves`, the compiler that returns `none` for every command, and its proof. Look at what the proof never touches.

@call key=A run=RUN-lean-preservation-frag surprise=yes
A "compiler" returns `none` for every command. Does it satisfy the theorem?

- A. Yes, vacuously.
  - why: The premise `compile c = some p` never holds, so the implication holds for every command.
- B. No.
  - why: A false premise makes an implication true.
  - mis: dp:G4
- C. Only if every source command aborts.
  - why: No compiled program exists to run, so nothing is compared.
  - mis: dp:G4

@after
The proof is three short tactics, and none of them mentions an observation {{run:RUN-lean-preservation-frag}}: it unfolds `Preserves`, introduces the premise, and `simp` finds that `refuse` never returns `some`. The template needs a companion: the compiler accepts every command of the fragment. That companion is `compile_complete`, which you prove in LAB-9.10, and it is the lesson on vacuous premises from S1 again.
:::

:::item role=segment family=GEN-call-it template=t4 kcs=KC-9.observations
@choice key=A
Which restatement of `preservation` is true?

- A. When the source commits, the compiled program commits with equal balances.
  - why: Equal observations include the outcome and every balance, once `obs` sees aborts, error codes and balances.
- B. The compiler accepts every command of the fragment it covers.
  - why: That is `compile_complete`, a separate theorem.
  - mis: dp:G4
- C. The compiled program takes as many steps as the source does.
  - why: Steps lie outside the observation.
  - mis: dp:P5
- D. Compiled programs never abort, whatever the source does.
  - why: They abort exactly when the source does, with the same error.
  - mis: dp:P4
:::

## What the template leaves out {minutes=12 kcs=KC-9.observations}

Preservation says nothing about what the observation leaves out. CompCert's list is explicit: execution time and memory consumption are excluded. Yours is the same kind of list. The steps the compiled program takes, the registers it uses and the stores it passes through all lie outside the outcome observation. That is a design choice, and it is also a place for a later problem to hide.

:::instrument ins=INS-pairs cell=3 recorded=RUN-tv-reference
```text
source      transfer 5 a1 a2
store       (a1, a2) = (10, 0)

compiled A  the reference compiler's output
compiled B  the same output with one redundant `read` before its first write

observers   outcome | steps
```

@direction
The pair view runs the source and both compiled programs from the store above, and shows each observer's view of all three.

@call key=D run=RUN-tv-reference surprise=no
Preservation holds under the outcome observation. Which of these can still differ between the source run and a compiled run?

- A. The final balances
  - why: They are inside the observation.
  - mis: dp:X2
- B. The error code
  - why: It is inside the observation.
  - mis: dp:X2
- C. Whether the command aborted
  - why: Aborts are observed, so this cannot differ.
  - mis: dp:P1
- D. The number of steps
  - why: Steps, registers and intermediate stores lie outside the observation, as CompCert's time and memory do.

@after
Both compiled programs commit with the same balances, and one takes more steps {{run:RUN-tv-reference}}. What an observation leaves out comes back in S9.L9.
:::

:::item role=segment family=GEN-leaks-to-observer template=t3 kcs=KC-9.observations
@choice key=A
Compiled B is the reference output plus one redundant `read` before its first write. Which command and store give runs that are equal under the outcome observation and different in steps?

- A. `transfer 5 a1 a2` from (10, 0)
  - why: Both commit with (5, 5), and B runs one more instruction.
- B. `transfer 5 a1 a2` from (3, 0)
  - why: Both abort with `insufficient` at the guard, before the redundant `read`, so the step counts match.
  - mis: dp:X2
- C. A store where B ends with different balances from the source
  - why: The extra `read` changes no write, so no such store exists.
  - mis: dp:X2
- D. None
  - why: Preservation makes the outcomes equal and says nothing about steps.
  - mis: dp:P5
:::

## Exit {minutes=5 kcs=KC-9.observations,KC-1.implication-vacuity}

:::item role=exit family=GEN-leaks-to-observer template=t3 kcs=KC-9.observations
@choice key=B
An observer maps every abort to the balances the run started with. A compiler turns a failed funds check into "change nothing, report success". Which command and store give runs that the observer equates and a client tells apart?

- A. `transfer 5 a1 a2` from (10, 0)
  - why: Both runs commit with (5, 5), so there is nothing to tell apart.
  - mis: dp:X2
- B. `transfer 5 a1 a2` from (3, 0)
  - why: The source aborts, and the observer reports the starting balances. The compiled program commits with the same balances. A client sees an error in one run and success in the other.
- C. `transfer 5 a1 a1` from (10, 0)
  - why: A self-transfer nets to zero in both runs, and both commit.
  - mis: dp:S1
- D. None of these commands
  - why: The observer still sees the balances, but not the abort that separates these runs.
  - mis: dp:P1
:::

  - why: It says nothing about commands the compiler refuses.
  - mis: dp:G4
- C. `preservation` covers only the commands that commit, not those that abort.
  - why: Aborts are observed, so it covers them too.
  - mis: dp:P1

  - why: Registers lie outside the observation.
  - mis: dp:P5
