## Where the proof stops {minutes=17 kcs=KC-9.tcb,KC-9.three-claims}

Every proof in this stage stands on a floor. Your system has more floors than the proofs mention: a parser, a checker, solvers, a compiler, a runtime and a database. For each one you can say which it is: proved, validated per run, tested or trusted. Start with a floor you can add by accident.

:::item role=prequestion family=GEN-which-stamp template=t1 kcs=KC-9.tcb,KC-9.three-claims
@choice key=B
`native_decide` closes one IR golden. What joins your trusted base?

- A. Nothing: the kernel still checks the proof.
  - why: `native_decide` has compiled code decide the goal, and the kernel does not evaluate it again.
  - mis: dp:L8
- B. The Lean compiler and its runtime.
  - why: Their output is trusted, and a native axiom appears in the list.
- C. Only the `decide` tactic.
  - why: The kernel checks what `decide` does. It does not check `native_decide`.
  - mis: dp:L8
- D. The SMT solver.
  - why: No solver is involved.
  - mis: dp:X2
:::

The build stays green and the base has grown. `#print axioms` for such a goal names a native axiom, and the checker refuses it while its own log still says the kernel accepts the solution {{run:RUN-lean-axioms}}. That is SP-9.5, and the stamp is PROVED [P] · kernel + compiler.

Three claims sound like one. The command preserves your invariants (S4). The compiler preserves what the command means (CL-9.2 and CL-9.3). The runtime follows the target (S6 and S8). Each has its own method and stamp, and the chain is as strong as its weakest link. CompCert's own list of what it still trusts is this table, drawn by its authors: the semantics, the parser, assembler and linker, and the proof assistant.

A compiler can preserve meaning and still leak. S7's observer saw response bodies only. Compile the document view two ways, and compare two worlds that differ in tenant Birch's private documents.

:::instrument ins=INS-pairs cell=1 recorded=RUN-lean-leaky-compile
```text
view     Open(frank, doc) from S7, for tenant Acme
plan 1   full scan: read every document row, keep the ones frank may see
plan 2   index scan: read only the rows frank may see

W0       Acme's documents, and Birch's private ones
W1       W0 plus one more private document of Birch's
```

@direction
Pair asserts: W0 and W1 agree on everything Acme may know. The viewer runs both plans in both worlds, and shows frank's response and the steps each run took.

@call key=A run=RUN-lean-leaky-compile surprise=yes
Both plans return the same body to frank in W0 and in W1. Can frank tell the worlds apart?

- A. Yes, by the full scan's running time.
  - why: The full scan's step count includes Birch's private rows, and the index scan's does not.
- B. No: the bodies are equal.
  - why: CL-7.3's observer sees bodies only. Time lies outside it, as CompCert's observations leave time out.
  - mis: dp:P5
- C. Yes, by the body.
  - why: The bodies are equal in both worlds.
  - mis: dp:X2

@after
The bodies match in both worlds, and the full scan's step count differs between them {{run:RUN-lean-leaky-compile}}. This is SP-9.6, an erosion: SEAM-10 cracks. The compiler preserved the observation you chose, and that observation omits time. Two remedies: widen the observer to include steps, which refutes CL-7.3 with this pair as [R], or state the timing channel as [N], choose the index plan, and claim only the observer you checked.
:::

:::item role=segment family=GEN-which-stamp template=t1 kcs=KC-9.tcb
@choice key=D
Your SQL compiler emits a plan for every command, and your validator replays each plan on both semantics. What status does the compiler get in your base?

- A. Proved: PROVED [P].
  - why: Nothing proves the compiler. Each plan is checked after it is made.
  - mis: dp:X1
- B. Trusted: ASSUMED [A].
  - why: Trusting it would skip the per-plan check. The validator is what you trust here.
  - mis: dp:P3
- C. Tested: TESTED [T], from its unit tests alone.
  - why: The unit tests are evidence about the compiler. The per-plan replay is what CL-9.3 stands on.
  - mis: dp:G8
- D. Validated per run: [T] · n commands or [M] · bound.
  - why: The compiler stays untrusted, and the validator checks each plan it makes.
:::

## Exit {minutes=3 kcs=KC-9.tcb,KC-9.three-claims}

:::item role=exit family=GEN-call-it template=t4 kcs=KC-9.three-claims,KC-9.tcb
@choice key=C
Your report says: "a transfer that hits a serialization failure is retried until it commits." Which of the three claims does that sentence belong to?

- A. The command preserves invariants.
  - why: That claim is about one command on the source, whatever the database does.
  - mis: dp:P3
- B. The compiler preserves meaning.
  - why: That claim is about what the compiled code means. Retries are about how it runs.
  - mis: dp:P3
- C. The runtime follows the target.
  - why: Retrying a failed transaction is the runtime's job, and its termination is assumed.
- D. All three, since one proof covers the chain.
  - why: Each claim has its own method and stamp, and a proof of one says nothing about the next.
  - mis: dp:P3
:::
