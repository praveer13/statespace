Your checker derives `Inv ∧ Guard ∧ Step ∧ ¬Inv′` for a command and sends it to Z3. `unsat` is only one of six outcomes.

| Checker output | Stamp | Action |
|---|---|---|
| `unsat`, premise witness satisfiable and replayed | PROVED [P], uncertified | no runtime check |
| `unsat`, premise witness unsatisfiable | none: vacuous | fix the encoding |
| a model that replays | REFUTED [R] | fix the command |
| a model that does not replay | none: a defeater against your generator | fix the encoding |
| `unknown` at the `rlimit` | UNKNOWN [?] | enforce at commit |
| a construct outside the fragment | NOT COVERED [N] | enforce at commit |

A model counts only once the interpreter replays it: decode it into a Mini-Plinth state, run the command, and see whether the invariant breaks. `unknown` is real: `x**y == 8, y > 1` returns it {{run:RUN-z3-unknown-pow}}, and in the tab only an `rlimit` stops a query that will not finish {{run:RUN-z3-budget-pyodide}}.

Proving costs one query per command and nothing at runtime. Enforcing costs a check on every call, and ENFORCED [E] names where it runs. A per-command obligation assumes one command at a time (SEAM-2), so an invariant over data that other commands change concurrently is enforced at commit until S6. Even a PROVED [P] keeps the open defeater "encoding unverified": Z3 decided your query, and nothing yet shows that the query is the command.

:::instrument ins=INS-z3 cell=1 recorded=RUN-check-fragment
Your emitter in miniature: build the obligation, ask Z3, decode the model, replay it, and pick the stamp.

```python editable
from z3 import *

def withdraw(state, guarded):                    # the interpreter, in miniature
    if guarded and not state['amount'] <= state['bal']:
        return 'Err', state                      # a failed guard returns Err and leaves the state alone
    return 'ok', {**state, 'bal': state['bal'] - state['amount']}

def check(guarded):
    bal, amount, bal2 = Ints('bal amount bal2')
    premises = [bal >= 0, amount > 0, bal2 == bal - amount]     # Inv, the type of amount, Step
    if guarded:
        premises.append(amount <= bal)                           # Guard
    s = Solver()
    s.set('rlimit', 200000)
    s.add(*premises, Not(bal2 >= 0))                             # and not Inv'
    verdict = s.check()
    print('solver says', verdict)
    if verdict == sat:
        m = s.model()
        state = {'bal': m[bal].as_long(), 'amount': m[amount].as_long()}   # decode the model
        outcome, after = withdraw(state, guarded)                           # replay it
        if outcome == 'ok' and after['bal'] < 0:
            return 'REFUTED [R] - fix the command'
        return 'no stamp: the witness does not replay - fix the encoding'
    if verdict == unsat:
        p = Solver()
        p.add(*premises)                                                    # the premise witness
        if p.check() == sat:
            return 'PROVED [P] - no runtime check needed'
        return 'no stamp: the premises contradict each other - fix the encoding'
    return 'UNKNOWN [?] - enforce at commit'

print('unguarded Withdraw:', check(guarded=False))
print('guarded Withdraw:  ', check(guarded=True))
```

@direction
Query asserts: a state with `bal ≥ 0`, a `Withdraw` of a positive amount, and an after-state with `bal < 0`. `sat` means such a state exists, and your checker may say REFUTED only after the replay agrees.

@call key=B surprise=moderate run=RUN-check-fragment
What does your checker stamp for `Withdraw` with no guard?

- A. PROVED [P]
  - why: With no guard a withdrawal can exceed the balance, so there is nothing to prove.
  - mis: dp:Z1
- B. REFUTED [R], once the witness replays
  - why: The overdraft is real, and the decoded state reproduces it in the interpreter.
- C. No stamp: the witness does not replay
  - why: A model that fails to replay needs a missing frame or a capture, and this encoding has neither.
  - mis: dp:O4
- D. UNKNOWN [?]
  - why: This is linear arithmetic, which Z3 decides outright.
  - mis: dp:Z2

@after
Z3 finds a violating state, the decoded state replays to a negative balance, and the stamp is REFUTED [R] {{run:RUN-check-fragment}}. Add the guard and the same code stamps PROVED [P] after a premise witness. Let the interpreter disagree with the encoding, and the model gets no stamp.
:::

`Withdraw(amount)` requires `amount ≤ bal`, and the invariant is `bal ≥ 0`. Which violation query does your checker send?

- A. `bal ≥ 0 ∧ amount > 0 ∧ amount ≤ bal ∧ bal′ = bal − amount ∧ ¬(bal′ ≥ 0)`
  - why: Invariant, parameter type, guard and step, then the negated invariant on the after-state.
- B. `bal ≥ 0 ∧ amount > 0 ∧ amount ≤ bal ∧ bal′ = bal − amount ∧ bal′ ≥ 0`
  - why: This asks for a state that keeps the invariant. A model proves nothing about a bug.
  - mis: dp:Z1
- C. `bal ≥ 0 ∧ amount > 0 ∧ amount > bal ∧ bal′ = bal − amount ∧ ¬(bal′ ≥ 0)`
  - why: This searches the amounts the guard already rejects, where the step never runs.
  - mis: dp:G3
- D. `bal ≥ 0 ∧ amount > 0 ∧ amount ≤ bal ∧ ¬(bal′ ≥ 0)`
  - why: With no step equation, `bal′` is free, so the query has a model and proves nothing.
  - mis: dp:O4
