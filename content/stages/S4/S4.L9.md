## Five layers under one stamp {minutes=14 kcs=KC-4.trust-stack}

:::item role=prequestion family=GEN-which-stamp template=t2 kcs=KC-4.trust-stack
@choice key=B
CL-1.1 reads PROVED [P] · Z3 {{run:RUN-z3-starter#version}} unsat · uncertified · rlimit N. What does "uncertified" admit?

- A. That no person has reviewed the proof yet.
  - why: Review is not what the qualifier records.
  - mis: dp:X2
- B. That it trusts the solver, with no certificate checked.
  - why: The qualifier names the part you are trusting: the solver.
- C. That the encoding was not checked against the code.
  - why: That is a separate open defeater, "encoding unverified".
  - mis: dp:O5
- D. That the result is bounded by the rlimit.
  - why: A bound would make it MODEL-CHECKED [M].
  - mis: dp:X1
:::

Every stamp in this stage rests on five layers, and each fails in its own way.

| Layer | Must get right | Evidence here | Effect on the stamp |
|---|---|---|---|
| Requirement | `Inv` means the rule | true and false scenarios | requirement-fit is never [P] |
| Semantics | the reference semantics | the Lean reference and its goldens | none |
| VC generator | exactly the fragment's steps | replay and equivalence tests | "encoding unverified" stays open |
| Solver and entry path | `unsat` means no model | a second solver; certificates, deferred | "uncertified" |
| Instrument | the tab's Z3 matches the native one | the course's differential tests | the badge |

The solver layer can fail. Z3 issue #11179 reports a wrong answer on a satisfiable input. Run it.

:::instrument ins=INS-z3 cell=1 recorded=RUN-z3-11179
Input 1 of the issue, sent through Z3's SMT-LIB command interpreter after `(push 1)`, as the report does it. The tab runs one Z3 release, and the recorded run holds four.

```python
from z3 import *

issue = """(set-logic ALL)
(declare-const y Real)
(push 1)
(assert (>= y 1))
(assert (< (^ (/ 1 2) y) (/ 1 2)))
(check-sat)"""

# Through the SMT-LIB command interpreter, as the issue reports it.
ctx = Context()
print('command interpreter:', Z3_eval_smtlib2_string(ctx.ref(), issue).strip())

# Pin y = 2: the same assertions are decided, and the model shows the input is satisfiable.
pinned = Solver()
pinned.from_string('(declare-const y Real)(assert (= y 2))(assert (>= y 1))(assert (< (^ (/ 1 2) y) (/ 1 2)))')
print('with y pinned to 2:', pinned.check())
```

@direction
Query asserts: a real `y` of at least 1 whose power `(1/2)^y` is below 1/2. `sat` is the truth, because `y = 2` works. The cell prints what the tab's release says. The recorded run holds what older releases said.

@call key=B surprise=yes run=RUN-z3-11179
In the recorded run, one release before the one in your tab, through the command interpreter, what does Z3 answer on input 1?

- A. `sat`
  - why: That is the truth, and this release missed it.
  - mis: dp:G8
- B. `unsat`
  - why: The recorded output is `unsat` on an input that has a solution. A solver can be wrong.
- C. `unknown`
  - why: That is the answer of the release in your tab, not the older one.
  - mis: dp:Z6

@after
That release, and two older ones, report no model for input 1, although `y = 2` is a solution. The tab's release says it cannot decide, and through the Python API so does every tested release {{run:RUN-z3-11179}}. The defect is in nonlinear real exponentiation, outside your checker's fragment. What carries over is that an `unsat` names its solver, its version and its entry path, and stays "uncertified" until something independent checks it. This cracks SEAM-7, the assumption that the solver is sound, which CL-1.1 planted.
:::

::specimen id=SP-4.5

A second solver is the cheapest independent check. On the Bench, cvc5 {{run:RUN-scaffold#values.cvc5}} reads the same SMT-LIB. It can also emit a certificate, an Alethe proof of its `unsat`, but a certificate can be partial: its proof for S1's guard query has {{run:RUN-cvc5-alethe#values.hole_steps}} `hole` steps, each marked "untranslated rewrite". Checking certificates is deferred (D-32), so two agreeing solvers raise your confidence and the stamp keeps "uncertified".

::specimen id=SP-4.6

Lean's experimental `vcgen` (Lean {{run:RUN-lean-vcgen#version}}, recorded 2026-10-24) reads an obligation from the other side. On a shallow contract for `transfer` over plain integers it proves the guarded version, and with the guard weakened it leaves one goal unproved: the sender's new balance is not known to be non-negative {{run:RUN-lean-vcgen}}. On a Mini-Plinth-style command type it does the same once it is given a weakest-precondition instance and one specification per construct {{run:RUN-vcgen-cmd}}. Your checker finds a violating state for the weakened obligation: an unprovable condition and a satisfiable negation are two faces of one obligation. The proofs close with `grind`, so each lists `Classical.choice`, which S2's manual proofs did not {{run:RUN-vcgen-cmd}} {{run:RUN-lean-ledger}}.

::specimen id=SP-4.7

Four things went wrong. Which one sits in the VC-generator layer?

- A. A solver reports no model for an input that has a solution.
  - why: That is the solver layer, as in SP-4.5.
  - mis: dp:O5
- B. An emitted query leaves out the frame for an untouched account.
  - why: The query no longer says what the command does, and both solvers will answer it faithfully.
- C. `Inv` says `bal ≥ 0`, but the README also forbids holds above the balance.
  - why: That is the requirement layer: the invariant means less than the rule.
  - mis: dp:X4

  - why: That is the solver and its entry path.
  - mis: dp:O5
