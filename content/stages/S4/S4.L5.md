## Primes and frames {minutes=15 kcs=KC-4.frame-condition}

:::item role=prequestion family=GEN-negate-it template=t1 kcs=KC-4.frame-condition mode=pick
@choice key=B
Your emitter forgets `c′ = c` for an account that Transfer does not touch. On a Transfer that really preserves `Inv`, what does the checker report?

- A. The obligation proved: fewer constraints can only hide bugs.
  - why: The reverse holds. Fewer premises admit more models, so a query that was `unsat` can turn `sat`.
  - mis: dp:O4
- B. A counterexample in which the untouched account changes.
  - why: `c′` is free, so the negated invariant can be met at `c`.
- C. `unknown`
  - why: The query stays in linear integer arithmetic, which Z3 decides.
  - mis: dp:Z2
- D. The same verdict as with the frame.
  - why: `Inv` mentions `c`, so a free `c′` can violate it.
  - mis: dp:O4
:::

A query is text: declared constants, asserted formulas, a check. The obligation needs two copies of the state, one before the step and one after. Here the state symbols are `a`, `b`, `c`, the state after the step takes the suffix `_p`, and a command's parameters take the prefix `p_`, as in `a_p` and `p_amount`.[^1]

The step must say what every symbol becomes. Say it for the two that change, `a_p = a − p_amount` and `b_p = b + p_amount`, and `c_p` stays free: any integer fits. A frame equation, `c_p = c`, closes the gap. With arrays, `store(bal, f, v)` states the frame for free, because it copies every other index. With scalars, or with constraints such as `select(bal_p, f) = …`, each untouched location needs its own frame equation.

Dropping a premise from a violation query can only turn `unsat` into `sat`, because fewer constraints admit more models. So a missing frame gives a false alarm and never a false proof: the model it finds is not a step of Transfer.

[^1]: Drawer D-13 holds sorts, `declare-const`, `assert` and `check-sat` on one page.

:::instrument ins=INS-z3 cell=1 recorded=RUN-z3-missing-frame
```python
from z3 import *

a, b, c, p_amount = Ints('a b c p_amount')       # state before, and the parameter
a_p, b_p, c_p = Ints('a_p b_p c_p')              # state after

inv_pre      = And(a >= 0, b >= 0, c >= 0)
guard        = And(p_amount > 0, p_amount <= a)
step         = And(a_p == a - p_amount, b_p == b + p_amount)
frame_c      = c_p == c                          # left out below
neg_inv_post = Not(And(a_p >= 0, b_p >= 0, c_p >= 0))

s = Solver()
s.add(inv_pre, guard, step, neg_inv_post)        # no frame_c
print(s.sexpr())
print(s.check())
print(s.model())
```

@direction
Query asserts: a state that meets the invariant and the guard, takes Transfer's step and leaves some account below zero. `sat` means a violating step exists.

@tap
Transfer keeps every account at zero or above

@call key=A run=RUN-z3-missing-frame surprise=yes
What does Z3 return?

- A. `sat`
  - why: `c_p` is free, so Z3 can set it below zero while `c` is untouched.
- B. `unsat`
  - why: Dropping a premise admits more models, never fewer.
  - mis: dp:O4
- C. `unknown`
  - why: A few linear integer constraints are decided outright.
  - mis: dp:Z2

@after
In the model, `c_p` is below zero and `c` is not. Put `frame_c` back and the same query comes back `unsat`, and then the last line fails: an `unsat` query has no model, so `s.model()` raises an exception. Print a model only after `sat`. Against the real step relation this witness is no step of Transfer, so a replay in the interpreter refuses it (S4.L7). {{run:RUN-z3-missing-frame}}
:::

::specimen id=SP-4.1

The encoding is also a claim about numbers. Over signed 64-bit integers, the same obligation with every frame stated is a different query.

:::instrument ins=INS-z3 cell=2 recorded=RUN-z3-bv64 call=false
```python
from z3 import *

A, B, C, X = BitVecs('A B C X', 64)              # signed 64-bit balances
A_p, B_p, C_p = BitVecs('A_p B_p C_p', 64)
inv = lambda x, y, z: And(x >= 0, y >= 0, z >= 0)   # >= is signed here

s = Solver()
s.add(inv(A, B, C), X > 0, X <= A)
s.add(A_p == A - X, B_p == B + X, C_p == C)      # every frame is stated
s.add(Not(inv(A_p, B_p, C_p)))
print(s.check())
```

@direction
Query asserts: the same obligation over signed 64-bit integers. `sat` means a violating step exists.

@after
The guard protects the sender. The recipient wraps: a very large balance plus the amount overflows to a negative value, a step that cannot occur over `Int`. {{run:RUN-z3-bv64}}
:::

:::item role=segment family=GEN-negate-it template=t3 kcs=KC-4.frame-condition mode=pick
@choice key=B
Debit on an array of balances has parameters `k` and `amt`, the guard `Pre` as `0 < amt ∧ amt ≤ bal(k)`, the step `bal′ = store(bal, k, bal(k) − amt)`, and the invariant `Inv(bal)` as `∀j. bal(j) ≥ 0`. Which query asks for a violating step?

- A. `Inv(bal) ∧ Pre ∧ bal′ = store(bal, k, bal(k) − amt) ∧ Inv(bal′)`
  - why: This asks for a step that works, so a model says nothing about bugs.
  - mis: dp:Z1
- B. `Inv(bal) ∧ Pre ∧ bal′ = store(bal, k, bal(k) − amt) ∧ ¬Inv(bal′)`
  - why: `store` copies every other index, so the frame comes with the step.
- C. `Inv(bal) ∧ Pre ∧ bal′(k) = bal(k) − amt ∧ ¬Inv(bal′)`
  - why: This constrains only index `k`. Every other `bal′(j)` is free, so a model can break `Inv` at an account the step never touches.
  - mis: dp:O4
:::

## Exit {minutes=4}

:::item role=exit family=GEN-spec-it template=t3 kcs=KC-4.frame-condition mode=pick
@choice key=C
`Pay` moves `amt` from account `x` to account `y`, and there is a third account `z`. Which postcondition states the command completely?

- A. `bal′(x) = bal(x) − amt ∧ bal′(y) = bal(y) + amt`
  - why: It says nothing about `z`, so `bal′(z)` may be anything.
  - mis: dp:O4
- B. `bal′(x) = 0 ∧ bal′(y) = bal(y) + bal(x) ∧ bal′(z) = bal(z)`
  - why: This fixes the amount at the whole balance of `x`, which is stronger than the command.
  - mis: dp:O2
- C. `bal′(x) = bal(x) − amt ∧ bal′(y) = bal(y) + amt ∧ bal′(z) = bal(z)`
  - why: Both changes are stated, and the untouched account is said to stay as it was.
:::
