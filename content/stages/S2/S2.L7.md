## A stream, not one transfer {minutes=2 kcs=KC-2.generalized-ih}

Your ledger will not see one transfer. It will see a stream of them, and each one starts from the state the last one left. Conservation of a single transfer is a fact about one step. The claim you want covers the whole stream, and getting from one to the other is an induction on the list, where a single word decides whether the proof works.

:::item role=prequestion family=GEN-proof-structure template=t3 kcs=KC-2.generalized-ih
@choice key=B
`run s (n :: ns) = run (transfer s n) ns`. You prove `total (run s ns) = total s` by induction on `ns`. In the step, the induction hypothesis has to hold for which state?

- A. `s`, the state the run starts from
  - why: The recursive call starts from `transfer s n`, not from `s`.
  - mis: dp:L5
- B. `transfer s n`, and in general every state
  - why: The state changes at every step, so only a hypothesis about all states applies.
- C. The empty list, where the run ends
  - why: That is the base case, which has no hypothesis.
  - mis: dp:L6
- D. None: conservation of one transfer is enough
  - why: The rest of the list still needs the hypothesis.
  - mis: dp:L6
:::

## The whole proof first {minutes=14 kcs=KC-2.generalized-ih}

Start with a finished proof, and read it before you change anything. A list of transfers runs one at a time: `runPos` applies the first transfer, then carries on with the rest from the state that transfer produced.

```lean
def runPos (s : Ledger) : List Int → Ledger
  | [] => s
  | n :: ns => runPos (transferPos s n) ns
```

The theorem says the total never changes, whatever list you feed in. It uses the one-step lemma from earlier in this stage, `transferPos_conserves`. Drawer D-05 has the same move in plain words.

:::instrument ins=INS-goal-replay cell=1 recorded=RUN-lean-s2-cells
```lean
theorem transferPos_conserves (s : Ledger) (n : Int) :
    total (transferPos s n) = total s := by
  unfold transferPos total
  split <;> simp <;> omega

theorem runPos_conserves (s : Ledger) (ns : List Int) :
    total (runPos s ns) = total s := by
  induction ns generalizing s with
  | nil => rfl
  | cons n ns ih => simp [runPos, ih, transferPos_conserves]
```

@direction
Replay shows: the proof of `runPos_conserves` one tactic at a time, with the goal after each, inside each case of the induction. Pay attention to what `ih` says in the `cons` case.

@tap
the total is the same after any sequence of transfers

@call key=C surprise=no run=RUN-lean-s2-cells
In the `cons` case, the hypothesis `ih` is stated for…

- A. `s` only
  - why: That would be the hypothesis without `generalizing`, tied to one fixed state.
  - mis: dp:L5
- B. `transferPos s n` only
  - why: `ih` covers every state. You choose `transferPos s n` when you use it.
  - mis: dp:L5
- C. every state
  - why: `generalizing s` puts `s` inside the hypothesis, so `ih` reads `∀ s, …`.

@after
`generalizing s` is the whole move. It takes `s` out of the context and puts it inside the hypothesis, so `ih` reads `∀ s, total (runPos s ns) = total s`. In the `cons` case the recursion carries on from `transferPos s n`, a different state, and `ih` still applies, because it was never about one state. Then `simp` unfolds `runPos`, uses `ih` at the new state, and finishes with one-step conservation.
:::

Three principles sit behind the three moves:

1. Generalize over whatever the recursion changes. Here that is the state.
2. The empty list changes nothing, so the base case is computation.
3. Use the hypothesis at the state the recursion moved to, then close with one-step conservation.

There is a second way to say the same thing. Quantify over the state after the list, and a plain `induction ns` works, because `∀ s` is already inside the statement:

```lean
theorem runPos_conserves' (ns : List Int) : ∀ s : Ledger, total (runPos s ns) = total s := by
  induction ns with
  | nil => intro s; rfl
  | cons n ns ih => intro s; simp [runPos, ih, transferPos_conserves]
```

:::item role=segment family=GEN-proof-structure template=t1 kcs=KC-2.generalized-ih
@choice key=D
`credits` threads a running total through a list. `credits_eq` is proved by `induction xs generalizing acc with`. In the `cons` case, what does Lean show?

```lean
def credits (acc : Int) : List Int → Int
  | [] => acc
  | x :: xs => credits (acc + x) xs

theorem credits_eq (acc : Int) (xs : List Int) :
    credits acc xs = acc + xs.sum := by
  induction xs generalizing acc with
  | nil => simp [credits]
  | cons x xs ih => sorry   -- the case in question
```

- A. `ih : credits acc xs = acc + xs.sum`, goal `credits acc (x :: xs) = acc + (x :: xs).sum`
  - why: That `ih` is about the one fixed `acc`. `generalizing acc` puts `acc` inside it.
  - mis: dp:L5
- B. `ih : ∀ acc, credits acc xs = acc + xs.sum`, goal `credits acc xs = acc + xs.sum`
  - why: That goal is for the shorter list. The step has to prove it for the longer one.
  - mis: dp:L6
- C. No `ih`: the step starts from the goal `credits acc (x :: xs) = acc + (x :: xs).sum` alone
  - why: Induction supplies the hypothesis for the shorter list, and using it is not circular.
  - mis: dp:L6
- D. `ih : ∀ acc, credits acc xs = acc + xs.sum`, goal `credits acc (x :: xs) = acc + (x :: xs).sum`
  - why: The goal is for the longer list and `ih` covers every accumulator.
:::

## Without generalizing {minutes=13 kcs=KC-2.generalized-ih}

Now leave the word out. The theorem is LAB-2's own `run_conserves`, which you prove in LAB-2.5, so this page shows only how the attempt fails. An induction failure is not a bug: every theorem here is true. The proof stops because the hypothesis is too narrow, and a failed proof says nothing against the statement.

:::instrument ins=INS-goal-replay cell=2 recorded=RUN-lean-ih-ungeneralised
```lean
structure Ledger where
  a : Int
  b : Int
deriving Repr, DecidableEq

def total (s : Ledger) : Int := s.a + s.b

def transfer (s : Ledger) (n : Int) : Ledger :=
  if 0 ≤ n ∧ n ≤ s.a then { a := s.a - n, b := s.b + n } else s

def run (s : Ledger) : List Int → Ledger
  | [] => s
  | n :: ns => run (transfer s n) ns

theorem run_conserves (s : Ledger) (ns : List Int) :
    total (run s ns) = total s := by
  induction ns with
  | nil => rfl
  | cons n ns ih => simp [run, ih]
```

@direction
Replay shows: the same induction with `generalizing s` left out, and the goal where the proof stops. Compare the state `ih` talks about with the state the goal talks about.

@tap
the total is the same after any sequence of transfers

@call key=B surprise=yes run=RUN-lean-ih-ungeneralised
Without `generalizing s`, does the `cons` case close?

- A. It closes: the hypothesis rewrites the goal as it stands.
  - why: The hypothesis is about the wrong state, so it has nothing to rewrite.
  - mis: dp:L5
- B. It fails: `ih` is about `s`, the goal about `transfer s n`.
  - why: After one step the recursion starts from `transfer s n`, and `ih` is about `s`.
- C. It fails: the base case is missing, so nothing starts the induction.
  - why: The base case closes by computation. The `cons` case is the one that stops.
  - mis: dp:L6

@after
The `cons` case stays open {{run:RUN-lean-ih-ungeneralised}}. The hypothesis says `total (run s ns) = total s`, but after one step the goal is about `run (transfer s n) ns`, which starts from a different state. Nothing in `ih` matches, and the linter points out that `ih` was never used. This is SP-2.3: a proof that fails because of how it was set up, with no counterexample behind it. The cure is the word you left out.
:::

:::item role=segment family=GEN-proof-structure template=t3 kcs=KC-2.generalized-ih
@choice key=A
Here the proof does generalize. Which instance of the hypothesis does the `cons` step need?

- A. `ih (transfer s n)`
  - why: The recursion carries on from `transfer s n`, so that is the state `ih` has to cover.
- B. `ih s`
  - why: That is the hypothesis for the state the step started from, and the recursion has left it.
  - mis: dp:L5
- C. `transfer_conserves s n` alone (one step)
  - why: One-step conservation covers one transfer, and the rest of the list still needs `ih`.
  - mis: dp:L6
- D. The goal itself
  - why: Using the goal to prove the goal is circular. `ih` is the claim for the shorter list.
  - mis: dp:L6
:::

## Fade it out {minutes=14 kcs=KC-2.generalized-ih}

You have now seen the proof twice. From here it fades: first the closing line of the `cons` case is yours, then the whole case, then everything after the header. Each blank can be filled from candidates that Lean has already elaborated, so you see the goal or error each one leaves before you choose.

:::instrument ins=INS-goal-replay cell=3 recorded=RUN-lean-s2-cells
```lean
theorem runPos_conserves (s : Ledger) (ns : List Int) :
    total (runPos s ns) = total s := by
  induction ns generalizing s with
  | nil => rfl
  | cons n ns ih => sorry   -- the blank: one closing line
```

@direction
Replay shows: the proof with the closing line of the `cons` case blank. Each candidate line, once chosen, shows the goal or the error it leaves.

@tap
the total is the same after any sequence of transfers

@call key=D surprise=moderate run=RUN-lean-s2-cells
Which line closes the blank?

- A. `rfl`: both sides reduce to one and the same total
  - why: The recursion moves to another state, and the total there equals `total s` only through the induction.
  - mis: dp:L2
- B. `simp [runPos]`: unfold the recursion and nothing more
  - why: It unfolds the recursion and leaves the goal for the shorter list. The hypothesis is never used.
  - mis: dp:L6
- C. `simp [runPos, ih]`: unfold, then use `ih` at the new state
  - why: It uses `ih` at the new state, then stops at `total (transferPos s n) = total s`. One-step conservation is missing.
  - mis: dp:L2
- D. `simp [runPos, ih, transferPos_conserves]`: unfold and use both
  - why: Unfold, use `ih` at the new state, then one-step conservation.

@after
Each partial attempt stops where an ingredient runs out {{run:RUN-lean-s2-cells}}. The next rungs blank the whole `cons` case, then everything after the header. The part to keep in your head is the header: `induction ns generalizing s with` is the decision, and the rest follows from it.
:::

- A. 4, 2, 3

  - mis: dp:L5

  - mis: dp:L6
- C. 1, 2, 3

## Exit {minutes=5 kcs=KC-2.generalized-ih}

**What the claim assumes.** `run_conserves` becomes a claim card, and the card carries one assumption: transfers run one at a time, each finishing before the next starts. That is SEAM-2, drawn dashed. The proof says nothing about two transfers overlapping, so a system that runs them concurrently is a separate question, and the card keeps it in view.

**Say it back.** Explain the induction in `run_conserves` without naming a tactic: what the base case is, what the step assumes, and why that assumption has to hold for every state. Nothing here is graded. Check yourself against three ideas: the empty list changes nothing; the step assumes the claim for the shorter list from any starting state; the first transfer moves the state, so a claim about one fixed state would not apply.

:::item role=exit family=GEN-proof-structure template=t3 kcs=KC-2.generalized-ih
@choice key=B
`drain` threads a balance through a list of withdrawals. You prove `drain bal xs = bal - xs.sum` by induction on `xs`, generalizing `bal`. In the `cons` step, the hypothesis is needed at which balance?

```lean
def drain (bal : Int) : List Int → Int
  | [] => bal
  | x :: xs => drain (bal - x) xs
```

- A. `bal`
  - why: The recursive call starts from `bal - x`, so the hypothesis at `bal` is about the wrong start.
  - mis: dp:L5
- B. `bal - x`
  - why: That is the balance the recursion carries on with.
- C. `x - bal`
  - why: The recursion subtracts `x` from the balance, not the balance from `x`.
  - mis: dp:L5
- D. `bal + x`
  - why: `drain` subtracts `x`, so the next balance is `bal - x`.
  - mis: dp:L4
:::
