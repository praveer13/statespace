## One line at a time {minutes=14 kcs=KC-2.proof-reading}

:::item role=prequestion family=GEN-proof-structure template=t3 kcs=KC-2.proof-reading
@choice key=B
A proof reaches the line "so 0 ≤ a − n". Which response explains the line, rather than repeating it?

- A. It says the sender's new balance after the transfer is not negative.
  - why: That restates the line in other words and gives no reason.
  - mis: dp:X2
- B. The allowed branch gives n ≤ a, and a minus at most a is at least 0.
  - why: It names the move, the fact that licenses it and the goal it serves.
- C. It says this line of the proof is right, with nothing to back that.
  - why: A verdict with no reason would fit any line of any proof.
  - mis: dp:X2
- D. It says the whole proof keeps both balances at 0 or above.
  - why: That summarizes the whole proof, not this line.
  - mis: dp:L4
:::

This is the first Lean you will see, and you only have to read it. A Lean proof is a list of tactics. Each tactic changes the goal, and the proof is finished when no goal is left. **Goal Replay** shows a proof one tactic at a time, with the goal Lean displays at each step. The proof below builds in real Lean {{run:RUN-lean-s2-cells}}.

A goal has two parts. Above the turnstile `⊢` are the facts you may use. Below it is what is left to show.

Reading a proof means asking three questions of every line, in Lean or in English:

1. **The move.** What does this line do?
2. **The reason.** What licenses it: a hypothesis, a definition, an earlier line?
3. **The goal.** How does it bring the proof closer to its end?

A paraphrase answers none of them: "the sender's balance is not negative" says a line again. An explanation gives the move, the reason and the goal.

Read the proof below once. In your notes, explain three of its lines in those three parts: `split` and the two `exact` lines. Then make your call, and compare your notes with the model.

:::instrument ins=INS-goal-replay cell=1 recorded=RUN-lean-s2-cells
`transferPos` is a transfer that also rejects a zero amount.

```lean
structure Ledger where
  a : Int
  b : Int
deriving Repr, DecidableEq

def transferPos (s : Ledger) (n : Int) : Ledger :=
  if 0 < n ∧ n ≤ s.a then { a := s.a - n, b := s.b + n } else s

theorem transferPos_nonneg (s : Ledger) (n : Int) (ha : 0 ≤ s.a) (hb : 0 ≤ s.b) :
    0 ≤ (transferPos s n).a ∧ 0 ≤ (transferPos s n).b := by
  unfold transferPos
  split
  · next hg => exact ⟨Int.sub_nonneg_of_le hg.2, Int.add_nonneg hb (Int.le_of_lt hg.1)⟩
  · exact ⟨ha, hb⟩
```

@direction
Replay shows: the proof of `transferPos_nonneg`, one tactic at a time. The first goal has `ha` and `hb` above the turnstile and the claim below it: if both balances start at zero or above, an allowed transfer leaves both there.

@call key=A surprise=no run=RUN-lean-s2-cells
The second branch closes with `exact ⟨ha, hb⟩`. Why is that enough?

- A. In the rejected branch nothing changes, and `ha` and `hb` are the goal.
  - why: `transferPos` returns `s` when the guard fails, and `ha` and `hb` already say what the goal asks.
- B. The guard makes both balances positive, and `exact` uses that.
  - why: In this branch the guard is false, so it licenses nothing.
  - mis: dp:L4
- C. `exact` accepts any term at all, whatever its type is.
  - why: `exact` succeeds only when the term's type is the goal.
  - mis: dp:L1
- D. It is not enough here; Lean will report an error on this line.
  - why: The recorded replay shows this branch closing with no error.
  - mis: dp:L4

@after
A model for the three lines. Compare it with your notes; nothing here is graded.

**`split`:** the move is a case split on the guard; the reason is that `transferPos` is an `if`, so its result is one of two states; the goal is to prove the claim for each state on its own.

**The first `exact`:** the move hands over both halves at once; the reason is `n ≤ s.a` from the guard for the sender, and `hb` with `0 < n` for the recipient; the goal is to close the allowed branch.

**The second `exact`:** the move closes the rejected branch with the starting facts; the reason is that the state is unchanged; the goal is the last one open.

Tick what you covered: the move, the reason, the goal. The ideas count, not the wording.
:::

:::item role=segment family=GEN-proof-structure template=t3 kcs=KC-2.proof-reading
@choice key=C
`topUp` adds `n` to a balance unless the result would pass the cap; then it leaves the balance alone. Which hypothesis does the line marked ◀ rely on? (`omega` closes whole-number arithmetic goals from the facts in scope.)

```lean
def topUp (bal n cap : Int) : Int := if bal + n ≤ cap then bal + n else bal

theorem topUp_le_cap (bal n cap : Int) (hb : bal ≤ cap) (hn : 0 ≤ n) (hc : 0 ≤ cap) :
    topUp bal n cap ≤ cap := by
  unfold topUp
  split
  · omega
  · omega   -- ◀
```

- A. `hn : 0 ≤ n`
  - why: In this branch `topUp` adds nothing, so `n` never enters the goal.
  - mis: dp:X2
- B. `hc : 0 ≤ cap`
  - why: It is in scope, but this goal never needs the cap to be non-negative.
  - mis: dp:X2
- C. `hb : bal ≤ cap`
  - why: In this branch `topUp` returns `bal` unchanged, so the goal is exactly `bal ≤ cap`.
- D. The theorem's own conclusion, `topUp bal n cap ≤ cap`
  - why: That is the goal being proved. Using it to prove itself is circular.
  - mis: dp:L6
:::

## Exit {minutes=4 kcs=KC-2.proof-reading}

From here on, worked examples stop asking you to explain each line: at most one short question follows a revealed step, and blanks carry none. Keep asking the three questions yourself.

:::item role=exit family=GEN-proof-structure template=t3 kcs=KC-2.proof-reading
@choice key=D
`spend` subtracts `n` from a balance when `n ≤ bal`, and otherwise leaves it alone. Which hypothesis does the line marked ◀ rely on?

```lean
def spend (bal n : Int) : Int := if n ≤ bal then bal - n else bal

theorem spend_le (bal n : Int) (h0 : 0 ≤ bal) (h1 : 0 ≤ n) (h2 : bal ≤ 100) :
    spend bal n ≤ bal := by
  unfold spend
  split
  · omega   -- ◀
  · omega
```

- A. `h0 : 0 ≤ bal`
  - why: The goal `bal - n ≤ bal` holds whatever the balance is, so `h0` is not used.
  - mis: dp:X2
- B. `h2 : bal ≤ 100`
  - why: A bound on the balance that this goal never uses.
  - mis: dp:X2
- C. The branch's own guard, `n ≤ bal`
  - why: It is in scope, but `bal - n ≤ bal` does not depend on it.
  - mis: dp:X2
- D. `h1 : 0 ≤ n`
  - why: Taking away something non-negative cannot raise a balance. With a negative `n` the goal would fail.
:::
