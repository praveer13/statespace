## A green build, and then what {minutes=2 kcs=KC-2.axioms-and-trust}

A green build feels like an answer. In Lean it is not one, and this lesson is about the gap: what each check actually looked at, what a proof quietly assumes, and what happened in 2026 when a checker itself was wrong.

## Four kinds of axiom {minutes=13 kcs=KC-2.axioms-and-trust}

A Lean proof is a term, and the kernel checks that the term has the type of the statement. The term may lean on assumptions that Lean does not prove: axioms. `#print axioms` lists every axiom a theorem depends on, following the dependencies all the way down. It re-checks nothing. It tells you what the proof assumes, and the assumptions fall into four kinds.

| Kind | The list shows | The stamp it earns |
|---|---|---|
| Standard | some of `propext`, `Classical.choice`, `Quot.sound` | PROVED [P] · Lean {{run:RUN-lean-toolchain#version}} kernel · axioms listed |
| Unfinished | `sorryAx` | no [P]: "PROVED modulo k assumed lemmas", each lemma ASSUMED [A] |
| Native | a name containing `_native` | PROVED [P] · kernel + compiler |
| Custom | an axiom someone declared | no [P]: the axiom is carried as ASSUMED [A], like `sorryAx` |

Here are five theorems, one for each kind and one for a tactic that adds nothing. Read the code, then make your call before you look at what `#print axioms` says about the native one.

:::instrument ins=INS-goal-replay cell=1 recorded=RUN-lean-axioms
```lean
-- standard: a proof by `omega`
theorem by_omega (x y : Int) (h : x ≤ y) : x - 1 < y := by omega
-- native: `native_decide` trusts the compiler
theorem big_native : (2^64 : Nat) % 7 = 2 := by native_decide
-- none: `decide` evaluates inside the kernel
theorem by_decide : (2^10 : Nat) % 7 = 2 := by decide
-- unfinished: `sorry`
theorem with_sorry : (1 : Nat) = 2 := by sorry
-- custom: a declared axiom
axiom cheat : False
theorem with_axiom : (1 : Nat) = 2 := cheat.elim

#print axioms by_omega
#print axioms big_native
#print axioms by_decide
#print axioms with_sorry
#print axioms with_axiom
```

@direction
Replay shows: five theorems, each followed by the axioms it depends on. Read each line for the kind of axiom it reports. The last two theorems state something false, and the proofs are still accepted as far as the build goes.

## Build, axioms, replay {minutes=14 kcs=KC-2.axioms-and-trust}

Three checks sound alike and are not. A **build** elaborates your files: it runs the tactics, and it reports errors. An **axiom list** says what the finished proof assumes. A **kernel replay** takes every declaration in the environment and checks it again, however it got there. The difference matters, because the elaborator is not the kernel.

Three specimens from recorded runs show the gaps:

- A file whose theorem ends in `sorry` builds with a warning, and its axiom list names `sorryAx` {{run:RUN-lean-axioms}}. A green build is no verdict on a proof.
- On a project with three non-standard axioms, `lake check` rejects each of them, and its log still prints `{{run:RUN-lean-axioms#values.lake_check_kernel_line}}` {{run:RUN-lean-axioms}}. Those are two verdicts: the kernel accepted the proofs, and the axiom policy refused three assumptions. Read every line.
- A declaration added while kernel checking is switched off by the option `debug.skipKernelTC`, and the theorem `1 = 2` built on it, both build clean and list no axioms {{run:RUN-lean-skipkernel}}. The source stays out of this page on purpose. The option line is the point.

:::instrument ins=INS-bench-lean cell=2 recorded=RUN-lean-skipkernel
```bash
lake build              # elaborates every module
leanchecker Probe       # replays every declaration through the kernel
```

@direction
Run: a project whose theorem `anything : 1 = 2` rests on a declaration added with `debug.skipKernelTC` set. The build and its axiom lines come first, then the replay. The declaration's source is withheld.

@tap
the theorem `1 = 2` is proved

@call key=C surprise=yes run=RUN-lean-skipkernel
The build is clean and `#print axioms` lists nothing for `anything : 1 = 2`. Is `1 = 2` proved?

- A. Yes: the build is clean and no axioms are listed.
  - why: Both outputs come from an elaborator told to skip the kernel, so neither checked that declaration.
  - mis: dp:L9
- B. No: `1 = 2` is false.
  - why: True, and still not something these outputs can show. Only a kernel replay rejects the declaration.
  - mis: dp:L9
- C. Can't tell: a kernel replay has to decide.
  - why: The replay checks every declaration again, whoever added it, and it rejects this one.

@after
The replay rejects the declaration {{run:RUN-lean-skipkernel}}. A build reports what the elaborator did, an axiom list reports what a proof assumes, and neither asks the kernel again. Only a replay does. That is why a Lean claim carries the checker's name: a stamp is only as good as the check behind it.
:::

## The day the kernel was wrong {minutes=14 kcs=KC-2.axioms-and-trust,KC-2.automation-scope}

One kernel is one place to trust. Comparator can run several: `--paranoid` checks your solution with every checker the toolchain bundles, and on a solution like yours it takes seconds {{run:RUN-lean-comparator}}. Its longer sibling, `lake check --paranoid`, replays the whole environment and takes minutes on a fast machine, so this lesson names it and does not wait for it {{run:RUN-bwrap-lanes}}.

In July 2026 an AI-assisted Lean "disproof" of the Collatz conjecture was published from a pipeline that replayed proofs, checked axioms and ran a pinned second checker. Run the check on your own project, and make your call about that pipeline before you read what happened.

:::instrument ins=INS-bench-lean cell=3 recorded=RUN-lean-comparator
```bash
lake comparator --paranoid
```

@direction
Run: comparator on the pinned challenge and your solution, with every bundled checker switched on. Each checker prints its own verdict line.

@tap
the pinned theorems are proved about the pinned definitions

@call key=A surprise=yes
A pipeline replayed proofs, checked axioms and ran a pinned second checker. Could it accept a proof of `False`?

- A. Yes, it could
  - why: It did: two bugs in two checkers, one of them a week out of date.
- B. No, it could not
  - why: Checks can share a blind spot, and a pinned checker can lag a fix.
  - mis: dp:X4

@after
`--paranoid` runs {{run:RUN-lean-comparator#values.paranoid_checkers}} checkers {{run:RUN-lean-comparator}}, and they can share a flaw: lean4lean ports the reference logic for inductive types. A PROVED stamp names its checkers and their versions, and an advisory can reopen it.
:::

:::card variant=dated-incident title="The day the kernel was wrong"
On 2026-07-25 a Lean "disproof" of the Collatz conjecture was published from a pipeline that replayed proofs, checked axioms and ran a pinned second checker, nanoda. On 2026-07-28 issue #14576 reduced it to a proof of `False` with no axioms, and the kernel was fixed the same day. The postmortem of 2026-08-01 found two bugs, chained: the official kernel "had a missing check in the nested inductive type support", and nanoda "did not verify the type name in a projection node". The repository "also passed a week-old version of nanoda". A third checker, lean4lean, shared the kernel's bug because its inductive types port the reference implementation. The advisory of 2026-08-02 says exploiting it "requires execution of a metaprogram within the Lean process", which is why `lake check` runs your build in a sandbox and replays an export of the result. Sources: [the postmortem](https://leodemoura.github.io/blog/2026-8-1-postmortem-for-kernel-soundness-bug-14576/) and [the advisory](https://www.openwall.com/lists/oss-security/2026/08/02/1).
:::

## Exit {minutes=5 kcs=KC-2.axioms-and-trust,KC-2.automation-scope}

**Assumed, and tested at every Lean Defence:** the Lean {{run:RUN-lean-toolchain#version}} kernel accepts only well-typed terms. That is SEAM-15, and it sits under every claim you mint in this stage. It is held, not cracked. If an advisory ever reopens it, the news reaches you as a note on your claims, never as a silent change to them.

**Say it back.** Retell the story in four sentences, without exploit detail: what the pipeline checked, what was wrong, why a second checker did not save it, and what the fix and the advisory changed. Nothing here is graded.
