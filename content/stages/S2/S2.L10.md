## Agreement is not the question {minutes=2 kcs=KC-2.kernel-not-requirement}

Several checkers can agree and still be answering a question you did not ask. In the last lesson you saw what each check re-checks. This one is about what no checker reads: your requirement.

:::item role=prequestion family=GEN-call-it template=t4 kcs=KC-2.kernel-not-requirement

- A. The pinned statements are proved about the pinned definitions, with permitted axioms, and every checker accepts the proofs.
  - why: That is what the check read, and all of it.
- B. The ledger meets its business requirements.
  - why: No checker reads requirements.
  - mis: dp:L3
- C. Your system's code behaves like the model.
  - why: Correspondence between code and model is a separate claim, made in S6.
  - mis: dp:P3
- D. Several confirmations that cannot share a flaw.
  - why: They can share one: lean4lean ports the reference logic for inductive types, as S2.L9 showed.
  - mis: dp:X4

## What comparator says {minutes=14 kcs=KC-2.statement-pinning}

Comparator works from a **challenge** and a **solution**. The challenge is a module you pin: the definitions and the statements, each statement ending in `sorry`, hashed so that nobody can change it quietly. The solution is a module with the same names and real proofs, written by you or by an agent. Comparator exports both and checks that every named theorem has exactly the pinned statement, that every definition the statements use is the pinned one, that the kernel accepts the proofs, and that they use only the axioms the pack permits. That is the boundary for an agent: it can write any proof it likes, and it still cannot change what is being proved.

Two recorded submissions show the first two checks. The honest solution is accepted. The solution with `(h : n = 0)` added under the same name builds green and is rejected as a statement mismatch {{run:RUN-lean-comparator}}. That is the cheap way to "prove" something: weaken the claim and keep the name.

Now a third submission. Every proof in it is valid, and `transfer` has been redefined to return its input:

```lean
-- in the solution module
def transfer (s : Ledger) (n : Int) : Ledger := s
```

:::instrument ins=INS-bench-lean cell=1 recorded=RUN-lean-comparator
```bash
lake comparator
```

@direction
Run: comparator on a solution whose proofs are valid but whose `transfer` returns its input. The challenge pins the original `transfer`, and the statements are unchanged.

@tap
the submitted solution proves the pinned statements

@call key=C surprise=no run=RUN-lean-comparator
What does comparator say about the redefined submission?

- A. Accepted: every proof is valid.
  - why: The proofs are valid only for a `transfer` that no longer matches the pin.
  - mis: dp:L9
- B. Rejected: a theorem statement does not match.
  - why: The text of every statement is unchanged. A constant that they use changed.
  - mis: dp:L4
- C. Rejected: a definition does not match.
  - why: Comparator compares the constants a statement uses, so the changed `transfer` is caught.

@after
Comparator rejects the submission and names the constant {{run:RUN-lean-comparator}}. A text diff of the theorems would have seen nothing, because the statements are unchanged. That is why a challenge pins the definitions as well as the statements. The weakening in the other submission was caught for the same reason: comparator compares against the pin, not against your intent.
:::

An exit code is not a verdict. Without bubblewrap, the sandbox tool, comparator exits with {{run:RUN-lean-bwrap-docker#values.no_bwrap_exit}}. Under default Docker the sandbox tool is there but cannot create a namespace, and comparator exits with {{run:RUN-lean-bwrap-docker#values.default_docker_exit}}, which is also the code of a rejection. What tells them apart is a line that begins `bwrap:` and reports a namespace-permission error. Your receipt records the sandbox as on, off or failed. Read the lines, not the number.

:::item role=segment family=GEN-call-it template=t1 kcs=KC-2.statement-pinning


- A. Rejected: a checker did not accept a proof.
  - why: No checker ran. The sandbox that wraps them failed first.
  - mis: dp:L9
- B. No verdict: the check did not run.
  - why: The `bwrap:` line is positive evidence that the sandbox failed, so no checker looked at anything.
- C. Rejected: the statement does not match the pin.
  - why: A mismatch would name a theorem or a constant. This output names neither.
  - mis: dp:L9
- D. Accepted: nothing reported a mismatch.
  - why: Silence about a mismatch is not acceptance when nothing ran.
  - mis: dp:L9
:::

## Several checkers and one requirement {minutes=14 kcs=KC-2.kernel-not-requirement}

Here is a requirement in plain words, the kind you would restate for your own system. Call it R: an allowed transfer debits exactly `n` from the sender and credits exactly `n` to the recipient; a disallowed transfer changes nothing; no balance goes negative; money is never created or destroyed.

The four pinned theorems are a formal rendering of most of that:

```lean
theorem transfer_conserves (s : Ledger) (n : Int) : total (transfer s n) = total s
theorem transfer_rejected (s : Ledger) (n : Int) (h : ¬ (0 ≤ n ∧ n ≤ s.a)) : transfer s n = s
theorem transfer_nonneg (s : Ledger) (n : Int) (ha : 0 ≤ s.a) (hb : 0 ≤ s.b) :
    0 ≤ (transfer s n).a ∧ 0 ≤ (transfer s n).b
theorem run_conserves (s : Ledger) (ns : List Int) : total (run s ns) = total s
```

Now take the redefinition from the last segment, the transfer that returns its input. Comparator caught it only because the challenge pins `transfer`. Suppose the pin had missed it. How many of the four statements would an idle transfer satisfy? The cell evaluates each statement as a property of whichever transfer you pick.

:::instrument ins=INS-interp cell=2 recorded=RUN-lean-intent
```text
transfer T: pinned      (switch to: idle, which returns its input)

property conserves(s, n):  total(T(s, n)) == total(s)
property rejected(s, n):   not (0 <= n and n <= s.a)  =>  T(s, n) == s
property nonneg(s, n):     s.a >= 0 and s.b >= 0  =>  T(s, n).a >= 0 and T(s, n).b >= 0
property sequence(s, ns):  total(run(T, s, ns)) == total(s)
```

@direction
Check: each property is evaluated on small states against the transfer you pick. Start with the pinned transfer, then switch to the idle one.

@tap
the four theorems say what the ledger must do

@call key=C surprise=yes run=RUN-lean-intent
How many of the four statements hold for the idle transfer?

- A. None
  - why: Sums, signs and rejection are all preserved by a transfer that changes nothing.
  - mis: dp:L3
- B. Conservation only
  - why: Non-negativity and rejection hold too, because nothing ever changes.
  - mis: dp:L3
- C. All four
  - why: None of them says that money moves. This is SP-2.9.

@after
All four hold for the idle transfer {{run:RUN-lean-intent}}. It never changes a sum, never creates a negative balance, and leaves a rejected transfer untouched, because it leaves everything untouched. The four theorems are true, proved and accepted by every checker, and they are silent on the one thing R cares most about: that money moves.
:::

:::item role=segment family=GEN-call-it template=t4 kcs=KC-2.kernel-not-requirement
@choice key=A
Each option gives an amount, the balances before, and the balances after. Which outcome do the four theorems permit and R forbid?

- A. Amount 5, before (10, 0), after (10, 0)
  - why: All four theorems allow it: nothing is created, nothing goes negative. R forbids it, because an allowed transfer must debit 5.
- B. Amount 5, before (3, 0), after (−2, 5)
  - why: The amount exceeds the balance, so `transfer_rejected` forbids any change, and the negative balance breaks `transfer_nonneg`.
  - mis: dp:L4
- C. Amount −5, before (10, 8), after (15, 3)
  - why: A negative amount is rejected, and `transfer_rejected` forbids any change.
  - mis: dp:L4
- D. Amount 4, before (10, 0), after (6, 4)
  - why: The theorems allow it, and so does R: it is exactly the outcome R requires.
  - mis: dp:L3
:::

## You state {minutes=14 kcs=KC-2.statement-pinning,KC-2.kernel-not-requirement}

Agents prove; you state. The cure for the idle transfer is a statement, not a better proof. A checker proves what you pin and nothing you left out, so if R says that money moves, some pinned statement has to say it. This is the one that does:

```lean
theorem transfer_moves (s : Ledger) (n : Int) (h : 0 ≤ n ∧ n ≤ s.a) :
    transfer s n = { a := s.a - n, b := s.b + n }
```

:::instrument ins=INS-interp cell=3 recorded=RUN-lean-intent
```text
transfer T: pinned      (switch to: idle)

the four properties from the last cell, and:
property moves(s, n):      (0 <= n and n <= s.a)  =>  T(s, n) == (a: s.a - n, b: s.b + n)
```

@direction
Check: the four properties and `moves`, evaluated against the transfer you pick. Run the idle transfer first.

@tap
the five statements together say what the ledger must do

@call key=B surprise=no run=RUN-lean-intent
You add `transfer_moves`: an allowed transfer yields exactly (a − n, b + n). The idle transfer is checked against all five statements. What happens?

- A. It passes all five statements.
  - why: A single small allowed transfer already breaks `moves`, because the idle transfer leaves the balances alone.
  - mis: dp:L3
- B. It fails `transfer_moves` only.
  - why: The new statement is the one that says money moves. The other four still hold.
- C. It fails conservation too.
  - why: Idling conserves the total, so the old statements still hold.
  - mis: dp:L4

@after
The idle transfer fails `transfer_moves` and nothing else {{run:RUN-lean-intent}}, and the pinned transfer passes all five. One allowed transfer of a single unit is enough to refute the idle one. The gap was never in the proofs. It was in what was pinned.
:::

:::item role=segment family=GEN-call-it template=t4 kcs=KC-2.kernel-not-requirement
@choice key=B
Which statement, added to the four, rules out the idle outcome and the wrong-amount outcome, and still holds for the pinned transfer?

- A. An allowed transfer changes the state.
  - why: An allowed transfer of zero is allowed and changes nothing, so this fails for the pinned transfer.
  - mis: dp:L4
- B. An allowed transfer lowers the sender by exactly `n`.
  - why: With conservation it also fixes the credit. The idle and wrong-amount outcomes both break it.
- C. The total is conserved and balances stay non-negative.
  - why: The idle transfer satisfies this too, so it rules out nothing new.
  - mis: dp:L3
- D. A disallowed transfer changes nothing.
  - why: That is `transfer_rejected` again. It is silent about allowed transfers.
  - mis: dp:L4
:::

## Exit {minutes=5 kcs=KC-2.kernel-not-requirement,KC-2.statement-pinning}

Even with `transfer_moves` proved, the requirement-fit part of a claim stays ASSUMED [A]: you restated R, and no checker read it. The pinned guard also allows a zero amount, and whether R should reject it is a decision that S3 records.

- A. Amount 9, before (8, 2), after (−1, 11)
  - why: The amount exceeds the balance, so `transfer_rejected` forbids any change.
  - mis: dp:L4
- B. Amount −3, before (8, 2), after (11, −1)
  - why: A negative amount is rejected, and the negative balance also breaks `transfer_nonneg`.
  - mis: dp:L4
- C. Amount 3, before (8, 2), after (6, 4)

- D. Amount 3, before (8, 2), after (5, 5)
  - why: This is the outcome R requires, and the theorems allow it.
  - mis: dp:L3
