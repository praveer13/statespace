## One account, two writes {minutes=14 kcs=KC-2.finite-map-update}

:::item role=prequestion family=GEN-find-the-witness template=t1 kcs=KC-2.finite-map-update
@choice key=C
An account holds 10 and transfers 5 to itself. Both new balances are computed from the old state, then written in order: the debit, then the credit. What is the final balance?

- A. 10
  - why: That is the balance you expect, and the one the fixed update leaves. This update does not.
  - mis: dp:L7
- B. 5
  - why: The credit is written after the debit, so the debit does not survive.
  - mis: dp:L7
- C. 15
  - why: The credit computes 10 + 5 from the old state and overwrites the debit's 5. {{run:RUN-lean-selftransfer}}
- D. 20
  - why: Only one 5 is added.
  - mis: dp:L7
:::

Until now a ledger had two fields. A system with many accounts keeps its state as a function from account numbers to balances, and a transfer becomes a pair of writes. Here `Bal := Acct → Int`, and `upd f k v` is `f` with the single account `k` set to `v`.

The roadmap says finite maps. Here accounts are a function from every account number to a balance, because a finite-map library would need Mathlib, which this stage leaves out {{run:RUN-lean-mathlib}}. The theorems cover the two accounts a transfer touches and every account it leaves alone. A total over many accounts is not proved.

```lean
abbrev Acct := Nat
abbrev Bal := Acct → Int

def upd (f : Bal) (k : Acct) (v : Int) : Bal := fun j => if j = k then v else f j

-- both new balances are computed from the OLD state, then written in order
def xferBuggy (f : Bal) (src dst : Acct) (n : Int) : Bal :=
  if 0 ≤ n ∧ n ≤ f src then upd (upd f src (f src - n)) dst (f dst + n) else f
```

Ask Z3 whether this update can ever change an account that sends to itself.

:::instrument ins=INS-z3 cell=1 recorded=RUN-z3-selftransfer
```python
from z3 import *

Bal = Array('Bal', IntSort(), IntSort())   # account number -> balance
src, dst, n = Ints('src dst n')

allowed = And(0 <= n, n <= Bal[src])       # the guard
# the buggy update: both new balances come from the OLD state
buggy = Store(Store(Bal, src, Bal[src] - n), dst, Bal[dst] + n)

s = Solver()
s.add(src == dst, allowed, buggy[src] != Bal[src])
print(s.check())
print(s.model())
```

@direction
Query asserts: one account is both sender and recipient, the guard allows the amount, and the balance afterwards differs from the balance before. `sat` means such a self-transfer exists.

@tap
a self-transfer leaves the account's balance unchanged

@call key=C surprise=yes run=RUN-z3-selftransfer
Under the buggy update, for which amounts does an allowed self-transfer change the balance?

- A. Never: the money leaves and arrives at the same account.
  - why: The credit is written last and overwrites the debit with the old balance plus `n`.
  - mis: dp:L7
- B. Only for amounts the guard rejects.
  - why: A rejected transfer returns the state unchanged.
  - mis: dp:L7
- C. For every positive amount the guard allows.
  - why: The final balance is the old balance plus `n`, which differs from the old balance whenever `n` is positive.
- D. For every amount, zero included.
  - why: With `n = 0` both writes store the old balance.
  - mis: dp:L7

@after
Z3 found a witness {{run:RUN-z3-selftransfer}}, and its values will differ from the next run's: a witness is checked, never matched. The reason is the order of the writes. The debit stores the old balance minus `n`; the credit then stores the old balance plus `n`, computed from the old state, on top of it. The account ends with its old balance plus `n`, so a self-transfer mints money. This is SP-2.1.
:::

The cure is to read the destination after the debit:

```lean
def xfer (f : Bal) (src dst : Acct) (n : Int) : Bal :=
  if 0 ≤ n ∧ n ≤ f src then
    let f1 := upd f src (f src - n)
    upd f1 dst (f1 dst + n)
  else f
```

Lean can check one instance of each with `decide`, which evaluates a closed, decidable claim. On another balance and amount, so the proofs in LAB-2.6 stay yours:

```lean
theorem mints_from_7 : xferBuggy (fun _ => 7) 0 0 3 0 = 10 := by decide
theorem fixed_from_7 : xfer (fun _ => 7) 0 0 3 0 = 7 := by decide
```

Lean accepts both {{run:RUN-lean-s2-cells}}. `decide` checks this instance, not the general theorem. The theorems in the lab are the general ones: every other account is untouched, the two accounts' sum is unchanged, and a self-transfer changes nothing.

:::item role=exit family=GEN-find-the-witness template=t1 kcs=KC-2.finite-map-update
@choice key=D
`xfer` reads the destination after the debit. Which self-transfer changes the balance?

- A. Balance 10 with amount 5, as in the buggy update
  - why: That is the buggy update's witness. `xfer` credits the balance after the debit, so 5 comes back.
  - mis: dp:L7
- B. Balance 10 with amount 10, the whole balance
  - why: The debit leaves 0 and the credit adds 10 to that 0, so the balance is 10 again.
  - mis: dp:L7
- C. Balance 10 with amount 1, the smallest amount
  - why: The debit leaves 9 and the credit adds 1 to it, so the balance is 10 again.
  - mis: dp:L7
- D. Not one of them, as each leaves the balance at 10
  - why: Whatever the guard allows, the credit starts from the debited balance and restores the original.
