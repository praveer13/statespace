## Two questions first {minutes=2 kcs=KC-2.theorem-statement-reading}

A proof that Lean accepts is only as useful as the statement it proves. Before you prove anything in the lab, practise reading a statement: what it covers, what it leaves out, and what happens when you weaken an assumption. Two questions to start; guess if you are unsure, because the point is to notice what you expect.

:::item role=prequestion family=GEN-call-it template=t4 kcs=KC-2.theorem-statement-reading
@choice key=A
`theorem transfer_conserves (s : Ledger) (n : Int) : total (transfer s n) = total s`. For which `n` does it promise anything?

- A. Every integer, allowed or not
  - why: The statement has no hypothesis about `n`, and both branches of `transfer` conserve the total.
- B. Only amounts the guard allows
  - why: The guard lives inside `transfer`, not in the statement.
  - mis: dp:L4
- C. Only `n ≥ 0`
  - why: Nothing in the statement restricts `n`.
  - mis: dp:L4
- D. Only when the transfer succeeds
  - why: A rejected transfer returns `s`, which keeps the total trivially, so the statement covers it too.
  - mis: dp:L4
:::

:::item role=prequestion family=GEN-call-it template=t4 kcs=KC-2.theorem-statement-reading
@choice key=B
Delete the guard from `transfer`. Which theorem stops being provable?

- A. Conservation: the total of both balances is unchanged
  - why: (a − n) + (b + n) equals a + b for every `n`, as Z3 showed in S1 {{run:RUN-z3-conservation-noguard}}.
  - mis: dp:L4
- B. Non-negativity: both balances stay at zero or above
  - why: With a = 0 and n = 1 the sender ends at −1, and 1 is the minimal such amount {{run:RUN-z3-optimize-min}}.
- C. Both: conservation and non-negativity alike
  - why: Conservation survives the loss of the guard.
  - mis: dp:L4
- D. Neither: the two theorems still go through
  - why: Non-negativity needs `n ≤ s.a`, which is the guard.
  - mis: dp:L4
:::

## What the statement promises {minutes=13 kcs=KC-2.theorem-statement-reading,KC-2.props-as-types}

A theorem statement is a promise about every value of its variables. Read what stands before the colon: `(s : Ledger) (n : Int)` means "for every ledger and every integer". What the theorem promises depends on those variables and on any hypothesis written there, and on nothing else. `transfer_conserves` has no hypothesis about `n`, so it covers amounts the guard rejects too. For those, `transfer` returns the state unchanged, and an unchanged state keeps the total.

You will prove `transfer_conserves` yourself in LAB-2.2. Here is a proof of its parallel theorem, the same statement about `transferPos`, which also rejects a zero amount. Read it for what it uses, and watch for the guard.

:::instrument ins=INS-goal-replay cell=1 recorded=RUN-lean-s2-cells
The proof of `transferPos_conserves`, read for what it uses.

```lean
structure Ledger where
  a : Int
  b : Int
deriving Repr, DecidableEq

def total (s : Ledger) : Int := s.a + s.b

def transferPos (s : Ledger) (n : Int) : Ledger :=
  if 0 < n ∧ n ≤ s.a then { a := s.a - n, b := s.b + n } else s

theorem transferPos_conserves (s : Ledger) (n : Int) :
    total (transferPos s n) = total s := by
  unfold transferPos total
  split <;> simp <;> omega
```

@direction
Replay shows: the proof of `transferPos_conserves`, one tactic at a time. Look at what each branch receives, and at what each one uses.

@call key=C surprise=yes run=RUN-lean-s2-cells
Before `split` is shown: will any branch of this proof use the guard as a hypothesis?

- A. The allowed branch
  - why: It receives the guard, but its goal holds for every `n`, so the guard goes unused.
  - mis: dp:L4
- B. The rejected branch
  - why: That branch returns `s`, and `s.a + s.b = s.a + s.b` needs no hypothesis.
  - mis: dp:L4
- C. Neither
  - why: Both branches conserve the total whatever the guard says. The guard shapes what `transferPos` does, not whether the total survives.

@after
Neither branch needed the guard. In the allowed branch `s.a - n + (s.b + n)` equals `s.a + s.b` for every `n`, so the guard is in scope and unused. The proof lists only `propext` and `Quot.sound` as axioms, the two axioms of Lean's own logic {{run:RUN-lean-s2-cells}}.
:::

:::item role=segment family=GEN-proof-structure template=t1 kcs=KC-2.props-as-types
@choice key=D
`transferAny s n` is `if n ≤ s.a then { a := s.a - n, b := s.b + n } else s`: a guard with no sign check. To prove `total (transferAny s n) = total s` you start with `unfold transferAny total` and `split`. What do the two goals look like?

- A. Two goals, and both of them have the guard `n ≤ s.a` as a hypothesis
  - why: Only the first branch has the guard. The second has its negation.
  - mis: dp:L1
- B. One goal: the `if` is removed, with no new hypothesis
  - why: `split` produces a goal for each branch.
  - mis: dp:L1
- C. No goals, because `split` has proved the total unchanged
  - why: `split` divides the work and proves nothing.
  - mis: dp:L2
- D. Two goals: one with `n ≤ s.a` in scope, one with its negation
  - why: Each branch gets its own condition, and the rejected branch is the untouched state.
:::

## Take the guard away {minutes=13 kcs=KC-2.theorem-statement-reading}

Now remove the guard and see what each proof really depended on. In the cell, `noGuard` is `transfer` with no `if` at all: it always moves `n`. Two theorems are tried, one per property, with the same tactic script for both.

:::instrument ins=INS-goal-replay cell=2 recorded=RUN-lean-noguard
```lean
def noGuard (s : Ledger) (n : Int) : Ledger :=
  { a := s.a - n, b := s.b + n }

theorem noGuard_conserves (s : Ledger) (n : Int) :
    total (noGuard s n) = total s := by
  unfold noGuard total
  simp <;> omega

theorem noGuard_nonneg (s : Ledger) (n : Int) (ha : 0 ≤ s.a) (hb : 0 ≤ s.b) :
    0 ≤ (noGuard s n).a ∧ 0 ≤ (noGuard s n).b := by
  unfold noGuard
  simp <;> omega
```

@direction
Replay shows: Lean's verdict on each theorem, with the guard removed from the transfer.

@call key=A surprise=yes run=RUN-lean-noguard
With no guard, does the conservation theorem still build?

- A. Yes, it does
  - why: Conservation is about the arithmetic of both fields, and (a − n) + (b + n) is a + b for every `n`. This is specimen SP-2.2.
- B. No, it does not
  - why: The guard protects signs, not sums.
  - mis: dp:L4

@after
Conservation builds and non-negativity does not: Lean reports a possible counterexample for the second {{run:RUN-lean-noguard}}. With an amount of 1 and a sender at 0, the sender ends at −1, and Z3 found the same smallest amount in S1 {{run:RUN-z3-optimize-min}}. The guard protects signs, not sums.
:::

:::item role=segment family=GEN-call-it template=t4 kcs=KC-2.theorem-statement-reading
@choice key=C
Which of these says exactly what `transfer_conserves` proves, no more and no less?

- A. For every ledger and every amount the guard allows, the total after a transfer equals the total before.
  - why: This promises less. The theorem also covers the amounts the guard rejects.
  - mis: dp:L4
- B. For every ledger and every amount the guard allows, neither balance goes below zero after a transfer.
  - why: That is non-negativity, another theorem. Conservation says nothing about signs.
  - mis: dp:L3
- C. For every ledger and every amount, the total after a transfer equals the total before.
  - why: It keeps every hypothesis and adds none.
- D. For every ledger there is an amount for which the total after a transfer equals the total before.
  - why: "For some amount" is a far weaker promise, and an amount of 0 already satisfies it. The theorem says every amount.
  - mis: dp:G6
:::

## If weakened {minutes=13 kcs=KC-2.theorem-statement-reading,KC-2.props-as-types}

A claim card says what you proved and what would break it. Its "if weakened" field asks for a counterexample when an assumption is weakened, which is the roadmap's third rule. The witness has to refute this claim, not its neighbor: a witness for non-negativity does nothing for conservation.

Below is a demo card for CL-2.1, the claim about `transfer_conserves`. Its method, tool and version come from the LAB-2.1 receipt, and its "if weakened" field already holds a witness: drop `n ≤ s.a`, and a sender at 0 sends 1. Before the check runs, decide whether claim validation accepts the card.

:::instrument ins=INS-bench-lean cell=3 recorded=RUN-lean-s2-cells
```text
claim: CL-2.1
proposition: transfer_conserves, for every ledger and every amount
assumptions: sender and recipient are two distinct fields
model: the pinned challenge
method: lake comparator, from your LAB-2.1 receipt
correspondence: none yet
if weakened: drop n ≤ s.a; a = 0, b = 0, n = 1 leaves the sender at -1
requirement: a transfer never creates or destroys money
```

@direction
Check shows: `statespace check` validating this card against the claim rules on your Bench. On a phone you see the recorded result, labeled with its run.

@call key=B surprise=yes
Will claim validation accept this card?

- A. Accepted: the witness overdraws the sender, as required
  - why: With no guard conservation still holds, so this witness refutes CL-2.2, not CL-2.1.
  - mis: dp:L4
- B. Rejected: the witness does not refute this card's proposition
  - why: Claim validation requires the witness to refute the card's own proposition under the weakened assumption.
- C. Rejected: the witness is not the minimal one there is
  - why: Minimality is not required, and an amount of 1 is minimal anyway.
  - mis: dp:L4

@after
The witness is real, but it belongs to the neighbor: it breaks non-negativity (CL-2.2), not conservation {{run:RUN-z3-optimize-min}}. For CL-2.1, weaken something that conservation actually uses. The next question gives you candidates.
:::

:::item role=segment family=GEN-call-it template=t4 kcs=KC-2.theorem-statement-reading
@choice key=B
Which entry is a witness that refutes CL-2.1's proposition, `total (transfer s n) = total s`, under its weakened assumption?

- A. Drop `n ≤ s.a`: a = 0, b = 0 and n = 1 leave the sender at −1.
  - why: That breaks non-negativity (CL-2.2). The total is still 0.
  - mis: dp:L4
- B. One account, both balances computed from the old state: a self-transfer of 1.
  - why: The account's balance changes, so the total does {{run:RUN-z3-selftransfer}}.
- C. Drop `0 ≤ n`: n = −5, so money moves from recipient to sender.
  - why: Money moves backwards and the total is unchanged.
  - mis: dp:L4
- D. One account, with the credit read after the debit: 10 transferring 5 to itself.
  - why: Reading after the debit is the fixed order, and the balance stays 10 {{run:RUN-lean-selftransfer}}.
  - mis: dp:L7
:::

## Exit {minutes=5 kcs=KC-2.theorem-statement-reading,KC-2.props-as-types}

:::item role=exit family=GEN-call-it template=t4 kcs=KC-2.theorem-statement-reading
@choice key=D
Which of these says exactly what `transfer_rejected` proves? Its statement is `theorem transfer_rejected (s : Ledger) (n : Int) (h : ¬ (0 ≤ n ∧ n ≤ s.a)) : transfer s n = s`.

- A. For every ledger and every amount, the transfer returns the ledger unchanged.
  - why: This drops the hypothesis `h`. An allowed transfer does change the ledger.
  - mis: dp:L4
- B. For every ledger there is an amount the guard rejects, and the transfer leaves the ledger unchanged for it.
  - why: "For some amount" promises less than every amount.
  - mis: dp:G6
- C. For every ledger and every amount the guard rejects, no balance goes negative.
  - why: That is another property. This theorem says nothing about signs.
  - mis: dp:L3
- D. For every ledger and every amount the guard rejects, the transfer returns the ledger unchanged.
  - why: It names the hypothesis and the conclusion, and adds nothing.
:::

:::item role=exit family=GEN-proof-structure template=t1 kcs=KC-2.props-as-types
@choice key=C
The goal is `(0 ≤ n ∧ n ≤ s.a) → n ≤ s.a`. After `intro h`, what do you have?

- A. One goal, still `(0 ≤ n ∧ n ≤ s.a) → n ≤ s.a`
  - why: `intro` moves the left side of the arrow into scope, so the goal shrinks.
  - mis: dp:L1
- B. Two goals, `0 ≤ n` and `n ≤ s.a`, one per conjunct
  - why: Splitting a conjunction is the job of `constructor`. `intro` names a hypothesis.
  - mis: dp:L1
- C. One goal `n ≤ s.a`, with `h : 0 ≤ n ∧ n ≤ s.a` in scope
  - why: A proof of an implication takes evidence in and gives evidence out. `intro` names the evidence you are handed.
- D. No goals: `intro` closes the implication by itself
  - why: `intro` names a hypothesis and proves nothing.
  - mis: dp:L2
:::
