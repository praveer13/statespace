## Base, step, and one trap {minutes=15 kcs=KC-2.induction-principle}

:::item role=prequestion family=GEN-proof-structure template=t3 kcs=KC-2.induction-principle
@choice key=A
`net` adds up a list of postings: `net [] = 0` and `net (x :: xs) = x + net xs`. To prove `net (xs ++ ys) = net xs + net ys` for all lists, which variable do you induct on?

- A. `xs`
  - why: `++` takes its first list apart, so `(x :: xs) ++ ys` unfolds one step at a time.
- B. `ys`
  - why: `++` never takes its second list apart, so nothing unfolds.
  - mis: dp:L5
- C. Both at once
  - why: One induction is enough. `ys` stays fixed.
  - mis: dp:L5
- D. Neither: `simp` proves it
  - why: With `xs` a variable, the step needs the hypothesis for `xs`, and `simp` alone has none.
  - mis: dp:L2
:::

You met induction on a number. The same idea works on a list, and a list is closer to a ledger: a list of postings is either empty or a first posting followed by the rest. To prove a claim about every list, prove it for the empty list (the base case), then prove it for `x :: xs` assuming it for `xs` (the step). That assumption is the **induction hypothesis**, `ih`. It is not circular: `ih` is about the shorter list `xs`, and you are proving the claim for the longer `x :: xs`.

Here the claim is that the net of two joined lists is the sum of their nets. You induct on `xs`, the list that `++` takes apart. In the base case both sides reduce to `net ys`. In the step, `net (x :: xs ++ ys)` unfolds to `x + net (xs ++ ys)`, `ih` rewrites `net (xs ++ ys)`, and what is left is adding up in a different order.

:::instrument ins=INS-goal-replay cell=1 recorded=RUN-lean-s2-cells call=false
```lean
def net : List Int → Int
  | [] => 0
  | x :: xs => x + net xs

theorem net_append (xs ys : List Int) : net (xs ++ ys) = net xs + net ys := by
  induction xs with
  | nil => simp [net]
  | cons x xs ih => simp [net, ih, Int.add_assoc]
```

@direction
Replay shows: the whole proof of `net_append`, one tactic at a time. The `nil` case is the base case; in the `cons` case, `ih` is the claim for the shorter list `xs`.
:::

Now the trap. Suppose the step skipped `ih` and appealed to the theorem itself on the same list, `x :: xs`. That uses the claim for the very list you are proving it for. Make your call before you see what Lean does.

:::instrument ins=INS-goal-replay cell=2 recorded=RUN-lean-s2-cells
```lean
theorem net_append_loop (xs ys : List Int) : net (xs ++ ys) = net xs + net ys := by
  cases xs with
  | nil => simp [net]
  | cons x xs => exact net_append_loop (x :: xs) ys
```

@direction
Replay shows: Lean's verdict on this variant, whose step appeals to the claim on the same list `x :: xs`.

@call key=B surprise=yes run=RUN-lean-s2-cells
What does Lean do with this variant?

- A. It accepts it: the appeal to the claim is fine
  - why: The appeal reuses the claim on the same list, so nothing gets smaller.
  - mis: dp:L6
- B. It rejects it: Lean fails to show termination
  - why: A theorem applied to its own argument is a recursion that does not shrink. `ih` is the claim for the shorter `xs`.
- C. It rejects it: the types do not match
  - why: The types match exactly. The termination check is what catches the circularity.
  - mis: dp:L6

@after
Lean's refusal is the machine version of "that is circular": the hypothesis may only be used for a smaller case {{run:RUN-lean-s2-cells}}.
:::

:::item role=segment family=GEN-proof-structure template=t2 kcs=KC-2.induction-principle
@choice key=C
These blocks belong to a proof of `net_append`, and some do not.

1. Induct on `xs`.
2. Induct on `ys`.
3. Base case: both sides reduce to `net ys`.
4. Step: rewrite with `ih`, the claim for the shorter list `xs`, then add up in the other order.
5. Step: rewrite with `net_append (x :: xs) ys`, the claim being proved.

Which list of blocks, in this order, is a proof?

- A. 2, 3, 4
  - why: `++` takes its first list apart, so inducting on `ys` leaves nothing to unfold.
  - mis: dp:L5
- B. 2, 4
  - why: Inducting on `ys` leaves nothing to unfold, and without the base case the empty list is never covered.
  - mis: dp:L6
- C. 1, 3, 4
  - why: Induct on the list `++` takes apart, cover the empty list, then step with the hypothesis.
- D. 1, 3, 5
  - why: Block 5 appeals to the claim for the very list being proved, which is circular.
  - mis: dp:L6
:::

:::item role=segment family=GEN-proof-structure template=t3 kcs=KC-2.induction-principle
@choice key=B
In the proof of `net_append`, which fact does the `x :: xs` case need?

- A. `net (x :: xs ++ ys) = net (x :: xs) + net ys`
  - why: That is the claim for the very list being proved, which is circular.
  - mis: dp:L6
- B. `ih : net (xs ++ ys) = net xs + net ys`
  - why: Unfolding leaves `x + net (xs ++ ys)`. `ih` rewrites that, and only adding up in another order is left.
- C. `net ([] ++ ys) = net [] + net ys`
  - why: That is the fact of the base case. The step is about `x :: xs`.
  - mis: dp:L6
- D. `net (ys ++ xs) = net ys + net xs`
  - why: That is the claim for the lists the other way round. It says nothing about `xs` followed by `ys`.
  - mis: dp:L5
:::

## Exit {minutes=5 kcs=KC-2.induction-principle}

:::item role=exit family=GEN-proof-structure template=t3 kcs=KC-2.induction-principle
@choice key=D
`doubleAll` doubles every posting in a list: `doubleAll [] = []` and `doubleAll (x :: xs) = (x + x) :: doubleAll xs`. To prove `(doubleAll xs).length = xs.length` by induction on `xs`, which fact does the `x :: xs` case need?

- A. `(doubleAll (x :: xs)).length = (x :: xs).length`
  - why: That is the goal of the case. Assuming it is circular.
  - mis: dp:L6
- B. `(doubleAll []).length = [].length`
  - why: That is the base case, and it says nothing about `xs`.
  - mis: dp:L6
- C. `x + x = 2 * x`
  - why: A true fact about one posting, but the lengths do not depend on it.
  - mis: dp:X2
- D. `ih : (doubleAll xs).length = xs.length`
  - why: Unfolding leaves `(doubleAll xs).length + 1 = xs.length + 1`, which `ih` closes.
:::

Explain it back to yourself: say why the base case is needed and what the step assumes, without naming a tactic. Nobody grades this.
