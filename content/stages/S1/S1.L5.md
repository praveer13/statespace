## Two questions first {minutes=2 kcs=KC-1.encoding-is-the-claim}

A solver's answer is about the encoding you gave it, and the encoding is a choice. So far the balances were mathematical integers. Real code stores them in 64 bits. Two questions before the lesson starts; guess if you are not sure.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-1.encoding-is-the-claim
@choice key=B
A claim proved over `Int`, "the guarded transfer never overdraws the sender", moves to code that stores balances as 64-bit integers. What carries over?

- A. All of it: the guard did not change.
  - why: `Int` never overflows, and 64-bit integers do. The encoding changed even though the guard did not.
  - mis: dp:Z4
- B. The sender's half, given `amount > 0`. The recipient needs its own check.
  - why: Over 64 bits the guarded sender still has no overdraft when the amount is positive, and the recipient's credit can wrap {{run:RUN-z3-bv64}}.
- C. Nothing: 64-bit arithmetic can wrap anywhere.
  - why: Overflow happens in particular operations. The sender's subtraction stays in range under the guard.
  - mis: dp:Z7
:::

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-1.encoding-is-the-claim

- A. Signed.

- B. Unsigned.

## The sender at 64 bits {minutes=13 kcs=KC-1.encoding-is-the-claim}

Over `Int`, a balance never overflows. The 64-bit encoding is `BitVec(64)`: its `<`, `<=` and `-` are signed, and its arithmetic wraps around at 2⁶⁴. Take the guard `X <= A` and leave out the premise `X > 0`. Then ask whether the sender can end below zero.

:::instrument ins=INS-z3 cell=1 recorded=RUN-z3-bv64-negamt
```python
from z3 import *
A, B, X = BitVecs('A B X', 64)      # 64-bit balances and amount
s = Solver()
s.add(A >= 0, B >= 0, X <= A)       # the guard, with no X > 0
s.add(A - X < 0)                    # the sender ends below zero
print(s.check())
print(s.model())
```

@direction
Query asserts: 64-bit balances and an amount that pass the guard, with no requirement that the amount be positive, and a sender who ends below zero. `sat` means one exists.

@tap
the sender never ends below zero

@call key=A run=RUN-z3-bv64-negamt surprise=yes
What will Z3 return?

- A. `sat`
  - why: A negative amount turns `A - X` into an addition, and the sum can wrap past the largest 64-bit value {{run:RUN-z3-bv64-negamt}}.
- B. `unsat`
  - why: Over `Int`, a negative amount makes the sender richer, never poorer. At 64 bits, subtracting a negative amount is an addition that can overflow.
  - mis: dp:Z4
- C. `unknown`
  - why: Bit-vector queries like this one are decided.
  - mis: dp:Z6

@after
Z3 found a transfer {{run:RUN-z3-bv64-negamt}}. It prints bit-vector values as unsigned numbers. In the recorded model X is {{run:RUN-z3-bv64-negamt#values.queries.bv64_sender_noguard.witness.X}}, which a signed 64-bit integer reads as {{run:RUN-z3-bv64-negamt#values.queries.bv64_sender_noguard.witness_signed.X}}: a negative amount. Add `X > 0` and the same search has no model {{run:RUN-z3-bv64-negamt}}.

Zero and negative amounts are a decision, not a detail. Stage S3 records it.
:::

## The total at 64 bits {minutes=13 kcs=KC-1.encoding-is-the-claim}

Conservation over 64 bits is the next question. Subtracting from one balance and adding to the other wrap in opposite ways, so the total may still hold.

:::instrument ins=INS-z3 cell=2 recorded=RUN-z3-bv64
```python
from z3 import *
A, B, X = BitVecs('A B X', 64)
prove((A - X) + (B + X) == A + B)   # conservation, modulo 2**64
```

@direction
Query asserts: whatever leaves the sender arrives at the recipient, with every operation wrapping at 2⁶⁴. `prove` prints `proved` when no counterexample exists.

@tap
the total is conserved

@call key=A run=RUN-z3-bv64 surprise=yes
What will `prove` print?

- A. `proved`
  - why: Arithmetic modulo 2⁶⁴ still cancels, so a wrap moves no money in this sum {{run:RUN-z3-bv64}}.
- B. `counterexample`
  - why: A wrap changes a balance, but the two wraps cancel in the total.
  - mis: dp:Z7
- C. `unknown`
  - why: Bit-vector arithmetic is decided.
  - mis: dp:Z6

@after
Conservation still holds {{run:RUN-z3-bv64}}, and the guarded sender still has no overdraft when the amount is positive {{run:RUN-z3-bv64}}. The recipient is another matter. In the recorded model, B is {{run:RUN-z3-bv64#values.recipient_witness.B}} and X is {{run:RUN-z3-bv64#values.recipient_witness.X}}. Their sum is 2⁶³, which signed 64-bit reads as -2⁶³, so the recipient ends below zero {{run:RUN-z3-bv64}}.

A related query gave a different witness {{run:RUN-z3-bv64-pyodide}}. Witnesses are not canonical, so graded items check the property, never the values.
:::

## Two readings of the same bits {minutes=13 kcs=KC-1.encoding-is-the-claim}

A bit-vector has no sign of its own. Each operator reads the bits one way: `<`, `<=` and `-` are signed, and `ULT`, `ULE` and `UGT` are unsigned. A guard and a property that read the same bits differently disagree about the state.

:::instrument ins=INS-z3 cell=3 recorded=RUN-z3-bv64
```python
from z3 import *
A, X = BitVecs('A X', 64)
s = Solver()
s.add(UGT(X, 0), ULE(X, A))         # the guard reads the bits as unsigned
s.add(A - X < 0)                    # the property reads them as signed
print(s.check())
print(s.model())
```

@direction
Query asserts: a guard written with unsigned comparisons, and a sender who ends below zero when read as signed. `sat` means one exists.

@tap
the sender never ends below zero

@call key=A run=RUN-z3-bv64 surprise=moderate
What will Z3 return?

- A. `sat`
  - why: A has its top bit set. The unsigned guard sees a huge balance, and the signed property sees a negative one {{run:RUN-z3-bv64}}.
- B. `unsat`
  - why: The guard and the property read the same bits, but not the same way, so they disagree about the state.
  - mis: dp:Z5
- C. `unknown`
  - why: Bit-vector queries like this one are decided.
  - mis: dp:Z6

@after
Z3 found a state {{run:RUN-z3-bv64}}. Pick one reading of the bits and use it in every comparison.
:::

::specimen id=SP-1.5 mount=true

Here is what "64-bit" means across the tools you will meet.

| Semantics | An overflowing credit | Evidence |
|---|---|---|
| Lean `Int` | cannot overflow: arbitrary precision | the definition of the type |
| Z3 `Int` | cannot overflow: mathematical integers | the definition, and the Z3 guide's "Arithmetic" |
| Z3 BitVec 64 | wraps modulo 2⁶⁴, and signedness is per operator | {{run:RUN-z3-bv64}} |
| PostgreSQL `bigint` | raises error {{run:RUN-pg-claims#values.e6_overflow_sqlstate}}, and the balance keeps its old value | {{run:RUN-pg-claims}} |
| PostgreSQL `numeric` | raises at its declared bound | {{run:RUN-pg-numeric-bound}} |
| Rust `i64` | a debug build panics, a release build wraps, and `checked_add` returns `None` | {{run:RUN-rust-i64}} |

Stage S6 comes back to the PostgreSQL row. There, your model takes a step the database refuses.
