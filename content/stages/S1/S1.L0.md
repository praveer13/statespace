## The pull request {minutes=4 kcs=KC-1.violation-as-sat}

An agent opened a pull request on your system. Its description says: "Transfer is now guarded; safe, 200 tests green." That is the agent's text, quoted and unreviewed. Here is the change.

```python
def transfer(src, dst, amount):
    if amount <= 0 or amount > dst.balance:   # "guard: sufficient funds"
        raise Rejected
    src.balance -= amount
    dst.balance += amount
```

You will make a call before anything answers: your verdict, and how sure you are, committed first. Then Z3, a solver, checks every whole-number input at once.

:::instrument ins=INS-z3 cell=1 recorded=RUN-z3-boot-variant
The same transfer, written as a search for a bug.

```python
from z3 import *
a, b, amount = Ints('a b amount')   # sender, recipient, amount
s = Solver()
s.add(a >= 0, b >= 0, amount > 0)   # balances start at zero or above
s.add(amount <= b)                  # the guard, as the pull request wrote it
s.add(a - amount < 0)               # the bug to find: the sender ends below zero
print(s.check())
print(s.model())
```

@direction
Query asserts: balances and an amount that pass the guard as written and leave the sender below zero. `sat` means Z3 found such a transfer, and the model shows it.

@tap
the sender never ends below zero

@call key=B run=RUN-z3-boot-variant surprise=moderate
Can the sender's balance go below zero after this transfer, for some whole-number balances?

- A. No: the guard checks funds before the debit.
  - why: The guard reads `dst`, so it checks the wrong balance. Green tests sample inputs, and tests that give both accounts the same balance never reach this case.
  - mis: dp:G8
- B. Yes: some inputs get past the guard.
  - why: Z3 searched every whole-number input and found one that passes the guard and overdraws the sender.
- C. Only when the amount exceeds both balances.
  - why: An amount above both balances fails the guard. The bad inputs are those where the recipient covers the amount and the sender does not.
  - mis: dp:Z3

@after
Z3 found a transfer that passes the guard and overdraws the sender: the sender holds {{run:RUN-z3-boot-variant#values.queries.variant_violation.witness.a}}, the recipient holds {{run:RUN-z3-boot-variant#values.queries.variant_violation.witness.b}}, and the amount is {{run:RUN-z3-boot-variant#values.queries.variant_violation.witness.amount}} {{run:RUN-z3-boot-variant}}. Your model may differ, because any transfer that passes the guard and overdraws the sender will do.

The guard reads `dst`, the recipient, so it checks the wrong balance. Tests that give both accounts the same balance cannot tell the two guards apart, which is how a suite like this one stays green {{run:RUN-z3-boot-variant}}.
:::

::specimen id=SP-1.1 mount=true

That model is a specimen: a counterexample you keep beside its fix. The fix is one word. The guard should read the sender, `src`, not the recipient, `dst`.

## What the answer was about {minutes=2 kcs=KC-1.violation-as-sat}

The stamp said "for whole numbers". Most code keeps balances in 64 bits, and 64-bit arithmetic wraps around. Here is the fixed guard again with 64-bit balances. There is no call this time, so just look.

:::instrument ins=INS-z3 cell=3 recorded=RUN-z3-bv64 call=false
The fixed guard, on 64-bit numbers, with a search for a recipient who ends below zero.

```python
from z3 import *
A, B, X = BitVecs('A B X', 64)        # 64-bit balances and amount
s = Solver()
s.add(A >= 0, B >= 0, X > 0, X <= A)  # the fixed guard
s.add(B + X < 0)                      # the recipient ends below zero
print(s.check())
print(s.model())
```

@direction
Query asserts: the fixed guard on 64-bit numbers, and a recipient who ends below zero after the credit. `sat` means Z3 found one.

@tap
the recipient never ends below zero

@after
Z3 found one {{run:RUN-z3-bv64}}. In the recorded result the recipient holds {{run:RUN-z3-bv64#values.recipient_witness.B}} and the amount is {{run:RUN-z3-bv64#values.recipient_witness.X}}, and together they read as a negative number. Your model may differ, because any pair that wraps will do. The same guard still protects the sender when the amount is positive {{run:RUN-z3-bv64}}.
:::
