## Two questions first {minutes=2 kcs=KC-1.violation-as-sat,KC-1.quantifier-negation,KC-1.only-if-direction,KC-1.witness-class}

A test suite checks the inputs its author thought of. A solver can be asked about every input, once you say what a bug is. This lesson is about saying it: you state the property, assert its negation, and ask for a witness. Two questions first. Guess if you are not sure, because the lesson answers both.

:::item role=prequestion family=GEN-negate-it template=t1 kcs=KC-1.violation-as-sat,KC-1.quantifier-negation,KC-1.only-if-direction mode=pick band=1
@choice key=B
The property: a transfer is allowed only if it leaves the sender at zero or above. Which formula do you hand the solver to hunt for a bug?

- A. `allowed ∧ bal′ ≥ 0`
  - why: A model of this is a transfer that works, which says nothing about the others.
  - mis: dp:Z1
- B. `allowed ∧ bal′ < 0`
  - why: "Allowed only if bal′ ≥ 0" is `allowed → bal′ ≥ 0` for every transfer. Its negation is "some allowed transfer has bal′ < 0", and a model of it is a bug.
- C. `¬allowed ∧ bal′ ≥ 0`
  - why: This negates `bal′ ≥ 0 → allowed`, which reads "only if" backwards: its model is a transfer that keeps the sender at zero or above and that the guard rejects.
  - mis: dp:G1
- D. `allowed → bal′ < 0`
  - why: Any input that is not allowed satisfies an implication, so a model of it need not be a bug.
  - mis: dp:G4
:::

:::item role=prequestion family=GEN-find-the-witness template=t1 kcs=KC-1.witness-class
@choice key=B
Z3 hands back one overdraft, `a = 0, b = 0, amount = 1`. You patch the code to refuse transfers when `a = 0` and ask again. What comes back?

- A. `unsat`: the patch removed the overdraft that Z3 found.
  - why: The patch removed one member of the class. Every transfer with `amount > a` still overdraws the sender.
  - mis: dp:Z3
- B. `sat`: another overdraft, such as `a = 1` and `amount = 2`.
  - why: The witness was one member of a class, and the patch leaves the rest of the class in place.
- C. `unknown`: Z3 cannot tell whether the patch is enough.
  - why: Linear integer constraints like these are decided outright, patched or not.
  - mis: dp:Z2
:::

## Negating English {minutes=14 kcs=KC-1.quantifier-negation,KC-1.only-if-direction}

Start with a worked example. The property is "every allowed transfer leaves the sender at zero or above". With a quantifier it reads `∀ inputs. allowed → a′ ≥ 0`, where `a′` is the sender's balance after the transfer. Its negation swaps the quantifier and negates what follows: `∃ inputs. allowed ∧ a′ < 0`. Some allowed input leaves the sender below zero, and that input is the bug.[^1]

Two more rules do most of the work. "Both balances stay at zero or above" is `a′ ≥ 0 ∧ b′ ≥ 0`, and its negation is `a′ < 0 ∨ b′ < 0`: either one going negative is a violation. And "P only if Q" is `P → Q`.

[^1]: Drawer D-03 holds the rules for negating a "for every" and a "for some". Drawer D-01 sets this search beside what a green test suite establishes.

:::instrument ins=INS-z3 cell=1 recorded=RUN-z3-demorgan
The unguarded transfer, with a negation that is slightly off.

```python editable
from z3 import *
a, b, amount = Ints('a b amount')
a2, b2 = a - amount, b + amount     # balances after the transfer
s = Solver()
s.add(a >= 0, b >= 0, amount > 0)   # the transfer has no guard
s.add(And(a2 < 0, b2 < 0))          # both balances end below zero
print(s.check())
```

@direction
Query asserts: an unguarded transfer after which both balances are below zero at once. `sat` means such a transfer exists.

@tap
both balances stay at zero or above

@call key=B run=RUN-z3-demorgan surprise=yes
This query asks for `a′ < 0 ∧ b′ < 0` on the unguarded transfer. What will Z3 return?

- A. `sat`
  - why: The unguarded transfer does allow overdrafts, but this query asks for both balances below zero at once, and the recipient only gains.
  - mis: dp:Z5
- B. `unsat`
  - why: No input makes both balances negative, because the recipient only gains {{run:RUN-z3-demorgan}}. The property is still violated: its real negation has an or in it.
- C. `unknown`
  - why: Three linear integer constraints are decided outright.
  - mis: dp:Z6

@after
That `unsat` did not say the transfer is fine. It answered the wrong question {{run:RUN-z3-demorgan}}.

The slip is De Morgan. The negation of `a′ ≥ 0 ∧ b′ ≥ 0` is `a′ < 0 ∨ b′ < 0`, not `a′ < 0 ∧ b′ < 0`. Change `And` to `Or` and check again. Z3 now finds a witness, a transfer that overdraws the sender {{run:RUN-z3-demorgan}}: the recorded one has the sender holding {{run:RUN-z3-demorgan#values.queries.correct_negation.witness.a}}, the recipient holding {{run:RUN-z3-demorgan#values.queries.correct_negation.witness.b}} and an amount of {{run:RUN-z3-demorgan#values.queries.correct_negation.witness.amount}}.
:::

A rule says: "A refund is allowed only if the charge has settled, unless it is a chargeback." Which query searches for a violation of the rule?

- A. `refund ∧ ¬settled ∧ chargeback`

  - mis: dp:G3
- B. `refund ∧ ¬settled ∧ ¬chargeback`

- C. `settled ∧ ¬refund ∧ ¬chargeback`
  - why: This reverses "only if". A settled charge does not have to be refunded.
  - mis: dp:G1
- D. `refund ∧ (¬settled ∨ ¬chargeback)`
  - why: This is a De Morgan slip. The negation of `settled ∨ chargeback` needs an and, not an or.
  - mis: dp:Z5

## The violation query {minutes=13 kcs=KC-1.violation-as-sat}

Now the move itself. To search for a bug, give the solver the premises and the negated property, then read its answer. `sat` comes with a model, and the model is a bug. `unsat` means no such input exists in this encoding. Here is a fresh variant, and you make the first call. A new pull request guards the transfer with a cap on the amount instead of a balance check.

:::instrument ins=INS-z3 cell=2 recorded=RUN-z3-vacuous-unsat
The cap is 100. The search is the same: premises, the guard, and the negated property.

```python
from z3 import *
a, b, amount = Ints('a b amount')
MAX_TRANSFER = 100
s = Solver()
s.add(a >= 0, b >= 0, amount > 0)   # the premises
s.add(amount <= MAX_TRANSFER)       # this pull request's guard: a cap
s.add(a - amount < 0)               # the bug to find: the sender ends below zero
print(s.check())
```

@direction
Query asserts: balances and an amount that pass the cap and leave the sender below zero. `sat` means such a transfer exists.

@tap
the sender never ends below zero

@call key=A run=RUN-z3-vacuous-unsat surprise=moderate
What will Z3 return for the violation query?

- A. `sat`
  - why: The cap limits the amount, not the amount against the balance. A sender holding nothing can still be asked for a small amount {{run:RUN-z3-vacuous-unsat}}.
- B. `unsat`
  - why: A cap sounds like a guard, but it never looks at the sender's balance.
  - mis: dp:Z1
- C. `unknown`
  - why: Linear integer constraints like these are decided outright.
  - mis: dp:Z6

@after
Z3 found a transfer the cap lets through {{run:RUN-z3-vacuous-unsat}}. In the recorded result the sender holds {{run:RUN-z3-vacuous-unsat#values.queries.max100_range_violation.witness.a}} and the amount is {{run:RUN-z3-vacuous-unsat#values.queries.max100_range_violation.witness.amount}}, so the sender ends below zero. A guard only helps if it constrains the thing the property is about.
:::

The roadmap's starter shows the same move. With the premises and the negation `a - amount < 0`, Z3 finds {{run:RUN-z3-starter#values.model}}: a sender holding nothing is asked for one {{run:RUN-z3-starter}}. You can check that witness by hand, because 0 - 1 is below zero. Add the guard `amount <= a` and the same search finds nothing {{run:RUN-z3-starter}}.

@choice key=C
A pull request guards the transfer with `amount <= a + 5`, an overdraft allowance. The premises are `a >= 0`, `b >= 0` and `amount > 0`. Which values are a witness that the sender can end below zero?

- A. `a = 3, b = 0, amount = 9`
  - why: The sender would end below zero, but 9 is above 8, so the guard rejects this transfer. A witness has to get past the guard.
  - mis: dp:Z5
- B. `a = 3, b = 0, amount = 2`
  - why: This transfer passes the guard and leaves the sender with 1. A transfer that works is no witness.
  - mis: dp:Z1
- C. `a = 3, b = 0, amount = 4`
  - why: The guard passes, because 4 is at most 8, and the sender ends at -1. The premises hold, the guard holds, and the property fails.
- D. `a = -2, b = 5, amount = 1`
  - why: The sender ends below zero, but the premise `a >= 0` fails. This starting state is not allowed.
  - mis: dp:Z5
:::

## One witness, one class {minutes=14 kcs=KC-1.witness-class}

A witness is one member of a larger class. Ask Z3 for the overdraft with the smallest amount, and see what it picks.

:::instrument ins=INS-z3 cell=3 recorded=RUN-z3-optimize-min
An Optimize query: the same overdraft search, with an objective.

```python
from z3 import *
a, b, amount = Ints('a b amount')
o = Optimize()
o.add(a >= 0, b >= 0, amount > 0)   # the premises
o.add(a - amount < 0)               # the overdraft
o.minimize(amount)                  # the smallest amount that overdraws
print(o.check())
print(o.model())
```

@direction
Query asks: among all overdrafts, the one with the smallest amount. `sat` with a model means one exists, and the model is the smallest by that measure.

@tap
the sender never ends below zero

@call key=B run=RUN-z3-optimize-min surprise=no
Z3 is asked for the overdraft with the smallest amount. What amount comes back?

- A. `0`
  - why: The premise `amount > 0` excludes 0.
  - mis: dp:Z5
- B. `1`
  - why: The minimizer chooses every variable, so it sets the sender's balance to 0 and the amount to 1 {{run:RUN-z3-optimize-min}}.
- C. One more than the sender's balance in the first witness.
  - why: This treats the first witness's balance as fixed. It is one member of the class, not the bug.
  - mis: dp:Z3

@after
The smallest amount is {{run:RUN-z3-optimize-min#values.minimal_amount}} {{run:RUN-z3-optimize-min}}. "Minimal" means minimal for the objective you asked for, here the amount, and nothing else.

The class is every input with `amount > a`. With `a >= 0` and `amount > 0`, those are exactly the transfers that overdraw the sender. The starter's witness and the one from Start here are both members. Patch only the instance, say by excluding `a = 0`, and Z3 hands you another member. A second overdraft that differs from the first in every variable is `a = 2, b = 7, amount = 5`.
:::

:::item role=segment family=GEN-find-the-witness template=t1 kcs=KC-1.witness-class
@choice key=C
Z3's first overdraft witness is `a = 0, b = 0, amount = 1`. Which description covers every overdraft, not just this one?

- A. `a = 0 ∧ b = 0`
  - why: A sender holding money can be overdrawn by a larger amount, so this describes one member of the class.
  - mis: dp:Z3
- B. `amount = 1`
  - why: An amount of 5 overdraws a sender holding 2, so this is one member of the class.
  - mis: dp:Z3
- C. `amount > a`
  - why: With `a >= 0` and `amount > 0`, the sender ends below zero exactly when the amount exceeds the sender's balance.
- D. `b < a`
  - why: The recipient's balance has no effect on whether the sender is overdrawn.
  - mis: dp:Z3
:::

A transfer is allowed when `amount <= a`. The property: every allowed transfer leaves the recipient with at most `cap`. Which formula do you hand the solver?

  - why: Negating the guard as well searches transfers that are already rejected.

The pull request from Start here guards the transfer with `amount <= b`, the recipient's balance. Which description covers every overdraft that guard lets through?

- A. `amount > b ∧ amount > a`
  - why: An amount above the recipient's balance fails the guard, so none of these gets through.
  - mis: dp:Z5
- B. `amount <= b ∧ amount > a`
  - why: The guard passes when the recipient covers the amount, and the sender is overdrawn when the amount exceeds the sender's balance. Those transfers are the bugs, and only those {{run:RUN-z3-boot-variant}}.

  - why: These are the values of one witness. They are a member of the class, not the class.
  - mis: dp:Z3
- D. `amount <= b ∧ amount = 1`
  - why: A larger amount can overdraw a richer sender, and a sender holding 1 or more covers this one, so it misses most of the class and keeps transfers that are fine.

"A transfer is allowed only if the balance covers the amount." Which formula says that?

- A. `allowed → covers`
