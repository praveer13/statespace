The violation query for "every transfer with `amount > 0` and `amount <= MAX_TRANSFER` leaves the sender at zero or above" is `unsat` when `MAX_TRANSFER = 0`. Which is true?

- A. The guarded transfer holds for every input.
  - why: An `unsat` over premises that cannot hold is vacuous.
  - mis: dp:Z1
- B. The claim is true, but it says nothing: no transfer meets its premises.
  - why: An implication with a false premise is true, which is why a claim card carries a premise witness beside its `unsat`.
- C. The claim is false.
  - why: This reads if-then as "and". With no allowed transfer, nothing can break the claim.
  - mis: dp:G7

## Beside every answer {minutes=14 kcs=KC-1.non-vacuity-check,KC-1.implication-vacuity,KC-1.claim-anatomy}

With the sufficient-funds guard, the violation query is `unsat` {{run:RUN-z3-starter}}. Read that exactly: for every input of this encoding, the guarded transfer leaves the sender at zero or above, if the solver is sound. The course also runs the query on a second solver, cvc5, at build time, and it agrees {{run:RUN-cvc5-alethe}}. Two solvers agreeing is diversity, not a checked proof, so the stamp still says uncertified.

An `unsat` can be empty, though. So every `unsat` gets a premise query beside it: the premises and the guard, with no negated property.

:::instrument ins=INS-z3 cell=1 recorded=RUN-z3-vacuous-unsat
```python
from z3 import *
a, b, amount = Ints('a b amount')
s = Solver()
s.add(a >= 0, b >= 0, amount > 0)   # the premises
s.add(amount <= a)                  # the sufficient-funds guard
print(s.check())                    # no negated property this time
print(s.model())
```

@direction
Query asserts: balances and an amount that satisfy the premises and the guard. With no negated property, `sat` means the premises can hold together.

@tap
the premises can all hold together

@call key=A run=RUN-z3-vacuous-unsat surprise=no
This is the premise query for the guarded transfer. What will Z3 return?

- A. `sat`
  - why: A sender can hold enough to cover a positive amount, so the premises can hold together {{run:RUN-z3-vacuous-unsat}}.
- B. `unsat`
  - why: This confuses the premise query with the violation query. The violation's `unsat` does not empty the premises.
  - mis: dp:Z1
- C. `unknown`
  - why: A small linear query is decided.
  - mis: dp:Z6

@after
The premise witness: a sender holding {{run:RUN-z3-vacuous-unsat#values.queries.cl11_premises.witness.a}}, a recipient holding {{run:RUN-z3-vacuous-unsat#values.queries.cl11_premises.witness.b}} and an amount of {{run:RUN-z3-vacuous-unsat#values.queries.cl11_premises.witness.amount}} {{run:RUN-z3-vacuous-unsat}}. Now the `unsat` beside it means something: some transfers are allowed, and none of them overdraws the sender.
:::

Now a config that empties the premises. A default sets `MAX_TRANSFER = 0` beside `amount > 0` and `amount <= MAX_TRANSFER`.

:::instrument ins=INS-z3 cell=2 recorded=RUN-z3-vacuous-unsat
Three queries on the config: (i) a violation of "the sender ends at zero or above", (ii) a violation of the absurd property "the sender ends 1,000,000 richer", and (iii) the premises alone.

```python
from z3 import *
a, b, amount = Ints('a b amount')
MAX_TRANSFER = 0                      # the config's default
premises = [a >= 0, b >= 0, amount > 0, amount <= MAX_TRANSFER]

def violation_of(prop):
    s = Solver()
    s.add(premises)
    s.add(Not(prop))                  # search for a violation of the property
    return s.check()

print(violation_of(a - amount >= 0))                # (i)
print(violation_of(a - amount == a + 1000000))      # (ii)
s = Solver()
s.add(premises)
print(s.check())                                    # (iii)
```

@direction
Query asserts: for each property, an allowed transfer that violates it. Query (iii) asks whether any allowed transfer exists.

@tap
the absurd property holds

@call key=B run=RUN-z3-vacuous-unsat surprise=yes
What will Z3 return for (ii), the violation of the absurd property?

- A. `sat`
  - why: An absurd property should be refuted, but with no allowed transfer every property about allowed transfers holds vacuously.
  - mis: dp:G4
- B. `unsat`
  - why: No allowed transfer exists, so no transfer can violate even an absurd property {{run:RUN-z3-vacuous-unsat}}.
- C. `unknown`
  - why: Linear integer constraints like these are decided.
  - mis: dp:Z6

@after
All three are `unsat` {{run:RUN-z3-vacuous-unsat}}. When the premises cannot hold together, every property is proved, and the premise query is the tell. Here `amount > 0` and `amount <= MAX_TRANSFER` conflict. Drawer D-02 holds the truth table.
:::

::specimen id=SP-1.6 mount=true

Now your first claim. A claim is a six-part guarantee card: the proposition, its assumptions, the model, the method, how the code corresponds to the model, and the counterexample you get when an assumption is weakened. It also has a requirement row and a three-segment strip: what the solver established about the model, whether the code matches the model, and whether it is the guarantee you wanted. Drawer D-06 explains each field.

Two assumptions on the card are drawn dashed: balances are unbounded integers (SEAM-1), and the solver is sound (SEAM-7). A seam is an assumption planted on purpose. Some give way later in the course; some are tested and hold.

Strike the guard from your first claim. Which values are an "if weakened" witness: every remaining premise holds, and the proposition fails?

- A. `a = 5, b = 0, amount = 2`

  - mis: dp:Z1
- B. `a = -1, b = 0, amount = 1`
