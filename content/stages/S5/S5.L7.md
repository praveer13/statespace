## Read a cycle {minutes=15 kcs=KC-5.lasso-reading,KC-5.fairness}

An agent's audit note reads: "TLC reported no deadlock, so every hold resolves." No deadlock is not progress. A hold that keeps retrying forever has no deadlock and never resolves. This lesson is about the promise that rules such behavior out, and about whose promise it is.

:::item role=prequestion family=GEN-lasso-or-not template=t1 kcs=KC-5.fairness
@choice key=B
The worker retries a capture, the provider may answer "busy" forever, and the scheduler is weakly fair to the retry. Must the hold resolve?

- A. Yes: weak fairness guarantees progress.
  - why: Weak fairness forces only an action that stays enabled. The capture is not enabled on every step of the retry cycle.
  - mis: dp:T14
- B. No.
  - why: Retry, busy, retry, busy forever is a fair behavior. The retry keeps being taken, and nothing forces a capture or an expiry.
- C. Yes, because `Timeout` exists.
  - why: An action that exists need not happen. Only fairness makes it happen.
  - mis: dp:T10
:::

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-5.fairness
@choice key=C
Which fairness may a claim about your system rest on without saying so?

- A. Weak fairness on every action, since it is standard.
  - why: That quietly promises things about the provider's actions, which your system cannot make.
  - mis: dp:T15
- B. Strong fairness on the provider, since providers answer eventually.
  - why: This is an unstated promise about someone else's system.
  - mis: dp:T15
- C. None.
  - why: Every fairness conjunct is an assumption: about your scheduler when it sits on your actions, about the world when it sits on the provider's.
:::

A spec allows every behavior its actions allow, including behaviors that stutter forever or never take a particular action. **Fairness** is a conjunct you add to `Spec` to rule such behaviors out. An action is *enabled* in a state when it can be taken from there. Two forms cover nearly everything:

- `WF_v(A)`, weak fairness: if `A` stays enabled continuously from some point on, `A` is eventually taken.
- `SF_v(A)`, strong fairness: if `A` is enabled infinitely often, `A` is eventually taken.

Written out, `WF_v(A) == <>[](ENABLED <<A>>_v) => []<><<A>>_v` and `SF_v(A) == []<>(ENABLED <<A>>_v) => []<><<A>>_v`. Strong fairness forces `A` in more behaviors, so it is the larger promise.

On a lasso whose cycle is C, the two have a simple reading rule. `WF` on A holds when A is taken somewhere on C, or A is disabled at some state of C. `SF` on A holds when A is taken on C, or A is disabled at every state of C.

Two common slips. Weak fairness does not mean "taken eventually if ever enabled": an action that is disabled now and then escapes it. And an enabled action does not happen on its own: without a fairness conjunct, a behavior may never take it.

Every fairness conjunct is an assumption, and the first question to ask of one is whose action it sits on. Put fairness on your own system's actions, such as the retry job your scheduler runs. "The provider answers eventually" is a wish about someone else's system, and a claim that rests on it has to say so.

**A worked example, start to finish.** Take the retrying hold from the last lesson and let expiry apply while a request is outstanding, with weak fairness on expiry alone:

```tla
---- MODULE HoldLive ----
EXTENDS Naturals
VARIABLES st, tries
vars == <<st, tries>>
Init == st = "held" /\ tries = 0
Try     == st = "held"    /\ st' = "pending"  /\ tries' = (tries + 1) % 2
Busy    == st = "pending" /\ st' = "held"     /\ UNCHANGED tries
Capture == st = "pending" /\ st' = "captured" /\ UNCHANGED tries
Timeout == st \in {"held", "pending"} /\ st' = "released" /\ UNCHANGED tries
Next == Try \/ Busy \/ Capture \/ Timeout
Fair == WF_vars(Timeout)
Spec == Init /\ [][Next]_vars /\ Fair
Resolved == st \in {"captured", "released"}
EventuallyResolves == <>Resolved
====
```

1. **The action and when it is enabled.** `Timeout` is enabled whenever `st` is `held` or `pending`, which is whenever the hold is unresolved. In the last lesson it applied only in `held`.
2. **The safety side still holds.** Every resolution requires an unresolved state, so a resolved hold stays resolved.
3. **The fairness conjunct.** `Fair == WF_vars(Timeout)`, on a system action only. Nothing here assumes the provider answers. Fairness is a promise. Whose? Yours: your scheduler runs your expiry job.
4. **The property.** `EventuallyResolves == <>Resolved`.
5. **The configuration and the stamp.** `SPECIFICATION Spec`, `PROPERTY EventuallyResolves`, no SYMMETRY and no CONSTRAINT, and the deadlock check off, because a resolved hold has nothing left to do {{run:RUN-tlc-eventually}}. The stamp is [M] · constants; fairness as [A].

You will run exactly this module in the third segment. First, read a lasso against fairness conjuncts.

```tla
---- MODULE Hold ----
\* A hold that a worker keeps retrying to capture; the provider may keep answering "busy".
EXTENDS Naturals

vars == <<st, tries>>
Init == st = "held" /\ tries = 0

Timeout == st = "held"    /\ st' = "released" /\ UNCHANGED tries
Next == Try \/ Busy \/ Capture \/ Timeout
Fair == WF_vars(Try) /\ WF_vars(Busy)        \* the scheduler is fair to Try and Busy only
Spec == Init /\ [][Next]_vars /\ Fair

====
```

@direction
Spec asserts: the retrying hold with `Fair == WF_vars(Try) /\ WF_vars(Busy)`. The check asks whether `EventuallyResolves` holds on every behavior that satisfies both fairness conjuncts. A violation comes back as a lasso. Read it against each conjunct.

@call key=B surprise=moderate run=RUN-tlc-hold-lasso
`Fair == WF_vars(Try) /\ WF_vars(Busy)`. Does this model satisfy `EventuallyResolves`?

- A. Yes.
  - why: Weak fairness on `Try` and `Busy` is satisfied by the cycle that retries forever. It does not force `Capture` or `Timeout`.
  - mis: dp:T14
- B. No.
  - why: No conjunct forces `Capture` or `Timeout`, so a behavior that retries and hears busy forever is fair and never resolves.
- C. No, but only if the provider acts maliciously.
  - why: Answering busy is legal provider behavior, not malice. A claim that needs the provider to behave has to say so.
  - mis: dp:T15

@after
TLC returns a lasso: `held`, `Try`, `pending`, `Busy`, `held`, `Try`, `pending`, `Busy`, and back to the first state {{run:RUN-tlc-hold-lasso}}. Both conjuncts hold on it, because `Try` and `Busy` are taken on the cycle. Nothing forces anything else.
:::

Read the cycle against each action:

| Action | Taken on the cycle | Enabled at |
|---|---|---|
| `Try` | yes | the two `held` states |
| `Busy` | yes | the two `pending` states |
| `Capture` | never | the two `pending` states only |
| `Timeout` | never | the two `held` states only |

`Busy` is the provider's action, so `WF_vars(Busy)` is already a promise about the world, and the hold still need not resolve.

:::item role=segment family=GEN-lasso-or-not template=t1 kcs=KC-5.lasso-reading,KC-5.fairness
@choice key=C
The retrying hold has `Fair == WF_vars(Try) /\ WF_vars(Capture)`. Which behavior is a lasso that violates `EventuallyResolves` and satisfies both fairness conjuncts?

- A. `Try`, then stuttering forever in `pending`.
  - why: `Capture` is enabled at every state of that cycle and never taken, so `WF_vars(Capture)` fails. The lasso is not fair.
  - mis: dp:T14
- B. Stuttering forever in `held`.
  - why: `Try` is enabled at every state and never taken, so `WF_vars(Try)` fails.
  - mis: dp:T10
- C. `Try`, `Busy`, `Try`, `Busy`, then back to the first state, forever.
  - why: `Try` is taken on the cycle. `Capture` is disabled at the `held` states, so weak fairness on it holds without it ever being taken. The hold never resolves.
- D. None: weak fairness on `Try` and `Capture` forces the hold to resolve.
  - why: Weak fairness forces only an action that stays enabled, and `Capture` does not stay enabled on the retry cycle.
  - mis: dp:T14
:::

## Weak or strong {minutes=15 kcs=KC-5.fairness}

Now change the promise and watch the lasso. Weak fairness forces an action that stays enabled. Strong fairness forces an action that keeps coming back enabled, even if something disables it in between. Decide with the reading rule first, then run.

:::instrument ins=INS-lasso cell=2 recorded=RUN-tlc-hold-lasso
```tla editable
---- MODULE Hold ----
EXTENDS Naturals
VARIABLES st, tries
vars == <<st, tries>>
Init == st = "held" /\ tries = 0
Try     == st = "held"    /\ st' = "pending"  /\ tries' = (tries + 1) % 2
Busy    == st = "pending" /\ st' = "held"     /\ UNCHANGED tries
Capture == st = "pending" /\ st' = "captured" /\ UNCHANGED tries
Timeout == st = "held"    /\ st' = "released" /\ UNCHANGED tries
Next == Try \/ Busy \/ Capture \/ Timeout

\* Start with the first Fair, then swap in one of the others.
Fair == WF_vars(Try) /\ WF_vars(Busy)
\* Fair == WF_vars(Try) /\ WF_vars(Busy) /\ WF_vars(Capture)
\* Fair == WF_vars(Try) /\ WF_vars(Busy) /\ SF_vars(Capture)
\* Fair == WF_vars(Try) /\ SF_vars(Timeout)

Spec == Init /\ [][Next]_vars /\ Fair
Resolved == st \in {"captured", "released"}
EventuallyResolves == <>Resolved
====
```

@direction
Spec asserts: the retrying hold under the `Fair` line you choose. The check asks whether the retry cycle is still a fair behavior. While it is, `EventuallyResolves` fails on it. Change one line at a time.

@call key=B surprise=yes run=RUN-tlc-hold-fairness
Add `WF_vars(Capture)` to `Fair`. Does the cycle survive?

- A. No.
  - why: This reads weak fairness as "taken eventually if ever enabled". It forces an action only when the action stays enabled.
  - mis: dp:T14
- B. Yes.
  - why: `Capture` is enabled only at the `pending` states, so on the cycle it is disabled at the `held` states. Weak fairness holds without `Capture` ever being taken.

@after
The same lasso is still a fair behavior {{run:RUN-tlc-hold-fairness}}. Now swap in `SF_vars(Capture)`. `Capture` is enabled at every `pending` state, and `pending` keeps coming back, so strong fairness forces it. The cycle stops being fair, and TLC finds no violation {{run:RUN-tlc-hold-fairness}}.
:::

Look at what that cost. `Capture` is the provider accepting, so `SF_vars(Capture)` promises that an acceptance, offered again and again, is eventually taken. It removes the cycle by assuming something about the provider's side. Keep fairness on your own actions.

A design that keeps the promise on your side can still fail. Try `WF_vars(Try) /\ SF_vars(Timeout)`, with `Timeout` enabled only at `held`. A provider that stays silent leaves the hold `pending` forever, and `Timeout` is disabled there, so strong fairness has nothing to force {{run:RUN-tlc-hold-fairness}}.

:::item role=segment family=GEN-lasso-or-not template=t2 kcs=KC-5.fairness
@choice key=C
The retrying hold has `Fair == WF_vars(Try) /\ SF_vars(Timeout)`, and `Timeout` is enabled only when `st = "held"`. Which behavior is a lasso that violates `EventuallyResolves` and satisfies both conjuncts?

- A. `Try`, `Busy`, `Try`, `Busy`, then back to the first state, forever.
  - why: `Timeout` is enabled at the `held` states, which return forever, and it is never taken. Strong fairness fails.
  - mis: dp:T14
- B. Stuttering forever in `held`.
  - why: `Try` is enabled at every state and never taken, so weak fairness on `Try` fails.
  - mis: dp:T10
- C. `Try`, then stuttering forever in `pending`.
  - why: `Try` is disabled in `pending`, so weak fairness holds. `Timeout` is disabled at every state of the cycle, so strong fairness holds too. The hold stays pending forever.
- D. None: strong fairness on `Timeout` makes the hold resolve.
  - why: Strong fairness forces `Timeout` only where it is enabled infinitely often. In `pending` it is never enabled.
  - mis: dp:T14
:::

## Whose promise {minutes=12 kcs=KC-5.fairness}

Back to the worked example: `Timeout` applies while the hold is `held` or `pending`, with `Fair == WF_vars(Timeout)` and nothing else. Predict what TLC says, then run it on the Bench.

:::instrument ins=INS-bench-tlc cell=3 recorded=RUN-tlc-eventually
```tla
---- MODULE HoldLive ----
EXTENDS Naturals
VARIABLES st, tries
vars == <<st, tries>>
Init == st = "held" /\ tries = 0
Try     == st = "held"    /\ st' = "pending"  /\ tries' = (tries + 1) % 2
Busy    == st = "pending" /\ st' = "held"     /\ UNCHANGED tries
Capture == st = "pending" /\ st' = "captured" /\ UNCHANGED tries
Timeout == st \in {"held", "pending"} /\ st' = "released" /\ UNCHANGED tries
Next == Try \/ Busy \/ Capture \/ Timeout
Fair == WF_vars(Timeout)
Spec == Init /\ [][Next]_vars /\ Fair
Resolved == st \in {"captured", "released"}
EventuallyResolves == <>Resolved
====
```

@direction
Spec asserts: expiry applies while the hold is unresolved, and the only fairness is weak fairness on `Timeout`. The check asks whether `EventuallyResolves` holds on every fair behavior. Config: `SPECIFICATION Spec` and `PROPERTY EventuallyResolves`, with no symmetry, no constraint and the deadlock check off.

@call key=C surprise=no run=RUN-tlc-eventually
Does `EventuallyResolves` hold now?

- A. No: the `Try` and `Busy` cycle still starves `Timeout`.
  - why: `Timeout` is now continuously enabled on that cycle, so weak fairness on it does force it. The cycle is no longer fair.
  - mis: dp:T14
- B. No: the behavior can stutter forever.
  - why: Weak fairness on `Timeout` rules out stuttering forever while `Timeout` is enabled, and it is enabled whenever the hold is unresolved.
  - mis: dp:T10
- C. Yes.
  - why: In any behavior that never resolves, `Timeout` is enabled at every state, because the hold is `held` or `pending` throughout. Weak fairness forces it, and taking it resolves the hold.

@after
With the deadlock check off, TLC finds no violation {{run:RUN-tlc-eventually}}. With the default flags it stops first, at a deadlock after `Timeout`: the released hold enables nothing, as in S5.L4 {{run:RUN-tlc-eventually}}. Look at what that result rests on: one fairness conjunct, on your system's own action, and one hidden assumption, that your scheduler really does run the expiry job.
:::

This result drafts claim CL-5.3: a held hold eventually resolves under weak fairness on `Timeout`. Its stamp is [M] · constants; fairness as [A]. The fairness is assumed, and the check has crash actions switched off. That plants SEAM-8, "the worker keeps running under weak fairness", which the card draws dashed because it is an assumption. Stage 8 checks it again with crashes on.

The model has a price, and the card says so. A provider acceptance racing the expiry is decided by whichever step comes first. A capture the provider performs after you release is outside the model (SEAM-4; S8.L4).

- A. `Try`, `Busy`, `Try`, `Busy`, then back to the first state, forever.

  - why: `Busy` is enabled at every state of the cycle and never taken, so `WF_vars(Busy)` fails.

  - why: `Try` is enabled at every state and never taken, so `WF_vars(Try)` fails.
  - mis: dp:T10

  - why: Enabled is not taken. Letting an action apply helps only once it carries fairness.
  - mis: dp:T10

  - mis: dp:T10

  - why: `Timeout` is your system's action, so a silent provider does not block it. The result needs no fairness on the provider.
  - mis: dp:T15

  - why: Strong fairness forces the action in more behaviors, so it is the larger promise.
