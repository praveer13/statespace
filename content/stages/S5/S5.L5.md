## The world misbehaves {minutes=14 kcs=KC-5.hostile-environment}

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-5.hostile-environment
@choice key=A
The provider's "ok" may arrive twice, or after the hold has expired. Which handler keeps `res <= 1`?

- A. Resolve the hold if its stored state is still `capturing`, testing and writing in one step.
  - why: A compare-and-set on durable state turns duplicate and late replies into no-ops.
- B. Remember each handled reply in the worker's memory, and skip any reply it has seen before.
  - why: A crash erases that memory, and the duplicate is handled again.
  - mis: dp:T13
- C. Check the stored state first, and write the result in a separate step that follows.
  - why: The check can go stale before the write, as in the double spend.
  - mis: dp:C3
:::

Your system does not run alone. A model with only your actions assumes a polite world, so add the world as actions the scheduler may pick at any time. A reply arrives at least once, so it can arrive twice or after the hold has expired: replies stay in a message set, and one can be handled twice. Expiry is a competing path that releases a hold nobody captured. A crash erases the worker's memory but not the stored hold, and a restart brings the worker back.

With those on, the lifecycle can resolve twice if handling a reply and expiring a hold are each a read followed by a write that trusts the read. Both read `capturing`, then both write.

:::instrument ins=INS-theater cell=1 recorded=RUN-tlc-resolved-twice
```tla
---- MODULE HoldsUnsafe ----
EXTENDS HoldsEnv  \* read-only: Reply, Crash, TypeOK, NeverTwice
VARIABLES wseen, eseen  \* what the worker and the expiry job last read
vars == <<hst, tries, msgs, sent, up, res, wseen, eseen>>

Init == /\ hst = "available" /\ tries = 0 /\ msgs = {} /\ sent = FALSE
        /\ up = TRUE /\ res = 0 /\ wseen = "none" /\ eseen = "none"

Place == /\ hst = "available" /\ hst' = "held"
         /\ UNCHANGED <<tries, msgs, sent, up, res, wseen, eseen>>

Dispatch == /\ hst = "held" /\ tries < MaxTries /\ up
            /\ hst' = "capturing" /\ tries' = tries + 1 /\ sent' = TRUE
            /\ UNCHANGED <<msgs, up, res, wseen, eseen>>

HandleRead(r) == /\ r \in msgs /\ up /\ hst = "capturing" /\ wseen = "none"
                 /\ wseen' = r
                 /\ UNCHANGED <<hst, tries, msgs, sent, up, res, eseen>>

HandleWrite == /\ up /\ wseen /= "none"
               /\ hst' = IF wseen = "ok" THEN "captured" ELSE "held"
               /\ res' = IF wseen = "ok" THEN res + 1 ELSE res
               /\ wseen' = "none"
               /\ UNCHANGED <<tries, msgs, sent, up, eseen>>

ExpireRead == /\ eseen = "none" /\ hst \in {"held", "capturing"}
              /\ eseen' = hst
              /\ UNCHANGED <<hst, tries, msgs, sent, up, res, wseen>>

ExpireWrite == /\ eseen /= "none"
               /\ hst' = "released" /\ res' = res + 1 /\ eseen' = "none"
               /\ UNCHANGED <<tries, msgs, sent, up, wseen>>

Restart == /\ ~up /\ up' = TRUE
           /\ UNCHANGED <<hst, tries, msgs, sent, res, wseen, eseen>>

Next == \/ Place \/ Dispatch \/ \E r \in Replies : HandleRead(r)
        \/ HandleWrite \/ ExpireRead \/ ExpireWrite \/ Restart
        \/ \E r \in Replies : Reply(r) /\ UNCHANGED <<wseen, eseen>>
        \/ Crash /\ wseen' = "none" /\ UNCHANGED eseen
Spec == Init /\ [][Next]_vars
====
\* MaxTries = 2, CrashesOn = TRUE, INVARIANT NeverTwice
```

@direction
Scene: the system's actions and the environment's side by side in the bar. Drive the hold with `Reply`, `Crash`, `Restart` and the expiry job, and watch `res`.

@call key=A run=RUN-tlc-resolved-twice surprise=no
With duplicates, late replies, crashes and expiry all on, can this variant reach `res = 2`?

- A. Yes.
  - why: The worker and the expiry job both read `capturing`, then both write. Each path trusts a read the other invalidates.
- B. No: each path checks the state before it writes.
  - why: Checking and writing in separate steps is the double spend again.
  - mis: dp:C1
- C. Only if the provider misbehaves on purpose.
  - why: Duplicates, delays and crashes are ordinary behavior for a network and a process.
  - mis: dp:T15

@after
TLC's own trace for this variant is the run {{run:RUN-tlc-resolved-twice}}. The fix makes each resolution one compare-and-set action on the stored state. With every environment action on and crashes on, TLC then finishes with no error, and both outcomes are reachable {{run:RUN-tlc-never-twice}}.
:::

The fixed actions test and write in one step:

```tla
Handle(r) == /\ r \in msgs /\ up /\ hst = "capturing"
             /\ hst' = IF r = "ok" THEN "captured" ELSE "held"
             /\ res' = IF r = "ok" THEN res + 1 ELSE res
             /\ UNCHANGED <<tries, msgs, sent, up>>

Expire == /\ hst = "held" /\ hst' = "released" /\ res' = res + 1
          /\ UNCHANGED <<tries, msgs, sent, up>>
```

Your claim CL-5.2 is drafted from that run, with one assumption dashed. This model sends the provider request in the same step that commits the hold, which a real system cannot do. That is SEAM-4, and a later stage takes the step apart.

:::item role=segment family=GEN-find-the-witness template=t2 kcs=KC-5.hostile-environment
@choice key=B
TLC's trace for the unsafe variant ends with `NeverTwice` violated: `Place`, `Dispatch`, `ExpireRead`, `Reply("ok")`, `HandleRead("ok")`, `HandleWrite`, `ExpireWrite` {{run:RUN-tlc-resolved-twice}}. Which class of witness is it?

- A. A duplicate reply handled again after a crash.
  - why: No crash and no duplicate appear in the trace. One reply is handled once.
  - mis: dp:T13
- B. Two different resolvers, each trusting a read the other invalidates.
  - why: The worker and the expiry job both read `capturing`, and each write undoes the other's assumption.
- C. One resolver whose own read went stale, with nothing else resolving.
  - why: Two resolvers write here. Either one alone would have kept `res` at 1.
  - mis: dp:C1
:::

## Exit {minutes=4 kcs=KC-5.hostile-environment}

:::item role=exit family=GEN-call-it template=t4 kcs=KC-5.hostile-environment
@choice key=C
`res <= 1` is checked with every environment action on, crashes included. Which statement is true?

- A. If it holds with crashes off, it holds with crashes on.
  - why: Adding actions adds behaviors, and one of them can break it.
  - mis: dp:T15
- B. If it holds, the provider charged at most once.
  - why: `res` counts resolutions in your model. The provider's ledger is not in it, and SEAM-4 is the gap.
  - mis: dp:P3
- C. If it holds with crashes on, it holds with crashes off.
  - why: Switching crashes off only removes behaviors, so a property of all behaviors survives it.
:::
