## Two kinds of witness {minutes=15 kcs=KC-5.safety-vs-liveness}

An agent reviews your hold model and writes: "The hold resolves exactly once." That one sentence makes two promises, and a model checker treats them in different ways. This lesson pulls them apart.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-5.safety-vs-liveness
@choice key=A
Which can a finite log refute: "a hold never resolves twice" or "a hold eventually resolves"?

- A. Only the first.
  - why: A second resolution shows up in a finite log. A hold that is still unresolved when the log ends may resolve later.
- B. Both.
  - why: A log that ends with the hold unresolved proves nothing, because the next step may resolve it.
  - mis: dp:C5
- C. Only the second.
  - why: This swaps the two kinds of property. It is "eventually" that no finite log can refute.
  - mis: dp:C5
:::

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-5.safety-vs-liveness
@choice key=A
"Every hold resolves before its deadline", with the deadline counted on a clock variable, is...

- A. safety
  - why: The witness is a finite prefix in which the clock passes the deadline while the hold is still unresolved.
- B. liveness
  - why: Bounded response sounds like "eventually", but a bad prefix exists, so it has a finite witness.
  - mis: dp:T12
- C. both at once
  - why: It is pure safety. "Exactly once" is the case that needs both kinds.
  - mis: dp:C5
:::

A property makes a claim about whole behaviors, and two questions sort almost every property you will write.

**Can a finite log refute it?** Then it is **safety**. There is a bad thing, and once it has happened no continuation repairs it. "A hold never resolves twice" is safety: a log with two resolutions shows the bad thing, and nothing later can undo it.

**Can no finite log ever refute it?** Then it is **liveness**. Every finite prefix can still be extended into a behavior that satisfies the property, so a good thing that has not happened yet may still happen. "A hold eventually resolves" is liveness. A log that ends with the hold held proves nothing, because the next step may resolve it.

Most promises mix the two. "A hold resolves exactly once" is both: "at most once" is safety and "at least once" is liveness. Every property splits this way, into a safety part and a liveness part.[^1]

[^1]: Alpern and Schneider proved the split in "Defining Liveness" (Information Processing Letters, 1985). The paper is optional reading.

See a safety witness by breaking the lifecycle on purpose. Let `Release` also run from `captured`:

```tla
Release == hst \in {"held", "captured"} /\ hst' = "released" /\ res' = res + 1
```

Now Place, Capture, Release is a behavior with `res = 2`, and `NeverTwice` fails. Those three steps are the whole witness, and every way of continuing them fails too. Keep that picture and look at the other kind of property.

:::instrument ins=INS-theater cell=1 recorded=RUN-spectacle-s5s8
```tla
---- MODULE Lifecycle ----
EXTENDS Naturals
VARIABLES hst, res
vars == <<hst, res>>

Init == hst = "available" /\ res = 0

Place   == hst = "available" /\ hst' = "held"     /\ UNCHANGED res
Capture == hst = "held"      /\ hst' = "captured" /\ res' = res + 1
Release == hst = "held"      /\ hst' = "released" /\ res' = res + 1

Next == Place \/ Capture \/ Release
Spec == Init /\ [][Next]_vars

Resolved == hst \in {"captured", "released"}
NeverTwice == res <= 1
EventuallyResolves == (hst = "held") ~> Resolved
====
```

@direction
Spec asserts: one hold is placed, then captured or released, once. The property asks: whenever the hold is held, is it later resolved? Play the graph by choosing enabled actions, and try to build a finite prefix that no continuation can repair.

@call key=C surprise=moderate run=RUN-spectacle-s5s8
Can any finite prefix of this spec violate `EventuallyResolves`?

- A. Yes: any prefix that ends while the hold is held.
  - why: This reads the property over finite logs only. A prefix that ends in `held` can still continue to `captured` or `released`.
  - mis: dp:T1
- B. Yes, if the prefix is long enough.
  - why: Length does not matter, continuation does. A longer prefix still has an extension that resolves.
  - mis: dp:C5
- C. No.
  - why: From every reachable state a resolved state is still reachable, so every finite prefix has a continuation that satisfies the property. Liveness has no finite witness.

@after
Every prefix you built had a way out: from `held`, Capture and Release are still enabled. The behavior that does break `EventuallyResolves` is infinite, because the hold stays in `held` and the behavior never moves on. No finite prefix shows it, since it is the forever that makes it a violation. The next segment draws that behavior.
:::

Sort a property by asking for its witness. Here is the list for your hold model:

| A promise about a hold | Kind | What shows it failed |
|---|---|---|
| A hold never resolves twice: `[](res <= 1)` | safety | a finite prefix with two resolutions |
| A resolved hold stays resolved | safety | a finite prefix with one step out of `captured` or `released` |
| A hold eventually resolves | liveness | a behavior that never resolves: a lasso |
| A hold resolves before its deadline | safety | a finite prefix in which the clock passes the deadline with the hold unresolved |
| A hold resolves exactly once | both | whichever half fails |

A common slip: "before its deadline" sounds like "eventually", so it feels like liveness. Ask for the witness instead. Once the clock has passed the deadline with the hold unresolved, no continuation repairs the behavior, so a finite prefix is enough. TLA+ formulas cannot see stuttering steps, so "within k steps" needs a clock variable in the spec, and with the clock it is safety.

:::item role=segment family=GEN-trace-allowed template=t1 kcs=KC-5.safety-vs-liveness
@choice key=C
With `Release` also enabled from `captured`, which finite prefix of the lifecycle violates `NeverTwice`?

- A. `Place`, `Capture`
  - why: Only one resolution has happened, so `res` is 1 and `NeverTwice` still holds. The prefix can continue without breaking it.
  - mis: dp:T11
- B. `Place`, `Release`
  - why: One resolution, so `res` is 1. The count is what fails, not the fact that a hold was released.
  - mis: dp:T11
- C. `Place`, `Capture`, `Release`
  - why: Two resolutions give `res = 2`. No continuation can bring the count back, so this finite prefix is the whole witness.
- D. None: a finite prefix cannot violate a property about what happens over time.
  - why: That is true of liveness. A safety property fails on a finite prefix, and this one does.
  - mis: dp:C5
:::

## Lassos {minutes=15 kcs=KC-5.lasso-reading,KC-5.safety-vs-liveness}

A safety violation is a finite trace. A liveness violation cannot be, because no finite prefix refutes it: you need a whole infinite behavior in which the good thing never comes. A model with finitely many states makes that practical. An infinite behavior over finitely many states must come back to a state it has already visited, so it can be drawn as a finite **stem** followed by a **cycle** that repeats forever. That shape is a **lasso**, and TLC reports one when a temporal property fails.

Here is a second model, a hold with a retrying worker, which you will meet again in the next lesson. `Try` moves `held` to `pending`. From `pending`, the provider answers `Busy`, which moves back to `held`, or accepts (`Capture`, to `captured`). From `held`, the hold may time out (`Timeout`, to `released`). The variable `tries` flips between 0 and 1 on each `Try` and does nothing else, except make cycles longer.

:::instrument ins=INS-lasso cell=2 recorded=RUN-tlc-lasso-json
```tla
---- MODULE Hold ----
\* A hold that a worker keeps retrying to capture; the provider may keep answering "busy".
EXTENDS Naturals
VARIABLES st, tries
vars == <<st, tries>>
Init == st = "held" /\ tries = 0
Try     == st = "held"    /\ st' = "pending"  /\ tries' = (tries + 1) % 2
Busy    == st = "pending" /\ st' = "held"     /\ UNCHANGED tries
Capture == st = "pending" /\ st' = "captured" /\ UNCHANGED tries
Timeout == st = "held"    /\ st' = "released" /\ UNCHANGED tries
Next == Try \/ Busy \/ Capture \/ Timeout
Spec == Init /\ [][Next]_vars          \* no fairness conjunct
Resolved == st \in {"captured", "released"}
EventuallyResolves == <>Resolved
====
```

@direction
Spec asserts: the retrying hold with no fairness conjunct at all. The check asks whether `<>Resolved` holds on every behavior of `Spec`. A violation comes back as a lasso: a stem, then a cycle that repeats forever.

@call key=B surprise=yes run=RUN-tlc-lasso-json
With no fairness conjunct, does this model satisfy `EventuallyResolves`?

- A. Yes: `Timeout` and `Capture` exist.
  - why: Existing is not happening. Nothing in `Spec` forces either action to be taken.
  - mis: dp:T10
- B. No.
  - why: The hold can stay `held` forever. The box in `[][Next]_vars` allows a step that changes nothing, as in S5.L1, and nothing forces `Try`, `Capture` or `Timeout`.
- C. Yes, for the states TLC explored.
  - why: A liveness verdict is not a bound. TLC visits every reachable state here, and the property still fails.
  - mis: dp:T5

@after
TLC's counterexample is one stuttering step: the hold stays held at the initial state, and the cycle is that single state {{run:RUN-tlc-lasso-json}}. Stuttering, from S5.L1, is the shortest cycle there is: one state that steps to itself. A fairness conjunct is what rules it out, and the next lesson is about which ones to write.
:::

Reading a lasso takes three tests, and the checker in this page applies them to every lasso you build. It must be a path: each step is an action that is enabled where it is taken. It must close: the last step returns to a state already on the lasso. And the property must fail on it: for `<>Resolved`, no state on the lasso is resolved.

Try one by hand. Start at `held` with `tries` at 0. `Try` gives `pending` with `tries` at 1. `Busy` gives `held` with `tries` at 1. `Try` gives `pending` with `tries` back at 0, and `Busy` returns to the state you started in. The path closes and no state on it is resolved, so it is a second lasso, made of real steps instead of one stuttering step.

:::item role=segment family=GEN-lasso-or-not template=t1 kcs=KC-5.lasso-reading,KC-5.safety-vs-liveness
@choice key=C
The retrying hold has no fairness conjunct. Which behavior is a lasso that violates `EventuallyResolves`?

- A. `Try`, `Capture`, then stuttering forever in `captured`.
  - why: `captured` is a resolved state, so `<>Resolved` holds on this behavior. A violating lasso never reaches one.
  - mis: dp:T8
- B. `Try`, then `Try` again, then back to the first state.
  - why: After `Try` the hold is `pending`, where `Try` is not enabled. This is not a path of the graph, so it is not a behavior of `Spec`.
  - mis: dp:T10
- C. `Try`, `Busy`, `Try`, `Busy`, then back to the first state, repeated forever.
  - why: Every step is enabled where it is taken, the cycle closes, and no state on it is resolved. Nothing in `Spec` forbids it.
- D. None: `Capture` and `Timeout` exist, so the hold always resolves.
  - why: Existing is not happening. A behavior that never takes them is allowed, and without fairness it is a lasso.
  - mis: dp:T10
:::

## Writing it {minutes=12 kcs=KC-5.temporal-operators}

Three operators carry most of the temporal logic you will write.

- `[]P` (always): P holds in every state of the behavior from here on.
- `<>P` (eventually): P holds in at least one state from here on.
- `P ~> Q` (leads to): whenever P holds, Q holds then or later. It is shorthand for `[](P => <>Q)`.

Two combinations are worth knowing on sight. `[]<>P` says P keeps happening forever. `<>[]P` says P eventually holds for good.

:::instrument ins=INS-lasso cell=3 recorded=RUN-tlc-bare-property
```tla editable
---- MODULE Lifecycle ----
EXTENDS Naturals
VARIABLES hst, res
vars == <<hst, res>>
Init == hst = "available" /\ res = 0
Place   == hst = "available" /\ hst' = "held"     /\ UNCHANGED res
Capture == hst = "held"      /\ hst' = "captured" /\ res' = res + 1
Release == hst = "held"      /\ hst' = "released" /\ res' = res + 1
Next == Place \/ Capture \/ Release
Spec == Init /\ [][Next]_vars

Resolved == hst \in {"captured", "released"}
Avail == hst = "available"
\* Then try, one at a time:  []Avail   <>Avail   <>Resolved
Responds == (hst = "held") ~> Resolved
====
```

@direction
Config asks: `SPECIFICATION Spec` and `PROPERTY Avail`, where `Avail == hst = "available"`. The check reads `Avail` as TLC reads it. A violation would be a behavior of `Spec` on which `Avail` fails.

@call key=A surprise=yes run=RUN-tlc-bare-property
Your config says `PROPERTY Avail`. Is it violated?

- A. No.
  - why: `Avail` has no temporal operator, so it is read at the first state of each behavior, and there it is true.
- B. Yes: `Avail` is false after Place.
  - why: This reads an implicit `[]`. Without the operator, later states are not looked at.
  - mis: dp:T1
- C. Yes, unless every hold is eventually placed.
  - why: This reads an implicit `<>`. A formula with no operator says nothing about later states.
  - mis: dp:T1

@after
TLC reads a formula with no temporal operator at the first state of each behavior, and it even warns that it checks such a formula only in the initial state {{run:RUN-tlc-bare-property}}. To say "always", write `[]Avail`, which fails once the hold is placed: TLC reports it as `Invariant Avail is violated` after `Place`, because `[]Avail` is what `INVARIANT Avail` means {{run:RUN-tlc-bare-property}}. To say "at some point", write `<>Avail`.
:::

Two habits follow. First, `INVARIANT Inv` means the property `[]Inv`, so use `INVARIANT` for "never" and write `PROPERTY` for what an invariant cannot say, with the operators spelled out. Second, write "exactly once" as `NeverTwice /\ EventuallyResolves`, two properties, never as one eager `<>`, which says only "at least once". For example, `Responds == (hst = "held") ~> Resolved` says that every held hold is later resolved.

Writing a formula from English goes wrong about twice as often as reading one back into English, in studies of students learning temporal logic. The exit items practice the harder direction.

:::item role=segment family=GEN-call-it template=t4 kcs=KC-5.temporal-operators
@choice key=D
On the retrying hold, let `P` be `st = "held"`. Which behavior, written as the values of `st` in order and repeated forever, satisfies `[]<>P` but not `<>[]P`?

- A. `held`, `held`, `held`, ... (stuttering in `held`)
  - why: P holds in every state, so it holds infinitely often and it also holds for good. This behavior satisfies both formulas.
  - mis: dp:T1
- B. `held`, `pending`, `captured`, `captured`, ...
  - why: P holds only at the start. It is not infinitely often and not for good, so neither formula is satisfied.
  - mis: dp:T1
- C. `pending`, `pending`, `pending`, ...
  - why: P never holds, so neither formula is satisfied.
  - mis: dp:T1
- D. `held`, `pending`, `held`, `pending`, ... (the `Try` and `Busy` cycle)
  - why: P holds again and again, so `[]<>P` is true. But `pending` keeps coming back, so P never holds for good, and `<>[]P` is false.
:::

## Exit {minutes=3}

:::item role=exit family=GEN-call-it template=t1 kcs=KC-5.safety-vs-liveness
@choice key=C
Which of these promises about a hold is both a safety property and a liveness property joined together?

- A. A hold is never both captured and released.
  - why: A single state shows it failed. It is safety alone.
  - mis: dp:C5
- B. Every held hold is eventually resolved.
  - why: A finite log that ends with the hold held does not refute it. It is liveness alone.
  - mis: dp:C5
- C. A resolved hold stays resolved, and every held hold is eventually resolved.
  - why: The first half fails on a finite prefix and the second only on a behavior that never resolves, so it needs both kinds.
- D. Every hold is resolved within five ticks of the clock.
  - why: With a clock variable, a finite prefix in which the clock passes the limit shows it failed. It is safety alone.
  - mis: dp:T12
:::

:::item role=exit family=GEN-lasso-or-not template=t1 kcs=KC-5.lasso-reading
@choice key=B
A job moves `queued`, then `running` (`Start`), then `done` (`Finish`). There is no fairness conjunct. Which behavior is a lasso that violates `<>(state = "done")`?

- A. `Start`, `Finish`, then stuttering forever in `done`.
  - why: This reaches `done`, so the property holds on it.
  - mis: dp:T8
- B. `Start`, then stuttering forever in `running`.
  - why: Every step is enabled, the cycle is one stuttering step, and `done` is never reached.
- C. `Start`, `Finish`, then back to `queued`, repeated forever.
  - why: Nothing moves a finished job back to `queued`. This is not a path of the graph.
  - mis: dp:T10
- D. None: `Start` and `Finish` are always enabled, so the job finishes.
  - why: Each action is enabled in one state only, and enabled is not taken. Without fairness the job may stall.
  - mis: dp:T10
:::

:::item role=exit family=GEN-call-it template=t1 kcs=KC-5.temporal-operators
@choice key=B
Which formula says "whenever a hold is held, it is eventually resolved"?

- A. `[] (hst = "held" => Resolved)`
  - why: This asks for `Resolved` in the same state as `held`, in every state. One state cannot be both, so it forbids ever being held. It has no "eventually".
  - mis: dp:T1
- B. `(hst = "held") ~> Resolved`
  - why: Whenever the left side holds, the right side holds then or later.
- C. `(hst = "held") /\ <>Resolved`
  - why: This says the hold is held at the first state and resolves later. It has no "always", so it constrains only the first state.
  - mis: dp:T1
:::
