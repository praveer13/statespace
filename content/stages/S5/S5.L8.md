## Change the constants {minutes=14 kcs=KC-5.bounded-scope}

:::item role=prequestion family=GEN-which-stamp template=t1 kcs=KC-5.bounded-scope
@choice key=A
TLC checks a transfer model with two workers and finishes with no error. What may you claim?

- A. [M] · two workers, these constants · complete
  - why: The stamp names the exact configuration, and every reachable state was visited.
- B. [P] for every size: the transfer never overspends
  - why: This presents a bounded check as proof. Nothing here covers other worker counts.
  - mis: dp:T5
- C. [T] · n = the distinct-state count
  - why: A complete model check is not a sample of tests.
  - mis: dp:X1
:::

A model check is a check of one finite model, and changing the model can change the verdict. Run the transfer model from S5.L3 with each worker spending 40 from a balance of 100.

:::instrument ins=INS-spectacle cell=1 recorded=RUN-spectacle-s5s8
```tla
---- MODULE DoubleSpend ----
EXTENDS Naturals
CONSTANTS Init, Amount, Workers
VARIABLES bal, pc, seen, spent
vars == <<bal, pc, seen, spent>>

Init_ == /\ bal = Init
         /\ pc = [w \in Workers |-> "read"]
         /\ seen = [w \in Workers |-> 0]
         /\ spent = 0

Read(w) == /\ pc[w] = "read"
           /\ seen' = [seen EXCEPT ![w] = bal]
           /\ pc' = [pc EXCEPT ![w] = IF bal >= Amount THEN "write" ELSE "done"]
           /\ UNCHANGED <<bal, spent>>

Write(w) == /\ pc[w] = "write"
            /\ bal' = seen[w] - Amount
            /\ spent' = spent + Amount
            /\ pc' = [pc EXCEPT ![w] = "done"]
            /\ UNCHANGED seen

Next == \E w \in Workers : Read(w) \/ Write(w)
NoOverspend == spent <= Init
====
```

@direction
Spec asserts: each worker reads the balance, checks the guard against what it read, then writes. The check asks whether `NoOverspend` can fail. Set `Init` to 100, `Amount` to 40 and two workers, run to completion, then add a third worker and watch the minimap.

@call key=B surprise=yes run=RUN-spectacle-s5s8
With `Init` 100, `Amount` 40 and two workers, checked to completion, does TLC report that `NoOverspend` fails?

- A. Yes, as at `Amount` 80.
  - why: That carries one configuration's verdict to another.
  - mis: dp:T5
- B. No.
  - why: Each worker spends 40 at most once, so two workers spend at most 80, whatever the interleaving.
- C. Only if you ask TLC to continue past errors.
  - why: Continuing keeps the search going after an error. It cannot create one.
  - mis: dp:T9

@after
Add a third worker and the same model fails, because three workers can spend 120. TLC finds the violation at {{run:RUN-tlc-unsafe-3w#values.w3-a40-deadlock-off.distinct_states}} distinct states, at depth {{run:RUN-tlc-unsafe-3w#values.w3-a40-deadlock-off.depth}}. One model is clean and the next fails, so a verdict belongs to the model you checked.
:::

**From a system to a finite model.** Your system has no fixed number of workers and no cap on a balance, and TLC can finish only on a finite graph. So a check explores a finite-state abstraction of your system: a model with finitely many states that stands in for it. Constants fix the number of workers and the amounts. A CONSTRAINT cuts the search off at a bound. SYMMETRY counts states that differ only by swapping interchangeable workers as one. What TLC reports is about that model, and it covers your system only as far as the model does.

Each choice has a cost.

- Constants change the size fast: at `Amount` 80 the model has {{run:RUN-tlc-full#values.distinct_states.w2}}, {{run:RUN-tlc-full#values.distinct_states.w3}}, {{run:RUN-tlc-full#values.distinct_states.w4}} and {{run:RUN-tlc-full#values.distinct_states.w5}} distinct states at two to five workers.
- A CONSTRAINT drops states silently, so the stamp is [M] · bound · partial.
- SYMMETRY can shrink the space by about n! for n interchangeable workers, but TLC warns that symmetry during liveness checking might miss violations {{run:RUN-tlc-sym-liveness}}. Liveness cards say symmetry off.
- A complete run prints collision estimates, {{run:RUN-tlc-fingerprint#values.calculated}} (optimistic) and {{run:RUN-tlc-fingerprint#values.actual}} (actual fingerprints), on a model of {{run:RUN-tlc-fingerprint#values.distinct_states}} distinct states. Complete means every reachable state, unless a collision hid one.
- TLC runs one worker unless told otherwise {{run:RUN-tlc-help}}, so claim a shortest trace only from a one-worker run.

:::item role=segment family=GEN-which-stamp template=t2 kcs=KC-5.bounded-scope
@choice key=B
A run of the transfer model with a CONSTRAINT that caps the balance finishes with no error. Which stamp?

- A. [M] · constants · complete
  - why: A CONSTRAINT drops states without saying which, so the run is not complete.
  - mis: dp:T5
- B. [M] · bound · partial
  - why: The stamp names the bound and says some states were never visited.
- C. [P] · bounded by the CONSTRAINT
  - why: A bounded check is never proof, whatever the bound.
  - mis: dp:X1
:::

## Exit {minutes=4}

:::item role=exit family=GEN-call-it template=t4 kcs=KC-5.bounded-scope
@choice key=D
A complete run of the two-worker transfer model finds no error. Which statement is true?

- A. It holds for three workers too.
  - why: The run covers two workers. Three workers is another model.
  - mis: dp:T5
- B. A CONSTRAINT would have reported the states it dropped.
  - why: A CONSTRAINT drops states silently, which is why its stamp says partial.
  - mis: dp:T9
- C. Symmetry never changes a liveness verdict.
  - why: TLC warns that symmetry during liveness checking might miss violations.
  - mis: dp:T9
- D. It holds for these constants, unless a fingerprint collision hid a state.
  - why: Complete means every reachable state, and TLC prints the odds that a collision hid one.
:::
