## Behaviors as sequences {minutes=14 kcs=KC-5.behaviors-stuttering}

:::item role=prequestion family=GEN-trace-allowed template=t3 kcs=KC-5.behaviors-stuttering
@choice key=C
A spec says `x = 0` at the start, and after that `[][x' = x + 1]_x`. Is the behavior 0, 1, 1, 2, 3, ... allowed?

- A. No: every step of the spec has to add 1 to `x`.
  - why: This reads the box as "always Next". The subscript is what permits a step that changes nothing.
  - mis: dp:T7
- B. Only if you tell TLC not to check for deadlock.
  - why: Flags change what TLC checks, never which behaviors a spec allows.
  - mis: dp:T9
- C. Yes: the box allows every step that leaves `x` unchanged.
  - why: `[A]_v` means `A \/ v' = v`, so a step that changes nothing is always allowed.
:::

A TLA+ spec describes your system as a set of *behaviors*. A *state* gives every variable a value, a *step* is a pair of states, and a behavior is an infinite sequence of states. The spec allows every behavior that starts in an initial state and whose every step is an action of `Next` or changes nothing.

That last clause is the box in `Spec == Init_ /\ [][Next]_vars`. `[Next]_vars` means `Next \/ vars' = vars`, so repeating a state is always allowed. This is *stuttering*. A system that finishes is not a short run. It is a behavior that stops changing and repeats its last state forever, which is why every finite prefix can be continued.

An action is *enabled* in a state when some next state satisfies it. Enabled is not taken: nothing in `Spec` forces a step. Forcing one is what fairness adds, later in this stage.

TLC, the model checker for TLA+, records which action took each step. Draw those names on the arrows between states and the reachable graph is a *labeled transition system*. A spec's actions are its labels, and a behavior is a path through the graph that may also stay where it is.

The module below is a transfer whose guard and write are one action, for two workers, 100 in the account and an amount of 80. `Init_` is its starting predicate, because `Init` is already the starting balance, and `NoOverspend` is the property later lessons check. Two tools in your browser carry this stage. Spectacle draws the reachable states of a spec you write. The Theater, which you use first, lets you play concurrency by hand on real TLC state graphs: the bar lists the actions enabled in the current state, you pick one to take a step, and stutter repeats the state.

:::instrument ins=INS-theater cell=1 recorded=RUN-tlc-atomic
```tla
---- MODULE DoubleSpendAtomic ----
EXTENDS Naturals
CONSTANTS Init, Amount, Workers
VARIABLES bal, pc, spent
vars == <<bal, pc, spent>>

Init_ == /\ bal = Init
         /\ pc = [w \in Workers |-> "go"]
         /\ spent = 0

Spend(w) == /\ pc[w] = "go"
            /\ IF bal >= Amount
                 THEN bal' = bal - Amount /\ spent' = spent + Amount
                 ELSE UNCHANGED <<bal, spent>>
            /\ pc' = [pc EXCEPT ![w] = "done"]

Next == \E w \in Workers : Spend(w)
Spec == Init_ /\ [][Next]_vars
NoOverspend == spent <= Init
====
\* Init = 100, Amount = 80, Workers = {w1, w2}
```

@direction
Scene: this spec's state graph, one arrow per action. Each step you take is one enabled action, and stutter repeats the current state. The Theater reports what you did, not whether a property holds.

@call key=A surprise=yes
Is the behavior that stays in the initial state forever, with no worker ever spending, a behavior of `Spec`?

- A. Yes: a step may leave the state unchanged.
  - why: Every step leaves `vars` unchanged, which the box permits, and nothing in `Spec` forces a step of `Next`.
- B. No: `Spend(w1)` is enabled, so the next step must be a `Spend`.
  - why: Enabled is not taken. A spec allows a step and never demands one.
  - mis: dp:T10
- C. No: a behavior must end in a state where nothing is enabled.
  - why: Behaviors are infinite, and a finished system repeats its last state forever.
  - mis: dp:T8

@after
The Theater draws the answer as the initial state with an arrow back to itself. Every state has one. So "nothing ever happens" is a behavior of every spec, and saying that something must happen takes a stronger statement.
:::

:::item role=segment family=GEN-trace-allowed template=t3 kcs=KC-5.behaviors-stuttering
@choice key=C
A counter goes 0, 1, 2, 0, 1, 2 and so on: `c = 0 /\ [][c' = (c + 1) % 3]_c`. Each prefix below is followed by stuttering forever. Which one is not a behavior of the spec?

- A. 0, 0, 1, 2
  - why: It stays at 0 for one step and then counts. Staying put is allowed, and the later steps are all `Next` steps.
  - mis: dp:T10
- B. 0, 1, 1, 2
  - why: The step from 1 to 1 changes nothing, so the box allows it. The counter then moves on.
  - mis: dp:T7
- C. 0, 1, 3, 0
  - why: The step from 1 to 3 is neither `c' = (c + 1) % 3` nor a repeat of the state.
:::

## Exit {minutes=4 kcs=KC-5.behaviors-stuttering}

:::item role=exit family=GEN-trace-allowed template=t2 kcs=KC-5.behaviors-stuttering
@choice key=B
A job is `idle`, `running`, `done` or `cancelled`. `Start` takes `idle` to `running`, `Finish` takes `running` to `done`, and `Cancel` takes `idle` or `running` to `cancelled`. Which actions are enabled in the state `running`?

- A. `Finish`, because it is the step the job is heading for.
  - why: Enabled depends on the guard, not on what is expected to happen next. `Cancel` applies too.
  - mis: dp:T10
- B. `Finish` and `Cancel`.
  - why: Both guards hold. Which one fires is the scheduler's choice, and neither has to.
- C. `Start`, `Finish` and `Cancel`: a step takes whichever apply.
  - why: `Start` needs `idle`, and one step takes one action.
  - mis: dp:T16
:::
