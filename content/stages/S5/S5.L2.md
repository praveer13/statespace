## Run it twice {minutes=14 kcs=KC-5.tlc-flags-matter}

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-5.tlc-flags-matter
@choice key=C
TLC stops with a deadlock report. What does that tell you?

- A. Two workers are waiting on each other's lock.
  - why: A lock cycle is one cause of that report, but a spec with no locks can raise it too.
  - mis: dp:T9
- B. The invariant holds, because TLC finished.
  - why: TLC stopped early. It checked the invariant only on the states it had explored so far.
  - mis: dp:T5
- C. Some reachable state enables no action of `Next`.
  - why: TLC's deadlock check looks for a reachable state with no successor. When every worker can finish, that state is the finished one.
:::

Here is the read-then-write transfer as a hand-written TLA+ spec. A worker's `Read` copies the balance into `seen` and decides from that copy whether it may write. Its `Write` later sets the balance to the copy minus the amount. `NoOverspend` says the account never pays out more than it started with. Run it on the Bench twice and read the raw output both times: the first line that names an error is the answer, and the counts and the trace follow it.

To read the syntax: `/\` is and, `\/` is or, `\E w \in Workers` is "for some worker", `x'` is the value of `x` in the next state, `UNCHANGED <<a, b>>` keeps both, and `[f EXCEPT ![w] = v]` is the function `f` with `w` mapped to `v`. The module is yours to edit after the first run.

PlusCal is pseudocode that translates into TLA+. The translator adds a `Terminating` action so that finishing is not reported as a deadlock {{run:RUN-pcal-doublespend}}, so the deadlock below belongs to the hand-written spec. Drawer D-09 shows the translation beside it.

:::instrument ins=INS-bench-tlc cell=1 recorded=RUN-tlc-doublespend
```tla editable
---- MODULE DoubleSpend ----
EXTENDS Naturals
CONSTANTS Init, Amount, Workers
VARIABLES bal, pc, seen, spent
vars == <<bal, pc, seen, spent>>

Init_ == /\ bal = Init
         /\ pc = [w \in Workers |-> "read"]
         /\ seen = [w \in Workers |-> 0]
         /\ spent = 0

Read(w) == /\ pc[w] = "read"
           /\ seen' = [seen EXCEPT ![w] = bal]
           /\ pc' = [pc EXCEPT ![w] = IF bal >= Amount THEN "write" ELSE "done"]
           /\ UNCHANGED <<bal, spent>>

Write(w) == /\ pc[w] = "write"
            /\ bal' = seen[w] - Amount
            /\ spent' = spent + Amount
            /\ pc' = [pc EXCEPT ![w] = "done"]
            /\ UNCHANGED seen

Next == \E w \in Workers : Read(w) \/ Write(w)
Spec == Init_ /\ [][Next]_vars
NoOverspend == spent <= Init
====
\* CONSTANTS Init = 100, Amount = 80, Workers = {w1, w2}
\* INIT Init_, NEXT Next, INVARIANT NoOverspend
```

@direction
Model asserts: `NoOverspend` holds in every reachable state. This run uses TLC's default flags, so the deadlock check is on, and one worker.

@call key=A run=RUN-tlc-doublespend surprise=yes
Default flags. What does TLC report first?

- A. A deadlock.
  - why: As recorded, in both jars. Both workers can finish, and that state enables no action.
- B. That the invariant is violated.
  - why: Breadth-first search reaches the finished state one level before the violation, and by default TLC treats "nothing enabled" as an error.
  - mis: dp:T9
- C. That no error was found.
  - why: The spec has a deadlock and a violation. A run that reports neither would be hiding one.
  - mis: dp:T5

@after
TLC stopped at depth {{run:RUN-tlc-doublespend#values.default.depth}}, one level before the invariant fails at depth {{run:RUN-tlc-doublespend#values.deadlock_off.depth}}. The trace is `Read(w1)`, `Write(w1)`, `Read(w2)`: worker 2 reads 20, which is below 80, and finishes. Nothing is enabled, so TLC reports it {{run:RUN-tlc-doublespend}}.

`-deadlock` turns that check off. TLC's own help says "{{run:RUN-tlc-help#values.deadlock_flag}}".
:::

Same spec, same constants, one worker, and the deadlock check off.

@direction
Model asserts: `NoOverspend` holds in every reachable state. This run adds `-deadlock` {{run:RUN-tlc-help}}.

@call key=B run=RUN-tlc-doublespend surprise=no
With the deadlock check off, how long is TLC's counterexample, in actions?

- A. 1–2 actions
  - why: Each write needs a read before it, so two writes cannot fit in two steps.
  - mis: dp:C1
- B. 3–4 actions
  - why: Both workers read, then both write: four actions, from {{run:RUN-tlc-doublespend#values.deadlock_off.trace_states}} states.
- C. 5–6 actions
  - why: This counts the states of the trace as steps. A trace of five states has four arrows.
  - mis: dp:T6
- D. 7 or more
  - why: This counts the states TLC generated, not the steps of the trace.
  - mis: dp:T6

@after
Both workers read 100 before either writes, so both pass the guard and the account pays out 160. That is the double spend, and the next lesson has you build it by hand. A receipt keeps TLC's version line because versions differ in small ways: the older jar prints `Read` where the newer prints `Read(w1)`, and only the newer writes a trace as JSON {{run:RUN-tlc-doublespend}}.
:::

:::item role=segment family=GEN-call-it template=t2 kcs=KC-5.tlc-flags-matter
@choice key=C
A variant has three workers, 100 in the account and an amount of 40. With the deadlock check off, how long is the shortest counterexample, in actions?

- A. 3 actions
  - why: This treats each worker as one step. A worker reads and writes in separate steps.
  - mis: dp:C1
- B. 4 actions
  - why: This carries the two-worker answer over to three workers.
  - mis: dp:T5
- C. 6 actions
  - why: All three workers must spend, and each spend is a read and a write. TLC's depth counts states, so it prints one more, {{run:RUN-tlc-unsafe-3w#values.w3-a40-deadlock-off.depth}} {{run:RUN-tlc-unsafe-3w}}.
- D. 7 actions
  - why: This counts the states of the trace, which is one more than its steps.
  - mis: dp:T6
:::

## Exit {minutes=4 kcs=KC-5.tlc-flags-matter}

:::item role=exit family=GEN-call-it template=t1 kcs=KC-5.tlc-flags-matter
@choice key=B
The atomic version of the transfer does its guard and write in one action, and `NoOverspend` holds. You run it with TLC's default flags. What does TLC report?

- A. That no error was found.
  - why: Every worker finishes, and the finished state enables no action. Default flags report that.
  - mis: dp:T9
- B. A deadlock.
  - why: The invariant holds, and TLC still stops at the finished state {{run:RUN-tlc-atomic}}.
- C. That the invariant is violated.
  - why: The guard and the write are one step, so no stale read can happen.
  - mis: dp:T5
:::
