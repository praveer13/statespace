## Two questions first {minutes=3 kcs=KC-5.interleaving-granularity}

An agent's change note on your transfer handler reads:

> "The guard runs before every write, so this is safe under concurrency."

You will test that by playing the scheduler yourself, and then by asking TLC to try every schedule. Two questions first. Guess if you are not sure, because the lesson answers both.

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-5.interleaving-granularity
@choice key=C
Two workers each read `bal`. If what they read is at least 80, they write back what they read minus 80. `bal` starts at 100, and the read and the write are separate steps. Can more than 100 be paid out?

- A. No: the guard runs before each write.
  - why: The guard tests a value that may be stale by the time of the write.
  - mis: dp:C1
- B. Only under a rare schedule, so not in practice.
  - why: A checker tries every schedule, and production traffic finds the rare ones.
  - mis: dp:C4
- C. Yes.
  - why: Both workers can read 100 before either one writes.
:::

:::item role=prequestion family=GEN-call-it template=t1 kcs=KC-5.interleaving-granularity
@choice key=A
Which change removes the overpayment?

- A. Read, check and write in one atomic step.
  - why: No other worker can act between the check and the write.
- B. Make the read and the write faster.
  - why: Speed narrows the window without closing it.
  - mis: dp:C4
- C. Re-check the balance in its own step just before the write.
  - why: The re-check is itself a step, so it can go stale before the write that follows it.
  - mis: dp:C3
:::

## Be the scheduler {minutes=15 kcs=KC-5.interleaving-granularity}

Each worker runs two steps. `Read` copies the balance into `seen` and decides from that copy whether it may write. `Write` sets the balance to the copy minus the amount. The agent's note is true as far as it goes: the guard does run before every write. What it tests is the copy, and the copy can be stale by the time of the write, because the other worker acts in between.

Call the steps R1 and R2 for the two reads, and W1 and W2 for the two writes. The Theater below loads this spec's whole state graph. The bar lists the actions enabled in the current state, and you choose which worker moves next. Your aim is a behavior that ends with more paid out than the account held.

:::instrument ins=INS-theater cell=1 recorded=RUN-tlc-doublespend
```tla
---- MODULE DoubleSpend ----
EXTENDS Naturals
CONSTANTS Init, Amount, Workers
VARIABLES bal, pc, seen, spent
vars == <<bal, pc, seen, spent>>

Init_ == /\ bal = Init
         /\ pc = [w \in Workers |-> "read"]
         /\ seen = [w \in Workers |-> 0]
         /\ spent = 0

Read(w) == /\ pc[w] = "read"
           /\ seen' = [seen EXCEPT ![w] = bal]
           /\ pc' = [pc EXCEPT ![w] = IF bal >= Amount THEN "write" ELSE "done"]
           /\ UNCHANGED <<bal, spent>>

Write(w) == /\ pc[w] = "write"
            /\ bal' = seen[w] - Amount
            /\ spent' = spent + Amount
            /\ pc' = [pc EXCEPT ![w] = "done"]
            /\ UNCHANGED seen

Next == \E w \in Workers : Read(w) \/ Write(w)
Spec == Init_ /\ [][Next]_vars
NoOverspend == spent <= Init
====
\* Init = 100, Amount = 80, Workers = {w1, w2}
```

@direction
Scene: this spec's state graph. Pick an enabled action to take a step. The trace table follows `bal`, `spent` and what each worker saw. Aim for `spent` above 100.

@call key=B run=RUN-tlc-doublespend surprise=moderate
Which orders of the four steps R1, R2, W1, W2 pay out 160, where each write follows its own read?

- A. Only R1, R2, W1, W2: the reads first, then the writes, each in worker order.
  - why: That is one witness taken for the whole bug. The order of the two writes does not matter.
  - mis: dp:Z3
- B. Any order in which both reads come before both writes.
  - why: Both workers then hold a copy of 100 and both pass the guard. Whichever writes last leaves 20 in the account.
- C. Any order in which each write follows its own read.
  - why: In R1, W1, R2, W2, worker 2 reads 20 and stops, so only 80 is paid out.
  - mis: dp:C1

@after
Try R1 and then W1 in the Theater: the balance drops to 20, and when worker 2 reads, its guard fails. Now try R1 and then R2: both copies say 100, and whatever you do next, both writes go through. The bug is a class of schedules, every order that puts both reads before both writes, and not one trace. TLC reported one of them as its counterexample {{run:RUN-tlc-doublespend}}.
:::

:::item role=segment family=GEN-find-the-witness template=t2 kcs=KC-5.interleaving-granularity
@choice key=B
Same spec: two workers, 100 in the account, an amount of 80. Which trace ends with `NoOverspend` violated?

- A. R1, W1, R2, W2
  - why: Worker 2 reads after worker 1 has written. It sees 20, which is below 80, so it stops and only 80 is paid out.
  - mis: dp:C1
- B. R2, R1, W1, W2
  - why: Both copies say 100, so both writes go through. This is the class of schedules from the call, with the reads in the other order.
- C. R1, R2, W1
  - why: Two stale copies exist, but only worker 1 has written. A violation needs the second write too.
  - mis: dp:T11
:::

## Ask TLC {minutes=15 kcs=KC-5.interleaving-granularity}

A schedule you found by hand is one behavior. TLC explores all of them, breadth first, and reports the first one that breaks the invariant. You already ran the Theater's module on the Bench with the deadlock check off in the last lesson, because with default flags TLC stops first at the finished state {{run:RUN-tlc-doublespend}}. Pull up that receipt, read its counts and its trace, and set the trace beside yours.

The repair is to merge the guard and the write into one action, `Spend(w)`, so that no other worker can act between the check and the write. That is the atomic spec from the first lesson, and it is what the next cell runs.

:::instrument ins=INS-bench-tlc cell=2 recorded=RUN-tlc-atomic
```tla editable
---- MODULE DoubleSpendAtomic ----
EXTENDS Naturals
CONSTANTS Init, Amount, Workers
VARIABLES bal, pc, spent
vars == <<bal, pc, spent>>

Init_ == /\ bal = Init
         /\ pc = [w \in Workers |-> "go"]
         /\ spent = 0

Spend(w) == /\ pc[w] = "go"
            /\ IF bal >= Amount
                 THEN bal' = bal - Amount /\ spent' = spent + Amount
                 ELSE UNCHANGED <<bal, spent>>
            /\ pc' = [pc EXCEPT ![w] = "done"]

Next == \E w \in Workers : Spend(w)
Spec == Init_ /\ [][Next]_vars
NoOverspend == spent <= Init
====
\* CONSTANTS Init = 100, Amount = 80, Workers = {w1, w2}
\* INIT Init_, NEXT Next, INVARIANT NoOverspend
```

@direction
Model asserts: `NoOverspend` holds in every reachable state of the atomic spec. This run adds `-deadlock` and uses one worker {{run:RUN-tlc-help}}.

@call key=C run=RUN-tlc-atomic surprise=no
The atomic spec does the guard and the write in one action. With the deadlock check off, what does TLC report?

- A. A violation, but with a shorter trace than before.
  - why: The grain changed which behaviors exist, not only how long they are.
  - mis: dp:C3
- B. A deadlock at the end of the run.
  - why: The flag turns that check off, so a finished state is not reported.
  - mis: dp:T9
- C. No error, and the exploration is complete.
  - why: No state lies between a read and its write, so no stale read exists. TLC finished with nothing left on its queue, after {{run:RUN-tlc-atomic#values.w2-deadlock-off.distinct_states}} distinct states.

@after
Both counts came from the same flags and constants: one worker, the deadlock check off, 100 in the account, an amount of 80 and two workers {{run:RUN-tlc-doublespend}} {{run:RUN-tlc-atomic}}. The unsafe spec reached {{run:RUN-tlc-doublespend#values.deadlock_off.distinct_states}} distinct states when the invariant failed, and the atomic one {{run:RUN-tlc-atomic#values.w2-deadlock-off.distinct_states}}.

Count them by depth in the Theater graph. The unsafe spec's states split 1, 2, 3, 4 and 1. The atomic spec's split 1, 2 and 1. The extra states of the unsafe spec are the moments between a worker's read and its write, while its copy can go stale. Run to completion without the invariant, the unsafe spec has the same {{run:RUN-tlc-full#values.distinct_states.w2}} states {{run:RUN-tlc-full}}.

A count means little without its flags and constants. With three workers and an amount of 40, the unsafe spec fails after {{run:RUN-tlc-unsafe-3w#values.w3-a40-deadlock-off.distinct_states}} distinct states and the atomic one finishes cleanly after {{run:RUN-tlc-atomic#values.w3-a40-deadlock-off.distinct_states}} {{run:RUN-tlc-unsafe-3w}}.
:::

Your claim CL-2.4, if you have minted it, says a run of transfers conserves the total. It rests on a seam, SEAM-2: transfers run one at a time. Before you answer, say its proposition to yourself from memory. That recall is not graded.

@choice key=B
The trace R1, R2, W1, W2 is a behavior of a system whose transfers run concurrently. Which segment of CL-2.4's strip does it crack?

- A. proposition-of-model
  - why: The theorem about sequential runs is still true. A trace of the concurrent system does not refute it.
  - mis: dp:P3
- B. correspondence
  - why: The running system is not sequential. SEAM-2, "transfers run one at a time", is the assumption that cracks.
- C. requirement-fit
  - why: Nothing about the requirement changed, and requirement-fit is not where proof status lives.
  - mis: dp:L3

The remedies are the one you just used, an atomic action (CL-5.1), and isolation, which a later stage covers.

@choice key=A
On the atomic spec with two workers, 100 in the account and an amount of 80, which prefix of a behavior first breaks `NoOverspend`, if any?

- A. None: every prefix keeps what is spent at 100 or less.
  - why: Each `Spend` tests and writes in one step, so no stale read exists. The double-spend order is not a behavior of this spec at all.
- B. `Spend(w1)`, then `Spend(w2)`: both guards pass.

## Change the grain {minutes=12 kcs=KC-5.interleaving-granularity}

Granularity is a modeling choice, and it decides which interleavings exist. This spec, M3, splits the check out of the read: `Read` copies the balance, `Check` tests the guard against the copy, and `Write` writes. Each worker now takes up to three steps, and there is one more place for the other worker to interrupt. Predict before you run: does the shortest violation get shorter, stay the same, or grow?

:::instrument ins=INS-spectacle cell=3 recorded=RUN-tlc-rtw3
```tla editable
---- MODULE RTW3 ----
EXTENDS Naturals
CONSTANTS Init, Amount, Workers
VARIABLES bal, pc, seen, spent
vars == <<bal, pc, seen, spent>>

Init_ == /\ bal = Init
         /\ pc = [w \in Workers |-> "read"]
         /\ seen = [w \in Workers |-> 0]
         /\ spent = 0

Read(w) == /\ pc[w] = "read"
           /\ seen' = [seen EXCEPT ![w] = bal]
           /\ pc' = [pc EXCEPT ![w] = "check"]
           /\ UNCHANGED <<bal, spent>>

Check(w) == /\ pc[w] = "check"
            /\ pc' = [pc EXCEPT ![w] = IF seen[w] >= Amount THEN "write" ELSE "done"]
            /\ UNCHANGED <<bal, spent, seen>>

Write(w) == /\ pc[w] = "write"
            /\ bal' = seen[w] - Amount
            /\ spent' = spent + Amount
            /\ pc' = [pc EXCEPT ![w] = "done"]
            /\ UNCHANGED seen

Next == \E w \in Workers : Read(w) \/ Check(w) \/ Write(w)
Spec == Init_ /\ [][Next]_vars
NoOverspend == spent <= Init
====
\* CONSTANTS Init = 100, Amount = 80, Workers = {w1, w2}
\* INIT Init_, NEXT Next, INVARIANT NoOverspend, deadlock check off
```

@direction
Model asserts: `NoOverspend` holds in every reachable state of the split spec. Spectacle searches breadth first and stops at the first violation.

@call key=C run=RUN-tlc-rtw3 surprise=yes
With the check split out of the read, the shortest violation is...

- A. shorter than 4 actions.
  - why: A finer grain adds steps. It never takes any away.
  - mis: dp:C3
- B. still 4 actions.
  - why: This treats a read and a check as one step. They are two, and the other worker can act between them.
  - mis: dp:C1
- C. longer than 4 actions.
  - why: Each worker now needs three steps, so six actions in all, and the extra scheduling point multiplies the interleavings.

@after
The shortest witness is `Read(w1)`, `Check(w1)`, `Read(w2)`, `Write(w1)`, `Check(w2)`, `Write(w2)`: {{run:RUN-tlc-rtw3#values.trace_actions}} actions, {{run:RUN-tlc-rtw3#values.trace_states}} states. TLC stops after {{run:RUN-tlc-rtw3#values.distinct_states}} distinct states, against {{run:RUN-tlc-atomic#values.w2-deadlock-off.distinct_states}} for the atomic spec {{run:RUN-tlc-rtw3}}. The bug did not move. The finer grain gave the other worker one more place to interrupt, and it made the check look like a safeguard that is not.
:::

:::item role=segment family=GEN-call-it template=t4 kcs=KC-5.interleaving-granularity
@choice key=C
The split spec has a check step between the read and the write. Which statement about it is true?

- A. Its shortest violation is no longer than the unsplit spec's, because the bug is the same.
  - why: Every worker needs an extra step, so the shortest witness grows.
  - mis: dp:C3
- B. Its violation depends on speed: if the workers run fast enough, it disappears.
  - why: A checker tries every schedule, and speed only changes how often a schedule occurs.
  - mis: dp:C4
- C. It has more reachable states than the atomic spec, because a worker can be interrupted in more places.
  - why: Each extra step is another place for the other worker to act, and each adds reachable states.
:::

Three workers, 100 in the account, an amount of 40, and the read and the write as separate steps. Which trace ends with `NoOverspend` violated?

- A. R1, W1, R2, W2, R3, W3
  - why: Each worker reads after the one before it has written. The third reads 20 and stops, so only 80 is paid out.
  - mis: dp:C1
- B. R1, R2, R3, W1, W2, W3
  - why: All three copies say 100, so all three writes go through and 120 is paid out of 100.
- C. R1, R2, W1, W2

  - mis: dp:C2
