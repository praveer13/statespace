## Log first, flush later {minutes=2}

A database records each change in its write-ahead log before it changes data pages. A commit is durable once its log record reaches stable storage. Data pages can be written later, and after a crash recovery replays the log. The tablespace course's lesson T3 teaches this layer.

A crash before the commit record is flushed leaves the transaction as if it never ran. A crash after leaves it committed, whatever had reached the data pages. Durability rests on the disk honoring flush requests, an assumption T3 examines and you carry as ASSUMED [A].

## One layer up {minutes=3}

Your outbox intent commits in the same transaction as the command, so it is durable exactly when the command is. The external effect is not in the database's log: a commit is not a send. A crash between the commit and the send, or between the send and its acknowledgement, leaves the intent pending, and recovery sends again. That is at-least-once, and it is the crash-window table of lesson S8.L3.

Anything kept only in the worker's memory dies with it. The no-outbox contrast in lesson S8.L1 keeps the intent in memory, so a crash can lose it.

The harness enumerates crashes: T3's labs stop the process at chosen points, and your spec injects a crash between every two steps. Neither waits on timing.
