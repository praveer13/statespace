## Failure as a value {minutes=3}

A step returns `Except Err (State × Output × List Effect)`: an error, or a new state with its outputs and effects. In stage S2 the transfer returned the unchanged state when its guard failed, so a caller could not tell a rejection from a successful step that changed nothing (the prequestion of lesson S3.L3).

`guardFailed`, `unknownAccount`, `holdNotOpen` and `badArgument` are outcome classes: values a caller can match on, with the order in which checks run fixed by the semantics. An error outcome is part of what the semantics says, not a defect.

For Rust readers: `Result<T, E>` makes the same move as `Except Err`. Where it breaks: Lean's evaluator is pure and total, so every outcome is a value, while Rust code can still panic outside its `Result`.

## In SQL {minutes=2}

An UPDATE whose WHERE clause matches no row succeeds with rowcount 0, silently, and a row whose balance is NULL is skipped the same way {{run:RUN-pg-anomalies}}. So the compiled transfer requires both rowcounts to equal 1 and maps each 0 to a typed error (lesson S6.L2).

On the builder's path this card is enough for lesson S6.L2. Stage S3 later gives these outcomes a full semantics.
