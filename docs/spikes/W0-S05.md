# W0-S05 · TLC lasso JSON

**Status:** decision record; the schema is a draft. **Task:** W0-S05 (the INS-lasso input format). **Date:** 2026-10-24 (machine clock). **Run:** {{run:RUN-tlc-lasso-json}}. **Draft schema:** `schemas/drafts/lasso.schema.json`. **Owner review:** 0.5 h.

## 1. Question

How does the pinned `tla2tools` 1.8.0 write a liveness counterexample, a lasso, when asked for `-dumpTrace json`, on the Hold spec whose lasso is already recorded [X RUN-tlc-hold-lasso]? And what must a draft `lasso@1` say so that INS-lasso can read TLC's file?

The tracker narrows the task to documenting that format and drafting the schema, because the recorded trace already closes its loop with a last step that targets state 1 (`curriculum/S05-time.md`, section 12, issue 4). The spine's W0-S05 row also names RUN-trace-validate-spike. No adopted task in the tracker records it; the proposed W0-S13 would spike it under a run ID of its own. This record does not cover it.

**Short answer.** On the Hold spec the JSON lists 4 states and 4 steps, and the fourth step goes from state 4 to `[1, …]`, a state already listed. That closing step is the whole encoding of the loop. The file has no loop field, no property name, no spec name and no tool version. The same rule held on three other lasso shapes: a stutter, a stem and a cycle, and a stem and a stutter. The draft `lasso@1` is TLC's file as written, checked by a strict schema and then by six reading rules. {{run:RUN-tlc-lasso-json}}

## 2. Method

1. Re-ran the Hold spec and config of RUN-tlc-hold-lasso on the pinned 1.8.0 jar, with one worker and `-dumpTrace json`, in a fresh container of the pinned Temurin image with no network, and compared the file with the recorded `Hold.trace.json` byte for byte.
2. Read the file beside TLC's text trace and beside the trace-exploration module TLC writes for the same run, to see where each marks the loop.
3. Ran probe configurations for the shapes Hold does not show: a stutter, a stem before a cycle, a stem before a stutter, and a parameterized action. The probes are in `scripts/spikes/W0-S05/probes/`. They are format probes, not course material.
4. Ran the same configurations on 1.7.4, which cannot write JSON, to read the fallback text.
5. Drafted the schema and wrote the reading rules as a dependency-free reader (`scripts/spikes/W0-S05/lasso-read.mjs`), then checked both against 24 fixtures: the schema with two JSON Schema validators, the rules with the reader.

To reproduce, with Docker, Node 22, `uv` and both pinned jars:

```
npm ci --prefix scripts/spikes/W0-S05
TLA2TOOLS_180=<1.8.0 jar> TLA2TOOLS_174=<1.7.4 jar> node scripts/spikes/W0-S05/record.mjs
```

`record.mjs` refuses a jar whose SHA-256 is not the pin, runs every configuration, runs the checks, and rewrites `runs/RUN-tlc-lasso-json.json` and `runs/RUN-tlc-lasso-json/`. `node scripts/spikes/W0-S05/check.mjs` repeats the checks alone.

## 4. Results

### 4.1 The Hold lasso, as TLC writes it

Hold is the course's model M4: `Try` moves a hold from held to pending, `Busy` moves it back, `Capture` and `Timeout` resolve it, and `Fair == WF_vars(Try) /\ WF_vars(Busy)`. The config names `SPECIFICATION Spec`, `PROPERTY EventuallyResolves`, `PROPERTY NeverTwice` and `CHECK_DEADLOCK FALSE`.

The run (config `hold-180`) is `java -XX:+UseParallelGC -jar tla2tools.jar -workers 1 -config Hold.cfg -dumpTrace json Hold.trace.json Hold.tla`. TLC exits 13 and prints `Error: Temporal property EventuallyResolves was violated.`, then the behavior, ending `Back to state 1: <Busy line 8, col 12 to line 8, col 64 of module Hold>`, then `9 states generated, 8 distinct states found, 0 states left on queue.` The file it writes is 835 bytes and has the SHA-256 of the recorded `Hold.trace.json`, so the recorded trace is reproducible. {{run:RUN-tlc-lasso-json}}

The text trace and the JSON describe the same five things:

| TLC text trace | In `Hold.trace.json` |
|---|---|
| `State 1: <Initial predicate>` with `tries = 0`, `st = "held"` | `state[0]` is `[1, {"tries":0,"st":"held"}]` |
| `State 2: <Try line 7, col 12 to line 7, col 73 of module Hold>` | `action[0]` leaves state 1, label `Try`, arrives at state 2 |
| `State 3: <Busy line 8, col 12 to line 8, col 64 of module Hold>` | `action[1]` leaves state 2, label `Busy`, arrives at state 3 |
| `State 4: <Try line 7, col 12 to line 7, col 73 of module Hold>` | `action[2]` leaves state 3, label `Try`, arrives at state 4 |
| `Back to state 1: <Busy line 8, col 12 to line 8, col 64 of module Hold>` | `action[3]` leaves state 4, label `Busy`, arrives at `[1, {"tries":0,"st":"held"}]`: the closing step |

The file, with the repeated parts shortened (`L7` is `{"beginLine":7,"beginColumn":12,"endLine":7,"endColumn":73,"module":"Hold"}` and `L8` is the same with line 8 and end column 64):

```json
{"counterexample":{
  "action":[
    [[1,{"tries":0,"st":"held"}],    {"name":"Try", "location":L7}, [2,{"tries":1,"st":"pending"}]],
    [[2,{"tries":1,"st":"pending"}], {"name":"Busy","location":L8}, [3,{"tries":1,"st":"held"}]],
    [[3,{"tries":1,"st":"held"}],    {"name":"Try", "location":L7}, [4,{"tries":0,"st":"pending"}]],
    [[4,{"tries":0,"st":"pending"}], {"name":"Busy","location":L8}, [1,{"tries":0,"st":"held"}]]],
  "state":[[1,{"tries":0,"st":"held"}],[2,{"tries":1,"st":"pending"}],
           [3,{"tries":1,"st":"held"}],[4,{"tries":0,"st":"pending"}]]},
 "vars":["st","tries"]}
```

Four states are listed and there are four steps. The fourth step leaves state 4 and arrives at `[1, …]`, a state already in the list. That is all the file says about the loop. TLC's trace-exploration module for the same run says the same in its own terms: `_TTraceLassoStart = 1` and `_TTraceLassoEnd = 4`, the closing step's target and the last listed state. {{run:RUN-tlc-lasso-json}}

Other facts about the layout, all from the same file:

- A state is `[index, values]`. The index is 1-based, as in the text trace, and the values are keyed by variable name.
- `vars` lists the variables in declaration order (`st`, `tries`). The values are written in another order (`tries` first), so read them by name.
- A step is `[source, action, target]`, with both states written out in full. The action is `{name, location}`, and `location` is `{beginLine, beginColumn, endLine, endColumn, module}`; for `Try` they are the numbers the text trace prints (`line 7, col 12 to line 7, col 73`).

### 4.2 Reading rules

These turn the file into a stem and a cycle. They compare parts of the document with each other, so no JSON Schema can state them. `lasso-read.mjs` applies them to a file that has passed the schema. The draft schema's description points here. {{run:RUN-tlc-lasso-json}}

1. **Indexes.** `state` lists the positions 1 to n in order.
2. **Count.** A lasso has n steps. A file with n − 1 steps is a finite counterexample, an invariant violation or a deadlock, and is not a lasso. Any other count is not TLC's shape. A finite counterexample of one state has no steps at all (TLC writes `"action":[]`), and the schema refuses it.
3. **Chain.** Step p starts at state p, with the same index and values, and ends at state p + 1, except a lasso's last step, which rule 4 covers.
4. **Closing.** The last step starts at state n and ends at a listed state k, 1 ≤ k ≤ n, with the values listed for k. The loop starts at k.
5. **Shape.** The stem is the states 1 to k − 1 and the cycle is the states k to n; the closing step returns from n to k. When k is 1 there is no stem, as in Hold.
6. **Stutter and labels.** When k equals n the cycle is the one state n repeated: a stuttering lasso. A step takes an action only if it changes the state, because `WF` and `SF` count only steps that satisfy `<<A>>_v`, which needs the variables to change. A label is a hint, and the label of a closing step that stays on state n says nothing about which action ran (section 4.3).

On the Hold file the reader returns: a lasso of 4 states, k = 1, an empty stem, a cycle of states 1 to 4, not a stutter, and a closing step `Busy` from state 4 to state 1. The five lasso files in the manifest read as section 4.3 says, the recorded Hold file and the fresh one alike. Three recorded finite traces read as finite: two invariant violations [X RUN-tlc-doublespend, RUN-tlc-rtw3] and a deadlock [X RUN-tlc-doublespend]. Four files broken on purpose are rejected with the number of the rule they break. A recorded trace in which a value was edited in two of its copies is rejected at rule 3. A recorded trace in which every copy of one value was edited alike passes: the rules check the file, not the spec, and only INS-lasso's graph checks refuse it. {{run:RUN-tlc-lasso-json}}

### 4.3 The other lasso shapes

Hold shows a cycle with no stem and no stutter. The probes add the rest. Source for the table and the notes: {{run:RUN-tlc-lasso-json}}, config ids as named.

| Config | Shape | JSON: states, steps | Closing step | The text trace ends |
|---|---|---|---|---|
| `hold-180` | cycle only (Hold) | 4, 4 | state 4 to 1, `Busy` | `Back to state 1: <Busy …>` |
| `hold-nofair-180` | stutter at state 1 (Hold, no fairness conjunct) | 1, 1 | state 1 to 1, `UnnamedAction`, module `--TLA+ BUILTINS--`, every position 0 | `State 2: Stuttering` |
| `stem-cycle-180` | one-state stem, cycle closes on state 2; `Open` is parameterized | 5, 5 | state 5 to 2, `Busy` | `Back to state 2: <Busy …>` |
| `stem-stutter-180` | two-state stem, stutter at state 3 | 3, 3 | state 3 to 3, labeled `Try` | `State 4: Stuttering` |

- **A stutter adds no state.** The text trace shows an extra `State n+1: Stuttering`, but the JSON lists n states and closes with a self-loop on state n.
- **The label of that self-loop says nothing about which action ran.** In `hold-nofair-180`, where no step led to state 1, it is `UnnamedAction` in module `--TLA+ BUILTINS--`. In `stem-stutter-180` it is `Try`, the label of the step that entered state 3, although `Try` needs `st = "held"` and state 3 has `st = "pending"`: no real `Try` step leaves state 3.
- **A parameterized action carries its arguments.** `Open(0)` is `{"name":"Open", …, "context":{"t":0}, "parameters":["t"]}`. 1.8.0's text prints `Open(0)` and 1.7.4's prints `Open`. In the nine unmodified TLC traces of the manifest, `context` and `parameters` come together or not at all.
- **A label is not always the name in a fairness conjunct.** In the stem probes the fairness conjunct names `OpenAny` and the step is labeled `Open`.
- **TLC's trace-exploration module agrees for a back edge.** Its constants are `_TTraceLassoStart` 1 and `_TTraceLassoEnd` 4 for `hold-180`, and 2 and 5 for `stem-cycle-180`, which are the JSON's k and n. The two stutters have no such constants.
- **Which lasso TLC reports depends on the fingerprint function.** The probe has two equally valid lassos, one that opens with `Open(0)` and one with `Open(1)`. Run with `-fp` 0 to 15 (`stem-branches-sweep-180`), TLC reported `Open(0)` for 0, 1, 2, 7, 10, 12 and 14 and `Open(1)` for the other nine. With a fixed `-fp 7` (`stem-branches-fp-180`) it reported the same trace in 6 of 6 runs. Without `-fp`, TLC picks the function at random and prints it in the banner as `fp N`; the banners of the runs in this record show different values. Hold has one lasso: its file had the same bytes in all 3 of those runs, which used four workers, and equals the one-worker file.

### 4.4 What the file leaves out

- **The property.** The JSON does not name the violated property, the spec, the config, the flags or the tool version. 1.8.0's text headline names the property, `Error: Temporal property EventuallyResolves was violated.`; 1.7.4's does not, `Error: Temporal properties were violated.`
- **Fairness.** The file says nothing about which actions were enabled along the cycle or about weak or strong fairness. INS-lasso gets that from the graph and the spec.
- **Value types.** Only integers, strings and functions over strings, written as objects, appear in the recorded traces.
- **Any statement that it is a lasso.** Only rules 2 and 4 say so.

### 4.5 The draft schema and its checks

`schemas/drafts/lasso.schema.json` is JSON Schema 2020-12 with `$id` `urn:statespace:lasso@1`, which matches the id pattern of the published schemas. It requires `counterexample` and `vars`; at least one state and one step; pairs and triples as `prefixItems` tuples; and an action of `name` and `location`, with `context` and `parameters` optional. The envelope, the counterexample, the action and the location reject unknown keys; state values are left open. It cannot state rules 1 to 6. It accepts a finite trace as readily as a lasso, and only the reader tells them apart. {{run:RUN-tlc-lasso-json}}

W0-T02's keyword subset (`schemas/codegen/subset.mjs`) does not admit the draft. Its own check, run on the draft, reports two problems, both the keyword `prefixItems`, which the draft uses for pairs and triples (`$defs/indexedState` and `$defs/step`); the subset takes `items` as one schema. The loader publishes only `schemas/*.schema.json`, so the draft is outside the subset until it is published; section 8, risk 4, says what that means. {{run:RUN-tlc-lasso-json}}

Ajv in strict mode and Python `jsonschema` accept the recorded Hold trace and the fresh one, and agree on all 24 fixtures: 14 valid (5 lassos, 3 recorded finite traces, 2 hand-edited recorded traces, 4 files broken at a rule) and 10 rejected (the one-state finite trace, which has no steps, and nine files each broken in one structural way). All 8 text traces (four shapes on each jar) agree with the JSON of the same shape on state count, ending, step labels and integer and string values. {{run:RUN-tlc-lasso-json}}

## 5. Decision

1. **lasso@1 is TLC's file, as written** [D]. It is the 1.8.0 `-dumpTrace json` counterexample, with no wrapper and no field added by the course, described by `schemas/drafts/lasso.schema.json` and read by rules 1 to 6. W3-T09 publishes it as `schemas/lasso.schema.json` once the tuple question of section 8, risk 4, is settled.
2. **Import order** [D]. On the instrument origin (I6): the size and structure caps of ARCHITECTURE section 5.6, the parse, the schema, rules 1 to 6, and then INS-lasso's own checks on the graph: the path, the closure, the property and the fairness conjuncts. The rules read the file and do not know the spec, so a consistent file with invented steps passes them and fails at the graph.
3. **Name the property from the receipt** [D]. The file does not carry it. On 1.8.0 a receipt's `runs[].verdictLines` do. On 1.7.4 they do not, and INS-lasso tests each configured PROPERTY against the lasso instead.
4. **Treat a step's label as a hint** [D]. INS-lasso decides that a step takes an action from the two states, and it ignores the label of a closing step that stays on state n.
5. **Keep the schema strict** [D]. Unknown keys fail, in the spirit of the unknown-field rule for receipts (ARCHITECTURE section 10.3). A TLC bump then fails loudly and goes through the re-run diff of GATE-runs; it is not absorbed.
6. **Fixtures are files** [D]. GATE-conformance compares the lasso validator with TLC on committed TLC output, starting with the recorded Hold trace, which has a single lasso and is stable. A regenerated fixture records `-workers 1` and a fixed `-fp` in its argv, because on a spec with several valid lassos the one reported varies with the default fingerprint function (section 4.3).
7. **Hand-offs** [D]. W3-T09 builds the TypeScript reader from rules 1 to 6; `scripts/spikes/W0-S05/lasso-read.mjs`, with `fixtures/manifest.json` and `fixtures/negative/` beside it, is the reference and its tests. W3-T05's TLC lane asks for `-dumpTrace json <file>` and records the file in the receipt's `tlc.traceFile`. It keeps the exit code but never reads it alone: here a liveness violation exited 13 on both jars and an invariant violation exited 12 {{run:RUN-tlc-lasso-json}}.

## 6. Fallback

The plan's fallback is to import from TLC's text trace, the 1.7.4 path [X RUN-tlc-doublespend]. It holds for lassos.

- **The text carries the same loop.** 1.7.4 asked for `-dumpTrace json` stops with `Error: Error: unrecognized option: -dumpTrace` and exit code 1 (`hold-dumptrace-174`). Without it, 1.7.4 prints `State i: <label>` with TLA+ values, and ends with `Back to state k: <label>` or `State n+1: Stuttering`. Read by `readTextTrace`, those texts agree with the JSON of the same shape, as section 4.5 says. {{run:RUN-tlc-lasso-json}}
- **Rules 1 to 6 carry over.** The number of `State i:` lines is n, `Back to state k` gives k, and `State n+1: Stuttering` is a stutter at state n.
- **What it costs.** 1.7.4's headline names no property (section 4.4). Values are TLA+ source text, so the importer must parse sets, records and functions itself; the check parses only integers and quoted strings. 1.7.4 prints `Open` where 1.8.0 prints `Open(0)`, so the values of a step's parameters are lost.
- **A sturdier text.** With `-tool`, 1.7.4 frames the same facts in message codes: 2217 for each state, 2122 for the back edge (`1: Back to state: <Busy …>`), 2218 for a stutter (`2: Stuttering`) and 2116 for the headline (`hold-tool-174`, `hold-nofair-tool-174`). They are recorded for Hold and its stutter and not parsed here; W3-T05 may prefer them for a parser. {{run:RUN-tlc-lasso-json}}

## 8. Open risks

1. **A rolling pre-release.** The `v1.8.0` asset is re-published under the same tag (`labs/TOOLS.md`, section 2.4), and the SHA-256 pins only the course's copy. A later build may add a loop marker or change the labels; this record describes one build. A bump re-runs `record.mjs` and shows the diff (GATE-runs).
2. **Values.** Only integers, strings and functions over strings appear in the recorded traces. Sets, sequences, records, booleans, model values and large numbers were not exercised, so the schema leaves state values open.
3. **The schema alone is not enough.** It accepts a finite trace and a lasso alike, and rules 1 to 6 live in the reader. A consumer that stops at the schema would accept a non-lasso.
4. **Tuples.** The draft writes pairs and triples with `prefixItems`, and W0-T02's published subset excludes it (section 4.5), so the draft cannot be published as written. Either the subset gains fixed-length tuples, or lasso@1 is published with fixed-length arrays and open element schemas and the reader checks the positions. W0-T02 and W3-T09 settle which; the subset may also have changed since this record.
5. **Labels and fairness.** A step's label cannot always be matched to a fairness conjunct by name (`OpenAny` against `Open`), so INS-lasso needs the actions' definitions or the graph for "taken". W3-T09 owns that.
6. **Reach.** The probes have at most 9 distinct states. Larger graphs, longer traces, several violated properties and `-continue` were not examined. ARCHITECTURE section 5.6 sets no size cap for a lasso file; the Hold file is 835 bytes. {{run:RUN-tlc-lasso-json}}
7. **Which lasso.** TLC may report any of several valid lassos, so INS-lasso must accept any valid one, and a fixture check that regenerated traces would flake unless `-fp` is fixed.
8. **One platform** (owner action 3).
