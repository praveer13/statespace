# W0-S06 · Sandbox lanes and `--paranoid` timing

**Status:** decision record, awaiting owner review (1 h). The CI-runner, Docker Desktop and Codespaces lanes could not be run on this machine: each has a labeled stand-in here and an owner action below. The pack's three solution files are private and not in this repository (Method 1; owner action 5). **Date:** 2026-10-24 (machine clock). **Run:** [X RUN-bwrap-lanes], recorded in `runs/RUN-bwrap-lanes.json` with raw outputs in `runs/RUN-bwrap-lanes/`. **Implements:** the INS-bench-lean sandbox record (spine §9.2).

## Question

What do Lean's bubblewrap sandbox and comparator's `--paranoid` mode do on GitHub's CI runners, Docker Desktop and Codespaces, and how long does `--paranoid` take on the LAB-2 challenge pack? Under default Docker a sandbox failure exits like a rejection [X RUN-lean-bwrap-docker], so the record must also say how `statespace check` tells the two apart. Spine §9.2 adds a condition: no `lake check --paranoid` had passed on disk, so nothing may depend on it until a run shows one.

## In short

1. **A default container cannot start the sandbox, and the failure exits like a rejection.** `lake comparator` and `lake check` print `bwrap: No permissions to create new namespace, ...` and `error: Child exited with 1`, and exit 1 [X RUN-bwrap-lanes]. The sandbox starts when three things hold together: the container's seccomp profile allows `clone`, `unshare`, `mount`, `umount2` and `pivot_root` (Docker's default profile plus one rule; each of the five is needed), `/proc` is not masked (`--security-opt systempaths=unconfined`), and the image has a `/run/user` directory. `--cap-add SYS_ADMIN` alone does not help, because Docker's default profile blocks `pivot_root` whatever the capabilities are [X RUN-bwrap-lanes].
2. **Ubuntu 24.04 adds a host-level condition.** On a stock Ubuntu 24.04 machine AppArmor's restriction on unprivileged user namespaces stops the sandbox as shipped (`bwrap: setting up uid map: Permission denied`); it starts after `sysctl kernel.apparmor_restrict_unprivileged_userns=0`, or with the restriction on and an AppArmor profile that gives `/usr/bin/bwrap` the `userns` permission. In Docker on such a machine, container options alone never start it: Docker's AppArmor profile denies `mount`, and without that profile (`apparmor=unconfined`, `--privileged`) the restriction applies; the sysctl at 0 together with `apparmor=unconfined` starts it [X RUN-bwrap-lanes].
3. **None of the three named lanes was run for real.** Each has a labeled stand-in (result 6) and an owner action. The stock Ubuntu 24.04 virtual machine is the nearest stand-in for a GitHub-hosted runner; Docker Engine on Linux stands in for Docker Desktop and for a Codespace's container, and says nothing about their VMs, Apple silicon or the options Codespaces passes.
4. **`--paranoid` costs 2.92 s in `lake comparator` and 172.6 s in `lake check`** on the LAB-2 pack (medians, this machine): comparator replays the closure of the seven named theorems, 1,364 declarations, while `lake check --paranoid` replays the whole environment, 57,966 declarations, through six checkers one after another. The existing "about 3 s" [X RUN-lean-comparator] is the first figure, not the second. With one added line, `import Std`, `lake check --paranoid` does not finish in 6 GiB: its nanoda checker is killed and Lake prints a rejection for it (result 4).
5. **A sandbox failure is told from a rejection by evidence, never by exit code.** A line that starts `bwrap: ` (or Lake's own "was not found" line) means the sandbox failed and nothing was judged, and it outranks every other line, because a failed sandbox at the checker stage prints the same `<name> kernel rejected the solution` as a real rejection. The rule is implemented and tested in `scripts/spikes/W0-S06/classify.mjs` against 185 recorded Lake runs, none misread as the other kind (result 7).
6. **Four findings other tasks need:** LAB-2's default targets cannot all define `Acct`, `Bal` and `upd` (`lake check` loads them into one environment); the Bench image needs `/run/user`, `git` and `env`; the "about 3 s" statements should name `lake comparator`; and `lake check` replays Lean's whole environment, so it costs 53.6 s plain and 172.6 s with `--paranoid` on this pack, almost all of it for Lean's own declarations and not the pack's (result 3) [X RUN-bwrap-lanes].

## Method

1. **The pack, and the files it does not hold.** `scripts/spikes/W0-S06/pack/lab2/` is the public part of the LAB-2 whole-lab pack of `curriculum/S02-proof.md` §3: `challenge/Challenge.lean` extracted from the spec's code block (its statement hash is in the record), the whole-lab `comparator.json` (seven theorems, the three standard axioms), and the layout `lakefile.toml`, `lean-toolchain`, `lake-manifest.json`, with `autoImplicit false`. The pack's three solution files, `Solution.lean` (proofs of the seven theorems), `broken/Broken.lean` and `fixed/Fixed.lean`, are **not in this repository**: complete proofs of a lab's theorems are reference solutions, and those stay in the private companion repository (spine §11.1; ARCHITECTURE §13.5). The harness reads them from a directory named by `--solutions DIR` or `W0S06_SOLUTIONS` and stops with a message when neither is given. The record keeps their SHA-256 values in `inputs[]` with the role "private fixture, not published", and `scripts/spikes/W0-S06/private-fixtures.json` holds the same values [X RUN-bwrap-lanes]. The eight rejected solutions of the full probe are not stored either: `mutate.mjs` makes each from `Solution.lean` by one edit that finds a theorem by name, so it holds none of the lab's proofs (its one variant that writes proofs, `redef`, redefines `transfer` as the identity and proves three statements for that definition only), and the eight it makes are byte for byte the files that ran (`mutate.mjs --solutions DIR --verify`). The recorded configurations ran while these files were still inside the pack folder, as their `docker-run.argv` files show; the files are the ones the record's hashes name, because the last of them was modified at 2026-10-24T12:52:41Z and the first configuration started at 13:41:34Z (`runs/RUN-bwrap-lanes/private-fixtures-provenance.txt` lists each file's hash and modification time, and the result of comparing the eight that `mutate.mjs` makes with the files that ran) [X RUN-bwrap-lanes]. `Broken` and `Fixed` import `Solution`, because `lake check` loads every default target into one environment and fails when two define the same name. No approval to publish the proofs is recorded (owner action 5).
2. **The image.** `scripts/spikes/W0-S06/image/Dockerfile`: Ubuntu 24.04, bubblewrap from the Ubuntu archive, and Lean 4.35.0 through elan 4.2.4 installed as the non-root user `lab`, with the commands of `labs/TOOLS.md` §2.2, and a `/run/user` directory (result 1). Devcontainers run as a non-root user too.
3. **The profiles.** `run-matrix.sh` runs the probe in Docker under the option sets of results 1 and 4, one container at a time, `--memory=6g` unless a profile sets its own cap; the `docker run` argv of each run is written beside its output. It copies the private solution files to a temporary directory, mounts that read-only at `/solutions`, and removes it when it exits. `make-seccomp-profile.mjs` builds the narrow profile: Docker's default seccomp profile for the engine in use plus one allow rule, and, for the ablation, the same with one of its five system calls left out.
4. **The probe.** `lane-probe.sh` copies the pack, lays the private solution files over it, runs two canaries (bubblewrap alone, and bubblewrap with Lake's own flag set around `lean --version`), `lake build`, and then `lake comparator`, `lake comparator --paranoid`, `lake check` and `lake check --paranoid`, each with the sandbox on and, as a control, off (`--inadvisably-no-sandbox`). Every step records its wall time, its CPU time, the 1-minute load average at its start and the container's memory high-water mark so far. In the profile "narrow" it runs the comparator commands five times and the sandboxed `lake check` commands three (the unsandboxed ones once); elsewhere once. It also runs the pack with eight deliberately broken solutions (made by `mutate.mjs`), with the exit-2 starts, and with faults injected through a `COMPARATOR_BWRAP` shim (`bwrap-shim.sh`) that adds a bind mount whose source does not exist to the N-th bubblewrap call, so that the real bubblewrap fails with its own diagnostic at that phase. The same shim, without a fault, logs Lake's argv and the time of each phase [X RUN-bwrap-lanes].
5. **The classifier.** `classify.mjs` reads a run's argv, exit code and merged output; `expectations.mjs` states what each step was built to show, written from how the step is constructed and from exploratory runs made before the recorded run; `assemble-run.mjs` compares the two and writes the run record. The sandbox state of every local container profile was predicted before the recorded run.
6. **What a lane's stand-in is.** Nothing was run on a GitHub-hosted runner, on Docker Desktop or in a Codespace. The container profiles ran on this machine's Docker Engine; `vm/run-vm.sh` boots Canonical's Ubuntu 24.04 cloud image under QEMU with KVM and runs the probe on the virtual machine and in Docker on it. Each stand-in's limits are in result 6, and the record's `environment.emulation` lists them.

## Results

### 1. What starts the sandbox in a container

Lake runs bubblewrap with `--unshare-all`, covers `/home`, `/root` and `/run/user` with a tmpfs and mounts a fresh `/proc` and `/dev` (result 2). In a container that asks for more than the default grants. The table lists the local container profiles with the first bubblewrap line of the Lake-shaped canary; 24 of 24 predictions made before the recorded run held [X RUN-bwrap-lanes].

| profile | docker run options | canary | sandbox | first bubblewrap line |
|---|---|---|---|---|
| cap-sys-admin | `--cap-add SYS_ADMIN` | failed | failed | bwrap: pivot_root: Operation not permitted |
| cap-sys-admin-systempaths | `--cap-add SYS_ADMIN --security-opt systempaths=unconfined` | failed | failed | bwrap: pivot_root: Operation not permitted |
| default | `(none)` | failed | failed | bwrap: No permissions to create new namespace, likely because ... |
| narrow | `--security-opt seccomp=<narrow profile> --security-opt systempaths=unconfined --security-opt apparmor=unconfined` | on | on |  |
| narrow-no-apparmor | `--security-opt seccomp=<narrow profile> --security-opt systempaths=unconfined` | on | on |  |
| narrow-no-run-user | `--security-opt seccomp=<narrow profile> --security-opt systempaths=unconfined --security-opt apparmor=unconfined --tmpfs /run` | failed | failed | bwrap: Can't mkdir /run/user: Read-only file system |
| narrow-no-systempaths | `--security-opt seccomp=<narrow profile> --security-opt apparmor=unconfined` | failed | failed | bwrap: Can't mount proc on /newroot/proc: Operation not permitted |
| narrow-root | `--security-opt seccomp=<narrow profile> --security-opt systempaths=unconfined --security-opt apparmor=unconfined --user 0` | on | on |  |
| privileged | `--privileged` | on | on |  |
| seccomp-unconfined | `--security-opt seccomp=unconfined` | failed | failed | bwrap: Can't mount proc on /newroot/proc: Operation not permitted |
| systempaths-unconfined | `--security-opt systempaths=unconfined` | failed | failed | bwrap: No permissions to create new namespace, likely because ... |
| unconfined-both | `--security-opt seccomp=unconfined --security-opt systempaths=unconfined` | on | on |  |

- **Default Docker blocks the start.** Its seccomp profile allows `clone` only without namespace flags, answers `clone3` with an error that makes libc fall back, allows `unshare`, `mount`, `umount2` and `setns` only when the container holds `CAP_SYS_ADMIN`, and does not allow `pivot_root` at all (rules read in Docker's default profile for 29.1.3, SHA-256 `01536f1d1df938ae611eba20d6349e0de7a99b6ecdee1549427a0b01b8301e28` [V]).
- **Three things are needed together.** `seccomp=unconfined` alone stops at `/proc` ("Can't mount proc"), `systempaths=unconfined` alone stops at the namespace, and the two together start it; with a `/run/user` hidden (`--tmpfs /run` over the image's directory) the start stops at `bwrap: Can't mkdir /run/user: Read-only file system`, because Lake covers `/run/user` with a tmpfs and bubblewrap cannot create the mount point in a read-only root [X RUN-bwrap-lanes]. The Lake-shaped canary fails there while the minimal one passes, which is why the canary carries Lake's flags.
- **`CAP_SYS_ADMIN` is not the lever.** With it, with or without unmasked system paths, the start stops at `bwrap: pivot_root: Operation not permitted`.
- **The narrow profile is Docker's default plus five calls**, and each of the five is needed:

| added rule | sandbox | first bubblewrap line |
|---|---|---|
| `clone`, `mount`, `pivot_root`, `umount2`, `unshare` (the narrow profile) | on | |
| `mount`, `pivot_root`, `umount2`, `unshare` (no `clone`) | failed | bwrap: No permissions to create new namespace, likely because ... |
| `clone`, `mount`, `pivot_root`, `umount2` (no `unshare`) | failed | bwrap: unshare user ns: Operation not permitted |
| `clone`, `pivot_root`, `umount2`, `unshare` (no `mount`) | failed | bwrap: Failed to make / slave: Operation not permitted |
| `clone`, `mount`, `pivot_root`, `unshare` (no `umount2`) | failed | bwrap: unmount old root: Operation not permitted |
| `clone`, `mount`, `umount2`, `unshare` (no `pivot_root`) | failed | bwrap: pivot_root: Operation not permitted |

- **Root and non-root both start**, with Docker's default capabilities, whose bounding set lacks `CAP_SYS_ADMIN` (`cap_sys_admin_in_bounding_set` is false in the narrow configurations' facts); `--privileged` starts too. So the sandbox needs no capability the container lacks. It needs the filter and the masks out of its way [X RUN-bwrap-lanes].
- **What the narrow profile gives up.** Against `seccomp=unconfined` it keeps every other syscall the default blocks (it adds one rule, naming five calls, to Docker's 31 and removes none). `systempaths=unconfined` "turns off confinement for system paths (masked paths, read-only paths)" [V] for every process in the container, which matters most to a root process. `apparmor=unconfined` removes Docker's AppArmor profile on a host that has one: on the Ubuntu machine of result 6 the container's process label read `unconfined` instead of `docker-default` [X RUN-bwrap-lanes]. None adds a capability. The default devcontainer does none of this (decision 5).
- **No AppArmor here.** This machine's security modules are capability, landlock, yama and bpf, so `apparmor=unconfined` changed nothing in these runs; result 6 has the Ubuntu runs that do exercise it.

The first bubblewrap line names the cause, so `statespace doctor` can print the matching hint (every line below is recorded, except the last row's, which is Lake's own text read in its source at v4.35.0 [V]):

| first line of the failure | what it means | what changes it |
|---|---|---|
| `bwrap: No permissions to create new namespace, likely because the kernel does not allow non-privileged user namespaces` | the container's seccomp profile blocks `clone` with namespace flags (default Docker), or the host forbids unprivileged user namespaces | the opt-in profile; on a host, user namespaces enabled |
| `bwrap: Can't mount proc on /newroot/proc: Operation not permitted` | the container masks `/proc` paths | `systempaths=unconfined` |
| `bwrap: Can't mkdir /run/user: Read-only file system` | the image has no `/run/user` | create the directory in the image |
| `bwrap: pivot_root: Operation not permitted` | seccomp blocks `pivot_root`, which Docker's default profile does even with `CAP_SYS_ADMIN` | allow it, as the opt-in profile does |
| `bwrap: unshare user ns: Operation not permitted`, `bwrap: Failed to make / slave: Operation not permitted`, `bwrap: unmount old root: Operation not permitted` | seccomp blocks `unshare`, `mount` or `umount2` | allow them |
| `bwrap: setting up uid map: Permission denied`, `bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted` | Ubuntu 24.04's AppArmor restriction on unprivileged user namespaces | on the host, the sysctl or an AppArmor profile for the binary (result 6) |
| `bwrap: Failed to make / slave: Permission denied` | Docker's AppArmor profile denies `mount` | `apparmor=unconfined` in the container (and, on an Ubuntu host, the line above) |
| `error: ... needs ... to sandbox the code it checks, and it was not found.` (exit 2) | bubblewrap is not installed or not on `PATH` | install it |
| `error: ... sandboxes the code it checks with bwrap, which needs Linux namespaces.` (exit 2) | the platform is not Linux | use the devcontainer |

### 2. What Lake asks of bubblewrap

The shim logged every bubblewrap call of `lake comparator --paranoid` (11 calls) and `lake check --paranoid` (8 calls) [X RUN-bwrap-lanes]. Every call has the same flag family, in this order (Lean 4.35.0):

```
--ro-bind / /
  --tmpfs /home
  --tmpfs /root
  --tmpfs /run/user
  --tmpfs /tmp
  --dir /tmp/home
  --dev /dev
  --proc /proc
  --clearenv
  --ro-bind <work>/lab2 <work>/lab2
  --ro-bind <elan>/toolchains/leanprover--lean4---v4.35.0 <elan>/toolchains/leanprover--lean4---v4.35.0
  --ro-bind <elan>/toolchains/leanprover--lean4---v4.35.0 <elan>/toolchains/leanprover--lean4---v4.35.0
  --bind <work>/lab2/.lake <work>/lab2/.lake
  --setenv PATH <elan>/bin:<elan>/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
  --setenv LEAN_ABORT_ON_PANIC 1
  --setenv HOME /tmp/home
  --unshare-all
  --die-with-parent
  --new-session
  --share-net
  --chdir <work>/lab2
```

- The first call (`lake env` or `lake resolve-deps`) adds `--share-net`; every later call has no network. Only `.lake` is writable.
- `/home`, `/root` and `/run/user` must exist, because Lake covers each with a tmpfs; `/run/user` is the one a container lacks.
- A `lake-manifest.json` must exist (exit 2 otherwise; the pack ships one). Lake also needs `git` and `env` on `PATH` (exit 2 otherwise; read in Lake's source at v4.35.0, not run) [V].
- A toolchain that lives under `/home` is bound back by Lake (`--ro-bind <toolchain> <toolchain>`), so a native elan install works.

### 3. How long `--paranoid` takes on the LAB-2 pack

Seconds, min / median / max (n runs); wall time, with the median CPU time in brackets; configuration `local-narrow`.

| command | sandbox on | sandbox off |
|---|---|---|
| `lake comparator` | 1.43 / 1.44 / 1.57 (n=5) [CPU 1.25] | 1.42 / 1.43 / 1.45 (n=5) [CPU 1.23] |
| `lake comparator --paranoid` | 2.90 / 2.92 / 2.94 (n=5) [CPU 3.35] | 2.86 / 2.87 / 2.90 (n=5) [CPU 3.32] |
| `lake check` | 53.5 / 53.6 / 53.6 (n=3) [CPU 53.5] | 54.1 / 54.1 / 54.1 (n=1) [CPU 54.1] |
| `lake check --paranoid` | 171.2 / 172.6 / 173.0 (n=3) [CPU 285.5] | 166.6 / 166.6 / 166.6 (n=1) [CPU 275.6] |

- **`lake comparator --paranoid`** takes 2.92 s against 1.44 s without `--paranoid`: it exports the closure of the seven named theorems (1,364 declarations) and replays it through six checkers. This is the "about 3 s" of the existing documents [X RUN-bwrap-lanes].
- **`lake check --paranoid`** takes 172.6 s against 53.6 s for `lake check`: it exports and replays the whole environment, 57,966 declarations, most of it Lean's own library, through six checkers one after another. Almost all of that is not the pack's own: the closure of all seven pinned theorems, with every library lemma they use, is 1,364 declarations, so a project that defines little still pays most of it [X RUN-bwrap-lanes].

The phases of one `lake check --paranoid` run, with the shim logging (seconds):

| call | phase | seconds |
|---|---|---|
| 1 | lake resolve-deps | 0.03 |
| 2 | lake check | 10.9 |
| 3 | leanchecker-paranoid | 43.4 |
| 4 | lean4lean | 50.8 |
| 5 | nanoda_bin | 8.05 |
| 6 | con-leche | 7.86 |
| 7 | con-ron | 5.04 |
| 8 | leanchecker | 36.0 |
| | total | 162.1 |

- **Three of the six checkers account for most of it.** `lean4lean`, `leanchecker-paranoid` and the default kernel take 130.2 s of the 162.1 s; `nanoda`, `con-leche` and `con-ron` take 20.9 s together [X RUN-bwrap-lanes].
- **The sandbox's cost is small, and for `lake check --paranoid` not pinned down.** With the sandbox on, `lake comparator` took 0.02 s more (5 runs each), `lake comparator --paranoid` 0.05 s more (5 runs each) and `lake check` 0.53 s less (3 runs on, 1 off) than with it off. `lake check --paranoid` took 5.91 s more (3 runs on, 1 off), 3.5 percent, more than the 1.75 s spread of its runs with the sandbox on; with one run off, that cannot be told from the host's load at that moment [X RUN-bwrap-lanes].
- **`--paranoid` uses more than one thread.** `lake check --paranoid` used 285.5 s of CPU in 172.6 s of wall time, because some checkers run several threads (Lake's configuration file for nanoda sets `num_threads` to 4: `src/lake/Lake/CLI/Check.lean` at v4.35.0 [V]); `lake check` without `--paranoid` is one thread's work, 53.5 s of CPU in 53.6 s. CPU count therefore matters for `--paranoid` (result 4) [X RUN-bwrap-lanes].
- **Wall time moves with the machine's load.** The 1-minute load average at the start of the primary configuration's steps ran from 3.35 to 6.30 on 20 CPUs, other jobs sharing the host, and the spread of the repeats is in the table.
- **The primary configuration's container reached 1.23 GiB** (the high-water mark of its cgroup after `lake check --paranoid`, page cache included) [X RUN-bwrap-lanes].

### 7. Telling a sandbox failure from a rejection

Lake itself separates "could not start" from a judgment: its `cannotRun` returns exit 2, and its source calls that "a failure to even start, which is distinct from a judgment" (`src/lake/Lake/CLI/Check.lean` at v4.35.0, read 2026-10-24 [V]). A bubblewrap failure that happens after Lake has started is not caught that way. It reaches Lake as a child that exited non-zero, and Lake throws `Child exited with 1`, which is exit 1, the code of a judgment [X RUN-bwrap-lanes]. A checker that bubblewrap cannot start is worse: Lake prints `<name> kernel rejected the solution` for any non-zero exit of the sandbox command, so a failed sandbox at the checker stage prints the same two lines as a real kernel rejection, and only a `bwrap:` line before them differs [X RUN-bwrap-lanes].

Six lookalikes that a rule built on exit codes or on "Child exited" lines would get wrong, all recorded:

1. **A failed sandbox that prints a kernel rejection.** With bubblewrap made to fail when Lake starts the first checker, the output is `bwrap: Can't find source path ...`, then `error: Lean default exited with 1` and `Lean default kernel rejected the solution`, and the exit code is 1 (`inject-comparator-call6`, and `inject-check-call3` for `lake check`). Under `--paranoid`, with the fault at the third of six checkers, five checkers print "accepts the solution" and one prints `nanoda kernel rejected the solution` after its `bwrap:` line (`inject-comparator-paranoid-call8`), which reads as a checker disagreeing [X RUN-bwrap-lanes]. The faults are injected through the shim (the real bubblewrap fails at setup with its own diagnostic); no natural fault was found that strikes only at those phases.
2. **A project that does not build** prints `error: Child exited with 1` after `error: build failed` and exits 1: it is a rejection, and the sandbox worked.
3. **A missing theorem** crashes the exporter: `PANIC at LeanExport.dumpConstant ... Constant xfer_self not found in environment.` and `error: Child exited with 134`, exit 1. It is a rejection of the solution (it does not contain the named theorem), and the sandbox worked.
4. **A real kernel rejection is not always exit 1.** Under `--paranoid`, with a proof the elaborator accepted while the kernel check was off, `leanchecker-paranoid`, `con-leche`, `con-ron` and the default kernel exit 1, `lean4lean` aborts with 134 on a PANIC, and `nanoda` exits 101 on a Rust panic; Lake prints `<name> kernel rejected the solution` for every one of them [X RUN-bwrap-lanes]. Only the first failing checker's code reaches the `error: <name> exited with N` line.
5. **A toolchain that cannot run inside the sandbox** (the NixOS loader in the measuring host's first attempt [X RUN-lean-toolchain]) prints `[nix-ld] FATAL ...` and `error: Child exited with 134`, with no `bwrap:` line. The run says nothing about the sandbox's start and nothing about the proof; only the canary settles it.
6. **A checker killed for memory prints a kernel rejection.** With `import Std` added to the pack in a 6 GiB container, the kernel's out-of-memory killer ended `nanoda_bin`, the other five checkers accepted, and Lake printed `nanoda kernel rejected the solution`, then `error: nanoda exited with 137`, and exited 1 (`local-narrow-std`, step `check-paranoid`; the kernel's report is in `kernel-oom.txt` beside it) [X RUN-bwrap-lanes]. There is no `bwrap:` line and the sandbox worked, and there is no verdict either, because nanoda did not finish. Exit 137 and 143 (SIGKILL and SIGTERM) on that error line read as a kill; a checker that rejects by crashing exits 134 or 101 (lookalike 4).

The rule, then, is positive evidence for every claim, in this order (`scripts/spikes/W0-S06/classify.mjs`, with `classify.test.mjs`):

1. **The sandbox failed** when the merged output of a run that did not exit 0 has a line that starts `bwrap: `, bubblewrap's own diagnostic (on a run that exits 0 such a line is a warning: bubblewrap 0.9.0 prints one when an option is given twice [V]), or Lake's "needs `bwrap` ... was not found" line (exit 2) or its "which needs Linux namespaces" line (exit 2). That outranks every other line, including a rejection line, because a failed sandbox judged nothing.
2. **The sandbox is off** only when the argv the CLI built holds `--inadvisably-no-sandbox` and Lake printed "WARNING: Sandbox disabled, this run is not trustworthy."; the two must agree [X RUN-bwrap-lanes].
3. **Rejected** needs a line from a closed list: a statement or constant mismatch, "Illegal axiom detected" (comparator) or "Axiom ... is not permitted" (`lake check`), `<name> kernel rejected the solution` (unless the `error: <name> exited with N` line, which names the first failing checker, has N = 137 or 143: a checker the kernel killed, which is no verdict), a named theorem missing from the solution, or a build that failed with Lean diagnostics.
4. **Accepted** needs exit 0, at least one accept line and no `error:` line.
5. **Anything else is no verdict**, whatever the exit code was, and the sandbox state is then unknown until the canary settles it.

The closed list holds the rejection lines that recorded runs printed. Lake's source holds judgments of a solution that no recorded run printed: a constant not found in the challenge or in the solution, a constant kind that does not match, a solution constant that is not a theorem or not a definition (`src/lake/Lake/Check/Compare.lean` and `Axioms.lean` at v4.35.0 [V]). The rule reads them as no verdict, which is the safe direction: the learner sees the evidence lines and the receipt carries no stamp. The test file pins that behavior, and W2-T32 adds each line to the list when a real run has printed it, because the exact text (the `error: ` prefix included) is unverified until then.

The unit tests (20, in `classify.test.mjs`) copy their fixtures from executed logs in `research/` and check each fixture verbatim against its file, and 4 of them run the rule over outputs of this recording. Over the recording, 185 of the 185 classified Lake runs have an expectation written from how the step was built, and 184 match, 0 classifier mismatches; 11 of them were built to be rejected and 76 to fail in the sandbox, and none was read as the other kind [X RUN-bwrap-lanes]. The one that is not a match is a prediction about resources and not a misreading: local-narrow-std check-paranoid was predicted to accept and a checker was killed for memory (result 4); the record keeps the prediction, the reading and the miss.

## Decision

1. **The sandbox stays recorded as `on`, `off` or `failed`, and is never required** (spine §9.2; the "Comparator sandbox" decision in `docs/DECISIONS.md`). A receipt's `environment.sandbox` is `on` when the check's verdict-producing runs ran inside bubblewrap, `off` when they ran with `--inadvisably-no-sandbox`, and `failed` when the sandbox did not start and no unsandboxed re-run followed; `sandboxDetail` holds the first bubblewrap line, and keeps it when a re-run turned the state into `off`. A check whose state is `failed` carries no verdict (`runs[].verdict: error`), as SP-2.8 asks [D].
2. **`statespace check` tells a sandbox failure from a rejection by the rule of result 7**, applied to the merged output of every `lake check` and `lake comparator` call: sandbox failed on a `bwrap: ` line or on Lake's two exit-2 sandbox messages; off only when the flag and Lake's warning agree; rejected only on a line of the closed list; accepted only on exit 0 with an accept line and no `error:` line; otherwise no verdict. `runs[].verdictLines` keeps every line the rule used, verbatim, including the `bwrap:` line that precedes what a rejection would print, so the tab's TypeScript parser, which re-derives each verdict from `verdictLines` (ARCHITECTURE §10.3), applies the same rule. The reference implementation and its tests are in `scripts/spikes/W0-S06/`; W2-T32 ports it to Python and TypeScript and runs both over the recorded outputs: `runs/RUN-bwrap-lanes.json`, `configs[].steps[]` where `expected` is set, each with its `argv`, `exit_code` and output file.
3. **`statespace doctor` runs the Lake-shaped canary**: bubblewrap with the flags of Lake 4.35.0 (result 2) around the toolchain's `lean --version`, 28 ms in a working container [X RUN-bwrap-lanes]. Exit 0 with the Lean banner is `on`; anything else is `failed`, with the first output line as the detail and the matching hint of result 1. The canary also settles a Lake run that left the state unknown (an exit code with no sandbox evidence, such as a loader that cannot run inside the sandbox). A Lean bump re-derives the flags with the shim, and GATE-runs re-records the run.
4. **A learner chooses to run without the sandbox, once; CI chooses in its configuration.** S02 §3 says a failed check re-runs with `--inadvisably-no-sandbox` on its own. Because the sandbox is the one thing between Lean that an agent wrote and the learner's files, and `labs/README.md` §4.4 already tells the learner to read that Lean first, the re-run needs a recorded choice: `statespace doctor` explains the failure and asks, or the learner passes `--sandbox=off`; the choice is kept in the lab repository's local settings, every receipt then says `off`, and an agent or script never makes it. A failure that is not positively a sandbox failure never triggers a re-run. CI sets `--sandbox=auto` (try the sandbox, re-run without it after a positively identified failure, record which), because it runs course-owned code [D].
5. **The devcontainer does not relax confinement by default; the opt-in profile is the narrow one.** Where Docker's default confinement applies, `statespace doctor` reports `failed` in the default devcontainer (result 1; Codespaces and Docker Desktop are unmeasured, owner actions 3 and 4), and decision 4 applies. The documented opt-in, for a Docker host without AppArmor's restriction on user namespaces, is the devcontainer's `securityOpt` set to `seccomp=<the narrow profile>`, `systempaths=unconfined` and `apparmor=unconfined`; `labs/README.md` §4.4 and `labs/TOOLS.md` §4 should name what each relaxes (result 1). The Bench image needs `/run/user`, `git`, `env` and bubblewrap. On an Ubuntu 24.04 host the options are not enough: the host's restriction (the sysctl, or an AppArmor profile for the binary) has to be lifted too, and a Codespace or Docker Desktop user cannot lift a host setting (result 6). `seccomp=unconfined` is the simpler fallback if the profile file cannot be referenced from `devcontainer.json` in Codespaces; it relaxes more.
6. **`--paranoid` goes where its cost buys something.** `lake comparator --paranoid` (2.92 s) is the six-checker replay of the pinned theorems' closure, which is what the "6 checkers" stamp qualifier and SEAM-15 need; it can run at every Defence step and in CI's fast lane. `lake check --paranoid` (172.6 s here) replays the whole environment, so run it once per lab at LAB-2.7 and the Defence over all default targets together, with the progress lines Lake prints for each checker and a first line that says about three minutes on a fast machine (five on two slow cores, result 4), and in CI's nightly lane. A lab whose solution imports `Std` cannot run `lake check --paranoid` in 6 GiB (result 4): for such a lab the Defence runs `lake comparator --paranoid`, and `lake check --paranoid` waits for a measurement of its memory (owner action 4). Every stated duration names its hardware and cites the run.
7. **Copy about the three lanes stays tagged until they are recorded.** Learner copy and the docs may state what was measured on Docker Engine on Linux and on stock Ubuntu 24.04, labeled so, and must keep `{{run:RUN-bwrap-lanes}}` on any sentence about Docker Desktop, Codespaces or a CI runner until owner actions 2 to 4 are done.

## Fallback

If a lane cannot start the sandbox, the receipt records `failed` or, by the learner's recorded choice, `off`; the sandbox is never required, and macOS and Windows learners use the devcontainer (spine §9.2). If `lake check --paranoid` proves too slow on learners' machines (owner action 4 and 3 measure it on real ones), LAB-2.7 and the Defence run `lake comparator --paranoid` with `lake check` and keep `lake check --paranoid` for the nightly lane. If the narrow profile cannot be referenced from `devcontainer.json` in Codespaces, the opt-in offers `seccomp=unconfined` in its place; if neither takes effect there, Codespaces stays at `off` by choice. If a Lean bump changes Lake's output, the closed list of rejection lines fails closed, to "no verdict", never to a verdict.
