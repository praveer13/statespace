# W0-S13 · Trace validation by TLC's trace-module method

**Status:** decision record. **Task:** W0-S13, adopted by the owner on 2026-10-25 (decision Q-2). **Date:** 2026-10-25 (UTC). **Run:** [X RUN-tlc-tracemodule], the ID W0-S13 proposes and W0-T10 registers. **Spike files:** `scripts/spikes/W0-S13/`. **Owner review:** 0.5 h.

## 1. Question

curriculum/S08-effects.md (section 13, issue 1) reports that trace validation is unspiked, and that the A2 review found TLC's trace-loading flag did not round-trip. S8 specifies the trace-module method of Cirstea, Kuppe, Loillier and Merz (arXiv 2404.16075 v2, section 4.2) as CCF applies it (Howard et al., NSDI 2025, arXiv 2406.17455 v2, section 6). Three questions follow:

1. Does the method run on the pinned `tla2tools` 1.8.0 with only the modules the jar bundles?
2. What does it report for an accepted, a rejected and a partial NDJSON trace?
3. What should `statespace trace validate` (W5-T14) take, print and write into a receipt?

**Short answer.** Yes, with two changes to the published idiom. The pinned jar bundles `Json` (with `ndJsonDeserialize`) and `TLCExt`, but not `IOUtils`, so the log's path goes into the TLC config as a constant. And the verdict must come from the line counter, not from TLC's search depth, because the course's trace module lets TLC fill in steps the log does not show. On a toy outbox, the accepted trace matched 11 of 11 lines (35 distinct states). The ack-before-store mutant was rejected at line 8, its first `Ack` (23 distinct states). A log cut after 8 lines matched all 8 (26 distinct states): the method accepts every prefix of a behavior, so only an end record can tell a whole log from a cut one. The trace-loading flag replays TLC's own traces, not implementation logs, and its JSON form fails on any state that holds a set. [X RUN-tlc-tracemodule]

## 2. Method

### 2.1 The method as published

Both sources were read on 2026-10-25 [V].

- **The paper** (https://arxiv.org/abs/2404.16075, v2, section 4.2). A trace specification extends the system specification together with `Json` and `IOUtils`, and reads the log with `ndJsonDeserialize(IOEnv.TRACE_PATH)`. A line counter `l` walks the log. `IsEvent(e)` is conjoined to every constrained action and advances `l`, so every step consumes a line. Success is the postcondition `TraceAccepted`, `TLCGet("stats").diameter - 1 = Len(Trace)`. The paper says not to check the constrained spec for deadlocks. It also says a failed validation yields no counterexample, only maximal behaviors that match a prefix of the log, and that incomplete logs can make a wrong trace pass.
- **CCF** (github.com/microsoft/CCF at commit `65f712da90e5`, 2026-10-23: `tla/consensus/Traceccfraft.tla` and `.cfg`, `tla/tlc.py`). The trace spec extends `ccfraft`, `Json` and `IOUtils`, and takes the path from `IOEnv.CCF_RAFT_TRACE`. The config names `SPECIFICATION TraceSpec`, `VIEW TraceView`, the temporal property `TraceMatched` (a check on `TLCGet("queue")`), `POSTCONDITION TraceMatchedNonTrivially` (`TLCGet("stats").diameter = Len(TraceLog)`), `ACTION_CONSTRAINT Termination` and `CHECK_DEADLOCK FALSE`. Two `ASSUME`s require breadth-first mode and one worker. Coarser implementation steps are matched with action composition (`\cdot`). The runner `tlc.py` puts `CommunityModules-deps.jar` on the classpath, sets `-Dtlc2.tool.impl.Tool.cdot=true`, and for trace validation sets `-Dtlc2.tool.queue.IStateQueue=StateDeque` (depth-first order).

### 2.2 What this spike built

All under `scripts/spikes/W0-S13/`.

- **`specs/ToyOutbox.tla`**, a toy outbox in S8's vocabulary. `Commit` records the command and its intent in one transaction. `Dispatch` is the relay: it sends the intent with the key minted for it, and sends again while no result is stored, so the provider may see the key twice. `Accept` is the provider: it charges unless its table holds the key, then replies. Then come `Persist` and `Ack`. There are no crashes. It is a probe, not the reference model W5-T02 authors.
- **`specs/TraceValidation.tla`**, the part of a trace module that does not depend on the spec: the constant `TraceFile`, the line counter `l`, `TraceLog`, `Line`, `IsEvent(e)`, `Unlogged` (a step that consumes no line), the end record, and the verdict.
- **`specs/ToyOutboxTrace.tla`**, the trace module. There is one disjunct per logged worker event: it takes the spec's action and constrains it by the fields the line records. An implementation-only line (`TimerArmed`) is a stuttering step. The end record may be the last line only. The provider's `Accept` is not logged, so TLC searches for it as a step that consumes no line, as S8.L6 specifies.
- **`specs/ToyOutboxTraceComposed.tla`**, the same module in the paper's shape: `Accept` is composed into the `Persist` that needs its reply, so every step consumes a line.
- **The verdict.** A state constraint, `TraceReach`, keeps the highest `l` of any state TLC generates in a named register. TLC 1.8.0 accepts a register name only with the prefix `s:` and keeps one value per worker (section 4.2). The postcondition `TraceVerdict` folds the registers once the search is over. It prints one line, `<<"trace-validation", [verdict |-> …, lines |-> …, matched |-> …, first_unmatched |-> …, end_record |-> …, diameter |-> …, paper_accepted |-> …]>>`, and holds only for an accepted trace. A trace is rejected when the highest `l` is at most the line count. Otherwise it is accepted if its last line is the end record, and partial if not. `paper_accepted` evaluates the paper's postcondition beside it, for comparison only.
- **The config**, which `record.mjs` writes for each trace, as the tool would: `CONSTANTS <constants>  TraceFile = "<trace>"`, `SPECIFICATION TraceSpec`, `CONSTRAINT TraceReach`, `POSTCONDITION TraceVerdict`, `CHECK_DEADLOCK FALSE`. Every run uses `-workers 1`, except the two four-worker cross-checks (`rejected-w4`, `register-prefixed-w4`).
- **`tv.mjs`**, the pieces W5-T14 ports: the NDJSON lint, the config, the parse of TLC's output, the message to quote when TLC stops without a verdict (section 4.9), and the line the command prints.
- **The traces**, written by hand in the shape a simulator would emit (W5-T15 builds the simulator). The three named traces are in `traces/`; the probes are in `traces/probes/`.

To reproduce, with Docker, the image `eclipse-temurin:21-jre`, Node and `python3` (the versions are in section 3):

```
node scripts/spikes/W0-S13/record.mjs
```

`record.mjs` refuses a jar whose SHA-256 is not the pin, runs each configuration in a fresh container with no network, checks every result it states, and rewrites `runs/RUN-tlc-tracemodule.json` and `runs/RUN-tlc-tracemodule/`. All 265 checks passed on 38 configurations [X RUN-tlc-tracemodule].

## 4. Results

### 4.1 What the jars bundle

The 1.8.0 jar ships `Json.tla` with `ndJsonDeserialize`, `TLCExt.tla`, and their Java overrides. It does not ship `IOUtils.tla`, so the paper's and CCF's `IOEnv.TRACE_PATH` stops the parse: `Cannot find source file for module IOUtils imported in module PaperIOEnv.`, exit code 150 (config `paper-ioenv`). The 1.7.4 jar ships none of the three, and the trace module stops on the first: `Cannot find source file for module Json imported in module TraceValidation.`, exit code 150 (config `accepted-174`). So the 1.8.0 jar runs the method with no extra jar, as long as the path is a config constant. The 1.7.4 text-trace fallback cannot run it at all without the CommunityModules jar, which this spike did not try. [X RUN-tlc-tracemodule]

### 4.2 The three traces

Each log has two commands. In each, c1 is sent twice with the same key, and a `TimerArmed` line is an implementation-only event. The provider's steps are not logged. The rows are from configs `accepted`, `rejected` and `partial`, each run three times with the same verdict and counts; the wall time is the median of the three [X RUN-tlc-tracemodule].

| Trace | Lines | What it is | Verdict | First non-conforming line | Lines matched | Distinct states | States generated | Depth | TLC exit code | Wall time |
|---|---|---|---|---|---|---|---|---|---|---|
| `accepted.ndjson` | 11 | the run as the spec allows it, ending with the end record | accepted | none | 11 of 11 | 35 | 56 | 15 | 0 | 0.433 s |
| `rejected.ndjson` | 11 | the ack-before-store mutant (SP-8.4's shape): line 8 acknowledges c1 before c1's result is stored | rejected | 8, `{"event":"Ack","cmd":"c1"}` | 7 | 23 | 38 | 11 | 10 | 0.402 s |
| `partial.ndjson` | 8 | the accepted log cut after its eighth line: no `Ack` and no end record | partial | none | 8 of 8 | 26 | 41 | 12 | 10 | 0.410 s |

The command, as `tv.mjs` words it, prints [X RUN-tlc-tracemodule]:

```
trace traces/accepted.ndjson: accepted (11 of 11 lines)
trace traces/rejected.ndjson: rejected at line 8 of 11: {"event":"Ack","cmd":"c1"} (lines 1-7 match)
trace traces/partial.ndjson: partial (8 of 8 lines conform; no End record, so the log may be cut short)
```

- **Accepted.** TLC found a behavior that consumes all 11 lines. The `TimerArmed` line is matched as a stuttering step, and the provider's `Accept` steps are filled in where the log needs them. The witness (section 4.7) shows the 11 logged steps in order, plus 2 provider steps. [X RUN-tlc-tracemodule]
- **Rejected.** Some behavior matches lines 1 to 7, and none matches line 8: `Ack` needs a stored result, and c1's comes only at line 9. TLC exhausted the constrained state space (0 states left on queue) and printed `Error: Postcondition TraceVerdict at … is false.`, exit code 10. As the paper says, there is no counterexample, only the line no behavior reaches. [X RUN-tlc-tracemodule]
- **Partial.** All 8 lines are matched. A safety spec allows every prefix of its behaviors, so the method by itself accepts a log that stops early. The paper's own postcondition, on the composed module where it is exact, accepts this cut log (config `composed-partial`). Only the missing end record makes the verdict partial. TLC also exits 10 here, so the exit code cannot separate partial from rejected; the verdict line does. [X RUN-tlc-tracemodule]
- **Cost.** At the same constants, the spec alone has 256 distinct states (673 generated, depth 15; no invariant violated, config `toy-spec`). The log cuts that down to tens. Every TLC run printed `Finished in 00s`; the wall time is mostly container and JVM start-up. [X RUN-tlc-tracemodule]

Three cross-checks agree. A state listing of each run (`-dump`, configs `*-dump`) holds the same number of states as TLC's distinct count, and its highest `l` is the verdict's matched lines plus one: 12, 8 and 9. With four workers (`rejected-w4`) the folded registers give the same verdict. With the depth-first queue (`accepted-dfs`, `rejected-dfs`), the verdicts and counts are unchanged; the banner still says breadth-first search and names the queue `StateDeque`, which is how CCF's `ASSUME` on breadth-first mode coexists with its depth-first switch. [X RUN-tlc-tracemodule]

The registers themselves were probed apart from the method. A register named `"reach"` stops TLC: `Error: The first argument of TLCSet should be a nonnegative integer, but instead it is:`, exit code 75 (config `register-plain`). Named `"s:reach"`, the form the jar's own `_Possible.tla` uses, it works, and `TLCGet("all:named")` in a postcondition returns one value per worker: `<<3>>` with one worker and `<<2, 2, 1, 1>>` with four (configs `register-prefixed`, `register-prefixed-w4`). [X RUN-tlc-tracemodule]

### 4.3 Why the verdict reads the line counter

When some steps consume no line, TLC's search depth counts states, not steps, so it is one more than the number of matched lines plus the unlogged steps on the longest path. On all three traces that is 3 provider steps, so the diameter is 15 for 11 matched lines, 11 for 7, and 12 for 8. The paper's postcondition, `diameter - 1 = Len(Trace)`, then fails in both directions [X RUN-tlc-tracemodule]:

| Config | Trace | Line-counter verdict | Diameter | Lines | Paper's postcondition |
|---|---|---|---|---|---|
| `accepted` | accepted, 11 lines | accepted | 15 | 11 | false: an accepted trace rejected |
| `rejected-noend` | the ack-before-store log without its end record, as the paper's logs are | rejected at line 8 | 11 | 10 | true: the mutant accepted |
| `rejected` | rejected, 11 lines | rejected at line 8 | 11 | 11 | false, as it should be; but a report that took the failing line from the depth would name line 11, not line 8 |

The table's rows are from [X RUN-tlc-tracemodule]. CCF's guard postcondition, `TraceMatchedNonTrivially`, also compares the diameter with the log's length, so it shares this limit. CCF's own trace module stays within it: every disjunct of its `TraceNext` goes through `IsEvent`, and coarser implementation steps are composed (at the commit of section 2.1) [V].

In the composed module every step consumes a line. There the diameter is always the matched lines plus one, the paper's postcondition agrees with the line counter about whether every line was consumed on all four traces, and the search is smaller: 16, 8 and 10 distinct states, against 35, 23 and 26 (configs `composed-*`). But the pinned jar refuses composition by default: `The current version of TLC does not support action composition.  An incomplete implementation can be enabled via the tlc2.tool.impl.Tool.cdot=true java property.`, exit code 75 (config `composed-no-flag`). The composed runs needed that property. [X RUN-tlc-tracemodule]

So the course keeps unlogged steps, which S8.L6 specifies and which a learner can write without knowing where each provider step falls. It reads the verdict from the highest line counter, which is exact either way.

### 4.4 Incomplete logs

- **A log that ends early** is accepted by the method as a prefix (section 4.2). It needs a rule outside TLC's search: a complete log ends with the end record. [X RUN-tlc-tracemodule]
- **A log that misses an event** is rejected at the first line that depends on the event, not where the event is missing. `missing-event.ndjson` omits c2's `Dispatch` between its lines 2 and 3, and is rejected at line 6, c2's `Persist`. The provider cannot reply to a request that was never sent. A hint must say "no behavior reaches this line", never "this line is wrong". [X RUN-tlc-tracemodule]
- **A log cut inside a line** stops TLC with an exception from the JSON reader: `com.google.gson.stream.MalformedJsonException: Unterminated string at line 1 column 23 path $.event`, exit code 75 (config `cut-line`). The position counts within the bad line, so TLC's message does not name the file's line 8. The lint in `tv.mjs` does: `error at line 8: not JSON`. [X RUN-tlc-tracemodule]

### 4.5 What the log must carry

The fresh-key mutant (SP-8.3's shape) re-sends c1 with a new key. With keys logged it is rejected at line 4, the re-send (config `fresh-key`, 6 distinct states). With the key fields dropped, the same run is accepted, 7 of 7 lines (config `fresh-key-unlogged`, 19 distinct states): a wrongly accepted trace, the paper's caution about incomplete logs. LAB-8's prove-it row predicts this. The trace schema must therefore require every field a disjunct constrains. [X RUN-tlc-tracemodule]

### 4.6 TLC's deadlock check

With the deadlock check left on, TLC reports `Error: Deadlock reached.` and exits 11 on both traces. On the accepted trace the deadlock is the end of the log (`l = 12`, every line consumed). On the rejected trace it is the state where line 8 cannot be matched (`l = 8`). So a deadlock report is not a verdict. On a larger trace a dead branch can deadlock first and stop the search early: the accepted run stopped with 2 states left on the queue. The config must say `CHECK_DEADLOCK FALSE`, as the paper and CCF do. [X RUN-tlc-tracemodule]

### 4.7 Two other ways to ask

- **An invariant witness.** With `INVARIANT TraceUnconsumed` (`l <= Len(TraceLog)`) and `-dumpTrace json`, TLC stops at a behavior that consumes every line and writes it out (config `accepted-witness`, exit code 12). The witness has 14 states and 13 steps: the 11 logged steps in order, plus 2 `ProviderStep`s TLC filled in. As the paper notes, this form says nothing on failure. [X RUN-tlc-tracemodule]
- **TLC's `_POSSIBLE`.** `_POSSIBLE TraceConsumed` (`l = Len(TraceLog) + 1`) passes on the accepted trace. On the rejected trace TLC prints `… was never witnessed.` and exits 10 (configs `accepted-possible`, `rejected-possible`); it gives no line [X RUN-tlc-tracemodule]. TLC's documentation calls the keyword provisional: it may be renamed or removed (https://explain.tlapl.us/possible-conditions, read 2026-10-25) [V].

### 4.8 The trace-loading flag

`-loadTrace` replays a trace that TLC itself wrote, holding each level of the search to the state the file gives for it [X RUN-tlc-tracemodule].

| Config | Trace loaded | Result |
|---|---|---|
| `replay-json` | the toy's own counterexample, written by `-dumpTrace json` (6 states, config `replay-dump`) | fails at once: `Attempted to check equality of the set {} with the value:` `<<>>`, 0 distinct states, exit code 75. JSON writes the set `durable = {}` as an array, and the array comes back as a tuple |
| `replay-bin` | the binary trace TLC writes beside its trace-exploration spec for the same counterexample, with `-loadTrace tlc` | round-trips: the same invariant violation, 6 distinct states, exit code 12 |
| `hold-json` | the recorded Hold lasso, integers and strings only, with `-loadTrace json` | round-trips: the same lasso back to state 1, 5 distinct states against 8 unconstrained [X RUN-tlc-lasso-json], exit code 13 |
| `hold-json-tampered` | the same lasso with state 3's `tries` changed in every copy | `No error has been found`, 2 distinct states, exit code 0 |

The table's rows are from [X RUN-tlc-tracemodule]. The earlier review's finding holds for any trace with a set-valued variable, and the course's outbox specs hold several (requests, replies, the provider's table). More to the point, the flag matches full TLC states, one per level. An implementation's log has implementation-only lines, leaves the provider's steps out and names events rather than states, so the flag cannot validate it. The trace-module method can.

### 4.9 When TLC stops without a verdict

When TLC stops on a syntax or semantic error, its first `Error:` line is `Parsing or semantic analysis failed.`, and when it stops on an exception, it is `TLC threw an unexpected exception.` Neither says what went wrong. The message that helps is in the lines around it, so `tlcProblem` in `tv.mjs` quotes SANY's message, or the exception's, with its location when it has one. Three configs edit one line of a copy of the trace module before TLC runs, as a learner's slip would (configs `typo-syntax`, `typo-operator` and `typo-field`; each edited copy is saved with its outputs). For those three and for two configs of the sections above, the command prints [X RUN-tlc-tracemodule]:

```
trace traces/accepted.ndjson: error: Encountered "IsAck" at line 23, column 1 and token ")" (module ToyOutboxTrace)
trace traces/accepted.ndjson: error: Unknown operator: `IsEvnt'. (line 23, col 15 to line 23, col 20 of module ToyOutboxTrace)
trace traces/accepted.ndjson: error: Attempted to select nonexistent field "cmmd" from the record [cmd |-> "c2", event |-> "Ack"] (line 23, col 33 to line 23, col 41 of module ToyOutboxTrace)
trace traces/accepted.ndjson: error: Cannot find source file for module Json imported in module TraceValidation.
trace traces/accepted.ndjson: error: The current version of TLC does not support action composition.  An incomplete implementation can be enabled via the tlc2.tool.impl.Tool.cdot=true java property.
```

| Config | What went wrong | TLC's first `Error:` line | TLC exit code |
|---|---|---|---|
| `typo-syntax` | `IsAck` defined with `=` for `==` | `Parsing or semantic analysis failed.` | 150 |
| `typo-operator` | `IsEvnt` for `IsEvent` in `IsAck` | `Parsing or semantic analysis failed.` | 150 |
| `typo-field` | `Line.cmmd` for `Line.cmd` in `IsAck` | `TLC threw an unexpected exception.` | 75 |

| `composed-no-flag` | the composed module without the cdot property (section 4.3) | `TLC threw an unexpected exception.` | 75 |

The table's rows are from [X RUN-tlc-tracemodule]. An evaluation error shows only when the search reaches a log line that makes TLC evaluate the slip: `typo-field` ran until line 9, the log's first `Ack` (the record the message quotes), so a slip in a disjunct goes unseen on a log without its event. For `cut-line` the lint names line 8 before TLC runs; without the lint, the tool would quote the JSON reader's message, which names line 1, column 23 of the bad line (section 4.4) [X RUN-tlc-tracemodule].

## 5. Decision

1. **Adopt the trace-module method** for `statespace trace validate` on the pinned 1.8.0 jar, using only its bundled modules: `Json`, `TLC` and `TLCExt`. No CommunityModules jar, and no `-loadTrace`. [X RUN-tlc-tracemodule]
2. **The log's path is a config constant** (`TraceFile`), written by the tool into a config for each trace. It replaces the paper's and CCF's `IOEnv`, which needs `IOUtils`. [D]
3. **The verdict comes from the line counter.** The course-supplied `TraceValidation.tla` keeps the highest `l` in a named register and reads it in a postcondition. The diameter-based postconditions of the paper and of CCF are exact only when every step consumes a line (section 4.3). [X RUN-tlc-tracemodule]
4. **Unlogged environment steps, not composition.** The skeleton supplies an `Unlogged` disjunct for the provider's and network's actions, and the learner writes one disjunct per worker event. Composition is off by default in the pinned jar, behind a property its own message calls incomplete. [D]
5. **A complete log ends with an end record**, `{"event":"End"}`, which the harness writes when the run ends normally. A log whose lines all conform but which lacks the end record is partial: it is reported, but it does not count toward n. [D]
6. **Fixed flags.** `CHECK_DEADLOCK FALSE` in every trace config; `-workers 1`; the default breadth-first queue. The depth-first queue may be enabled for long traces: it changed no verdict here (section 4.2). [X RUN-tlc-tracemodule]
7. **Lint before TLC.** The tool checks the NDJSON first, so that a malformed line is named by its line number in the file (section 4.4). [D]
8. **The witness is optional.** For an accepted trace, the tool may write the matching behavior, with its filled-in provider steps, using the invariant form of section 4.7. It is useful for debugging; the verdict never depends on it. [D]

## 6. The fallback W5-T14 builds on

The tracker asks for a fallback W5-T14 can build on. Since the method works, that is the method as tested here, with the pieces listed below.

**Command** [D]. `statespace trace validate <spec> <traces>`: `<spec>` is the learner's spec, for example `spec/Outbox.tla`; `<traces>` is one or more `*.ndjson` files or directories of them. Beside the spec, LAB-8 supplies:

- the trace module `TraceOutbox.tla`, a skeleton the learner completes with one disjunct per worker event;
- `TraceValidation.tla`, pinned and hashed into `statements[]`;
- a pinned file of the trace configuration's constants.

**For each trace**: lint it; write the config of section 2.2; run `java -jar tla2tools.jar -workers 1 -config <cfg> TraceOutbox.tla` on the pinned 1.8.0 jar; read the `trace-validation` line; print one line [D]:

| Verdict | When | The line it prints | Counts toward n |
|---|---|---|---|
| accepted | some behavior consumes every line, and the last line is the end record | `trace <path>: accepted (N of N lines)` | yes |
| rejected | the search ends, and the highest line counter k is at most N | `trace <path>: rejected at line k of N: <line k, verbatim> (lines 1-(k-1) match)` | no |
| partial | every line is consumed, but the last line is not the end record | `trace <path>: partial (N of N lines conform; no End record, so the log may be cut short)` | no |
| error | the lint finds a problem, or TLC stops without a verdict line (a parse or evaluation error, a timeout) | `trace <path>: error at line k: <problem>` from the lint, or `trace <path>: error: <message>` quoting SANY or TLC, with the location when it gives one (section 4.9) | no |

The command then prints a summary line and exits 0 only when every trace is accepted. It never reads TLC's exit code alone: here TLC exited 0 when accepted, 10 when rejected or partial, and 75 or 150 on an error [X RUN-tlc-tracemodule]. For a parse error and for an exception, TLC's first `Error:` line is generic, so the tool quotes SANY's message, or the exception's, with its location when it has one (section 4.9); for any other stop it quotes TLC's first `Error:` line, and the line after it when that ends with a colon. `tv.mjs` holds the lint, the config, the parse, the quoted message and the printed line, ready to port to `bench/statespace/trace.py`.

**Receipt fields.** receipt@1 already has the block S8's issue 7 asked for: spine section 9.4's `traces`, and in `schemas/receipt.schema.json` `traces {n, seedListSha256, verdicts[{trace, seed, verdict: accepted | rejected | partial, firstNonConformingLine}]}`. This spike fixes their meaning and asks for five additions [D]:

## 8. Open risks

1. **A rolling pre-release.** The verdict depends on `TLCSet("s:…")`, `TLCGetOrDefault` and `TLCGet("all:named")`. These are recent features of a jar re-published under one tag, and the SHA-256 pins only the course's copy. The fallbacks are in section 6, and a bump re-runs `record.mjs` (GATE-runs). The messages the tool quotes on an error (section 4.9) are SANY's and TLC's text, not an interface; the checks of `record.mjs` pin the five lines.
2. **Search growth.** Unlogged steps interleave freely while lines remain: 35 distinct states against 16 for the composed module, on 11 lines [X RUN-tlc-tracemodule]. W5-T02's model adds crashes, timeouts and key pruning, and a seed's log will be longer. Measure on the real fixtures before fixing LAB-8.6's n and timeouts. If the search grows too large, the remedies are the depth-first queue, logging the simulated provider's steps (the harness sees them), or allowing an unlogged step only before a line that needs it.

4. **The reported line is where a drift shows, not where it happened** (section 4.4). Copy, hints and graded keys for "first non-conforming line" items must use the tool's meaning.
5. **The toy is small.** It has no crashes, at most 11 lines and at most 35 distinct states per trace [X RUN-tlc-tracemodule]. W5-T01 records RUN-tlc-trace-validation on LAB-8.c6's real fixtures; nothing here stands in for that run.
