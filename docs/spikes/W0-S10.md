# W0-S10: Goal Replay through `$/lean/plainGoal`

**Status:** proposed; awaiting owner review. **Date:** 2026-10-24 (machine clock). **Task:** W0-S10, which implements INS-goal-replay. **Run:** RUN-replay-gen. **Owner review:** 0.5 h [D].

## In one line

Generate Goal Replay strips at build time by asking the pinned toolchain's language server for `$/lean/plainGoal` at the start of each tactic. The output is byte-identical across cold runs [X RUN-replay-gen], and a toolchain change shows up as a state-by-state diff that a reviewer can read [X RUN-replay-gen].

**Read first:** section 5 (the decision), then 7 (what the owner must do) and 9 (what could go wrong). Sections 2 to 4 hold the method and the evidence.

## 1. Question

Can Goal Replay be generated deterministically from `$/lean/plainGoal`, with a diff on a simulated bump? The acceptance line in `tracker/tasks.yaml` is "RUN-replay-gen: identical strips across two runs; a simulated bump produces a diff". Four questions sit under it:

1. At which position in a proof does the server show which state?
2. Is the output byte-identical across cold runs and under different scheduling?
3. What does a reviewer see when the toolchain changes?
4. What does the build need from its container, and what does the fallback cost?

## 2. Method

- **Corpus.** Nine theorems in two Lean files under `scripts/spikes/W0-S10/corpus/`. `Ledger.lean` is the file of RUN-lean-ledger, unchanged, with SHA-256 `4ac24c5d0ae6afa568dc9cbb65410b5e1b4c9c0c7b854352326085a0d56acafb`, the same hash as `research/spikes/lean/Ledger.lean`; three of its theorems are used, the two the A5 probe read and `transfer_nonneg`. `Shapes.lean` is new, imports `Std`, and adds six theorems for proof shapes that S2 needs and the ledger lacks: a list induction with a multi-line case, `obtain`, `constructor` followed by bullets, a tactic that closes the goal by itself, an empty context under `import Std`, and a last tactic that spans two lines.
- **Spec.** `corpus/strips.json` lists, for each theorem, the texts of the tactics at which to read the goal, in order. It never holds a goal, so every goal in a strip is Lean's output.
- **Generator.** `gen-strips.mjs` resolves each tactic text to a position in the source, starts `lean --server` from the pinned image in a container (no network, 6 GiB of memory, the corpus mounted read-only, a UTC `/etc/localtime` file mounted), opens each source and waits for `textDocument/waitForDiagnostics`. It refuses a file with any error or warning and any source with a carriage return. It then asks `$/lean/plainGoal` at the start of each tactic and at the end of the proof, and writes one JSON file per strip (authoritative), a text view of it, and a manifest with the toolchain banner and binary hash, the options, the spec and source hashes, the diagnostics and the code points used. No timestamp, path or timing enters a file.
- **Comparator.** `diff-strips.mjs` compares two output directories byte for byte (the equality GATE-replay needs). When they differ it prints the manifest changes and then, state by state, each changed goal in full with removed and added lines marked.
- **Position scan.** `scan-positions.mjs` asks for the state at every character of every proof, to show where each state is reported.
- **Driver.** `run-spike.mjs record` runs the groups below and writes `runs/RUN-replay-gen.json` and `runs/RUN-replay-gen/`. `run-spike.mjs verify` re-executes and compares with the committed outputs, as `statespace run RUN-replay-gen` will.

| Group of configurations | What it runs | Asserted |
|---|---|---|
| `identical-runs` | two cold generations, compared byte for byte | yes (acceptance) |
| `identical-under-other-scheduling` | one generation in a container pinned to CPU 0, and three further cold generations | yes |
| `bump-simulated` | the pinned toolchain with `-Dpp.fieldNotation=false` passed to the server | yes (acceptance) |
| `probe-releases` | Lean 4.34.1 and 4.36.0-rc1 from toolchain directories | reported |
| `layout-and-positions` | `-Dformat.width=40`; the position scan | reported |
| `scale` | one source with 100 copies of one proof, under different names | reported |
| `fail-closed` | four corpus variants that must be refused | yes |
| `server-start-up` | the server with no `/etc/localtime` | yes |
| `fallback-guard-msgs` | a `#guard_msgs` docstring checked by `lean` itself | yes |

**Emulated:** the bump. A toolchain bump is simulated by flipping a pretty-printer option on the pinned toolchain, which is the same Lean and not a different release. The two probes on other releases are real and are reported, not asserted.

## 4. Results

### 4.1 Where the server shows which state

The scan asked for the state at 1,173 positions across the nine proofs (config `scan-positions`, output `runs/RUN-replay-gen/position-scan.txt`) [X RUN-replay-gen]. It shows:

| Position | State shown |
|---|---|
| before the `by` token | none: the server answers with no goal information |
| the `by` token | the theorem's initial goal |
| the first character of a tactic, and the blanks before it | the state before that tactic |
| strictly inside a simple tactic (`unfold`, `simp`, `omega`, `exact`) | the state after it |
| inside `split <;> simp <;> omega` | one state per piece: before `split`, then before `simp` (two goals), then before `omega` (one goal), then none |
| inside `rw [Int.add_comm]` | an intermediate state, `y + x = y + x`, that the strip does not contain; the end of the line shows no goals, because `rw` closes the goal itself |
| inside `induction xs with` | the state before the whole tactic; each case alternative (`nil`, `cons`) starts at that case's goal |
| the `·` of a bullet | the goals still open at that point: both at the first bullet, one at the second; the tactic after the bullet shows the focused goal |
| the end of the proof | no goals |

So a state is reported by position, and the same state is reported at many positions. The generator reads the start of each tactic, which is stable, and the end of the proof. It never reads inside a tactic. The A5 probe hard-coded five positions and printed them to the terminal only. The generator resolves the same five: line 14 character 2 and line 15 character 2 for `transfer_conserves`; lines 32, 33 and 34 at characters 2, 11 and 20 for `run_conserves` [X RUN-replay-gen]. W0-S11 still records that probe as RUN-lean-plaingoal.

### 4.2 The strips

Nine strips, 33 states, from two sources [X RUN-replay-gen]:

| Strip | Tactics | States | Shape it covers |
|---|---|---|---|
| `Ledger.transfer_conserves` | 4 | 5 | `unfold`, then a `<;>` chain: two goals, then one |
| `Ledger.transfer_nonneg` | 4 | 5 | the same with two hypotheses in the context |
| `Ledger.run_conserves` | 3 | 4 | induction with `generalizing`: `case nil`, and `case cons` with `ih` over every state |
| `Shapes.net_append` | 4 | 5 | list induction, one case over two lines |
| `Shapes.guard_leaves_funds` | 2 | 3 | `obtain` splits a hypothesis in two |
| `Shapes.and_swap_example` | 4 | 5 | `constructor`, then two bullets |
| `Shapes.add_comm_example` | 1 | 2 | a tactic that closes the goal itself |
| `Shapes.std_empty_size` | 1 | 2 | a source that imports `Std`; an empty context |
| `Shapes.and_intro_example` | 1 | 2 | a last tactic that spans two lines |

One strip, as generated (`runs/RUN-replay-gen/strips/Ledger.run_conserves.strip.txt`):

```
[0] before `induction ns generalizing s with`   (line 32, character 2)
    s : Ledger
    ns : List Int
    ⊢ total (run s ns) = total s

[1] before `rfl`   (line 33, character 11)
    case nil
    s : Ledger
    ⊢ total (run s []) = total s

[2] before `simp [run, ih, transfer_conserves]`   (line 34, character 20)
    case cons
    n : Int
    ns : List Int
    ih : ∀ (s : Ledger), total (run s ns) = total s
    s : Ledger
    ⊢ total (run s (n :: ns)) = total s

[3] end of proof   (line 34, character 54)
    no goals
```

The goals match what `curriculum/S02-proof.md` describes: the `if … then … else …` inside a sum after `unfold` (S2.L3), two goals after `split` (S2.L5), and an `ih` stated for every state (S2.L7) [X RUN-replay-gen].

A strip is a list of states by position, and not a chain in which each state is the result of the previous tactic. In a tree-shaped proof, the state at the first tactic of a case is that case's goal, and "no goals" at the end of a branch means that branch is closed. The interface has to show the `case` tag Lean prints, and the spec has to name the bullet when the two-goal state after `constructor` matters (`and_swap_example` does) [X RUN-replay-gen].

### 4.3 Determinism

Two cold runs, each in a new container, produced 19 files that are byte-identical, with set hash `9b3f1849…22e9` (config `compare-1-2`) [X RUN-replay-gen]. A run in a container pinned to CPU 0 and three further cold runs are also byte-equal to run 1 (configs `compare-1-1cpu`, `compare-1-soak-1` to `compare-1-soak-3`) [X RUN-replay-gen]. A generation of the nine strips took 0.96 to 1.80 s including the toolchain probe and a container start (configs `generate-1`, `generate-2`, `generate-1cpu`, `generate-soak-1` to `generate-soak-3`) [X RUN-replay-gen]. A scale probe, one source with 100 copies of the `transfer_conserves` proof under different names (500 states), took 1.8 s (config `generate-scale-100`) [X RUN-replay-gen]. What varies between runs, the container name and the durations, never enters a file [D].

### 4.4 A simulated bump produces a diff

Passing `-Dpp.fieldNotation=false` to the server makes Lean print `Ledger.a s` where it printed `s.a`. Three of the nine strips change (`transfer_conserves`, `transfer_nonneg`, `std_empty_size`), 8 of 33 states change, and 30 goal lines are added and 29 removed (config `compare-baseline-bump-simulated`; full report `runs/RUN-replay-gen/bump-simulated.diff.txt`); the diff exits with 1 [X RUN-replay-gen]. The six other strips, which have no field access, are untouched. The report prints only changed states, each changed goal whole:

```
strip Ledger.transfer_conserves: 3 of 5 states changed
  state 1 (before `split`)
      s : Ledger
      n : Int
    - ⊢ (if 0 ≤ n ∧ n ≤ s.a then { a := s.a - n, b := s.b + n } else s).a +
    -       (if 0 ≤ n ∧ n ≤ s.a then { a := s.a - n, b := s.b + n } else s).b =
    -     s.a + s.b
    + ⊢ Ledger.a (if 0 ≤ n ∧ n ≤ Ledger.a s then { a := Ledger.a s - n, b := Ledger.b s + n } else s) +
    +       Ledger.b (if 0 ≤ n ∧ n ≤ Ledger.a s then { a := Ledger.a s - n, b := Ledger.b s + n } else s) =
    +     Ledger.a s + Ledger.b s
```

### 4.5 Other releases

Lean 4.34.1 and 4.36.0-rc1 each answered `$/lean/plainGoal` and produced all 33 states identical to the baseline. Only the manifest differs, by the toolchain banner and the binary hash; the report says "every strip identical; only the manifest differs" (configs `compare-baseline-probe-4.34.1`, `compare-baseline-probe-4.36.0-rc1`) [X RUN-replay-gen]. Two readings follow. A bump that changes no goal still leaves a one-line manifest diff, so no bump is silent. And this corpus has not shown a real release changing a goal, so the simulated bump is the only demonstration of a state diff; it does not show that no real bump will change one.

### 4.6 The generator fails closed

Four variants of the corpus were each refused with exit 1 and no output directory (group `fail-closed`) [X RUN-replay-gen]:

| Variant | Refused because |
|---|---|
| the spec names `linarith`, which the proof does not contain | tactic not found after the previous one |
| `transfer_conserves` edited to state `total s + 1` | the file does not elaborate cleanly: three errors |
| a `sorry` in another theorem of the same file | the file does not elaborate cleanly: a `sorry` warning |
| `Shapes.lean` with CRLF line endings | carriage return found |

### 4.7 What the container must provide

- **A `/etc/localtime` file.** Given `initialize`, `initialized` and `didOpen` on stdin, the 4.35.0 server in the image, which has no such file, exits with status 1 and prints `Watchdog error: no such file or directory (error code: 2)` and `file: /etc/localtime` (config `server-without-localtime`) [X RUN-replay-gen]. The generator mounts a 114-byte UTC file, so no host timezone reaches the container. The Bench image of W0-T05 needs tzdata, or its runner must mount a file.
- **`import Std` works without Lake.** `Shapes.lean` imports `Std`, and its strips generate from the plain server [X RUN-replay-gen]. Course modules that import each other were not tried [U].

### 4.8 Layout

Lean lays the goal text out itself, and the `format.width` option did not change it: `-Dformat.width=40` left all 33 states unchanged (config `compare-baseline-width-40`) [X RUN-replay-gen]. The longest goal line in the baseline strips is 81 characters (`maxGoalLineLength` in the manifest) [X RUN-replay-gen]. A 360 px screen therefore needs the interface to wrap or scroll Lean's lines, or a richer request than `$/lean/plainGoal`, which was not tried [U].

### 4.9 The fallback works

`trace_state` inside a proof, with a `#guard_msgs` docstring holding the goal, passes on the pinned toolchain (exit 0, no output) and fails under the simulated bump (exit 1) with Lean's own mismatch report, which marks the old lines with `-` and the new with `+` (configs `fallback-pinned`, `fallback-simulated-bump`) [X RUN-replay-gen].

### 4.10 Code points

The strips use nine non-ASCII code points: U+00AC `¬`, U+00B7 `·`, U+2200 `∀`, U+2227 `∧`, U+2264 `≤`, U+22A2 `⊢`, U+271D `✝`, U+27E8 `⟨` and U+27E9 `⟩` [X RUN-replay-gen]. GATE-glyphs checks goal strips against the JuliaMono subset; W0-S12 records that coverage (RUN-juliamono-glyphs), and `✝`, which Lean prints on inaccessible names such as `h✝`, is the one most likely to be missing [U].

## 5. Decision

Adopt generation through `$/lean/plainGoal` for INS-goal-replay. These rules are proposals for W2-T03 to build on:

1. **Inputs.** Lean sources with LF endings that elaborate with no error and no warning, and a spec of tactic texts. The spec never holds goals. Strips are never hand-written.
2. **Request.** `$/lean/plainGoal` through `lean --server` of the pinned image, with no network, a memory cap, the source read-only and a UTC `localtime` file. Wait with `textDocument/waitForDiagnostics` before asking.
3. **Where to read.** State k is the position at the start of tactic k; the last state is the end of the proof. Never read inside a tactic (section 4.1).
4. **What a strip is.** States by position, with Lean's `case` tags kept; not a chain of tactic results (section 4.2).
5. **Output.** One JSON file per strip, a text view, and a manifest naming the toolchain banner, the binary hash, the options and the source and spec hashes. No timestamp, path or timing.
6. **GATE-replay.** Regenerate in the pinned image and require byte equality, which `diff-strips.mjs` reports by exit code 0. Nightly, as in SPINE §11.2.
7. **A bump.** Regenerate with the new toolchain and read the report. If no goal changed, only the manifest stamp is committed; if goals changed, the changed states are read and the new strips and stamp are committed together (the step in `labs/TOOLS.md` §6.2, "regenerate what was generated"). The monthly run on the newest stable Lean reports the diff and does not block [D].
8. **Failing candidates are not strips.** The generator refuses a file with an error. S2's recorded failures and faded-blank candidates are captured another way, either as `#guard_msgs` outputs (section 4.9) or from the diagnostics; W2-T03 chooses.

Limits of the spike's generator: `theorem` declarations only; each tactic text on one line; the end of the proof is the last non-blank character of the declaration; single-file sources.

## 6. Fallback

PLAN §W0 states it: strips limited to recorded `#guard_msgs` outputs, still regenerated by GATE-replay [D]. Section 4.9 shows it works on the pinned toolchain and trips under the simulated bump. It costs three things: the source must carry a `trace_state` at every state to be shown, so the learner-facing source is not the source that was elaborated; the recorded docstrings must be written once from Lean's output, and this spike has no tool for that; and the comparison is `lean`'s own, with no per-state report like the one in section 4.4.

Use it if `$/lean/plainGoal` disappears or changes meaning in a release the course must follow, or if position rules (section 4.1) change so often that the diff is noise. Nothing in this spike suggests either: 4.34.1, 4.35.0 and 4.36.0-rc1 agree on all 33 states [X RUN-replay-gen].

## 9. Open risks

| Risk | What limits it |
|---|---|
| `$/lean/plainGoal` is a Lean extension, not part of the language-server protocol, and may change | it worked on three releases [X RUN-replay-gen]; the fallback (section 6) |
| The position rules are Lean's, and a release could move them | the generator fails or the diff shows it; section 4.1's scan is re-run by `verify` |
| Nine theorems are a small corpus; real drift in `simp` or `omega` output is unmeasured | the diff tool and the monthly run; the corpus grows with the proof bank |
| Platform: one platform only (Linux x86_64) | owner action 3 |
| Metavariable and hygiene names (`?m.12`) are unstable under edits | the manifest lists a warning for any goal that shows one; none did [X RUN-replay-gen] |
| Course modules that import each other need their imports built first | not tried [U] |
| Tactic texts are anchored as text; only `--` comments are skipped | a mis-anchor shows in the strip, and the scan lists the positions |
| Goals are wide for a phone | owner action 2 |
| Scale: 500 states of one proof shape took 1.8 s [X RUN-replay-gen]; a real bank has varied proofs, whose elaboration may be slower | one server serves many files; W2-T03 measures its own bank |

## 10. Re-running

```
node scripts/spikes/W0-S10/gen-strips.mjs --out <empty dir>
node scripts/spikes/W0-S10/diff-strips.mjs runs/RUN-replay-gen/strips <that dir>
node scripts/spikes/W0-S10/run-spike.mjs verify [--bump-toolchain-dir <dir>]...
```

A `--bump-toolchain-dir` holds one toolchain, installed with `docker run --rm -e ELAN_HOME=/elanx -v <dir>:/elanx ss-lean:4.35.0 elan toolchain install leanprover/lean4:v4.36.0-rc1`. Without it, `verify` skips the release probes. The run record is `runs/RUN-replay-gen.json`; its outputs are under `runs/RUN-replay-gen/`.
