# W0-S01 · Instrument origin on a custom subdomain

**Status:** decision record, accepted by the owner on 2026-10-25 (review page) and reopened the same day by OD-6 (changed); see the addendum. **Task:** W0-S01 (the instrument origin, I6; OD-5). **Date:** 2026-10-24 (machine clock). **Run:** [X RUN-origin-subdomain], recorded in `runs/RUN-origin-subdomain.json` with raw outputs in `runs/RUN-origin-subdomain/`. **Live:** the same harness also ran on the real origins on GitHub Pages, with real DNS and certificates [X RUN-origin-subdomain-live] (section 4.9). The offline session, the hostile embedder and configuration C stand on the local stand-in only (section 3).

## 1. Question

Does the instrument origin work on its own custom subdomain (OD-5)? Concretely:

- Does Z3 run there cross-origin in Chromium, Firefox and WebKit while the parent's storage stays unreadable? The executed result [X RUN-browser-origin] showed this for two localhost ports over plain HTTP; this spike moves it to the hosting plan of ARCHITECTURE.md section 5.2: HTTPS, two hostnames under one registrable domain, the build path `b/<buildId>/`, and the meta CSPs of section 15.4.
- Do same-site framing and the MessagePort handshake of section 5.3 hold, against a hostile embedder too?
- Do the framed origin's Cache API and service worker persist across desktop sessions under storage partitioning (ARCHITECTURE.md section 20, issue 16)? If they do not, consent prompts repeat and offline use degrades. **Superseded in part, 2026-10-25.** OD-6 changed: no download asks first, so what repeats is a download, not a prompt (see the addendum).

It also answers two questions the architecture leaves to this spike: whether the iframe may carry `sandbox="allow-scripts allow-same-origin"` (section 5.3), and whether the engine-cache mechanics of section 15.4 work in all three engines.

**Short answer.** Yes, on a faithful local stand-in, in all three engines. Z3 5.3.1 ran in a module worker on the instrument origin in all 27 browser sessions, and the parent's storage was unreadable from the frame and from its worker. The framed service worker and engine cache survived every browser restart: after a restart the worker controlled the frame from its first request, all six engine files came from the cache, no consent was asked, and Z3 ran while the instrument hostname answered 503 to every request. This held where the browser partitioned the frame's storage (WebKit even for the same-site frame; all three engines for a cross-site frame). The sandbox attribute changed nothing measured and blocked top navigation, so this record adopts it. [X RUN-origin-subdomain]

## 2. Method

1. **Three static sites**, built by `scripts/spikes/W0-S01/build.mjs` from `scripts/spikes/W0-S01/site/`:
   - *The main origin* (stands in for `https://<course-domain>/`). Its page writes a marker token into every store it owns: localStorage, sessionStorage, an IndexedDB database `statespace-evidence`, a Cache API cache `main-shell`, a host-only cookie and a cookie scoped with `Domain=` to the registrable domain. It embeds the instrument host exactly as section 5.3 shows (`hidden`, a `title`, `referrerpolicy="no-referrer"`), runs the handshake, and carries the main-origin meta CSP of section 15.4.
   - *The instrument origin* (stands in for `https://instruments.<course-domain>/`). `b/<buildId>/host.html` carries the instrument CSP of section 15.4. The host posts `hello` only to the allowed parent and adopts one `connect` (allowed origin, `event.source` is the parent, matching build, exactly one port). It refuses to start at the top level, and when `location.ancestorOrigins` names a parent that is not allowed. After a handshake it registers `/sw.js` with scope `/`. It refuses a first load above 5,000,000 bytes without consent (OD-6; the byte value is a course parameter [D]). It asks the service worker to fill the engine cache, then runs the roadmap starter in a module worker on Pyodide 314.0.7 with the `z3_solver` 5.3.1.0 wheel, with an `rlimit` of 5,000,000. The worker checks the model against the property and never matches model values.
   - *The service worker* serves engine files (`/b/<buildId>/engines/…`) only from the engine cache and answers 504 otherwise. It fills that cache only with bytes whose SHA-256 matches the build manifest, precaches the small build shell, and logs which kind of client each response went to. The manifest lists one decoy file whose served bytes differ from its listed hash.
2. **Stand-in hosting.** One dependency-free Node server (`server.mjs`) inside the pinned Playwright container served the sites over HTTPS on port 443, routed by `Host` header. Its headers are like those GitHub Pages sends: no COOP or COEP, `Access-Control-Allow-Origin: *`, `Cache-Control: max-age=600`, an ETag, no compression. Four hostnames under the reserved `.test` TLD resolved to 127.0.0.1: `course-domain.test` (main), `instruments.course-domain.test` (instrument, same site), `instruments.other-host.test` (instrument on another registrable domain) and `attacker.test`. A throwaway CA made per run (`certs.sh`) was trusted in each engine's own store.
3. **Three configurations**, each on one fresh persistent profile per engine:

   | Configuration | Instrument frame | Stands for |
   |---|---|---|
   | A | same-site, plain iframe | the hosting plan (section 5.2) |
   | B | same-site, `sandbox="allow-scripts allow-same-origin"` | the hardening option of section 5.3 |
   | C | cross-site, plain iframe | the fallback's worst case: another static host on its own domain |

4. **Three browser sessions per configuration.** A session is one headless browser process on the persistent profile: launch, work, close.
   - *s1, online and cold:* `run` without consent; a `peek` at one engine file before the cache is filled; `warm` with consent; `run`; storage probes from the frame, from its worker and from the harness itself; a second `connect`; a `document.domain` probe.
   - *s2, online, after a restart:* the cache and controller state are read before any request; `run` without consent; the probes again; then the instrument origin is opened top-level in a new tab, to compare its first-party storage with the framed one.
   - *s3, after a restart, with the instrument hostname answering 503 to every request:* `run` without consent, then `evict`.
5. **Negative tests**, per engine: a page on `attacker.test` frames the host twice, once with the default referrer policy and once with `no-referrer`, and sends each frame a forged `connect` carrying a port. The host is also opened top-level.
6. **Top navigation**, per engine, configuration and target, each in a fresh session in which the harness never evaluates inside the frame. The frame tries to navigate the top-level page 6 s after the request, past the 5 s transient-activation window, to a page on the main origin or to a page on `attacker.test`. Each target needs its own session, because a navigation that succeeds ends the page.
7. **Playwright's defaults.** Playwright 1.63.0 changes two browser defaults, and the harness changed them back. It relaunched Chromium without the `--disable-features` entry `ThirdPartyStoragePartitioning`. It set Firefox's `network.cookie.cookieBehavior` to 5, the value the Firefox build's own `defaults/preferences/firefox.js` sets, where Playwright's `playwright.cfg` sets 4. It left Firefox's `fission.webContentIsolationStrategy` at Playwright's 0. `meta.json` and `firefox-pref.txt` in the run folder record both browsers' settings.

To reproduce, with Docker, Node 22 and npm:

```
scripts/spikes/W0-S01/run.sh <work-dir> --record
```

`run.sh` installs playwright-core 1.63.0 into the work directory from the task-local `package.json`. It fetches and verifies the engines (the npm integrity hash for Pyodide, PyPI's SHA-256 for the wheel), builds the sites, makes the CA in a prep container, runs `harness.mjs` in the pinned image, and has `record.mjs` rewrite the run record and its 60 checks. The whole matrix took 262.6 s. [X RUN-origin-subdomain]

## 4. Results

### 4.1 Z3 runs cross-origin in three engines

In all 27 sessions (3 engines × 3 configurations × 3 sessions) the run returned `5.3.1 sat [b = 0, amount = 1, a = 0] unsat` and the witness satisfied the property. In every session that probed it (s1 and s2), the worker reported the instrument origin as its own, and the frame's origin differed from the page's in every configuration. Ready time (Pyodide plus the wheel, from the engine cache) was 1,286–1,652 ms in Chromium, 1,527–2,457 ms in Firefox and 1,493–2,642 ms in WebKit, in the desktop container. These are not phone budgets; W0-S02 measures those. [X RUN-origin-subdomain]

### 4.2 The parent's storage stays unreadable

| Probe | Result, every engine and configuration |
|---|---|
| `window.parent.localStorage`, `window.parent.document` and `window.parent.indexedDB`, read from the frame | SecurityError |
| `window.parent.localStorage` and `window.parent.location.href`, evaluated by the harness inside the frame | SecurityError |
| the parent's marker in the frame's own localStorage and sessionStorage | absent |
| the parent's database `statespace-evidence` in `indexedDB.databases()`, frame and worker | absent |
| the parent's cache `main-shell` in `caches.keys()`, frame and worker | absent |
| the parent's host-only cookie | not visible |
| the parent's cookie with `Domain=` the registrable domain | visible in A and B (same site); not visible in C |

[X RUN-origin-subdomain]

The last row is the one store the two origins share: the instrument origin can read any cookie the main origin scopes to the whole registrable domain. The course sets no cookies, so nothing leaks today; section 5 makes the rule explicit.

### 4.3 The handshake

- The handshake completed in every session, and a second `connect` after it was never answered. [X RUN-origin-subdomain]
- The hostile page received no `hello` in any engine, neither forged `connect` was answered, and no service worker was registered under it. [X RUN-origin-subdomain]
- Chromium and WebKit reported `https://attacker.test` in `location.ancestorOrigins` for both hostile frames, and the host refused before listening. Firefox reported it for the plain frame, which the host refused, and `"null"` for the `no-referrer` frame. In that frame the host listened, and the handshake rejected the forged `connect` on its origin. [X RUN-origin-subdomain]
- Opened top-level, the host showed its notice and registered nothing. [X RUN-origin-subdomain]
- In the course's own `no-referrer` frame, Chromium and WebKit reported `https://course-domain.test` in every session. Firefox reported `"null"` in s1, where the frame document came from the network, and the parent origin in s2 and s3, where the service worker served it. [X RUN-origin-subdomain] Section 5.5's rule as written, "refuses to start unless its first entry is an allowed parent", would therefore have refused the course's own first load in Firefox.

### 4.4 Consent and the engine cache

- **Consent.** In s1, `run` without consent returned `consent-required` with the detail `20056541 bytes`, in every engine and configuration. [X RUN-origin-subdomain]
- **No network fallthrough.** Before the fill, with the service worker controlling the page, a fetch of an engine file came back 504 from the service worker in every engine. An uncached engine file never reaches the network. [X RUN-origin-subdomain]
- **Integrity.** The fill cached 6 of 6 files (20,056,541 bytes) and refused the decoy, whose bytes did not match its hash, in every engine and configuration. [X RUN-origin-subdomain]
- **Workers are controlled.** In every session that ran Z3, the service worker's log shows the module worker's six engine requests (two module imports and four fetches) served from the engine cache to a client of type `worker`. A dedicated module worker is controlled by the frame's service worker in all three engines. [X RUN-origin-subdomain]
- **CSP.** Neither page reported a CSP violation in any session. [X RUN-origin-subdomain]
- **Evict.** `evict` deleted both caches and unregistered the service worker; the next `caps` reported the engine uncached and needing consent. [X RUN-origin-subdomain]

### 4.5 The framed cache across browser restarts

| Engine | After a restart (s2), in A, B and C | Requests to the instrument host after a restart | Instrument host answering 503 (s3) |
|---|---|---|---|
| Chromium 153.0.8010.12 | controlled at load; 6 of 6 entries; Z3 ran without consent | none | Z3 ran; no request |

[X RUN-origin-subdomain]

No engine file reached the server after a restart in any engine or configuration. `navigator.storage.persisted()` returned false in every session, so the cache survived as best-effort storage. `navigator.storage.estimate()` reported a quota of 104,857,600 bytes for the framed origin in WebKit, against 10,737,418,240 bytes or slightly more in Chromium and Firefox. [X RUN-origin-subdomain]

### 4.6 Storage partitioning

In s2, after the framed checks, the instrument origin was opened top-level in a new tab. That first-party page saw:

| Engine | Same-site frame (A, B) | Cross-site frame (C) |
|---|---|---|
| Chromium | the framed cache (6 entries) and registration: one storage | nothing: partitioned |
| Firefox | the framed cache (6 entries) and registration: one storage | nothing: partitioned |
| WebKit | nothing: partitioned by the top-level origin | nothing: partitioned |

[X RUN-origin-subdomain]

Persistence therefore held in partitioned and unpartitioned storage alike (section 4.5). In WebKit, the framed instrument origin's storage is keyed by the main origin although the two origins are same-site, so it is never shared with the instrument origin opened directly.

### 4.7 The sandbox attribute

Configuration B matched A on every check: Z3, storage, handshake, consent, integrity, persistence and evict. It differed in two places, both hardening. The frame could not navigate the top-level page (SecurityError, in every engine and for both targets). Assigning `document.domain` threw SecurityError. [X RUN-origin-subdomain]

### 4.8 Top navigation and `document.domain`

A frame that never had user activation tried to navigate the top-level page:

| Target | Frame | Chromium | Firefox | WebKit |
|---|---|---|---|---|
| a page on the main origin | plain (A, C) | navigated | blocked (SecurityError) | navigated |
| a page on another site | plain (A, C) | blocked (SecurityError) | blocked (SecurityError) | blocked (SecurityError) |
| either | sandboxed (B) | blocked (SecurityError) | blocked (SecurityError) | blocked (SecurityError) |

[X RUN-origin-subdomain]

The frame reported no activation (`isActive` and `hasBeenActive` false) at the request, and again at the attempt wherever it was still there to report. The parent page had activation, because Playwright's `evaluate` counts as a user gesture. Chromium ignored the frame's assignment to `document.domain` and logged that the agent cluster is origin-keyed. Firefox and WebKit let the frame set it to `course-domain.test`. In all three engines the parent stayed unreachable (SecurityError), because the main page never sets it. [X RUN-origin-subdomain]

## 5. Decision

1. **OD-5 stands.** The instruments live on their own custom subdomain, same-site with the main origin, framed and reached through one MessagePort after the handshake of section 5.3. On the stand-in, all three engines ran Z3 there, kept the parent's storage unreadable and kept the engine cache [X RUN-origin-subdomain]. I6 is unchanged.
2. **The framed cache persists across desktop sessions** in Chromium 153, Firefox 155 and WebKit 26.6, in partitioned and unpartitioned storage, offline included [X RUN-origin-subdomain]. Consent is asked once per engine and device, until the cache is evicted. This closes ARCHITECTURE.md section 20, issue 16, for desktop engines on the stand-in; section 7 lists the check on the real origins and real browsers. **Superseded in part, 2026-10-25.** OD-6 changed: no download asks first and none warns; the loader shows each engine's size while it downloads. Decision 2's sentence on consent follows the replaced rule (see the addendum). The measurements above stand.
3. **Adopt `sandbox="allow-scripts allow-same-origin"` on the instrument iframe** [D]. Section 5.3 made it conditional on identical worker and cache behavior, which the run shows, and it blocks top navigation and `document.domain` in all three engines [X RUN-origin-subdomain].
4. **Amend the `ancestorOrigins` rule of section 5.5** [D]: refuse when the first entry is a real origin outside the allowed list; treat `"null"` as unknown and rely on the handshake. Keep `referrerpolicy="no-referrer"`: in the masked case, the handshake alone rejected the forged `connect` [X RUN-origin-subdomain].
5. **Register the service worker only after a successful handshake** [D], so a hostile embedder causes no side effect. A registration from an earlier session still controls the frame from its first request [X RUN-origin-subdomain].
6. **The main origin sets no cookies, and never one with a `Domain` attribute** [D]. Such a cookie is the one store a same-site instrument origin can read [X RUN-origin-subdomain].
7. **The engine-cache mechanics of section 15.4 hold, for W1-T06 to build on.** The service worker fills the cache only with manifest-verified bytes, serves engine files only from that cache (504 otherwise), and controls the module worker's fetches; `evict` clears it [X RUN-origin-subdomain]. The spike's host, service worker and worker under `scripts/spikes/W0-S01/site/instruments/` are a reference, not product code.

## 6. Fallback

If the custom subdomain cannot be served, for example because the hosting account or the DNS setup does not allow it, the instrument origin moves to another static host [D]. I6 is never relaxed. Until an instrument origin exists, the features that parse untrusted input wait: in-tab Z3 cells, receipt, bundle and fragment imports, and Lane A. Recorded runs, pocket checkers and the Bench carry the course meanwhile. In order of preference:

1. **Another static host serving the same custom subdomain**, `instruments.<course-domain>`. The browser sees the same origin, so every result above carries over; only the deployment configuration changes.
2. **A static host on its own registrable domain** (configuration C). On the stand-in it still worked in all three engines: Z3 ran, the parent's storage stayed unreadable, and the service worker and engine cache persisted, in a partition keyed by the main site [X RUN-origin-subdomain]. The cost is that the instrument origin becomes a third-party frame. Safari applies its tracking-prevention rules to third-party storage, which Playwright's WebKit does not model [U]. The main page's `frame-src` also names the other host.

If the framed cache is lost (eviction, cleared site data, a browser that partitions it away), the behavior is the fallback of ARCHITECTURE.md section 19: recorded runs stay available, consent is asked again, and the evidence log is unaffected. The `evict` step shows the host then reports the engine as uncached and needing consent [X RUN-origin-subdomain]. **Superseded in part, 2026-10-25.** OD-6 changed: no download asks first, so after an eviction the engine downloads again and the loader shows its size (see the addendum).

## 9. Open risks

1. **The real hosting is tested for DNS, certificates and framing** [X RUN-origin-subdomain-live]. How GitHub Pages compresses the large engine files is measured by W0-S02's wire check.
2. **Elapsed time is untested.** Sessions were seconds apart. WebKit's seven-day cap on script-written storage [webkit7d], eviction under storage pressure (`persisted()` was false throughout), and browser updates were not exercised. Section 6 covers a lost cache.
3. **Playwright's browsers are not the shipped ones.** Two defaults were changed back (Chromium's storage partitioning, Firefox's cookie policy), others may differ, and Firefox ran with frames sharing a process (`fission.webContentIsolationStrategy` 0).
4. **WebKit's quota.** WebKit reported a quota of 104,857,600 bytes for the framed origin, and Pyodide with Z3 takes 20,056,541 of them [X RUN-origin-subdomain]. Later engines (PGlite, Spectacle) share that quota; measure it again when they land.
5. **A frame with user activation was not measured.** If the instrument origin ever shows interactive UI (SCR-instrument), a plain frame with activation may navigate the top page more freely. The sandbox attribute blocks that whatever the activation state.
6. **Firefox's `ancestorOrigins` differs** between a frame served by the network and one served by the service worker. The amended rule (section 5, item 4) does not depend on it.
7. **Phones** are W0-S02's to measure.
