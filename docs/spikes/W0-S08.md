# W0-S08: PGlite row-level security and first-load size

**Status:** proposed; awaiting owner review. **Date:** 2026-10-24 (machine clock). **Task:** W0-S08, which implements INS-pglite. **Runs:** RUN-pglite-rls and RUN-pglite-0511. **Owner review:** 0.5 h [D].

## In one line

S7.L4 runs in the tab on PGlite 0.5.11 and on the Bench on PostgreSQL 18.6. PGlite gave PostgreSQL's answer on 52 of 53 specimen steps and on all 200 seeded worlds, under Node and in Chromium, Firefox and WebKit [X RUN-pglite-rls]; the one step that differs, `RESET SESSION AUTHORIZATION`, is not a statement the lesson needs. The first load is 5,580,851 bytes of gzip [X RUN-pglite-0511], above OD-6's 5 MB, so the tab asks first. A live instance adds 565 to 1,125 MiB to a desktop browser's resident memory [X RUN-pglite-0511], so hands-on S7.L4 is for laptops and phones show recorded runs.

**Read first:** section 5 (the decision), then 7 (what the owner must do) and 9 (what could go wrong). Sections 2 to 4 hold the method and the evidence. The specimens also found one fault in the lesson text and two things its copy must say (section 4.6).

## 1. Question

The tracker's acceptance is "RUN-pglite-rls and RUN-pglite-0511 recorded; the decision record fixes S7.L4's lane", and the spine adds "in a browser". Five questions sit under it:

1. Does row-level security work in PGlite as S7.L4 uses it: `CREATE POLICY`, `SET ROLE`, `FORCE ROW LEVEL SECURITY`, the owner bypass, `UPDATE 0`, `WITH CHECK` and the covert channel?
2. Does PGlite give PostgreSQL 18.6's answers to those, in a module worker in Chromium, Firefox and WebKit?
3. Where does it differ, and what would a learner or an author trip over?
4. What does the 0.5.11 pin report, and does the patch release keep RUN-pglite's specimens?
5. How large is the first load, counted the way OD-6 counts it, and what do the load and a live instance cost in time and memory?

## 2. Method

One command, `node scripts/spikes/W0-S08/run-all.mjs`, wrote both runs. It logs every step with its argv, start time, duration and exit code (`runs/RUN-pglite-*/commands.jsonl`), and `record-run.mjs` turns the outputs into the two records.

- **One specimen suite, run unchanged everywhere.** `rls-spec.mjs` holds the SQL, the access model and the checks, and uses no Node or browser API. It ran against PostgreSQL 18.6 on one node-postgres connection, against PGlite under Node, and against PGlite in a module worker in each of the three browsers (the shape ARCHITECTURE §6.1 gives an engine). The page came from a loopback server that sends no cross-origin isolation headers, as the course's static hosting sends none (`labs/TOOLS.md` §5).
- **The access model is plain code.** `canread` evaluates S7's three read rules (`curriculum/S07-secrecy.md` §1) with team nesting by closure, and gives the matrix that each engine's `SET ROLE` answers are compared with.
- **Part 1, named specimens.** 53 steps and 34 checks on a reference world, following the behaviors of S7.L4's three segments: S7's W0, plus Risk (a team nested in Payments, with eli in it), ivy (a teamless user) and a revoked share of roadmap to gia. The schema, `user_teams()`, the three read policies and a `SET ROLE` per user follow the lesson; the UPDATE and INSERT policies and the editor function are written here.
- **Part 2, seeded worlds.** For seeds 1 to 200 a generator draws a world in S7's ranges (2 to 3 tenants, 2 to 5 teams, 3 to 8 users, 3 to 10 documents, nesting depth 0 to 2, shares, revocations and teamless users). Each world is loaded, then for every user the harness runs `SET ROLE u`, sets `app.user`, reads the visible ids and compares them with the matrix row. It repeats this under the four variants of S7.L4's graded item (a restrictive policy for a permissive one, `<@` for `&&`, a dropped `NOT s.revoked`, a missing policy) and then runs the owner probe without and with `FORCE`.
- **Equal** means equal on kind, rows, row count, SQLSTATE, message and detail for a statement, and equal SHA-256 hashes of the world, the matrix, every user's visible ids under the baseline and under each variant, and the owner probe's counts for a world.
- **Single-session specimens.** RUN-pglite's facts (22003, a NULL amount affecting 0 rows, the default isolation level) and S6.L1's two NULL specimens, compared the same way; the two interleaved workers on PGlite only. RUN-pglite's three scripts also ran unchanged on 0.5.11, and two of them on 0.5.10.
- **The patch release.** The same suite on 0.5.10 under Node, compared with 0.5.11 (`labs/TOOLS.md` §6.2, step 4).
- **First load.** A page whose module worker imports PGlite, builds the default in-memory database and runs one query; the files the engine requests are the first load. Sizes are computed from the file bytes (raw; gzip at levels 5, 6 and 9 with stock zlib; Brotli at 11). The browser server sent level-5 gzip copies made on the host, and its log and the engine's resource timing give the bytes received. A probe of public sites served by GitHub Pages found what that host compresses and at which gzip level its bytes match.
- **Time and memory.** Three cold loads per engine and encoding, each in a new browser context, one warm load, and four further fresh instances in the same worker. A separate run holds one instance and replaces it four times, sampling the resident memory of every process in the browser's container, minus the driver's, after each step.
- **Emulated: slow devices.** Chromium's DevTools CPU throttle is tried first. Because it does not reach the worker, the slow-CPU runs cap the whole container's CPU quota instead (`docker run --cpus`), with a fixed loop in the worker as the yardstick. Neither is a phone.

### 4.6 The one divergence, and what it means for the lesson text

1. **`RESET SESSION AUTHORIZATION` does nothing on PGlite 0.5.11.** After `SET SESSION AUTHORIZATION app_owner`, `current_user` and `session_user` stay `app_owner`; on PostgreSQL they return to `postgres`. 0.5.10 behaves the same way (53 of 53 steps equal between the two builds). `SET SESSION AUTHORIZATION postgres` works, and so does `SET ROLE`/`RESET ROLE`, which the lesson uses [X RUN-pglite-rls, RUN-pglite-0511].
2. **`SET app.user = 'u'` does not parse, on PostgreSQL 18.6 or PGlite.** `curriculum/S07-secrecy.md`, Segment 2, writes the differential as `SET ROLE u; SET app.user = 'u'; SELECT id FROM documents;`. The statement fails with `42601 syntax error at or near "user"` on both [X RUN-pglite-rls]; `USER` is a reserved key word (PostgreSQL 18 manual, appendix C, read 2026-10-24) [V]. The quoted form `SET app."user" = 'u'` and `SELECT set_config('app.user', 'u', false)` both work and name the same setting; the policies' `current_setting('app.user', true)` is unaffected.
3. **PGlite's only connection is the superuser `postgres`.** It bypasses row security even on a forced table, so every RLS statement has to follow a `SET ROLE` to a non-superuser, and the owner probe is `SET ROLE app_owner` (owner-ness follows the effective role) [X RUN-pglite-rls]. This is a limit of the tab, not a fault of the lesson, but its copy should say it where it says "the application connects as the owner".
4. **The covert channel is a bit, not a value.** Under row security PostgreSQL and PGlite withhold the DETAIL line that names the key, and only the error class differs between the two worlds [X RUN-pglite-rls]. S7.L4's copy ("frank still learned a bit") is right; a sentence that said frank learns the slug's owner or value would not be.

GitHub Pages is what the course is served by (ARCHITECTURE §3.1). That is why level 5 is the headline. The probed files are under 1 MB, and none is a `.data` file, so the host's treatment of a 10 MB wasm file is an assumption until the first deployment is measured (owner action 3).

The package holds 294 more files, 8,162,945 B, that a first load does not request, among them 37 extension tarballs of 1,468,166 B in all; the largest is `pgcrypto.tar.gz` at 1,151,286 B [X RUN-pglite-0511]. No extension is loaded unless asked for.

### 4.11 Slow devices: an emulation

Chromium's CPU throttle at 4x and 6x left the worker's fixed loop at 48.2 and 49.0 ms against 55.9 ms unthrottled, and PGlite's ready time at 1,153.1 and 1,284.8 ms against 1,210.1 ms: the throttle does not reach a same-origin module worker, as it did not reach the cross-origin iframe's worker in [X RUN-browser-origin] [X RUN-pglite-0511]. ### 4.12 What was not tested

The READ COMMITTED policy-subquery race (catalog row H17), which needs two sessions; the lab template's own policies, which do not exist yet; views and `security_invoker`; extensions; PGlite's IndexedDB and OPFS back ends (the instrument uses the in-memory one); other PGlite versions than 0.5.10 and 0.5.11; browsers on a phone; GitHub Pages' handling of a file the size of `pglite.wasm`; a bundled build, where a bundler can split or rename only the eight JavaScript files, 144,066 B of the 5,580,851 B as gzip, and leaves `pglite.wasm`, `pglite.data` and `initdb.wasm` as they are.
