# W0-S04 · Spectacle on Stage 5/8 specs and state pairs

**Status:** decision record, awaiting owner review (1 h). **Task:** W0-S04 (the INS-spectacle decision). **Date:** 2026-10-24 (machine clock). **Run:** [X RUN-spectacle-s5s8], recorded in `runs/RUN-spectacle-s5s8.json` with raw outputs in `runs/RUN-spectacle-s5s8/`. **Emulated:** the browsers are desktop engines, headless, in the pinned Playwright container on one shared Linux host; no phone, and timings are single runs (section 3).

## 1. Question

The spine's W0 row and PLAN.md ask: does Spectacle cover the S5 and S8 specs, local `EXTENDS` and state pairs, fast enough? ARCHITECTURE.md section 6.3 splits that into four things to confirm: local `EXTENDS`, operator coverage on S5 and S8 specs, the state-pair check, and whether Spectacle runs in a worker or needs the host page's main thread. The task adds the comparison with TLC, under one worker and an explicit deadlock flag, on verdicts and distinct-state counts, and asks for INS-spectacle's scope spec by spec. Lessons wait on this record: S5.L2's exit item keys come from TLC "until W0-S04 shows whether Spectacle reports deadlocks", and S8.L2–S8.L4 and S8.L7 use INS-spectacle only "if W0-S04 covers the S8 specs" (curriculum S08, section 13, issue 2).

The state-pair check is the question "is (s, t) a step of the spec, and which action takes it?". S5.L1's and S8.L2's GEN-trace-allowed grade a learner's trace step by step and name its first non-step; S8.L3 and S8.L4 have "Spectacle (or the precomputed TLC graph) replay the trace"; S5.L9's GEN-cti-or-bug needs the same check from a state that is not reachable.

**Short answer.** Yes for safety checking, within four rules and a time budget. Spectacle at 5827c22, driven by a small course-side adapter, matched TLC exactly on every S5 and S8 configuration it could evaluate: the same reachable states, initial states and edges, the same verdict, and the same distinct-state count, depth and trace length at the verdict, in Node and in Chromium, Firefox and WebKit. 45 of 56 curriculum configurations are in Spectacle's scope; the other 11 are Theater-only, for six reasons: liveness and fairness, an action property, symmetry, trace validation, size, and a recorded `TypeOK` over `Nat`. Where Spectacle cannot evaluate a spec it throws rather than return a verdict: `Nat`, `Int` and `STRING` are not implemented, and a module it cannot fetch stops the parse. Spectacle runs in a classic worker on the instrument origin with no main-thread work; a local `EXTENDS` resolves from the same directory on that origin. The state-pair check, done by enumerating Spectacle's successors of s, accepted every TLC edge and rejected every sampled non-edge, from reachable and unreachable states. Spectacle's own checker misses a violation in an initial state and has no deadlock check, so the adapter carries both. [X RUN-spectacle-s5s8]

[X RUN-spectacle-s5s8]
4. **Driver.** `scripts/spikes/W0-S04/harness/driver.js`, 716 lines of course-side adapter code over Spectacle's `TlaInterpreter.computeInitStates` and `computeNextStates`. It runs a breadth-first search in TLC's order: invariants on each new state when it is generated, the deadlock check when a state with no successor is expanded. It keeps exact canonical keys beside Spectacle's 32-bit fingerprints, and it lists the operators each spec uses from Spectacle's own tree-sitter parse, separating the constructs that INIT, NEXT and the invariants reach from those only parsed. It also calls Spectacle's own checker, `computeReachableStates`, where that applies.
5. **State-pair check.** For every TLC state, the driver rebuilds the state in Spectacle from TLC's own state formula, enumerates its Spectacle successors action by action, and compares them with TLC's edges: every TLC edge must be accepted, and no extra successor may appear. It samples up to 400 non-edges per configuration, which must be rejected. It replays each TLC counterexample step by step, every step and the lasso's back edge, and checks the first state against Spectacle's initial states when the configuration has a TLC graph, the only case in which the driver keeps that set; it also replays a mutant with the middle state removed, against TLC's graph. For S5.L9 it checks two pairs from the unreachable state `bal = 100, spent = 50`, with TLC's verdict taken from a run whose INIT is that state.
6. **Engines and modes.** Node v22.22.2 (V8) headless, and Chromium 153, Firefox 155 and WebKit 26.6 in `mcr.microsoft.com/playwright:v1.63.0-noble` (`scripts/spikes/W0-S04/browsers.mjs`). A 10 ms heartbeat on the main thread measured how long the page was blocked. The jobs with a local `EXTENDS` ran in three module modes: "fetch" (Spectacle fetches the module from the root module's directory), "shim" (the fetch is answered from memory) and "overrides" (Spectacle's own `module_overrides` argument). A watchdog step terminated a worker in the middle of the largest job. The server sent `Content-Security-Policy: default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'; worker-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self'` on every response and logged every request. ### 4.4 Worker or main thread

Spectacle needs no main thread. `eval.js` touches no DOM, and every job ran in a classic dedicated worker that loads Spectacle's four scripts with `importScripts` (tree-sitter fetches its two `.wasm` files itself), in all three engines, with results identical to the main thread's (174 of 174 job runs across the three engines). Worker startup, including the parser's initialization, took 41 ms in Chromium, 48 ms in Firefox, 49 ms in WebKit. With the job in the worker, the main thread's largest gap stayed at 14 ms or less; on the main thread, the page was blocked for the whole job, 28.2 to 43.3 s on the two-command Outbox. Terminating the worker 500 ms into that job and starting a fresh one ran M1 correctly 81 to 103 ms later. [X RUN-spectacle-s5s8]

A module worker would need Spectacle's four scripts bundled into one, since module workers have no `importScripts`. The classic worker is enough here; ARCHITECTURE.md's module workers come from Pyodide, whose classic-worker paths failed [X RUN-browser-origin].

Which action took a step is a separate question. Spectacle names an action by the disjunct of `Next` it comes from, so its names match TLC's labels when each disjunct of `Next` applies one operator, as in every spec written by hand for this spike (8,635 of 8,635 comparable edges in Node). M1's `Next == \E w \in Workers : Read(w) \/ Write(w)` is one Spectacle action, so only half of M1's TLC labels match (6 of 12 edges); PlusCal's translation wraps both actions in `worker(self)`, so 3 of its 15 edges match. TLC, for its part, labels a step with the name "Next" when it cannot split a disjunct into one operator call, as for `\E r \in reqs : Accept(r)`, whose bound set is a variable. ### 4.7 Deadlocks, and what Spectacle's own checker misses

Spectacle's own checker, `TlaInterpreter.computeReachableStates`, answers a different question from TLC's:

| Probe or configuration | TLC | Spectacle's own checker | The adapter |
|---|---|---|---|
| `probe-init-inv`: the initial state violates `Inv`, its successor satisfies it | "Invariant Inv is violated by the initial state" | holds: it tests successor states only | violated in the initial state |
| `probe-deadlock`: the third state has no successor, deadlock check on | "Deadlock reached" at 3 distinct states | holds: it has no deadlock check | deadlock at 3 |
| M1 and the other specs whose definitions are not named `Init` and `Next` | — | not applicable: it uses `Init` and `Next` whatever the configuration says | runs the configured names |

On violations it reports the number of states it had dequeued, not TLC's distinct count: 48 for M5 unsafe, where TLC reports 66. So INS-spectacle uses Spectacle for initial states and successors only, and the adapter owns the search, the invariant checks, the deadlock check and the counts. With that, the answer to S5.L2's question is yes: the adapter's verdict on "which comes first" matched TLC on both configurations with the deadlock check on (M1 deadlocks first; the PlusCal translation never deadlocks). [X RUN-spectacle-s5s8]

### 4.8 Fingerprints

Spectacle identifies states, set elements and function arguments by 32-bit hash fingerprints (hash-sum). On distinct states built directly from values, the fingerprints collided 0 times in 10,000 and 0 times in 100,000 states, and 223 times in 1,000,000 states, where a uniform 32-bit hash would expect 116.4. The adapter keyed its search by Spectacle's fingerprints and checked exact keys beside them: the two counts were equal in every configuration. [X RUN-spectacle-s5s8]

## 5. Decision

### 5.1 The rule

A configuration is in Spectacle's scope when, on this run: (1) Spectacle loads every module it uses from the instrument origin, local `EXTENDS` included, with no third-party request; (2) every construct that INIT, NEXT and the checked invariants reach evaluates, and the complete state graph equals TLC's in Node and in all three browser engines; (3) the verdict and the counts equal TLC's (`-workers 1`, explicit deadlock setting); (4) the state-pair check accepts every TLC edge and step of TLC's counterexample, and rejects the sampled non-edges; and (5) the complete exploration at the lesson's constants takes at most 10 s in a worker in every engine [D]. Otherwise it is Theater-only: the tab shows authored TLC graphs (INS-theater) and TLC runs on the Bench (INS-bench-tlc). Liveness and fairness, action properties, symmetry and trace validation are Theater-only by construction, because Spectacle does not check them; INS-lasso keeps lassos.

### 5.3 What INS-spectacle adds around Spectacle (W3-T08)

1. **The search is the adapter's.** Spectacle supplies initial states and successors; the adapter runs the breadth-first search in TLC's order, checks invariants on initial states too, checks deadlocks, reports TLC's counts, and keys states by exact canonical values rather than 32-bit fingerprints [D]. Its trace replay checks every trace's first state against the initial states; this spike's driver did that only where it was given a TLC graph (section 4.6). `scripts/spikes/W0-S04/harness/driver.js` is a reference, not product code.
2. **A classic dedicated worker** on the instrument origin, terminated by the watchdog; never the main thread.
3. **Modules from the instrument origin only.** The adapter answers Spectacle's module fetches itself, from the course's read-only modules and the learner's text, and refuses any community-module name before Spectacle can fetch it; it names a missing module itself, since Spectacle's error does not.
4. **Refuse what Spectacle does not check, before calling it**: temporal properties, fairness, action properties, `SYMMETRY`, and specs that use `Nat`, `Int` or `STRING` where Spectacle evaluates them. The cell offers "send to the Bench".
5. **A time budget, not only a state cap.** About 5k states [D] is too many for S8-sized specs: 3,887 Outbox states took 41.7 s. Budget the worker by wall clock, 10 s [D], and stop at the bound with `stopped: bound`.
6. **Action labels**, where the cell shows them, decomposed for compound disjuncts and PlusCal translations, or the spec written with one operator per disjunct of `Next` (section 5.4).
7. **GATE-conformance reuses this harness**: TLC's graph against Spectacle's, per authored spec, in Node, which gave the same counts and verdicts as the three browsers on 59 of 59 configurations.

### 5.4 Authoring rules for Spectacle-run specs (W3-T11, W5-T02)

1. Invariants that Spectacle checks use finite sets: `x \in 0..N`, never `Nat`, `Int` or `STRING` [D].
2. Only the nine built-in modules and the course's own modules in `EXTENDS`; no community modules.
3. `Next` as a disjunction with one operator per disjunct, quantifier inside: `\E w \in Workers : Read(w)`, then `\E w \in Workers : Write(w)` [D].
4. Parenthesize an implication inside a box action formula: TLC rejects S5.L4's `[][hst \in {"captured", "released"} => hst' = hst]_hst` as written (`Encountered "]_" at line 12, column 67`, `probe-action-parse`), and accepts `[][(hst \in {"captured", "released"}) => hst' = hst]_hst` (`s5-lifecycle-prop`). Spectacle's tree-sitter parser accepts both, so a spec that loads in the tab can still fail SANY on the Bench: every authored spec passes SANY first (GATE-conformance does, through TLC).
5. Lesson constants keep the complete exploration within the time budget; sizes above it run on the Bench.

## 9. Open risks

1. **The authored specs are not these specs.** W3-T11 and W5-T02 will write the lesson specs; a construct this spike did not exercise (`INSTANCE`, `LAMBDA`, strings beyond equality, `Bags`, `Seq(S)`) may fail. GATE-conformance on every authored spec is the guard.
2. **Speed was measured on one desktop host, in single runs, beside other tasks' containers.** A slow laptop is slower, and phones were not measured; phones show recorded runs (spine §9.3).
3. **Fingerprints.** At 10,000 and 100,000 states no collision appeared, but Spectacle also merges set elements and function arguments by these 32-bit fingerprints, inside values, where the adapter's exact keys cannot see.
4. **Error quality.** Spectacle's failures are exceptions with engine-specific messages; the adapter must turn them into a refusal before a learner sees "Assertion failed".
5. **Two parsers.** Spectacle's tree-sitter grammar accepted a module that SANY rejects (`probe-action-parse`). A learner's spec edited in the tab can look fine there and fail on the Bench; LAB-5's re-checks are safe because they start from a receipt's spec, which TLC has parsed, but S5.L4-style in-tab writing is not.
6. **Upstream drift.** The repository's head moved after the pin, and it has one maintainer; a bump waits for GATE-conformance (labs/TOOLS.md).
