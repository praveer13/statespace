## 1. Question

## 2. Method

- **The tester is PostgreSQL's own.** `isolationtester` is the format's authority, and the 18.6 source tree ships its own specs with expected outputs (R4 F17). It was built from `postgresql-18.6.tar.bz2` (SHA-256 `555610c24d53e4316da5b7d3fc25c279d96856d5e0e23ee308c328c5fa881d9f`, equal to the checksum file published beside it) with gcc 14.2.0, in a throwaway container of the `postgres:18` image, so that it links the same Debian 13 libraries as the server [X RUN-pg-catalog]. It is not `statespace isorun`, which W4-T16 builds.
- **The server** is the stock `postgres:18` image, reporting `PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2)`, in a container capped at 6 GiB with its data directory on tmpfs (a speed choice) and every setting at its default except csv error logging; `deadlock_timeout` is 1 s [X RUN-pg-catalog].
- **A row is a spec.** Each session is one connection; each step is one line of SQL; the level of a transaction is in its begin step (`s1b_ser` is `BEGIN ISOLATION LEVEL SERIALIZABLE`), so a permutation and its output say which level they ran at. What a session read goes into a temporary table `seen` (the client's memory), and the write uses that value, as an application's read-then-write does; this is R4's proposed encoding, now checked (section 4.1). Writes end in `RETURNING old.…, new.…`, which prints each row's before and after (PostgreSQL 18). An observer session `obs` reads the committed state last.
- **Which interleavings run.** A permutation that asks a blocked session for its next step cannot finish, and isolationtester gives up on it after twice its step timeout (40 s with the setting used here, from the tester's source; no recorded permutation reached it). So every spec lists its permutations. For the rows that have a grid pattern (H01, H02, H04, H05, H06b, H22a, H22b), the spec lists every interleaving that cannot hang, level by level. A small lock model decides: a write is possibly blocking when another session has an open write to the same row, a session that might be blocked is not scheduled again until its blockers end, and a lock cycle of certain writes is allowed because the server resolves it. The model is sound and incomplete (it can skip an interleaving that would have run, such as a write whose guard fails) [X RUN-pg-catalog]. Every lock wait the tester reported in the grid, 1,337 of them, was one the model predicted, and no cell needed the one-permutation fallback [X RUN-pg-catalog].
- **SQLSTATEs.** isolationtester prints `ERROR:  <message>` and never the SQLSTATE. The server logs each error with its SQLSTATE and the session's `application_name`, which the tester sets to `<tag>/<session>`. The runner joins the two: for every session, the messages the tester printed must equal the messages the server logged, in order, or the run stops. In the row runs, 564 printed errors matched 564 logged ones, and each message maps to exactly one SQLSTATE [X RUN-pg-catalog].
- **Two passes, byte for byte.** Every spec runs twice in each execution and the outputs are compared. The grid does the same; a history that differed between passes would stay out of the pool, and none did [X RUN-pg-catalog].
- **Upstream baseline.** 25 upstream specs that sit behind the rows run on the same rig, and their outputs are compared with the expected files in the source tree.
- **The grid.** Section 4.5 describes it; its generator is `scripts/spikes/W0-S09/patterns.py`, and `verify.py` regenerates every cell from the seed with no database.

### 4.3 The transient errors under SERIALIZABLE

This is the evidence S6.L7's policy needs. Facts of H12a and H12b (a key or a booking range that two sessions create, with or without an existence check first), H22, H23, H24 and the grid's attempt logs, all [X RUN-pg-catalog]:

| SQLSTATE | Raised when | Whole-command retry |
|---|---|---|
| 40001, "read/write dependencies among transactions" | at SERIALIZABLE, when both sessions read before either wrote (H05, H06, H10, H11, H12a and H12b scenario A, H14, H23); at the write, at the read or at COMMIT. The server adds the hint "The transaction might succeed if retried." and a reason code such as "Canceled on identification as a pivot, during commit attempt" | H23: B reads 20 available and its guard refuses; H12a after scenario A: the retry that re-checks ends without an error. In the grid, the failed session's retry never failed again in 198 of 198 histories (holds and conditional UPDATE): it inserted or updated in 132 and was refused by its own guard in 66 |
| 40001, "concurrent update" | at REPEATABLE READ and SERIALIZABLE, when a session writes a row another transaction changed and committed after its snapshot (H01, H02, H03, H13, H16, H17, H22b, H24). No hint | H24: 0 rows (the guard now reads 20) |
| 40P01 | at every level, when two sessions lock two rows in opposite orders (H22a): 8 of 12 permutations at each level. The hint is "See server log for query details." | the victim's retry committed in 216 of 216 histories (grid pattern `retry-opposite`) |
| 23505 | an insert of a key another transaction inserted, at every level and in every scenario of H12a except A and Aw at SERIALIZABLE, where both sessions checked first and the server raises 40001 instead. So the session that checked first still gets 23505 when the other inserted blind (B and Bp), at all three levels. No hint | a retry that re-checks ended without an error after B and after a blind race (H12a), because it saw the key; a blind retry failed with 23505 again, in H12a and in 9 of 9 grid histories |
| 23P01 | the same pattern with an exclusion constraint (H12b): scenario A gives 23P01 at READ COMMITTED and REPEATABLE READ and 40001 at SERIALIZABLE; two blind inserts give 23P01 at SERIALIZABLE, the only level run | a blind retry failed with 23P01 again; after scenario A, a retry that re-checks ended without an error |
| 22003 | a credit past 9223372036854775807, at every level (H19) | never transient: the same credit failed again in 27 of 27 grid histories |

So the same SQLSTATE, 23505 or 23P01, appears where a retry that re-decides ends without error and where a blind retry fails again. The server does not tell the two apart, and neither does the SQLSTATE. A 23505 raised to a session that checked first (scenario B) is also a unique violation that could not occur in a serial run of the application's own logic, as the manual warns [V] (section 13.2.3: "even after explicitly checking that the key isn't present"; section 13.5: these codes "might represent persistent error conditions rather than transient failures").

### 4.4 Where the expectations did not hold, and what the spec text needs

- **H22 differs.** S6's spec section 12 expects "both commit" when both sessions issue their statements in ascending account order. That holds at READ COMMITTED (6 of 6 permutations) and not at REPEATABLE READ or SERIALIZABLE, where 4 of the 6 still fail with 40001, because the second session's first statement waits on a row the first has changed and committed. Ordering the locks removes the deadlock (40P01), not the serialization failure [X RUN-pg-catalog]. In those 4, the failed session's next statement meets 25P02 ("current transaction is aborted"); a real runtime would stop at the first error.
- **H12 gains cases R4 did not state** (section 4.3): which of 40001 and 23505 appears depends on whether the failing session checked first and on the order of the two inserts.
- **H17 at the higher levels** is "prevented", but by failure: mallory's locking read fails with 40001 rather than returning nothing [X RUN-pg-catalog].
- **H13, H14, H15 and H16 at levels R4 left blank** are now recorded (section 4.2).

### 4.5 The grid

**Definition.** Seed `statespace/GEN-anomaly-id/grid/1`. The generator is mulberry32 seeded by FNV-1a-32 of `<seed>/<purpose>`, with integer-only `randint`; `grid/grid.json` gives the algorithm and test vectors (the first five outputs for purpose `vectors` are 968685933, 460802865, 103897943, 3545672292 and 2397217856) so that W4-T20's TypeScript can reproduce the draws [X RUN-pg-catalog]. Balances: 100, the canonical balance of the executed spikes, and two seeded multiples of 10, which came out 60 and 180. Amounts, on a lattice of 5, come in three classes per balance: two debits that together exceed the balance but each fit (`contend`), that together equal it (`exact`), or that leave room (`fit`); the canonical cell (balance 100, amounts 80 and 80; the team-sum debits 150 and 150) is fixed inside the grid, so the rows are grid cells. The levels are READ COMMITTED, REPEATABLE READ and SERIALIZABLE, the same for every session of a cell, plus the six mixed assignments of one read-skew pattern; the derived retry patterns use the levels where a retryable failure occurs (SERIALIZABLE for holds, REPEATABLE READ and SERIALIZABLE for the conditional UPDATE, all three for opposite-order moves). Interleavings: every one that cannot hang the tester, except for the two three-session patterns, which draw a seeded sample of 8 and 12 per cell. Two kinds of attempt log are derived from recorded outcomes: for a base pattern whose history has exactly one retryable failure and no follow-on error, the failed session's whole command is appended as a new transaction (`retry-holds`, `retry-cond`, `retry-opposite`); `retry-overflow` and `retry-unique` have fixed permutations.

**Counts.** 369 cells (315 base and fixed, 54 derived) ran twice; 3,717 histories ran in each pass; all 3,717 were byte-identical across the passes; 3,609 are in the pool, and 108 were left out because the failed session's next write met 25P02 (a spec cannot stop at the first error as an application would) [X RUN-pg-catalog].

### 4.6 Stability

Each execution compared two passes of every row, upstream and variant spec and found them byte-identical. Across four executions the 24 row outputs had the same SHA-256 each time (compared in a chain, each against the one before) [X RUN-pg-catalog]. The full grid ran in four executions, a development run that was replaced and then three more, with the same counts for every template and pattern each time; the four pool files of the last three had the same SHA-256, which `grid.json` records [X RUN-pg-catalog]. Durations were 64 s for the rows and their two passes, and about 16 minutes for the grid, most of it the 1 s `deadlock_timeout` of the deadlock cells [X RUN-pg-catalog].

## 5. Decision

1. **The rows are recorded.** Adopt RUN-pg-catalog as the record of rows H01 to H24; the IDs resolve as the keys of `rows` in `runs/RUN-pg-catalog.json` and as the entries of `content/pg-catalog/catalog.json`. Copy may cite a row's recorded outcome, for the levels and interleavings in section 4.2, with `{{run:RUN-pg-catalog}}` and the row ID. The cells section 4.2 lists as not run stay out of copy.
2. **The retry rule stays a [D] policy, and its basis is recorded.** The 23505 and 23P01 rule is a decision, not an observation, so it keeps its [D] tag, now with the run that tells the policy what it must decide (section 4.3). The recorded behavior supports this wording for S6.L7: retry 40001 and 40P01 by running the whole command again; retry 23505 or 23P01 only inside a command that re-reads the key before it writes, a bounded number of times, and never by re-sending the same blind insert, because the SQLSTATE alone does not say whether the condition persists; never retry 22003. The spine's text ("23505 or 23P01 only when transient") cannot be applied from the SQLSTATE, and the S6.L7 classifier must be told which of its commands re-check.
3. **The grid is adopted as the pool for GEN-anomaly-id.** Keep the seed, the target of 200 histories per template with at least 100 per half, and the display and graded halves, as [D] defaults for W4-T20 to confirm. The class of each history stays the history checker's key at grade time (W4-T18); nothing here is a key. ## 6. Fallback

If a row stops reproducing (a re-record after PostgreSQL 19 reaches general availability, OD-12, or a different image), the recorded 18.6 outputs stay the record for 18.6 and copy that cites the row waits on the new run; the rows are runs, so there is nothing to retract. If `statespace isorun` (W4-T16) cannot reproduce a row's classes, these `.out` files are the expected outputs it is tested against, and the isolationtester built here stays the reference. If the owner rejects the grid's design defaults, the cells and histories are unaffected: only the target, the halves and the pattern list change, and `verify.py` shows what moved. The retry rule stays a [D] policy either way (ARCHITECTURE.md section 19).

## 8. Open risks

- **The tester is not `isorun`.** isolationtester detects a blocked step with `pg_isolation_test_session_is_blocked`; the architecture's `isorun` uses `pg_blocking_pids`. A difference would show as a different set of waiting steps, which the row outputs would reveal [D].
- **One server, one build, one platform.** PostgreSQL 18.6 as packaged by Debian, on x86_64. The recorded outcomes are the documented behavior (the manual's chapter 13) on that build, not a proof about any other.
- **The lock model is incomplete.** It skips interleavings that would have run, so a cell's count is a lower bound on its valid space; the cell list records both numbers.
- **The pool counts histories, not independent problems.** Histories of one cell differ only in interleaving, and cells of one pattern differ only in numbers; section 4.5 gives the distinct-shape counts. t4's attempt-log supply (patterns `retry-*`) is 459 histories and 55 shapes, which suits S6.L7's one graded item but is the thinnest part of the pool.
- **Serialization outcomes depend on the planner and on predicate-lock limits.** H11 depends on the plan (recorded in its output) and on `max_pred_locks_per_page` and `max_pred_locks_per_transaction` at their defaults.
- **A deadlock victim depends on equal `deadlock_timeout`.** It is the session that waited first, 24 of 24 times here; a different setting per session changes it (the upstream `deadlock-simple` does this on purpose).
- **Follow-on errors.** A spec cannot stop a session at its first error, so histories with 25P02 are left out; the row outputs for H22 keep them.
- **The "client memory" model is a model.** The temporary table stands for an application's read-then-write; drivers, pools and retries in a real runtime add behavior it does not show.
- **The design defaults are mine.** The target, the half rule, the amount classes and the sampling limits are [D]; a different seed produces a different pool.
