## 1. Question

How does the tab's Z3 behave on a phone, from the instrument origin? The tracker names five measurements, and the spine adds three cases in browsers:

- **First-load size**: the compressed bytes one engine needs on its first load, as ARCHITECTURE.md section 5.9 counts them for OD-6, so that the consent sheet and `GATE-bundle` have a figure.
- **Load time**: from the consent tap to a live verdict (cold), from a restart with the cache in place (warm), and what a stopped worker costs the next request.
- **Memory**: what the engine claims, and what the browser adds.
- **`rlimit` timing**: how long a given `rlimit` runs, because `timeout` never returned under Pyodide in a Node harness [X RUN-z3-budget-pyodide] and the existing figures all come from that harness (`curriculum/S01-counterexample.md`, section 13, item 3).
- **Cache persistence**: whether the engine, once downloaded, is still there in a later session.
- **In browsers, the `timeout` case, the `unknown` case and `Fixedpoint`** (spine section 13), which so far ran only under Node.

One deliverable is derived from these: **the Boot timing budget** that `GATE-bundle` enforces (spine section 11.2; W1-T41 builds the gate).

CI cannot stand in for a phone. Chromium's CPU throttling did not reach the cross-origin worker [X RUN-browser-origin], and again did not reach a same-origin worker in W0-S08's run [X RUN-pglite-0511], so only real devices count for the phone figures. No phone was available to this task, which is why section 3 is labeled as it is and section 7 hands the sessions to the owner.

**Short answer.** No phone was measured. The byte counts are exact. Every time and memory figure comes from an emulation of a slow device on three desktop engines, and the budget is provisional.

- *Size.* The first load of Pyodide with the Z3 wheel is 12,893,420 bytes on the wire as gzip level 5 (12.9 MB), 8,829,693 as Brotli 11 and 20,056,541 unpacked. It is above OD-6's 5 MB however the host encodes it, so the tab asks first [X RUN-phone-pyodide]. **Superseded in part, 2026-10-25.** OD-6 changed: no download asks first and none warns, so "the tab asks first" no longer holds; the loader shows the size while the engine downloads (see the addendum, item 1). The measurements stand.
- *Time.* On the emulated slowest tier (0.25 CPUs, where a fixed single-thread loop ran 4.1x to 4.2x slower than unthrottled, engine by engine) a first live verdict came 14.0 s to 17.3 s after the consent tap on a loopback link, and 7.3 s to 16.8 s after a restart with the cache in place, against 1.6 s to 1.8 s and 1.3 s to 1.6 s unthrottled. A stopped worker costs the next request the warm start again [X RUN-phone-pyodide].
- *A fill longer than a minute.* On the emulated 1.6 Mbit/s link the fill takes about 65.7 s. The planned fill, one message to the service worker, finished in Chromium and WebKit and did not in Firefox, which stopped the worker 60.3 s after the first file was requested; a message to the worker every 15 s let the fill finish in all three engines, and after Firefox's stop a second request fetched only the file the cache lacked (section 4.8) [X RUN-phone-pyodide].
- *Responsiveness.* While the engine was fetched and started at that tier, no tick of a 50 ms timer on the page's main thread came more than 160 ms late [X RUN-phone-pyodide].
- *`rlimit`.* A 5,000,000 `rlimit` on the cubes query ran 1.0 s unthrottled in Chromium and up to 6.9 s at 0.25 CPUs. `timeout` still never returned in Chromium, Firefox or WebKit; the wall-clock watchdog is what stops a runaway query [X RUN-phone-pyodide].
- *Cache.* The framed cache survived every browser restart in all three engines at every tier, and an offline restart, with no engine byte reaching the server. Whether a phone keeps it for days is the owner's measurement [X RUN-phone-pyodide].
- *Budget.* The Boot budget of section 5.3 is 21.0 s for a live verdict with the cache warm and 22.0 s for the CPU part of a cold start, plus the fetch (35.0 s in all on a 10 Mbit/s link) [D].

## 2. Method

The kit is in `scripts/spikes/W0-S02/`. It reuses W0-S01's topology and mechanics: a main origin that embeds the instrument origin in a hidden `sandbox="allow-scripts allow-same-origin"` frame, the MessagePort handshake of ARCHITECTURE.md section 5.3 with W0-S01's amendments, the instrument service worker that fills and serves the engine cache, a Pyodide module worker, and the section 15.4 meta CSPs. It adds what a phone measurement needs.

1. **One page, run the same way by a person and by the harness.** `site/main/index.html` is a page that works at 360 px, with one main button. A tap runs a session. The page keeps every session in a ledger in its own `localStorage` and copies the whole ledger as one JSON report. The Playwright harness calls the same `runSession` function, so the desktop runs and the phone runs differ in the browser, not in the code.
2. **The sessions.** A *first visit* connects to the frame, reads the environment, checks that a run without consent is refused (OD-6), has the service worker fetch and verify the six engine files, creates the worker, starts Pyodide with the Z3 wheel, runs the roadmap starter, and then runs a CPU yardstick, the three browser cases and the `rlimit` ladder, reads memory, stops the worker and starts another, and runs the yardstick once more. A *return visit* does the same without the consent check and the fill, after first reading what survived: whether the cache holds six files, whether the service worker controls the frame from the first request, and whether the frame's own marker is still in its `localStorage`. Each session also records whether the page was hidden at any moment (a hidden page has its timers and workers slowed, so such a session is flagged and left out of the medians), whether a screen wake lock was granted, and a main-thread lag monitor that counts how late a 50 ms timer fires in each phase, which is the Boot gate's question: does the page stay interactive while the engine loads?
3. **What each figure means.**

   | Figure | Definition |
   |---|---|
   | handshake | the frame is created, loads its host page and manifest, and reports `ready` with the engine's caps |
   | fill | the service worker's fetch, SHA-256 check and cache write of the six files, after consent |
   | worker creation | the first call to a new module worker, which pays for loading its scripts |
   | ready | W0-S01's `readyMs`: `import('pyodide.mjs')`, `loadPyodide` and `loadPackage` of the Z3 wheel, inside the worker |
   | start to first verdict | from asking the worker to start to the first verdict: ready, `import z3` and the roadmap starter |
   | consent to verdict | fill, worker creation and start to first verdict, added, so that a harness pause between them is not counted |
   | restart | `worker.terminate()`, then the next request's time to a verdict: what the watchdog's stop costs the learner |
   | yardstick | a fixed xorshift loop, 100 million steps in JavaScript and 3 million per call in a hand-assembled WebAssembly module, run in the worker. A device report carries the same loop, so a phone can be put on the scale of the emulated tiers |

4. **The `rlimit` ladder** runs two queries that no search ends, at `rlimit` 100,000, 1,000,000 and 5,000,000: the cubes query of RUN-z3-budget-pyodide (`x*x*x + y*y*y == z*z*z` over `Int`, each above 2), and the factoring of a 62-bit semiprime in `BitVec 64`. The `timeout` case runs the cubes query with `s.set('timeout', 2000)` and a 25 s watchdog. The `unknown` case is `x**y == 8` with `y > 1`; `Fixedpoint` is the stratified-negation policy of RUN-z3-fixedpoint; the wrap is the recipient query of RUN-z3-bv64-pyodide, with its witness checked against the property and never compared by value.
5. **First-load size.** The manifest lists each engine file with its raw size, its size as gzip level 5 (stock zlib 1.3.1, the bytes GitHub Pages sent for four small public files [X RUN-pglite-0511]) and its size as Brotli 11. The stand-in server sends the gzip copies. The sizes of section 4.1 are read three ways, which must agree: the browser's Resource Timing or `Content-Length`, the server's log of body bytes sent, and the manifest.
6. **The harness** (`harness.mjs`, in `mcr.microsoft.com/playwright:v1.63.0-noble`) drives Chromium, Firefox and WebKit through one plan per container. The `matrix` plan, at each CPU tier and in each engine, runs a first visit on a fresh profile (every case, the ladder and the restart), a restart on that profile with the same full set, two more restarts, and two more fresh profiles that stop at the first verdict, so each cell holds three first visits and three return visits. The `extras` plan runs an offline restart (the instrument host answers 503 to every request) and the 25 s `timeout` case. The `link` plan runs first visits through a shaped link, with two fills: the one ARCHITECTURE.md section 5.9 plans (the host sends the service worker one message, and the worker fetches, verifies and caches the six files and answers), at both links; and, at the slow link, the same with the host also sending the worker a message every 15 s while the fill runs. A fill with no answer after 180 s is called unfinished, and the host then asks the worker for its instance id (a random string the worker makes when it starts), which it also read before the fill, to tell a worker that was stopped from a slow network. The page then reads what the cache holds and asks for the fill once more, with the heartbeat, and the session ends there. The server's log records, for a response the browser closed early, when and how much had been sent. The `ui` plan starts and reads one session through the page's own buttons (Run, Copy, Save and the two clearing buttons), as a person would. The harness also reads the resident (RSS) and proportional (PSS) memory of every process in the container except itself and the server, at fixed points between timed stretches, and peak RSS from a 250 ms sampler.
7. **Emulation of a phone** (the closest faithful substitute on this machine, and no more). The CPU is a CFS quota on the whole container (`docker run --cpu-period=10000 --cpu-quota=<cpus x 10000>`), which reaches every browser thread, the worker's included, where DevTools throttling does not. The tiers are no quota, 1, 0.5 and 0.25 CPUs, as W0-S08 used. The yardstick says what the quota does to one thread; start-up slows more than one thread's speed because the browser's background threads share the quota, so the emulation is pessimistic for a phone with several cores. The network is a shared-link shaper in the stand-in server, at 10 Mbit/s with a 50 ms round trip and at 1.6 Mbit/s with 150 ms; the links are chosen, not measured [D].
8. **The budget** (section 5.3) is computed from the run by `derive-budget.mjs`. The reference profile is the slowest one on file: every real device if any report is merged, else the emulated 0.25-CPU tier in each engine. Each quantity's reference value is the largest median among the reference profiles (for a real device, which holds few sessions, the largest value), and the budget is that value times 1.25, rounded up to the next 500 ms. The margin, the rounding, the two links and the watchdog factor are course parameters [D].

To reproduce the emulated run, with Docker, Node 22, npm and `python3` [D]:

```
scripts/spikes/W0-S02/run.sh <work-dir> --record
```

`run.sh` installs playwright-core 1.63.0 into the work directory, fetches and verifies Pyodide and the wheel, builds the two sites, inspects the two zip-like files, runs each CPU tier in its own container, and has `record.mjs` write `runs/RUN-phone-pyodide.json` and `runs/RUN-phone-pyodide/`. The whole run took 2,021 s [X RUN-phone-pyodide].

- **The engine's own heap is small and the same everywhere.** Pyodide's linear memory was 30.0 MiB after `loadPyodide`, 52.8 after the wheel and 63.3 after `import z3`, and the three browser cases brought it to 76.0 (12.7 MiB more than after `import z3`). ### 4.8 A service worker stopped during a long fill

On the 1.6 Mbit/s link the fill takes about a minute, which is where a browser's limit on how long it keeps a service worker running starts to matter. The `link` plan therefore ran the cold session twice at that link in each engine (section 2, item 6): with the fill as ARCHITECTURE.md section 5.9 plans it, and with the host sending the worker a message every 15 s while the fill runs. The results are the 1.6 Mbit/s rows of the table in section 4.6.

- **Firefox stopped the worker, and the planned fill never finished.** With the planned fill, Firefox's cold session at 1.6 Mbit/s got no answer from the worker in 180.0 s, and the worker's instance id had changed, so it had been stopped and started again. The server's log shows the browser closing the connection of the wheel, the sixth and last file, 60.3 s after the first engine file was requested, with 84.0 percent of the wheel's 6,511,752 bytes sent and 5 files finished. Chromium and WebKit finished the same fill, in 65.7 s and 65.7 s [X RUN-phone-pyodide].
- **The files finished before the stop were kept, and a second request fetched only the rest.** After the stop the cache held 5 of the 6 files. The page then asked for the fill again, with the heartbeat: the worker skipped 5 files and fetched 1, the wheel, in 32.9 s, and the cache then held 6 of 6 [X RUN-phone-pyodide].
- **A message every 15 s kept the worker alive.** With the heartbeat the fill finished in all three engines at the slow link, on the same worker instance from start to end. In Firefox it took 65.7 s, longer than the 60.3 s after which the plain fill was stopped, and every heartbeat fill was within 0.5 percent of the arithmetic of section 4.6 [X RUN-phone-pyodide].
- **The cause was not examined.** The numbers fit a limit of about a minute on how long Firefox lets a worker run after the last message it received, which a new message restarts. Whether that is a timer for an idle worker or one for a long event, and what Firefox for Android does, were not examined. The 15 s period of the heartbeat is a choice, well under the minute, and no other period was tried [U].
- **Why it matters.** A fill of this length is ordinary on a phone. The arithmetic for the whole fill at 1.6 Mbit/s is 65.4 s, and for the wheel alone 32.7 s [X RUN-phone-pyodide] [D]. Two other ways around the limit were not tried: one message for each file, which would still lose the wheel on a link slower than about 0.9 Mbit/s, where the wheel alone takes as long as the plain fill ran before it was stopped; and ranged requests, whose handling by GitHub Pages was not measured. Decision 6 of section 5.1 adopts the heartbeat, and has `warm` report a fill that did not finish instead of waiting for it [D].

### 4.9 The page a phone opens

The `ui` plan drives the page's own buttons in each engine, as a person would: it types a device name, chooses the two options, taps **Run**, and then the other buttons. In all three engines Run made one session card; **Copy the report** produced a report that parses as `w0-s02/report@1`, holds one session and carries the device name that was typed; **Save the report as a file** offered `w0-s02-report.json` as a download; **Clear the engine cache** deleted both caches and unregistered the service worker; and **Clear the list of sessions** emptied the cards. Headless Chromium refused the clipboard write and the page then selected the report and said "copying is not allowed here: the report is selected, copy it by hand", which is the path a phone takes when the browser denies the clipboard; Firefox and WebKit answered "copied the report". The persistence button answered `{"before":false,"granted":false,"after":false}` in Chromium, and the same in the other two: none of the desktop engines granted persistent storage [X RUN-phone-pyodide].

When the page is opened at an `http://` address that is not `localhost`, the browser offers no service worker and no Cache API; the page says so and measures from the network, with the engine's files warmed into the HTTP cache. That path was checked by hand in the three desktop engines while the kit was built, and is not part of the recorded run [U].

### 4.10 What the emulation cannot say

- **A phone's CPU is not a quota.** The quota slows every thread of the browser together. A phone has a few fast cores and several slow ones, a clock that rises and falls with heat and charge, and a scheduler that may park the page. The yardstick is how the first report shows the distance: the same loops, run on the device.
- **A phone's memory is not a container's.** The harness read the resident memory of the browser's processes in a container with 6 GB and no pressure. A phone ends a tab that grows too large, and a report shows that as a session that *ended during* a phase.
- **A phone's browser is not Playwright's.** Chromium, Firefox and WebKit here are Linux desktop builds, and WebKit is the WPE port, whose memory and worker behaviors differed from the other two in this run (sections 4.3 and 4.4). None of them is Safari or Chrome for Android.
- **No time passed.** Restarts were seconds apart on a persistent profile, so eviction, the seven-day window of WebKit's storage rules [webkit7d] and browser updates were not exercised.
- **The links are a shaper, not a mobile network.** They have a fixed rate and a fixed round trip, no loss, no variation and one connection at a time, which is how the service worker fetches. How long a phone's browser keeps a service worker running is that browser's own rule (section 4.8), and Safari and Chrome for Android were not run.
- **One host.** GitHub Pages' handling of the large files is assumed (section 9).

### 5.1 What the tab does with the engine on a phone

1. **INS-z3 stays in the tab on phones, behind consent, and no lesson waits for it.** The first load is 12,893,420 bytes as gzip level 5, above OD-6's 5 MB in every encoding measured [X RUN-phone-pyodide]. Boot already completes on recorded runs alone (`docs/DESIGN.md`, SCR-boot), so the live solver is an offer made after the recorded result. A learner who declines, or whose phone is too slow, loses nothing graded [D].
2. **OD-6's unit is one engine's compressed first load, from the build's manifest** [D], as ARCHITECTURE.md section 5.9 says; this record confirms the choice with a number (section 4.1). The manifest lists each file's size as the host will send it, the consent sheet prints that total, and `wire-check.mjs` compares it with the deployed host (owner action 2).
3. **The engine pins stay.** Pyodide 314.0.7 and the 5.3.1.0 wheel ran in three engines at every tier with no CSP violation, with the roadmap starter's verdict and checked witness in every session [X RUN-phone-pyodide].
4. **The cache is best-effort, and consent follows it** [D]. A framed cache that survives restarts is a fact for desktop engines on a stand-in, here and in W0-S01 [X RUN-phone-pyodide, RUN-origin-subdomain]; the phone sessions test the rest. The main origin's consent record (ARCHITECTURE.md section 5.9) is honored only while the host's `caps` says the engine is cached. When `caps` says it is not, the consent sheet is shown again with the manifest's size, so a browser that evicts the cache but keeps the main origin's working state never refetches 12.9 MB unasked.
5. **One worker per instrument frame, started after consent, ended by the watchdog only.** A stop costs the next request the warm start again (section 4.2), so the supervisor does not stop a worker on a timer. It also does not add a second `WebAssembly.instantiate` to the Pyodide worker after Pyodide has loaded (section 4.4); any other module goes in its own worker [D].
6. **The fill is kept alive, and a fill that does not finish is reported** [D]. `warm` sends the service worker a message every 15 s until the worker answers, and a fill with no answer within a limit that W1-T06 sets from the manifest's size is reported as an unfinished download that the learner can retry, not waited on (section 4.8). A worker that was stopped is told from a slow network by its instance id, as `host.js` does [X RUN-phone-pyodide]. The fill writes each file to the cache after its hash check, so a retry finds the files finished before the stop and fetches only the rest (section 4.8) [X RUN-phone-pyodide].
7. **Every call carries an `rlimit`, and `timeout` is not used** (section 5.2) [D].
8. **An unbounded solver run is the memory risk on a phone** (section 4.3). The `rlimit` and the watchdog bound it in time; a Z3 memory cap was not tried here and is the next step if a phone report shows a killed tab [D].
9. **The first load can shrink, at a price** [D]: a wheel repackaged without its second `libz3.so` would take 3.1 MB off it, and changes the pinned wheel hash, so it needs its own run and a logged decision. It is not adopted here.
